1. Stack Frames in Depth

In Handbook I, you learned that the stack stores local variables and return addresses. Now we go deeper. Every function call creates a stack frame — a block of memory on the stack that holds the function's local variables, saved registers, and the return address. Understanding the exact layout of a stack frame is essential for debugging crashes, reading disassembly, and understanding how compilers optimize code.

The stack grows downward on virtually all modern architectures: it starts at a high address and grows toward lower addresses. When a function is called, it allocates space by decrementing the stack pointer (sp). When it returns, it deallocates by incrementing sp. The frame pointer (fp / s0 in RISC-V, rbp in x86-64) marks the top of the current frame and provides a stable reference point for accessing local variables, even as sp changes.

/* RISC-V Stack Frame Layout (grows downward) */ High addresses ┌─────────────────────┐ │ Caller's frame │ ├─────────────────────┤ <── previous fp (saved by callee) │ Saved ra (return │ │ address) │ ├─────────────────────┤ │ Saved s0..s11 │ callee-saved regs ├─────────────────────┤ <── fp (s0) points here │ Local variables │ │ (int x, char buf[]) │ ├─────────────────────┤ │ Spill area for │ │ caller's a0..a7 │ ├─────────────────────┤ <── sp points here │ (unused / red zone) │ └─────────────────────┘ Low addresses

Frame Pointer Prologue and Epilogue

Every function that uses a frame pointer follows a standard pattern. The prologue sets up the frame at function entry; the epilogue tears it down before returning. In RISC-V, the prologue saves the return address (ra) and the old frame pointer, then sets fp to the current stack position.

# RISC-V function prologue my_func: addi sp, sp, -16 # allocate 16 bytes on stack sd ra, 8(sp) # save return address sd fp, 0(sp) # save old frame pointer addi fp, sp, 16 # fp = top of frame # ... function body ... # Access locals as: fp + offset # RISC-V function epilogue .Lepilogue: ld ra, 8(sp) # restore return address ld fp, 0(sp) # restore old frame pointer addi sp, sp, 16 # deallocate frame ret # return (jr ra)

Variable-Length Arrays and alloca

When you use a variable-length array (VLA) in C, or call alloca(), the compiler cannot know the frame size at compile time. Instead, it adjusts sp dynamically at runtime. This is why VLAs are dangerous: if the size is too large, you get a stack overflow with no warning. The compiler typically aligns the resulting sp to a 16-byte boundary after the dynamic allocation.

// C code with VLA void func(int n) { int buf[n]; // size unknown at compile time // ... } # RISC-V: dynamic stack allocation func: addi sp, sp, -16 sd ra, 8(sp) sd s0, 0(sp) mv s0, sp # save sp in s0 (frame base) # Compute VLA size: n * 4, round up to 16 slli a0, a0, 2 # a0 = n * 4 addi a0, a0, 15 # round up: +15 srli a0, a0, 4 # /16 slli a0, a0, 4 # *16 (now 16-byte aligned) sub sp, sp, a0 # dynamically allocate! # buf is now at sp

Stack Alignment Rules

Most ISAs require the stack pointer to be aligned to a specific boundary at function call boundaries. This is not just a suggestion — misaligned stacks can cause hardware exceptions on some architectures and performance penalties on others.

ISARequired Alignment at CallReason
RISC-V16 bytesStandard calling convention; ensures 128-bit aligned access for SIMD
x86-64 (SysV)16 bytesRequired before call instruction; SSE instructions expect it
ARM64 (AArch64)16 bytesSP must be 16-byte aligned at all public function boundaries
MIPS8 bytesO32 ABI requires 8-byte alignment
Key Idea: Why 16-byte alignment?

Modern CPUs load 16 or more bytes at once (e.g., for SIMD registers). If sp is not 16-byte aligned, a single 16-byte load would cross a cache line boundary, requiring two memory accesses. Worse, some architectures (like SPARC) raise a bus error on misaligned access. The calling convention guarantees alignment so that callees can safely use 16-byte loads/stores without re-checking.

The x86-64 Red Zone

The x86-64 System V ABI defines a 128-byte red zone below the stack pointer. Leaf functions (functions that don't call other functions) can use this space without adjusting rsp. This is an optimization: it saves two instructions (the sub rsp and add rsp) for small leaf functions. However, signal handlers and interrupts will overwrite this area, so the red zone is only safe in non-interruptible contexts.

# x86-64 leaf function using red zone (no stack adjustment!) small_func: mov rax, rdi # use rdi directly add rax, rsi mov [rsp-8], rax # store in red zone (no sub rsp!) mov rax, [rsp-8] ret
Warning: Red Zone is x86-64 Only

RISC-V and ARM64 do not have a red zone. On those architectures, you must adjust sp before writing to the stack, even in leaf functions. The Windows x64 ABI also does not use a red zone.

2. Heap and Dynamic Memory

The stack is automatic and fast, but it has a major limitation: memory is freed when the function returns. If you need memory that outlives the function call — like a linked list node or a string you'll return to the caller — you need the heap. The heap is a region of memory managed by the C library's memory allocator (malloc, free, calloc, realloc).

Unlike the stack, the heap does not have a strict LIFO ordering. You can allocate memory in any order and free it in any order. This flexibility comes at a cost: the allocator must track which blocks are free and which are in use, leading to fragmentation and overhead. Understanding how malloc works at the assembly level helps you understand memory leaks, performance issues, and security vulnerabilities.

How malloc Works Internally

When you call malloc(64), the allocator doesn't just hand you 64 bytes. It gives you a slightly larger block that includes metadata — a header before the returned pointer that records the block's size and status (free or allocated). Typical allocators (like glibc's ptmalloc) maintain free lists: linked lists of free blocks sorted by size. When you call free, the block is returned to the free list and may be coalesced (merged) with adjacent free blocks.

/* Heap block layout (simplified) */ ┌──────────────────┐ │ Block header │ size, flags (8-16 bytes) ├──────────────────┤ │ │ │ User data │ <── malloc() returns this pointer │ (requested size) │ │ │ ├──────────────────┤ │ Padding / align │ round up to alignment ├──────────────────┤ │ Next block hdr │ ...or free list pointer └──────────────────┘

How the Heap Grows: sbrk and mmap

Where does the heap memory actually come from? The C library obtains memory from the operating system using two system calls: brk/sbrk and mmap. sbrk extends the program break — the boundary of the data segment. Small allocations typically use sbrk, while large allocations (typically > 128KB) use mmap, which maps a new page-aligned region.

# RISC-V: calling sbrk(64) to grow the heap # sbrk is a libc wrapper around the brk syscall grow_heap: li a7, 214 # SYS_brk on RISC-V li a0, 0 # 0 = query current break ecall # returns current brk in a0 mv s1, a0 # save old break addi a0, a0, 64 # new break = old + 64 li a7, 214 # SYS_brk ecall # set new break mv a0, s1 # return old break (usable memory) ret

Fragmentation

Over time, as blocks are allocated and freed in different orders, the heap becomes fragmented. There are two types: external fragmentation (free space is scattered in small pieces, so a large allocation fails even though total free space is sufficient) and internal fragmentation (the allocator rounds up the allocation size, wasting space inside each block). Fragmentation is why long-running programs (like web servers) can slowly consume more memory than they actually need.

Memory Leaks in Assembly

In C, a memory leak happens when you call malloc but never call free. In assembly, the same thing happens: you call the allocator but lose the pointer. This is actually easier to do in assembly because there's no compiler to warn you. If you store a heap pointer in a register, overwrite that register, and have no other copy, the memory is leaked forever.

Common Bug: Overwriting a Heap Pointer

In assembly, if you call malloc and the result is in a0, you must save it somewhere (another register, the stack, or a global) before calling another function. If the next function call clobbers a0, you've lost the only pointer to that memory — a leak. Always save return values from malloc immediately.

3. Memory Segments and Linking

When you compile a C program, the resulting binary contains several segments (also called sections). Each segment has a different purpose: some are read-only, some are writable, some are executable. Understanding these segments is crucial for understanding how your program is laid out in memory, how the linker works, and how security features like NX (No-Execute) and ASLR operate.

How the Linker Combines Object Files

When you compile main.c and util.c separately, each produces an object file (.o). Each object file has its own .text, .data, and .bss sections, but with unresolved symbols — references to functions or variables defined in other files. The linker (ld) combines all object files by concatenating their sections and resolving cross-references.

The process has three phases: symbol resolution (match each undefined symbol to its definition), relocation (patch addresses in the code to point to the correct locations), and section merging (combine all .text sections into one, all .data into one, etc.). The linker also inserts startup code (_start, crt0) that sets up the environment before calling main.

# Before linking: main.o has an unresolved call to helper() # The compiler emits a placeholder + relocation entry: call 0x00000000 # placeholder address # Relocation entry: R_RISCV_CALL, offset=0x4, symbol=helper # After linking: the linker patches the address call 0x00401234 # actual address of helper()

Static vs Dynamic Linking

Static linking copies all library code into the executable. The result is a large but self-contained binary. Dynamic linking defers resolution to runtime: the executable contains references to shared libraries (.so on Linux, .dll on Windows), and the dynamic linker (ld-linux) loads them when the program starts. Dynamic linking saves disk space and memory (shared libraries are loaded once for all processes) but adds runtime overhead and complexity.

PLT and GOT: Dynamic Symbol Resolution

When you call a function from a shared library (like printf), the compiler can't know its address at link time. Instead, it uses the Procedure Linkage Table (PLT) and Global Offset Table (GOT). The PLT is a trampoline: each entry is a small stub that jumps to an address stored in the GOT. On the first call, the GOT points back to the dynamic linker, which resolves the symbol and patches the GOT. Subsequent calls jump directly to the real function.

/* PLT/GOT lazy binding flow */ /* 1. Your code calls printf@plt */ call printf@plt /* 2. PLT stub: jump to GOT entry */ printf@plt: ld t1, [got_printf] # load GOT entry jr t1 # jump to it /* 3. First call: GOT points to resolver */ /* Resolver finds printf, patches GOT, jumps there */ /* 4. Subsequent calls: GOT has real address, direct jump */
Key Idea: Lazy Binding

PLT/GOT uses lazy binding: symbols are resolved on first use, not at program start. This speeds up startup (only resolve what you use) but can cause unpredictable latency on first call. You can force eager binding with LD_BIND_NOW=1 or the -z now linker flag.

4. Recursion and Stack Usage

Recursion is a natural fit for the stack-based execution model. Each recursive call creates a new stack frame, so each level of recursion has its own copy of local variables. This is elegant but also dangerous: deep recursion consumes stack space proportional to recursion depth, and the stack has a fixed (and relatively small) size. Understanding how recursion maps to stack operations is key to understanding both its power and its limitations.

Factorial in RISC-V Assembly

Let's trace a recursive factorial(n) function. Each call saves ra (because it calls itself), decrements n, and recurses. The base case (n <= 1) stops the recursion and returns 1. Each returning frame multiplies its n by the result of the recursive call.

# RISC-V recursive factorial # int fact(int n) { if (n <= 1) return 1; return n * fact(n-1); } fact: # Prologue: we call fact, so must save ra addi sp, sp, -16 sd ra, 8(sp) sd s0, 0(sp) # Base case: if (n <= 1) return 1 li t0, 1 ble a0, t0, .Lbase # Save n in callee-saved register mv s0, a0 # s0 = n # Recursive call: fact(n-1) addi a0, a0, -1 # a0 = n - 1 call fact # ra = return addr, jump to fact # a0 now holds fact(n-1) # Multiply: n * fact(n-1) mul a0, s0, a0 # a0 = n * fact(n-1) j .Lepilogue .Lbase: li a0, 1 # return 1 .Lepilogue: ld ra, 8(sp) ld s0, 0(sp) addi sp, sp, 16 ret

Stack Growth During Recursion

Each recursive call adds a 16-byte frame (in this example). For fact(5), the stack grows by 5 frames = 80 bytes before any returns happen. For fact(10000), that's 160,000 bytes — which may exceed the stack limit. This is called stack overflow. The OS sets a default stack size (typically 8 MB on Linux), and exceeding it causes a SIGSEGV (segmentation fault).

/* Stack during fact(3) */ Call fact(3) Call fact(2) Call fact(1) ┌─────────┐ ┌─────────┐ ┌─────────┐ │ ra, s0 │ │ ra, s0 │ │ ra, s0 │ │ n=3 │ │ n=2 │ │ n=1 │ ← base case └─────────┘ └─────────┘ └─────────┘ sp → low sp → lower sp → lowest Returns: 1 → 2*1=2 → 3*2=6 → answer = 6

Tail Call Optimization

Some recursive functions can be transformed into loops, eliminating stack growth entirely. A tail call is a function call that is the last action before return — its result is returned directly, with no further computation. The compiler can replace a tail call with a jump (reusing the current frame) instead of a call (creating a new frame). This is called tail call optimization (TCO).

// NOT tail-recursive: multiply happens AFTER the call int fact(int n) { if (n <= 1) return 1; return n * fact(n - 1); // multiply after call } // Tail-recursive: call is the LAST action, uses accumulator int fact_tail(int n, int acc) { if (n <= 1) return acc; return fact_tail(n - 1, n * acc); // pure tail call }
# Compiler turns tail-recursive fact_tail into a loop: fact_tail: .Lloop: li t0, 1 ble a0, t0, .Ldone # if n <= 1, return acc mul a1, a0, a1 # acc = n * acc addi a0, a0, -1 # n = n - 1 j .Lloop # loop! (no new stack frame) .Ldone: mv a0, a1 # return acc ret
Key Idea: TCO = Free Loop

Tail call optimization converts recursion into iteration without growing the stack. The function reuses its own frame by jumping back to the top instead of calling. This means fact_tail(1000000, 1) uses the same stack space as fact_tail(1, 1) — no overflow. RISC-V and ARM64 guarantee TCO; x86-64 does it when possible but doesn't guarantee it.

5. Variadic Functions

Functions like printf and scanf take a variable number of arguments. How does the CPU know where each argument is? There's no argument count in the call — printf figures it out by parsing the format string. The mechanism that makes this work is called variadic functions, and it depends heavily on the calling convention.

How printf Works

When you call printf("%d %s %d\n", 42, "hi", 7), the arguments are passed according to the normal calling convention. In RISC-V, the first 8 arguments go in registers a0–a7, and additional arguments go on the stack. printf receives the format string in a0, then reads subsequent arguments by parsing format specifiers (%d, %s, etc.) and fetching the next argument each time.

// printf("%d %s %d\n", 42, "hi", 7) // Argument layout in RISC-V: // a0 = pointer to "%d %s %d\n" // a1 = 42 (first %d) // a2 = "hi" (first %s) // a3 = 7 (second %d) # RISC-V: calling printf la a0, .Lfmt # a0 = format string li a1, 42 # a1 = 42 la a2, .Lhi # a2 = "hi" li a3, 7 # a3 = 7 call printf .Lfmt: .asciz "%d %s %d\n" .Lhi: .asciz "hi"

va_list Implementation

The C standard library provides va_list, va_start, va_arg, and va_end to access variadic arguments portably. Under the hood, va_list is a structure that tracks the current position in the argument list. On register-based ABIs (like RISC-V and x86-64), it must handle two cases: arguments still in registers and arguments that have spilled to the stack.

/* RISC-V va_list structure (simplified) */ typedef struct { void *gp_offset; /* offset into reg save area */ void *fp_offset; /* offset into FP reg save area */ void *overflow_arg; /* pointer to stack args */ void *reg_save; /* saved register area */ } va_list; /* va_arg(ap, type): 1. If gp_offset < 8*8, read from reg_save[gp_offset] 2. Else, read from overflow_arg, advance overflow_arg 3. Advance gp_offset by sizeof(type) */

The Overflow Area

The tricky part of variadic functions on register-based ABIs is the overflow area. When a variadic function is called, the compiler doesn't know how many register arguments will be accessed. The solution: the callee saves all register arguments (a0–a7) into a contiguous register save area on the stack. Then va_arg can read from this area sequentially, and when it runs out of register slots, it continues reading from the overflow area (where extra arguments were pushed by the caller).

/* Stack layout for a variadic function in RISC-V */ ┌──────────────────────┐ │ Overflow args │ ← a8, a9, ... (if > 8 args) ├──────────────────────┤ │ Return address (ra) │ ├──────────────────────┤ │ Saved fp │ ├──────────────────────┤ <── fp │ Reg save area: │ │ [0] = a0 │ ← va_arg reads from here │ [8] = a1 │ │ [16] = a2 │ │ ... │ │ [56] = a7 │ ← last register arg ├──────────────────────┤ │ Local variables │ └──────────────────────┘ <── sp
Key Idea: Register Save Area

Variadic functions must save all argument registers to the stack at entry, even if they might not use them all. This is why variadic functions are slightly slower than fixed-argument functions: they pay the cost of saving 8 registers (64 bytes) upfront. The va_list then walks this saved area as if it were a flat array.

Stack-Based vs Register-Based Varargs

On older ABIs (like MIPS O32 and 32-bit x86), all arguments are passed on the stack. This makes variadic functions trivial: va_arg just increments a stack pointer. On modern ABIs (RISC-V, x86-64, ARM64), arguments are in registers, which is faster for normal calls but requires the register save area trick for variadic functions. This is a classic tradeoff: optimize for the common case (fixed arguments in registers) at the expense of the uncommon case (variadic functions).

6. Inline Assembly in C

Sometimes you need to write a few instructions that C can't express: reading a CPU control register, executing a barrier, or using a special instruction like fence. GCC and Clang provide inline assembly via the __asm__ keyword, letting you embed assembly directly in C code while letting the compiler handle register allocation and optimization around it.

Basic Syntax

GCC inline assembly uses a template string with placeholders, followed by input operands, output operands, and a clobber list. The syntax is powerful but notoriously hard to read. The general form is: __asm__ (template : outputs : inputs : clobbers).

/* Basic inline assembly: add two numbers */ int add(int a, int b) { int result; __asm__ ( "add %0, %1, %2" /* template */ : "=r"(result) /* output: %0 = result, in a register */ : "r"(a), "r"(b) /* inputs: %1 = a, %2 = b */ ); return result; }

Constraints

Constraints tell the compiler how to pass values to and from the assembly. The most common constraints are "r" (any general-purpose register), "=r" (output register, write-only), "+r" (read-write register), "i" (immediate constant), and "m" (memory operand). The compiler chooses which register to use and substitutes the %0, %1, etc. placeholders accordingly.

ConstraintMeaningExample Use

The Clobber List

The clobber list tells the compiler which registers (or memory) your assembly modifies, so the compiler doesn't assume they're preserved. If you forget to list a clobbered register, the compiler may store important data there and your assembly will corrupt it. The special clobber "memory" means your assembly reads or writes memory in a way the compiler can't predict, forcing a memory barrier.

/* Reading RISC-V cycle counter (rdcycle) */ static inline unsigned long rdcycle(void) { unsigned long cycles; __asm__ volatile ( "rdcycle %0" : "=r"(cycles) : /* no inputs */ : /* no clobbers */ ); return cycles; } /* Memory barrier: fence iorw, iorw */ static inline void mb(void) { __asm__ volatile ("fence iorw, iorw" ::: "memory"); }

The volatile Keyword

The volatile qualifier on __asm__ tells the compiler not to optimize away or reorder the assembly, even if the output appears unused. This is critical for instructions with side effects: reading a hardware counter, executing a barrier, or performing an I/O operation. Without volatile, the compiler might delete your assembly if it thinks the result is unused.

Warning: Always Use volatile for Side Effects

If your inline assembly reads a hardware register, executes a barrier, or has any side effect beyond producing an output value, always use __asm__ volatile. Without it, the compiler may remove the instruction entirely during optimization, leading to subtle, hard-to-debug failures.

Practical Examples

/* Atomic compare-and-swap on RISC-V (LR/SC) */ static inline int atomic_cas(int *addr, int old, int new) { int result; __asm__ volatile ( "1: lr.w %0, (%2) \n" /* load-reserved */ " bne %0, %1, 2f \n" /* if != old, exit */ " sc.w %0, %3, (%2) \n" /* store-conditional */ " bnez %0, 1b \n" /* retry if sc failed */ "2: \n" : "=&r"(result) : "r"(old), "r"(addr), "r"(new) : "memory" ); return result; } /* Read CSR (Control and Status Register) */ static inline unsigned long r_csr(unsigned long csr) { unsigned long val; __asm__ volatile ("csrr %0, %1" : "=r"(val) : "i"(csr)); return val; }

7. Atomic Operations and Memory Ordering

When multiple threads (or CPU cores) access the same memory, you need atomic operations — operations that complete without interruption. A simple count++ in C is not atomic: it compiles to a load, an add, and a store. If two threads execute it simultaneously, one update can be lost. Atomic operations solve this by providing instructions that read and write memory in a single, indivisible step.

The Read-Modify-Write Problem

Consider count++ on a multi-core system. Thread A loads count (value 5), adds 1 (getting 6), and stores 6. But if Thread B loads count (also 5) before A stores, both will store 6 — one increment is lost. This is a race condition. The solution is to make the load-add-store sequence atomic: no other core can observe or modify the value in between.

/* Race condition: count++ is NOT atomic */ // Thread A Thread B ld t0, (count) ld t0, (count) # both read 5 addi t0, t0, 1 addi t0, t0, 1 # both compute 6 sd t0, (count) sd t0, (count) # both write 6 (lost update!) /* Atomic version: amoswap (single instruction) */ amoswap.w a0, a1, (a2) # swap atomically

Atomic Exchange: amoswap

The simplest atomic operation is exchange: atomically swap a register value with a memory location. RISC-V provides amoswap for this. It reads the old value from memory into a register and writes a new value, all in one indivisible step. This is the building block for spinlocks.

# RISC-V: atomic swap # amoswap.w rd, rs2, (rs1) # rd = M[rs1]; M[rs1] = rs2 (all atomic) li a1, 1 # value to store la a2, lock_var # address amoswap.w a0, a1, (a2) # a0 = old, M[a2] = 1 # if a0 == 0, we got the lock!

Compare-and-Swap (CAS)

Compare-and-swap (CAS) is the most versatile atomic operation. It atomically compares a memory location to an expected value; if they match, it writes a new value and reports success. If they don't match, it does nothing and reports failure. CAS is the foundation of most lock-free data structures. On x86-64, it's the cmpxchg instruction; on RISC-V, it's implemented via load-linked/store-conditional (LR/SC).

# RISC-V: CAS via LR/SC (load-reserved / store-conditional) cas: .Lretry: lr.w t0, (a0) # load-reserved: t0 = M[a0] bne t0, a1, .Lfail # if t0 != expected, fail sc.w t1, a2, (a0) # store-conditional: M[a0] = new bnez t1, .Lretry # if sc failed (t1!=0), retry li a0, 0 # success ret .Lfail: li a0, 1 # failure ret
Key Idea: LR/SC vs cmpxchg

x86-64 has a single cmpxchg instruction that does compare-and-swap atomically. RISC-V and ARM64 use a two-instruction approach: load-linked (or load-reserved) marks the address, and store-conditional only succeeds if no other write occurred to that address since the load-linked. If it fails, you retry. This is more flexible but requires a retry loop.

Memory Ordering and Fences

On a single-core CPU, memory operations appear to execute in program order. But on multi-core systems, the CPU and compiler may reorder memory operations for performance. This means Thread A's writes may become visible to Thread B in a different order than A executed them. Memory barriers (fences) prevent this reordering, ensuring that operations before the fence complete before operations after it.

The ABA Problem

CAS compares values, not "has this changed?" This leads to the ABA problem: Thread 1 reads value A, Thread 2 changes it to B then back to A, and Thread 1's CAS succeeds because the value is "still A" — but something did change in between. This can corrupt lock-free data structures. Solutions include tagged pointers (append a version counter) or hazard pointers (see Chapter 9).

The ABA Problem

Thread 1: reads A from ptr. Thread 2: changes ptr to B, frees A, allocates new object at same address as A, sets ptr back to A. Thread 1: CAS succeeds (value is A), but the object at A was freed and reallocated — use-after-free! This is why lock-free programming is hard.

8. Spinlocks in Assembly

A spinlock is the simplest synchronization primitive: a thread that wants the lock repeatedly tries to acquire it, "spinning" in a loop until it succeeds. Spinlocks are used in the OS kernel and in low-level performance-critical code where the lock is held for a very short time and sleeping would be too expensive. Understanding spinlocks at the assembly level reveals exactly how atomic instructions, memory ordering, and CPU caches interact.

How a Spinlock Works

A spinlock is typically a single word in memory: 0 means unlocked, 1 means locked. To acquire, a thread atomically swaps 1 into the lock word. If the old value was 0, the thread got the lock. If the old value was 1, someone else had it, so the thread spins and retries. To release, the holder simply writes 0 to the lock word.

# RISC-V spinlock (from xv6 kernel/spinlock.h concept) # lock = 0: unlocked, lock = 1: locked acquire: .Lspin: li t1, 1 amoswap.w.aq t0, t1, (a0) # atomic swap: t0=old, M[a0]=1 bnez t0, .Lspin # if old was 1, keep spinning ret # got the lock! release: fence rw, w # release fence: flush writes sd zero, 0(a0) # lock = 0 (release) ret

The amoswap Instruction

The key instruction is amoswap.w.aq. The .aq (acquire) suffix ensures that all memory operations after the lock acquisition appear to happen after the acquisition. Without it, the CPU might reorder a write to protected data before the lock is actually acquired, causing a race. The release uses a fence rw, w to ensure all writes to protected data complete before the lock is released.

x86-64: The lock Prefix

On x86-64, atomicity is achieved with the lock prefix, which turns a normal instruction into an atomic one by asserting a hardware lock on the cache line. The xchg instruction is implicitly locked. x86-64 also has a strong memory model: loads and stores are already ordered, so explicit fences are rarely needed for spinlocks.

# x86-64 spinlock acquire: .Lspin: mov edx, 1 xchg dl, [rdi] # atomic exchange (implicit lock) test dl, dl # was old value 0? jnz .Lspin # if not 0, spin ret release: mov byte [rdi], 0 # release (x86 strong ordering) ret

ARM64: ldaxr / stlxr

ARM64 uses load-exclusive/store-exclusive pairs, similar to RISC-V's LR/SC. The ldaxr (load-acquire-exclusive) and stlxr (store-release-exclusive) instructions provide both exclusivity and memory ordering in one step.

# ARM64 spinlock acquire: .Lspin: ldaxr w1, [x0] # load-acquire-exclusive cbnz w1, .Lspin # if != 0, spin mov w2, 1 stlxr w3, w2, [x0] # store-release-exclusive cbnz w3, .Lspin # if store failed, retry ret release: stlr wzr, [x0] # store-release 0 ret

Backoff Strategies

Naive spinlocks waste CPU cycles and cause heavy cache-line bouncing: every core spinning on the lock repeatedly issues atomic operations, flooding the interconnect. A backoff strategy adds a delay between retries, reducing contention. Exponential backoff doubles the delay each time, spreading out retries and reducing collisions.

# RISC-V spinlock with exponential backoff acquire_backoff: li s2, 1 # initial delay = 1 .Lspin: li t1, 1 amoswap.w.aq t0, t1, (a0) beqz t0, .Lgot # got it! # Backoff: delay loop mv t2, s2 .Ldelay: addi t2, t2, -1 bnez t2, .Ldelay slli s2, s2, 1 # double the delay j .Lspin .Lgot: ret

Fair Spinlocks (Ticket Lock)

A simple spinlock is unfair: there's no guarantee about which waiting thread gets the lock next. Under heavy contention, some threads may starve. A ticket lock solves this: each thread takes a "ticket" (an incrementing number) and waits until its ticket is called. This guarantees FIFO ordering — no starvation.

# RISC-V ticket lock # struct { int next; int owner; } ticket_acquire: li t1, 1 amoadd.w t0, t1, (a0) # atomically get my ticket (t0) # t0 = old next ticket, now next++ .Lwait: lw t1, 4(a0) # read owner bne t0, t1, .Lwait # wait until owner == my ticket ret ticket_release: lw t0, 4(a0) addi t0, t0, 1 sw t0, 4(a0) # owner++ (next in line) ret
Key Idea: Ticket Lock = FIFO Fairness

The ticket lock guarantees that threads acquire the lock in the order they requested it. Each thread gets a unique ticket number via atomic increment, then waits until the owner counter reaches its ticket. No thread can "cut in line." The downside: under low contention, the extra atomic add adds overhead compared to a simple spinlock.

9. Lock-Free Programming

Locks are simple but have drawbacks: they can cause deadlocks, priority inversion, and performance bottlenecks. Lock-free programming avoids locks entirely, using atomic operations to coordinate threads. This is harder to get right but can be faster and more robust. However, lock-free code is notoriously difficult to write correctly — subtle bugs can lurk for years before manifesting.

Lock-Free vs Wait-Free

Lock-free means at least one thread always makes progress (the system as a whole moves forward, but individual threads may starve). Wait-free is stronger: every thread makes progress in a bounded number of steps (no starvation). Wait-free algorithms are harder to design but guarantee fairness. Most practical lock-free data structures (like lock-free queues) are lock-free but not wait-free.

Lock-Free Stack with CAS

A classic lock-free data structure is the Treiber stack — a LIFO stack using CAS for push and pop. To push, you create a new node, set its next pointer to the current head, and CAS the head pointer from old-head to new-node. If the CAS fails (someone else changed head), you retry. Pop is similar: read head, read head->next, CAS head from old-head to head->next.

// Lock-free push (Treiber stack) void push(Node **head, Node *node) { Node *old_head; do { old_head = *head; // snapshot node->next = old_head; // link to current head } while (!CAS(head, old_head, node)); // retry if changed } // Lock-free pop Node *pop(Node **head) { Node *old_head, *next; do { old_head = *head; if (old_head == NULL) return NULL; next = old_head->next; // DANGER: old_head may be freed! } while (!CAS(head, old_head, next)); return old_head; }
The Pop Problem: Use-After-Free

The pop operation above has a subtle bug: after reading old_head, another thread might pop it, free it, and then our next = old_head->next dereferences freed memory. This is the ABA problem combined with use-after-free. Solving it requires hazard pointers or epoch-based reclamation.

Hazard Pointers

A hazard pointer is a per-thread pointer that says "I'm using this memory, don't free it." Before accessing a shared node, a thread publishes its address in a hazard pointer. Before freeing a node, a thread checks all hazard pointers — if any match, the free is deferred. This prevents use-after-free in lock-free code.

// Hazard pointer protected pop (simplified) Node *pop(Node **head) { Node *old_head, *next; retry: old_head = *head; if (old_head == NULL) return NULL; // Publish hazard pointer: "I'm using old_head" my_hazard = old_head; // Re-check: is head still old_head? (might have changed) if (*head != old_head) goto retry; next = old_head->next; // safe now: node won't be freed if (!CAS(head, old_head, next)) goto retry; // Retire old_head: check all hazards, defer if needed retire_node(old_head); my_hazard = NULL; return old_head; }

RCU (Read-Copy-Update) Basics

RCU is a synchronization mechanism used heavily in the Linux kernel for read-heavy data structures. The idea: readers don't lock at all — they just access the data. Writers create a copy, modify the copy, and atomically swap the pointer. Old data is freed only after all readers that might be using it have finished (a "grace period"). RCU is extremely fast for readers (no atomic operations) but adds complexity for writers.

// RCU-style update (conceptual) void update(Data **ptr, Data *new_data) { Data *old = *ptr; rcu_assign_pointer(*ptr, new_data); // publish new synchronize_rcu(); // wait for all readers free(old); // now safe to free } // RCU read (no locks!) Data *read(Data **ptr) { rcu_read_lock(); Data *d = rcu_dereference(*ptr); // safe read // use d... rcu_read_unlock(); return d; }
Key Idea: When to Use Lock-Free

Use lock-free when: (1) contention is high and locks cause too much blocking, (2) you can't afford deadlock (e.g., signal handlers), or (3) latency must be bounded. Use locks when: (1) the critical section is long, (2) correctness matters more than peak performance, or (3) the data structure is complex. Default to locks — lock-free should be a last resort, not a first choice.

10. Context Switching

A context switch is the mechanism by which the OS saves one process's state and restores another's, allowing multiple programs to share a single CPU. At the assembly level, this means saving all registers, switching the stack pointer, and potentially switching page tables. In xv6, the context switch code lives in kernel/swtch.S — a small, carefully written assembly file that is the heart of the scheduler.

The swtch.S Function

xv6's swtch function is remarkably simple: it saves callee-saved registers (ra, sp, and s0–s11) from the old context and loads them from the new context. It does not save caller-saved registers — those are the caller's responsibility. It also doesn't switch page tables; that's done separately. The beauty of swtch is its minimalism: it saves exactly what's needed to resume execution later.

# xv6 kernel/swtch.S (RISC-V) # void swtch(struct context *old, struct context *new); # a0 = old context, a1 = new context .globl swtch swtch: sd ra, 0(a0) # save return address sd sp, 8(a0) # save stack pointer sd s0, 16(a0) # save s0 (frame pointer) sd s1, 24(a0) # save s1 # ... save s2-s11 ... sd s11, 104(a0) # save s11 ld ra, 0(a1) # restore return address ld sp, 8(a1) # restore stack pointer ld s0, 16(a1) # restore s0 ld s1, 24(a1) # restore s1 # ... restore s2-s11 ... ld s11, 104(a1) # restore s11 ret # jump to new ra (new context)

What swtch Does NOT Do

swtch is deliberately minimal. It does not switch page tables (that's done by scheduler() via w_satp), does not save floating-point registers (xv6 doesn't use them), and does not save caller-saved registers (the caller must save those if needed). The key insight is that swtch only needs to save what the C compiler expects to be preserved across function calls — the callee-saved registers plus ra and sp.

Kernel Stack vs User Stack

Each process has two stacks: a user stack (for user-mode code) and a kernel stack (for kernel code executing on behalf of that process). When a user program makes a syscall or triggers a trap, the CPU switches to the kernel stack automatically (via sscratch in RISC-V). The context switch (swtch) operates on kernel stacks — it switches from one process's kernel stack to another's. The user stack is saved in the trapframe and restored when returning to user mode.

/* Process memory layout (xv6) */ ┌──────────────────────┐ │ User stack │ ← user sp (user mode) │ (user program) │ ├──────────────────────┤ ← trampoline page │ Trapframe │ ← saved user registers ├──────────────────────┤ │ Kernel stack │ ← kernel sp (kernel mode) │ (kernel code for │ │ this process) │ └──────────────────────┘ ↑ swtch switches between different processes' kernel stacks

The Scheduler Context

The scheduler itself runs in a special context. In xv6, each CPU has a scheduler() function that loops forever, picking the next runnable process and calling swtch to switch to it. When a process yields (or is preempted), swtch switches back to the scheduler's context. This means swtch is always called from two places: scheduler() (switching to a process) and yield() (switching from a process back to the scheduler).

Key Idea: swtch is Symmetric

swtch(old, new) saves the current state into old and loads from new. When the new context was previously saved by a swtch call, ret returns into that previous call's caller. This is how execution "resumes" — it's not a new call, it's a return to a previously suspended call.

11. Trap Handling in Detail

When a user program makes a syscall, triggers a page fault, or is interrupted by a timer, the CPU transfers control to the OS via a trap. In RISC-V, the trap mechanism is controlled by several Control and Status Registers (CSRs): stvec (trap vector), scause (trap cause), sepc (exception PC), and sscratch (scratch register). Understanding this flow is essential for OS development.

The Trap Flow

When a trap occurs in supervisor mode (or user mode traps to supervisor), the hardware does the following atomically: (1) saves the current PC to sepc, (2) records the cause in scause, (3) sets the SPP bit in sstatus to indicate the previous privilege level, (4) loads stvec into the PC. The OS trap handler then runs, examines scause, and dispatches to the appropriate handler.

# RISC-V trap entry (xv6 kernel/trampoline.S, simplified) .globl uservec uservec: # At this point: a0 = user's a0, sscratch = user sp # Swap: put user sp in a0, put trapframe addr in sscratch csrrw a0, sscratch, a0 # Save all user registers into trapframe (at a0) sd ra, 40(a0) sd sp, 48(a0) sd gp, 56(a0) sd tp, 64(a0) sd t0, 72(a0) # ... save all 32 registers ... # Restore kernel stack pointer from trapframe ld sp, 8(a0) # kernel sp # Call the C trap handler call usertrap

The Trampoline Page

xv6 maps a special trampoline page at the same virtual address in both user and kernel page tables. This is critical: when a trap occurs, the page table is still the user's. The trap handler code (in the trampoline page) must be accessible in the user's address space. The trampoline saves user registers into the trapframe, switches to the kernel stack, switches the page table to the kernel's, and then calls the C-level trap handler (usertrap).

/* Trampoline page mapping */ User page table: Kernel page table: ┌──────────────┐ ┌──────────────┐ │ TRAMPOLINE │ ← same VA → │ TRAMPOLINE │ │ (trap code) │ │ (trap code) │ ├──────────────┤ ├──────────────┤ │ TRAPFRAME │ │ │ │ (saved regs) │ │ kernel data │ ├──────────────┤ ├──────────────┤ │ user code │ │ kernel code │ │ user data │ │ kernel data │ └──────────────┘ └──────────────┘ Trap: uservec (in trampoline) saves regs to TRAPFRAME, switches to kernel page table, calls usertrap()

Returning from Trap: sret

To return to user mode, the OS uses the sret instruction. Before sret, the OS restores the user's registers from the trapframe, sets sepc to the saved user PC, switches the page table back to the user's, and then executes sret. The hardware then: (1) sets the PC to sepc, (2) restores the privilege level from SPP, (3) resumes user execution.

# RISC-V trap return (xv6 kernel/trampoline.S, simplified) .globl userret userret: # a0 = trapframe address # a1 = user page table (satp) # Switch to user page table csrw satp, a1 sfence.vma zero, zero # flush TLB # Restore all user registers from trapframe ld ra, 40(a0) ld sp, 48(a0) # ... restore all registers ... # Swap a0 and sscratch: a0 = user's a0, sscratch = trapframe csrrw a0, sscratch, a0 # Return to user mode sret
Key Idea: sscratch Trick

The sscratch register holds the user stack pointer while in kernel mode, and the trapframe address while in user mode. The csrrw instruction atomically swaps a0 and sscratch, so in one instruction: (1) the user's a0 is saved to sscratch, and (2) the trapframe address (previously in sscratch) is loaded into a0. This is how the trap handler gets the trapframe address without clobbering any user register.

12. Boot Code and Startup

When you power on a computer, the CPU starts executing at a fixed address (the reset vector). At this point, there is no stack, no C runtime, no page tables — just raw hardware. The boot code (written in assembly) must set up the minimum environment needed before any C code can run. In xv6 on RISC-V, this code lives in kernel/entry.S and kernel/start.c.

The Reset Vector

On RISC-V, the CPU starts in machine mode (the most privileged mode) at address 0x80000000 (on QEMU). The first instructions must be assembly because no C runtime exists yet. The very first task is to set up a stack pointer so that C functions can be called. Without a valid sp, any function call (which pushes to the stack) will crash.

# xv6 kernel/entry.S (RISC-V, simplified) # QEMU loads the kernel at 0x80000000 and jumps here .section .text .globl _entry _entry: # Set up stack pointer for each hart (CPU core) # stack0 is defined in start.c, each hart gets its own stack la sp, stack0 li a0, 1024 # stack size per hart csrr a1, mhartid # get hart ID addi a1, a1, 1 # hart 0 uses stack[0..1024] mul a0, a0, a1 # offset = 1024 * (hartid+1) add sp, sp, a0 # sp = stack0 + offset # Now we have a stack — call start() call start # Unreachable spin: j spin

What Happens Before main()

After entry.S sets up the stack, it calls start() (in start.c). This function runs in machine mode and performs critical setup: (1) delegating traps to supervisor mode (so the OS can handle them), (2) setting up page tables (creating the initial mapping), (3) configuring timers (for preemption), and (4) dropping to supervisor mode via mret. Only then does it jump to main().

// xv6 kernel/start.c (simplified) void start() { // Set MPP (Machine Previous Privilege) to Supervisor unsigned long x = r_mstatus(); x |= MSTATUS_MPP_S; w_mstatus(x); // Set return address to main() w_mepc((uint64)main); // Delegate traps to supervisor mode w_medeleg(0xffff); w_mideleg(0xffff); // Set up page tables (identity mapping) // ... kvmmake() ... // Drop to supervisor mode and jump to main() asm volatile("mret"); }

Clearing BSS and Initializing .data

Before main() runs, the C runtime must initialize the BSS segment (uninitialized globals) to zero. In a normal Linux program, the OS and C runtime (crt0) handle this. In a bare-metal OS like xv6, the startup code must do it manually. If BSS isn't zeroed, uninitialized global variables will contain garbage, leading to unpredictable behavior.

# Clearing BSS (typical startup code) clear_bss: la t0, __bss_start # start of BSS la t1, __bss_end # end of BSS .Lbss_loop: bgeu t0, t1, .Lbss_done sd zero, 0(t0) # zero 8 bytes addi t0, t0, 8 # advance j .Lbss_loop .Lbss_done:

Setting Up Page Tables

Before enabling paging, the OS must create page tables that map virtual addresses to physical addresses. In xv6, start() creates an identity mapping (virtual address = physical address) so that when paging is enabled, the existing code continues to work. The satp register is set to point to the root page table, and then paging is enabled by setting a bit in sstatus.

Key Idea: Boot Order

The boot sequence is a strict chain: (1) entry.S sets up the stack, (2) start.c configures the CPU (trap delegation, page tables, timer), (3) main() initializes subsystems (console, virtual memory, file system), (4) the first user process is created. Each step depends on the previous one. Skip a step, and the system crashes immediately.

13. Interrupts and Exception Handling

Exceptions and interrupts are both "traps" — transfers of control to the OS — but they differ in origin. An exception is synchronous: it's caused by the current instruction (page fault, illegal instruction, division by zero). An interrupt is asynchronous: it comes from outside the CPU (timer, disk, keyboard) and can arrive at any time. The OS must handle both, but the strategies differ.

Interrupt Controller Basics

External devices don't connect directly to the CPU. Instead, they connect to an interrupt controller (like the PLIC on RISC-V, or APIC on x86). The interrupt controller collects interrupts from all devices, prioritizes them, and delivers them to the CPU one at a time. The OS must acknowledge each interrupt (tell the controller it's been received) and enable/disable specific interrupt sources.

/* RISC-V PLIC (Platform-Level Interrupt Controller) */ // Enable timer interrupt (interrupt source 5) *(uint32*)PLIC_SENABLE(hart) |= (1 << 5); // Claim interrupt: read claim register uint32 irq = *(uint32*)PLIC_SCLAIM(hart); // Handle the interrupt... // Complete: tell PLIC we're done *(uint32*)PLIC_SCLAIM(hart) = irq;

Top-Half and Bottom-Half

Interrupt handlers run with interrupts disabled, so they must be fast. A common strategy splits handling into two parts: the top-half (the actual interrupt handler) does the minimum — acknowledge the interrupt, copy data, schedule deferred work — and returns quickly. The bottom-half (deferred work) does the heavy processing later, with interrupts enabled. In Linux, bottom-halves are called "softirqs" or "tasklets"; in xv6, the pattern is simpler but the concept is the same.

Analogy: Top-Half = Triage Nurse

Think of the top-half as a triage nurse in an emergency room: they quickly assess the situation, stop the bleeding, and schedule the patient for full treatment later. The bottom-half is the full treatment — it takes time but can be done without blocking other emergencies. You never want the triage nurse doing surgery — that would block the whole ER.

Interrupt Stacking

When an interrupt arrives, the CPU must save enough state to resume the interrupted code. In RISC-V, the hardware saves the PC to sepc and the cause to scause, but does not save general-purpose registers. The trap handler (in the trampoline page) must save all registers to the trapframe. This is why the trapframe is so large — it holds all 32 general-purpose registers plus the saved PC and status.

Reentrant Interrupts

By default, the CPU disables interrupts of the same or lower priority when entering an interrupt handler. This prevents nested interrupts (an interrupt inside an interrupt), which can cause stack overflow if they nest too deeply. Some systems allow reentrant interrupts — re-enabling interrupts inside the handler — but this requires careful design: the handler must be reentrant (no static variables), and the stack must be large enough for nesting.

Warning: Interrupt Handler Constraints

Interrupt handlers run in a restricted context: you cannot sleep, cannot acquire certain locks, and cannot access user space directly (in some OS designs). Violating these constraints causes deadlocks or crashes. Always check what's safe in your handler — when in doubt, defer work to a bottom-half.

14. Compiler Optimization and Assembly

The C compiler doesn't just translate your code to assembly — it transforms it. With optimization flags like -O2 and -O3, the compiler reorders instructions, eliminates redundant code, unrolls loops, and even rewrites your logic entirely. Understanding what the compiler does is essential for reading generated assembly, debugging, and writing high-performance code.

Optimization Levels

Register Allocation

At -O0, the compiler stores every variable in memory (on the stack) and loads/stores it for each operation. At -O2, the compiler performs register allocation: it analyzes which variables are live simultaneously and assigns them to CPU registers, eliminating most loads and stores. This is the single biggest optimization — memory access is 100x slower than register access.

// C code int sum(int a, int b, int c) { return a + b + c; } # -O0: loads from stack, adds, stores back sum: addi sp, sp, -16 sw a0, 12(sp) # store a sw a1, 8(sp) # store b sw a2, 4(sp) # store c lw a0, 12(sp) # reload a lw a1, 8(sp) # reload b add a0, a0, a1 # a + b lw a1, 4(sp) # reload c add a0, a0, a1 # + c addi sp, sp, 16 ret # -O2: everything in registers, 1 instruction! sum: add a0, a0, a1 # a + b add a0, a0, a2 # + c ret

Instruction Scheduling

The compiler reorders instructions to avoid pipeline stalls. If an instruction depends on a load from memory (which takes several cycles), the compiler moves independent instructions into the gap so the CPU doesn't idle. This is called instruction scheduling. The result: the assembly may not match your source code's order at all, even though the observable behavior is the same.

Loop Unrolling

A loop has overhead: incrementing the counter, checking the condition, and jumping back. Loop unrolling duplicates the loop body multiple times, reducing the overhead per iteration. At -O3, the compiler unrolls loops automatically. This trades code size for speed.

// C: sum array for (int i = 0; i < 100; i++) sum += arr[i]; # -O3: unrolled by 4 .Lloop: lw t0, 0(a1) # arr[i] lw t1, 4(a1) # arr[i+1] lw t2, 8(a1) # arr[i+2] lw t3, 12(a1) # arr[i+3] add a0, a0, t0 add a0, a0, t1 add a0, a0, t2 add a0, a0, t3 addi a1, a1, 16 # advance by 4 elements addi a2, a2, -4 # count -= 4 bnez a2, .Lloop # loop if more

Common Subexpression Elimination

If the same expression is computed multiple times, the compiler computes it once and reuses the result. This is common subexpression elimination (CSE). For example, a[i] + a[i] loads a[i] once and doubles it, rather than loading twice.

Key Idea: -O0 vs -O2

At -O0, assembly is easy to read but slow: every variable lives in memory, every operation loads and stores. At -O2, the compiler is aggressive: variables stay in registers, loops are transformed, dead code is removed. When debugging, use -O0 for predictable behavior. For production, always use -O2 (or -O3 for compute-heavy code).

15. Branch Prediction and Pipeline

Modern CPUs are deeply pipelined: they work on multiple instructions simultaneously, like an assembly line. When a branch instruction (like if/else) is encountered, the CPU doesn't know which path to take until the branch is resolved — which may be many cycles later. To avoid stalling, the CPU guesses the branch outcome using a branch predictor. If the guess is wrong, the pipeline must be flushed, wasting 10-20 cycles.

Branch Penalty

When the CPU mispredicts a branch, it must discard all the instructions it speculatively fetched and start over from the correct path. This is the branch misprediction penalty. On modern CPUs, this can be 15-20 cycles. In tight loops with unpredictable branches, mispredictions can dominate execution time.

// Branch-heavy code: hard to predict if (data[i] < threshold) count++; else count--; # Assembly: branch may mispredict ~50% if data is random lw t0, (a1) bge t0, a2, .Lelse # 50% mispredict = 10 cycle penalty addi a0, a0, 1 j .Lnext .Lelse: addi a0, a0, -1 .Lnext:

Branch Prediction Buffers

CPUs use several prediction mechanisms: branch history tables (remember the last outcome of each branch), branch target buffers (remember the target address), and two-level adaptive predictors (track patterns of taken/not-taken). Modern predictors achieve >95% accuracy on typical code, but pathological cases (random data, adversarial patterns) can drop accuracy to 50%.

Branch-Free Code: cmov

One way to avoid branch mispredictions is to eliminate branches entirely. The conditional move (cmov on x86-64, sel/ite on ARM64) instruction selects between two values based on a condition — without branching. RISC-V doesn't have a conditional move instruction in the base ISA, but the compiler can emulate it with arithmetic.

// Branch-free version int delta = (data[i] < threshold) ? 1 : -1; count += delta; # x86-64: cmov (no branch!) mov eax, 1 # assume true mov edx, -1 # alternative cmp [a1], a2 # compare cmovl eax, edx # if less, use -1 (no branch!) add [count], eax # RISC-V: branch-free with arithmetic lw t0, (a1) slt t0, t0, a2 # t0 = (data < threshold) ? 1 : 0 addi t1, zero, -1 # t1 = -1 addi t2, zero, 1 # t2 = 1 # select: if t0==1, use t2; else use t1 mul t0, t0, t2 # t0 = t0 * 1 = 0 or 1 # ... (or use: neg + and + or trick)

Predication in ARM64

ARM64 takes predication further: many instructions can be conditionally executed based on flags. Instead of branching, the instruction simply does nothing if the condition is false. This is called predication. The ite (if-then-else) suffix makes the next 1-4 instructions conditional.

# ARM64: conditional execution (predication) cmp w0, w1 # compare csel w0, w2, w3, lt # if less: w0=w2, else w0=w3 (no branch!)
Key Idea: When to Go Branch-Free

Branch-free code helps when the branch is unpredictable (~50% taken). If the branch is highly predictable (>90%, like a loop condition), a branch is better — the predictor gets it right, and branch-free code adds extra instructions. Rule of thumb: use branch-free for data-dependent branches on random data; use normal branches for loop control and common cases.

16. SIMD and Vector Instructions

Single Instruction, Multiple Data (SIMD) instructions process multiple data elements in parallel using a single instruction. Instead of adding two numbers, a SIMD add can add 4, 8, or 16 numbers at once. This is one of the most powerful performance optimizations available: if your code processes arrays or streams of data, SIMD can give 2-8x speedup with no algorithmic change.

How SIMD Works

SIMD uses wide registers that hold multiple values. A 128-bit register can hold 4 × 32-bit integers, or 2 × 64-bit doubles, or 16 × 8-bit characters. A single SIMD instruction operates on all elements simultaneously. For example, adding two arrays of 4 floats takes 1 SIMD instruction instead of 4 scalar instructions.

/* SIMD: 4 floats in one 128-bit register */ Register A: [ f0 | f1 | f2 | f3 ] (128 bits = 4 × 32-bit floats) Register B: [ g0 | g1 | g2 | g3 ] ───────────────────── A + B → [f0+g0|f1+g1|f2+g2|f3+g3] (one instruction, 4 additions!)

RISC-V V Extension

The RISC-V V extension adds vector instructions with configurable vector length (VLEN). Unlike fixed-width SIMD (like x86 SSE), RISC-V vectors can be any length the hardware supports. The vsetvli instruction configures the vector length and element width before a vector operation.

# RISC-V V extension: add two arrays # void vec_add(float *a, float *b, float *c, int n) vsetvli t0, a3, e32 # set VL: 32-bit elements, up to n vle32.v v0, (a0) # load vector from a vle32.v v1, (a1) # load vector from b vfadd.vv v2, v0, v1 # v2 = v0 + v1 (all elements!) vse32.v v2, (a2) # store vector to c

ARM64 NEON

ARM64 includes NEON (also called Advanced SIMD), with 32 vector registers of 128 bits each. NEON instructions can operate on lanes of 8, 16, 32, or 64 bits.

# ARM64 NEON: add 4 floats at once ld1 {v0.4s}, [x0] # load 4 × 32-bit floats ld1 {v1.4s}, [x1] # load 4 × 32-bit floats fadd v2.4s, v0.4s, v1.4s # 4 parallel adds st1 {v2.4s}, [x2] # store result

x86-64 SSE/AVX

x86-64 has SSE (128-bit, 16 registers) and AVX/AVX2 (256-bit, 16 registers). AVX-512 extends to 512 bits. The instructions use xmm (128-bit), ymm (256-bit), and zmm (512-bit) registers.

# x86-64 AVX: add 8 floats at once vmovups ymm0, [rdi] # load 8 × 32-bit floats vmovups ymm1, [rsi] # load 8 × 32-bit floats vaddps ymm0, ymm0, ymm1 # 8 parallel adds vmovups [rdx], ymm0 # store result

Auto-Vectorization

At -O3, the compiler attempts to auto-vectorize loops: it detects simple loops over arrays and converts them to SIMD instructions. This is free performance — but only if your loop is "vectorizable" (no data dependencies between iterations, no branches, contiguous memory access).

// Auto-vectorizable loop for (int i = 0; i < 1000; i++) c[i] = a[i] + b[i]; // compiler turns this into SIMD! // NOT vectorizable: data dependency for (int i = 1; i < 1000; i++) a[i] = a[i] + a[i-1]; // depends on previous iteration
Key Idea: SIMD for String Operations

SIMD is excellent for string operations. Instead of checking one character at a time, SIMD can check 16 characters (128 bits) per instruction. This is how strlen, strcmp, and memcpy are optimized in modern libc — they use SSE/AVX to process 16-32 bytes per cycle instead of 1.

17. Cache-Aware Assembly

The CPU cache is the single most important factor in performance. A cache hit takes ~4 cycles; a cache miss (going to main memory) takes ~100-300 cycles. Writing cache-aware code — code that accesses memory in patterns the cache likes — can give 10-100x speedups. Understanding cache behavior at the assembly level lets you write code that works with the cache, not against it.

Cache Lines

Memory is not accessed byte-by-byte. The cache loads data in cache lines (typically 64 bytes). When you read one byte, the entire 64-byte line containing it is loaded into cache. If you then read adjacent bytes, they're already in cache — a hit. But if you jump around randomly, every access is a miss. This is why sequential access is much faster than random access.

/* Cache line: 64 bytes = 8 × 8-byte values */ ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐ │ [0] │ [1] │ [2] │ [3] │ [4] │ [5] │ [6] │ [7] │ └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘ ←─────────────── 64 bytes, loaded together ──────────────→ # Sequential: 1 miss, 7 hits per line ld t0, 0(a0) # MISS (loads whole line) ld t1, 8(a0) # HIT ld t2, 16(a0) # HIT # ... # Strided: every access is a miss! ld t0, 0(a0) # MISS ld t1, 64(a0) # MISS (different line) ld t2, 128(a0) # MISS

False Sharing

False sharing occurs when two threads write to different variables that happen to be on the same cache line. Even though they're not sharing data, the cache coherence protocol invalidates the line on every write, causing a performance collapse. The fix is padding: add unused bytes to push each thread's variable onto its own cache line.

// False sharing: counter1 and counter2 on same cache line struct { long counter1; // Thread A writes this long counter2; // Thread B writes this } stats; // SAME cache line → false sharing! // Fix: pad to 64 bytes (cache line size) struct { long counter1; char pad[56]; // pad to 64 bytes long counter2; char pad2[56]; } stats; // now on separate lines

Prefetching

The CPU has a hardware prefetcher that detects sequential access patterns and loads data into cache before you ask for it. You can also explicitly prefetch using the prefetch instruction (x86) or prefetch.i/prefetch.r (RISC-V). Prefetching is useful when you know you'll need data soon but can't access it sequentially.

# RISC-V: prefetch hint (if available) # Prefetch next iteration's data while processing current prefetch.r 128(a0) # hint: will need this soon ld t0, 0(a0) # process current # ...

Non-Temporal Stores

When you're writing a large block of data that you won't read again soon (like streaming video), normal stores pollute the cache, evicting useful data. Non-temporal stores bypass the cache, writing directly to memory. This avoids cache pollution and can be faster for large, write-once data.

# x86-64: non-temporal store (bypass cache) movntps [rdi], xmm0 # store without caching # RISC-V: no direct non-temporal store, but can use # fence and cache management instructions

Cache Flush and DMA Coherency

When using DMA (Direct Memory Access) — where a device reads/writes memory directly — the CPU's cache may be stale. The CPU must flush (write back dirty cache lines) before DMA reads, and invalidate (discard cache lines) after DMA writes. On RISC-V, this is done with the fence instruction and cache management instructions (cflush, cinval).

Warning: DMA and Cache Coherency

If you forget to flush the cache before DMA reads your buffer, the device may read stale data from memory (the CPU's writes are still in cache, not written back). If you forget to invalidate after DMA writes, the CPU may read stale data from cache. This is one of the hardest bugs to find — it works "most of the time" and fails unpredictably.

18. Stack Smashing and Buffer Overflows

A buffer overflow occurs when a program writes past the end of a buffer, corrupting adjacent memory. If the buffer is on the stack, the overflow can overwrite the return address — allowing an attacker to redirect execution to arbitrary code. This is called stack smashing, and it's one of the oldest and most dangerous security vulnerabilities. Understanding how it works at the assembly level is essential for writing secure code and understanding modern defenses.

How Buffer Overflows Work

Consider a function with a local buffer. On the stack, the buffer is below the saved return address. If you write past the end of the buffer, you overwrite the saved ra/rip. When the function returns, it jumps to the overwritten address — which an attacker can set to the address of their own code (shellcode) or to a chain of existing code fragments (ROP).

/* Stack layout: buffer below return address */ ┌──────────────────┐ │ saved ra (0x...42a)│ <── attacker overwrites this! ├──────────────────┤ │ saved fp │ ├──────────────────┤ │ buf[60] │ │ buf[59] │ │ ... │ │ buf[1] │ │ buf[0] ← writes start here └──────────────────┘ // Vulnerable function void vulnerable() { char buf[64]; gets(buf); // no bounds checking! // If input > 64 bytes, overflows into saved ra }
# Assembly of vulnerable function (RISC-V) vulnerable: addi sp, sp, -80 # allocate 80 bytes sd ra, 72(sp) # save return address at sp+72 addi a0, sp, 8 # buf starts at sp+8 call gets # reads unlimited input into buf ld ra, 72(sp) # load (possibly overwritten) ra addi sp, sp, 80 ret # jumps to overwritten ra! # buf is at sp+8, ra is at sp+72 # Overflow: 72-8 = 64 bytes to reach ra # Input: 64 bytes of padding + 8 bytes of new ra

Stack Canaries

The first line of defense is the stack canary: a random value placed on the stack between the buffer and the return address. Before returning, the function checks if the canary has been modified. If it has, the program aborts. The canary value is random (set at program start), so an attacker can't easily guess it. GCC adds canaries with the -fstack-protector flag.

# Stack with canary (RISC-V, -fstack-protector) vulnerable: addi sp, sp, -96 sd ra, 88(sp) # Load canary from global variable __stack_chk_guard la t0, __stack_chk_guard ld t1, (t0) sd t1, 80(sp) # save canary at sp+80 # ... function body with buffer at sp+8 ... # Check canary before return la t0, __stack_chk_guard ld t1, (t0) ld t2, 80(sp) # load saved canary bne t1, t2, __stack_chk_fail # abort if changed! ld ra, 88(sp) addi sp, sp, 96 ret

NX Bit (DEP)

The NX bit (No-Execute, also called DEP — Data Execution Prevention) marks certain memory pages as non-executable. Even if an attacker writes shellcode to the stack, the CPU will refuse to execute it. This is enforced by the MMU: the stack's page table entries have the execute permission bit cleared. NX makes classic stack-smashing attacks (inject shellcode + jump to it) much harder.

ASLR

Address Space Layout Randomization (ASLR) randomizes the base addresses of the stack, heap, libraries, and (with PIE) the executable. This means an attacker can't predict where their shellcode or target functions will be in memory. Each time the program runs, the addresses are different. ASLR doesn't prevent overflows, but it makes exploiting them much harder — the attacker must either leak an address or guess (with $1/2^{32}$ or $1/2^{64}$ probability).

Return-Oriented Programming (ROP)

Even with NX and ASLR, attackers use Return-Oriented Programming (ROP). Instead of injecting new code, ROP chains together fragments of existing code (called gadgets) — typically ending in ret instructions. By overwriting the stack with a sequence of return addresses, each pointing to a gadget, the attacker builds a "program" out of existing code. Since the code is already executable (it's in .text), NX doesn't help.

/* ROP chain on the stack */ ┌──────────────────┐ │ addr of gadget1 │ ← ret jumps here (e.g., pop rdi; ret) ├──────────────────┤ │ argument for g1 │ ← popped into rdi by gadget1 ├──────────────────┤ │ addr of gadget2 │ ← next ret jumps here (e.g., pop rsi; ret) ├──────────────────┤ │ argument for g2 │ ← popped into rsi ├──────────────────┤ │ addr of system() │ ← call system("/bin/sh") └──────────────────┘
Security: Defense in Depth

No single defense is sufficient. Modern systems use defense in depth: canaries (detect overflow), NX (prevent code execution on stack), ASLR (randomize addresses), and CFI (Control Flow Integrity, restrict valid targets). Each defense closes some attack vectors; together, they make exploitation extremely difficult. But determined attackers still find ways — security is an ongoing arms race.

19. Spectre and Meltdown

In 2018, two of the most severe CPU vulnerabilities in history were disclosed: Meltdown (CVE-2017-5754) and Spectre (CVE-2017-5753, CVE-2017-5715). These are not software bugs — they exploit fundamental features of modern CPU architecture: speculative execution and caches. Understanding them requires understanding how the CPU pipeline and cache interact, and how side channels can leak information.

Speculative Execution

Modern CPUs execute instructions speculatively: when they encounter a branch, they guess the outcome and start executing the predicted path before the branch is resolved. If the guess is wrong, the results are discarded — the architectural state (registers, memory) is rolled back. But the cache is not rolled back. This is the crack that Spectre and Meltdown exploit: speculative execution leaves cache traces that can be measured.

// Spectre v1: Bounds Check Bypass if (x < array1_size) { // Speculatively executed even if x is out of bounds! y = array2[array1[x] * 512]; // array1[x] reads SECRET data (out of bounds) // array2[...] loads a cache line based on SECRET // Even though result is discarded, cache is modified! }

Cache Side Channels

The attack measures cache timing: if a memory location is cached, accessing it is fast (~4 cycles); if not, it's slow (~100+ cycles). By measuring access time to different cache lines, the attacker can determine which lines were loaded during speculative execution — and thus infer the secret value. This is a side-channel attack: information leaks through a channel (cache timing) that wasn't designed to carry data.

// Meltdown: measure cache timing to extract secret // Step 1: Flush all cache lines in probe array for (int i = 0; i < 256; i++) clflush(probe[i * 4096]); // Step 2: Trigger speculative access (Meltdown) // Speculatively read kernel memory (forbidden!) // value = *kernel_addr; ← raises exception // probe[value * 4096] accessed speculatively // Step 3: Measure access time to each probe line for (int i = 0; i < 256; i++) { long t1 = rdtsc(); // read timestamp counter volatile char v = probe[i * 4096]; long t2 = rdtsc(); if (t2 - t1 < THRESHOLD) { // This line was cached → i is the secret byte! secret = i; } }

Meltdown (Variant 3)

Meltdown exploits exception handling and out-of-order execution. The attacker tries to read kernel memory (which is mapped but inaccessible). The CPU starts executing the load speculatively, reads the value, and uses it to access a probe array — all before the permission check completes. When the permission check fails, an exception is raised and the results are discarded. But the cache line corresponding to the secret value is already loaded. The attacker catches the exception (e.g., via signal handler) and measures cache timing to recover the secret.

# Meltdown assembly (x86-64, simplified) # rcx = kernel address (secret) # rbx = probe array base .Ltry: # Speculatively read kernel memory mov al, [rcx] # FORBIDDEN: reads kernel byte # At this point, CPU has speculatively loaded the byte shl rax, 12 # multiply by 4096 (page offset) mov dl, [rbx + rax] # access probe[secret * 4096] # Exception fires here, but cache is already modified! .Lexcept: # Signal handler jumps here # Now measure cache timing to find which probe line is hot

Spectre v1 (Bounds Check Bypass)

Spectre v1 tricks a victim program into speculatively executing code that leaks data. The attacker trains the branch predictor to expect the bounds check to pass, then provides an out-of-bounds index. The CPU speculatively executes the body (reading secret data and touching a probe array) before the bounds check fails. The result is discarded, but the cache trace remains. Unlike Meltdown, Spectre works across privilege levels and even across processes.

Spectre v2 (Branch Target Injection)

Spectre v2 poisons the branch target buffer (BTB) — the predictor that guesses indirect branch targets. The attacker trains the BTB to redirect an indirect branch in the victim to a gadget (like in ROP). The victim speculatively executes the gadget, leaking data through the cache. This is harder to exploit but can leak data across process boundaries.

Key Idea: Speculation Leaks Through Cache

The fundamental issue is that speculative execution modifies the cache, and cache state is observable through timing. Even though the CPU discards speculative results architecturally, the microarchitectural state (cache) is not rolled back. This is not a bug in any specific CPU — it's a consequence of the performance optimization (speculation + caching) that all modern CPUs use. The mitigations add barriers (fence, retpoline) or isolate address spaces (KPTI) at a performance cost.

Warning: Mitigations Have Cost

Spectre/Meltdown mitigations have real performance costs. KPTI (Kernel Page Table Isolation) can add 5-30% overhead to syscall-heavy workloads. Retpolines slow indirect calls. This is why some systems allow disabling mitigations (mitigations=off in Linux) for trusted environments where performance matters more than security. Always understand the tradeoff.
