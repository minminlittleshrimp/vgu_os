Lab 06: C-to-Assembly Compiler Explorer

Use the compiler explorer to understand how C constructs map to assembly, and how optimization levels transform code.

Objectives

  • Use the compiler explorer (simulator) to compile C code to assembly
  • Understand how C variables, arrays, structs, and pointers map to assembly
  • Compare optimization levels: -O0, -O1, -O2, -O3
  • Understand stack spilling (when variables go to the stack vs registers)
  • Observe how recursion is compiled at different optimization levels
  • Recognize compiler optimization patterns (constant folding, dead code elimination, tail-call optimization)

Prerequisites

  • Complete Lab 01 and Lab 02
  • Basic understanding of C (variables, arrays, structs, pointers, functions)
  • Open the Simulator in compiler explorer mode
What Is a Compiler Explorer?
A compiler explorer (like Godbolt) lets you type C code and instantly see the generated assembly. You can change optimization levels, target architectures, and compiler versions. Our simulator provides similar functionality.
Hands-On Exercise 1: Compile hello.c with -O0, -O1, -O2, -O3 - Compare

Compile the same function at four optimization levels and observe how the compiler transforms the code.

Enter this C code
int compute(int x) { int a = 5; int b = 10; int c = a + b; int d = c * x; return d + 1; }
Compile with -O0 (no optimization)

Set optimization to -O0. Observe:

  • Every variable is stored on the stack (spilled)
  • Multiple sw/lw (or sd/ld) instructions
  • The computation follows the C source line by line
  • Many instructions just move data between stack and registers
Compile with -O1

Switch to -O1. Observe:

  • Stack spills are reduced - variables stay in registers
  • Constant folding: a + b = 15 is computed at compile time
  • Fewer instructions overall
Compile with -O2

Switch to -O2. Observe:

  • No stack frame at all - everything in registers
  • The entire function may be just 2-3 instructions
  • Constant folding: 5 + 10 = 15, so d = 15 * x
  • Expected: li t0, 15; mul a0, a0, t0; addi a0, a0, 1; ret
Compile with -O3

Switch to -O3. Observe:

  • May be identical to -O2 for this simple function
  • For larger functions, -O3 adds aggressive inlining and vectorization

Optimization Levels Explained
  • -O0: No optimization. Easy to debug, every variable on stack.
  • -O1: Basic optimization. Reduces code size and execution time.
  • -O2: Standard optimization. Most production code uses this. Aggressive register allocation.
  • -O3: Maximum optimization. Adds inlining, vectorization. May increase code size.
Hands-On Exercise 2: Local Variables - Stack vs Registers

Understand when the compiler stores local variables on the stack and when it keeps them in registers.

Enter this C code
int locals(int a, int b) { int x = a + 1; int y = b + 2; int z = x + y; return z; }
Compile with -O0

At -O0, observe that x, y, and z are each stored on the stack. Look for sw (store word) and lw (load word) instructions.

Compile with -O2

At -O2, the compiler keeps everything in registers. There should be no stack access at all. The function may be as simple as:

locals: addi a0, a0, 1 # x = a + 1 addi a1, a1, 2 # y = b + 2 add a0, a0, a1 # z = x + y ret
Force stack spilling

Add the volatile keyword to force the compiler to store on the stack:

int locals_volatile(int a, int b) { volatile int x = a + 1; volatile int y = b + 2; return x + y; }

Compile with -O2. Even at -O2, volatile forces stack stores. Observe the sw/lw instructions return.

Answer these questions
  • At -O0, how many stack slots are allocated?
  • At -O2, how many stack slots are allocated?
  • What does volatile tell the compiler?
  • Why does the compiler prefer registers over the stack?
Register Allocation
The compiler's register allocator decides which variables live in registers and which spill to the stack. At -O0, everything spills (for debuggability). At -O2, the allocator tries to keep as many variables in registers as possible. volatile forces the compiler to always access memory, bypassing the allocator.
Hands-On Exercise 3: Arrays - How arr[i] Is Compiled

Understand how array indexing compiles to assembly using base + index x scale addressing.

Enter this C code
int sum_array(int *arr, int n) { int sum = 0; for (int i = 0; i < n; i++) { sum += arr[i]; } return sum; }
Compile with -O2 and find the array access

Look for the instruction that loads from the array. In RISC-V, it looks like:

# arr[i] access in RISC-V slli t0, t0, 2 # t0 = i * 4 (shift left by 2) add t0, a0, t0 # t0 = arr + i*4 (address of arr[i]) lw t1, 0(t0) # t1 = arr[i] (load word)
Compare with x86-64

Switch to x86-64 and compile the same code. The array access is a single instruction:

# arr[i] access in x86-64 mov eax, DWORD PTR [rdi + rcx*4] # eax = arr[i]

x86-64's addressing mode [base + index*scale] does the multiply and add in hardware.

Understand the scale factor

The scale factor depends on the element size:

C TypeSize (bytes)Scale FactorShift Amount
char110 (no shift)
short221 (slli 1)
int442 (slli 2)
long / ptr883 (slli 3)
Try a 2D array

Compile this and observe the double indexing:

int get(int arr[4][4], int i, int j) { return arr[i][j]; }

The compiler computes arr + (i*4 + j) * 4 - a multiply, add, and another multiply.

Hands-On Exercise 4: Structs - How struct Access Is Compiled

Understand how struct field access compiles to fixed-offset memory loads.

Enter this C code
struct point { int x; int y; int z; }; int get_y(struct point *p) { return p->y; }
Compile with -O2

Look for the load instruction. In RISC-V:

get_y: lw a0, 4(a0) # load word at offset 4 (y field) ret

The offset 4 is the byte offset of y in the struct (after x which is 4 bytes).

Understand struct layout
FieldTypeOffsetSize
xint04 bytes
yint44 bytes
zint84 bytes

Total struct size: 12 bytes. The compiler knows each field's offset at compile time.

Try a struct with different types
struct mixed { char c; # offset 0, 1 byte int i; # offset 4 (padded!), 4 bytes long l; # offset 8, 8 bytes }; long get_l(struct mixed *m) { return m->l; }

Compile and check the offset of l. It should be 8 - there's 3 bytes of padding after c to align i to a 4-byte boundary.

Answer these questions
  • What is the offset of y in struct point?
  • Why is there padding in struct mixed?
  • How does the compiler know the offset at compile time?
  • What instruction is used for a 4-byte load? An 8-byte load?
Struct Padding
The compiler inserts padding to align fields to their natural alignment. int is 4-byte aligned, long is 8-byte aligned. This ensures efficient memory access. You can use #pragma pack(1) or __attribute__((packed)) to disable padding, but it may slow down access.
Hands-On Exercise 5: Pointers - How *p Is Compiled

Understand how pointer dereference compiles to a single load instruction.

Enter this C code
int deref(int *p) { return *p; }
Compile with -O2

In RISC-V:

deref: lw a0, 0(a0) # load word from address in a0 ret

The pointer p is in a0. lw a0, 0(a0) loads 4 bytes from that address.

Try pointer arithmetic
int deref_offset(int *p, int idx) { return p[idx]; }

This is equivalent to *(p + idx). The compiler generates:

# RISC-V slli a1, a1, 2 # a1 = idx * 4 add a0, a0, a1 # a0 = p + idx*4 lw a0, 0(a0) # a0 = *(p + idx)
Try double pointer
int double_deref(int **pp) { return **pp; }

This requires two loads: first load *pp to get p, then load *p to get the value:

double_deref: ld a0, 0(a0) # a0 = *pp (load pointer) lw a0, 0(a0) # a0 = **pp (load value) ret
Answer these questions
  • What is the difference between lw (load word) and ld (load double)?
  • Why does p[idx] multiply idx by 4 for int*?
  • How many loads does **pp require?
  • What would ***ppp (triple dereference) look like?
Challenge Exercise 6: Recursion - -O0 (Real Recursion) vs -O2 (May Optimize to Loop)

Compare how the compiler handles recursion at different optimization levels. At -O2, the compiler may transform recursion into iteration.

Enter this C code
int sum_to(int n) { if (n <= 0) return 0; return n + sum_to(n - 1); }
Compile with -O0

At -O0, you will see:

  • A full stack frame (prologue/epilogue)
  • n spilled to the stack
  • A call sum_to instruction (recursive call)
  • Each call creates a new frame - true recursion
Compile with -O2

At -O2, the compiler may apply tail-call optimization or recursion elimination:

  • The recursive call may be replaced with a j (jump) - reusing the same stack frame
  • Or the compiler may convert it to an explicit loop with bgt/ble
  • No new stack frames are created - it runs in constant stack space
Try non-tail-recursive factorial
int factorial(int n) { if (n <= 1) return 1; return n * factorial(n - 1); }

Compile with -O2. This is not tail-recursive (the * happens after the call), so the compiler cannot simply convert it to a loop. However, some compilers can still optimize it using accumulator transformation.

Tail-Call Optimization (TCO)
When the recursive call is the last operation before return (tail position), the compiler can replace call with j (jump). No new stack frame is created - the recursion becomes iteration. sum_to is tail-recursive after transformation (accumulator). factorial is not, because n * happens after the call.
