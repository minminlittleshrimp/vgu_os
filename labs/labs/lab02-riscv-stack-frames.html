Lab 02: RISC-V Stack Frames and Calling Convention

Master the stack frame: prologues, epilogues, callee-saved registers, stack spilling, and recursion.

Objectives

  • Understand the RISC-V stack frame layout and the role of sp (stack pointer) and fp/s0 (frame pointer)
  • Write function prologues and epilogues that save and restore ra and callee-saved registers
  • Pass more than 8 arguments by using the stack
  • Implement a recursive function (factorial) with proper stack management
  • Read and understand the xv6 swtch.S context switch code
  • Compare -O0 vs -O2 compilation of recursive functions

Prerequisites

  • Complete Lab 01: RISC-V Assembly Basics
  • Understand call, ret, ra, and basic register usage
  • Read Handbook Chapter 7: RISC-V Calling Convention
  • Open the RISC-V Simulator
Why Stack Frames?
When a function calls another function, the caller's ra (return address) and any callee-saved registers (s0-s11) must be preserved. The stack frame is the memory region where these are saved. Without it, nested calls and recursion would overwrite return addresses and crash.
Hands-On Exercise 1: Simple Prologue and Epilogue

Write a function that saves ra and s0 on the stack (prologue), does some work, then restores them (epilogue).

Understand the prologue/epilogue pattern

Every non-trivial function follows this pattern:

# PROLOGUE addi sp, sp, -16 # Allocate frame sd ra, 8(sp) # Save return address sd s0, 0(sp) # Save frame pointer addi s0, sp, 16 # Set frame pointer # ... function body ... # EPILOGUE ld ra, 8(sp) # Restore return address ld s0, 0(sp) # Restore frame pointer addi sp, sp, 16 # Deallocate frame ret
Enter this complete program
main: li a0, 5 call my_func ret my_func: # Prologue addi sp, sp, -16 sd ra, 8(sp) sd s0, 0(sp) addi s0, sp, 16 # Body: double the argument and call another function add a0, a0, a0 # a0 = a0 * 2 call helper # This clobbers ra! # a0 now has the result from helper # Epilogue ld ra, 8(sp) ld s0, 0(sp) addi sp, sp, 16 ret helper: addi a0, a0, 1 # a0 = a0 + 1 ret
Run and verify

The result should be 11 (5 x 2 = 10, then + 1 = 11).

Remove the prologue and observe the crash

Comment out the sd ra, 8(sp) and ld ra, 8(sp) lines. Run again - the program should crash or return to a wrong address because call helper overwrites ra.

Critical Rule
If your function contains a call instruction, you must save and restore ra. Otherwise, the ret at the end of your function will jump to whatever address call left in ra, not back to your caller.
Hands-On Exercise 2: Pass 10 Arguments (8 in registers, 2 on stack)

The RISC-V calling convention passes the first 8 arguments in a0-a7. Arguments 9 and 10 are passed on the stack.

Understand stack argument passing

When a function needs more than 8 arguments:

  • Arguments 1-8 go in a0-a7
  • Arguments 9+ are pushed onto the stack by the caller
  • The callee reads them from the stack using sp offsets
Enter the caller code
main: li a0, 1 # arg 1 li a1, 2 # arg 2 li a2, 3 # arg 3 li a3, 4 # arg 4 li a4, 5 # arg 5 li a5, 6 # arg 6 li a6, 7 # arg 7 li a7, 8 # arg 8 # Push args 9 and 10 onto the stack addi sp, sp, -16 li t0, 9 sd t0, 0(sp) # arg 9 at sp+0 li t0, 10 sd t0, 8(sp) # arg 10 at sp+8 call sum_ten # Clean up stack (caller removes args) addi sp, sp, 16 ret
Enter the callee
sum_ten: # a0-a7 have args 1-8 # args 9 and 10 are on the caller's stack # After our prologue, they are at sp+16 and sp+24 addi sp, sp, -16 sd ra, 8(sp) # Sum args 1-8 add a0, a0, a1 add a0, a0, a2 add a0, a0, a3 add a0, a0, a4 add a0, a0, a5 add a0, a0, a6 add a0, a0, a7 # Add args 9 and 10 from stack ld t0, 16(sp) # arg 9 (sp+16 = original sp+0) add a0, a0, t0 ld t0, 24(sp) # arg 10 (sp+24 = original sp+8) add a0, a0, t0 ld ra, 8(sp) addi sp, sp, 16 ret
Run and verify

The result should be 55 (1+2+3+...+10).

Stack Offset Calculation
After the callee does addi sp, sp, -16, the caller's stack arguments move. If the caller pushed args at sp+0 and sp+8, the callee (after subtracting 16) finds them at sp+16 and sp+24. Always account for your own frame size!
Hands-On Exercise 3: Recursive Factorial

Write a recursive factorial(n) function. Recursion requires saving ra on every call, because each call needs to return to a different point.

Understand the algorithm

factorial(n) = n * factorial(n-1), with factorial(0) = 1. Each recursive call must save ra and n on the stack.

Enter the program
main: li a0, 5 # Compute 5! call factorial ret factorial: # Prologue: save ra and s0 (we use s0 for n) addi sp, sp, -16 sd ra, 8(sp) sd s0, 0(sp) mv s0, a0 # s0 = n (save n in callee-saved reg) # Base case: if n == 0, return 1 beqz s0, base_case # Recursive case: n * factorial(n-1) addi a0, s0, -1 # a0 = n - 1 call factorial # a0 = factorial(n-1) mul a0, a0, s0 # a0 = factorial(n-1) * n j epilogue base_case: li a0, 1 # return 1 epilogue: ld ra, 8(sp) ld s0, 0(sp) addi sp, sp, 16 ret
Run and verify

The result should be 120 (5! = 120).

Trace the stack growth

Use the Step button to trace execution. Watch sp decrease by 16 each time factorial is called. Count how many stack frames are created for factorial(5) - it should be 6 (for n=5,4,3,2,1,0).

Test with larger values

Try li a0, 10 - the result should be 3628800 (10! = 3,628,800).

Why s0 for n?
We store n in s0 (a callee-saved register) because a0 gets overwritten by the recursive call. Since s0 is callee-saved, the inner call will save and restore it for us. This is the standard pattern for preserving local variables across calls.
Reading Exercise 4: Read xv6 swtch.S Context Switch

The xv6 operating system uses a function called swtch to switch between thread contexts. Read and understand it.

Read the swtch.S code

Here is the xv6 swtch.S (simplified). Read it carefully:

# void swtch(struct context *old, struct context *new); swtch: sd ra, 0(a0) sd sp, 8(a0) sd s0, 16(a0) sd s1, 24(a0) sd s2, 32(a0) # ... saves s3-s11 similarly ... sd s11, 96(a0) ld ra, 0(a1) ld sp, 8(a1) ld s0, 16(a1) ld s1, 24(a1) ld s2, 32(a1) # ... loads s3-s11 similarly ... ld s11, 96(a1) ret # jumps to new ra

Understand the context structure

The context struct in xv6 is:

struct context { uint64 ra; // offset 0 uint64 sp; // offset 8 uint64 s0; // offset 16 // ... s1 through s11 ... uint64 s11; // offset 96 };

Each field is 8 bytes. The sd/ld offsets match the struct layout exactly.

Key Insight
swtch doesn't need a prologue because it doesn't call any other function - it just saves and loads registers. The ret at the end doesn't return to swtch's caller; it returns to whatever ra was loaded from the new context. This is how execution "jumps" to a different thread.
Hands-On Exercise 5: Compile C Recursion - -O0 vs -O2

Compile a recursive C function at two optimization levels and compare the generated assembly.

Enter this C code in the simulator
int sum_to(int n) { if (n <= 0) return 0; return n + sum_to(n - 1); }
Compile with -O0

Set optimization to -O0 and compile. Observe:

  • The prologue saves ra and allocates stack space
  • n is stored on the stack (spilled)
  • The recursive call to sum_to is present
  • Each call creates a new stack frame
Compile with -O2

Switch to -O2 and recompile. Look for:

  • The compiler may convert the recursion into a loop (tail-call optimization or recursion elimination)
  • No call sum_to - just a j or beq loop
  • No stack frame needed (everything in registers)

Try a non-tail-recursive function

Try this function where the recursion is NOT in tail position:

int factorial(int n) { if (n <= 1) return 1; return n * factorial(n - 1); }

At -O2, the compiler cannot easily eliminate this recursion because the multiplication happens after the recursive call. Compare the assembly - you should still see a call instruction.

Tail Call Optimization (TCO)
When the recursive call is the last operation (tail position), the compiler can replace it with a jump - no new stack frame needed. This turns recursion into iteration. But if there's work after the call (like n * ...), TCO doesn't apply and the recursion stays.
