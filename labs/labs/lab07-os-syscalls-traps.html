What Is a System Call?
A system call is how a user program asks the kernel to do something it can't do itself (like I/O, memory allocation, process creation). The user program executes a special instruction (ecall on RISC-V) that traps into the kernel. The kernel handles the request and returns to the user program.
Hands-On Exercise 1: Write Raw write() Syscall in RISC-V Assembly

Write a raw write() syscall without using libc. This is how xv6 user programs make system calls.

Understand the RISC-V syscall convention

In xv6 (RISC-V), syscalls use the same calling convention as functions:

  • Syscall number in a7 (x17)
  • Arguments in a0-a0
  • Invoke with ecall instruction

The write syscall number in xv6 is 16.

Enter this assembly program
.globl main main: # write(1, msg, 5) - write "Hello" to stdout li a0, 1 # fd = 1 (stdout) la a1, msg # buf = address of msg li a2, 5 # count = 5 li a7, 16 # syscall number for write ecall # trap into kernel ret .data msg: .ascii "Hello"
Understand each instruction

Run in the simulator

Run the program. The simulator should display "Hello" in the output panel. The ecall instruction triggers the trap, and the kernel's sys_write function handles it.

Modify the message

Change the message to "World\n" (6 bytes) and update the count to 6. Run again to see "World" printed.

ecall Does What?
ecall (environment call) does three things: (1) switches from user mode (U) to supervisor mode (S), (2) saves the return address in sepc (supervisor exception PC), and (3) jumps to the address stored in stvec (supervisor trap vector). The kernel reads sepc to know where to return.
Hands-On Exercise 2: Write Raw exit() Syscall

Write a raw exit() syscall to terminate the process with a specific exit code.

Understand the exit syscall

The exit syscall number in xv6 is 2. It takes one argument: the exit code.

Enter this program
.globl main main: # First, write a message li a0, 1 # stdout la a1, msg li a2, 14 li a7, 16 # write ecall # Then exit with code 42 li a0, 42 # exit code li a7, 2 # syscall number for exit ecall # Should never reach here - exit doesn't return spin: j spin .data msg: .ascii "Goodbye, world"
Run and verify

The output should show "Goodbye, world" and the exit code should be 42.

Note the infinite loop after exit

The j spin after the exit syscall is a safety measure. exit never returns - the kernel destroys the process. But if something goes wrong, the infinite loop prevents execution from falling through to garbage code.

Reading Exercise 3: Trace the Syscall Path

Trace the complete path of a syscall from user code through the trampoline to the kernel and back.

Understand the full path

When a user program calls ecall, the following happens:

# 1. USER CODE li a7, 16 # syscall number ecall # <- trap happens here # 2. HARDWARE (automatically) # - Switch from U mode to S mode # - Save PC in sepc (sepc = address of ecall) # - Jump to stvec (trampoline address) # 3. TRAMPOLINE (uservec in trampoline.S) # - Swap user/kernel stack via sscratch # - Save user registers to trapframe # - Jump to usertrap() # 4. KERNEL (usertrap in trap.c) # - Read scause to determine trap type # - If syscall: read a7 for syscall number # - Call sys_write() / sys_read() / etc. # - Set return value in trapframe->a0 # - Call usertrapret() # 5. RETURN (usertrapret + userret) # - usertrapret: set up sstatus, sepc for return # - userret: restore user registers from trapframe # - sret instruction: switch back to U mode # 6. USER CODE RESUMES # - a0 now has the return value # - Execution continues after ecall
Draw the flow diagram

Draw (on paper or in a diagram tool) the following flow:

User Code | | ecall (a7=16) v Hardware Trap | | sepc <- PC, jump to stvec v Trampoline (uservec) | | save regs to trapframe, swap stack v Kernel (usertrap) | | read a7, call sys_write() | set trapframe->a0 = return value v Return (usertrapret -> userret) | | restore regs, sret v User Code (continues after ecall)

Key RISC-V CSRs for Traps
  • stvec - Supervisor Trap Vector: address of trap handler (trampoline)
  • sepc - Supervisor Exception PC: PC where the trap occurred
  • scause - Supervisor Cause: reason for the trap (8 = syscall)
  • sscratch - Scratch register: used for the stack swap trick
  • sstatus - Supervisor Status: contains privilege mode bits
Reading Exercise 4: Read xv6 uservec / usertrap / usertrapret / userret

Read the four key functions in xv6's trap handling path and understand each one's role.

Read uservec (trampoline.S)

uservec is the first code that runs after a trap. It's in the trampoline page, mapped at the same address in both user and kernel space.

uservec: # sscratch holds the trapframe address # Save user registers to trapframe csrrw t0, sscratch, sp # swap sp and sscratch # Now sp = trapframe addr, t0 = user sp sd ra, 40(sp) # save ra sd sp, 2(sp) # save user sp (from t0) sd a0, 112(sp) # save a0 # ... save all user registers ... # Load kernel stack pointer csrr sp, sscratch # sp = kernel stack (was in sscratch) # Wait - actually sscratch was swapped, so now it has user sp # The trapframe address was loaded from a0 originally # Call usertrap() call usertrap
Read usertrap (trap.c)

usertrap is the C function that handles the trap in the kernel:

void usertrap(void) { // Save PC in trapframe p->trapframe->epc = r_sepc(); // Check why we trapped if (r_scause() == 8) { // It's a syscall p->trapframe->epc += 4; // skip ecall instruction // Call the syscall handler intr num = p->trapframe->a7; p->trapframe->a0 = syscalls[num](); } else { // Other traps (page fault, etc.) } // Return to user usertrapret(); }
Read usertrapret (trap.c)

usertrapret prepares to return to user mode:

void usertrapret(void) { // Set up sstatus for return to U mode struct proc *p = myproc(); // Set SPP to 0 (return to U mode, not S mode) w_sstatus(r_sstatus() & ~0x100); // Set sepc to user PC w_sepc(p->trapframe->epc); // Jump to trampoline return code uint64 fn = TRAMPOLINE + (userret - trampoline); ((void(*)(uint64, uint64))fn)( uint64)(p->trapframe), uint64(user_satp)); }
Read userret (trampoline.S)

userret restores user registers and executes sret:

userret: # a0 = trapframe address, a1 = user page table # Restore user registers from trapframe ld ra, 40(a0) ld sp, 2(a0) ld a0, 112(a0) # ... restore all registers ... # Swap sscratch back (for next trap) csrrw sp, sscratch, a0 # Return to user mode sret

Challenge Exercise 5: Understand the sscratch Swap Trick

The sscratch register is key to the trap mechanism. Understand how the swap trick works.

The problem

When a trap occurs, the kernel needs to switch from the user stack to the kernel stack. But how does it find the kernel stack? All registers still hold user values. There's no free register to use.

The solution: sscratch

sscratch is a special CSR (control and status register) that the kernel sets up before returning to user mode. It holds the trapframe address (or kernel stack pointer).

The swap trick

At trap entry (uservec), the code does:

# Before: sscratch = trapframe addr, sp = user sp csrrw sp, sscratch, sp # After: sp = trapframe addr, sscratch = user sp

This single instruction swaps sp and sscratch. Now:

  • sp points to the trapframe (where we save user registers)
  • sscratch holds the user's stack pointer (saved for later)
The reverse swap at return

At trap return (userret), the swap is reversed:

# Before: sscratch = user sp, a0 = trapframe addr csrrw sp, sscratch, a0 # After: sp = user sp, sscratch = trapframe addr (for next trap)

Now sp is restored to the user stack, and sscratch is set up for the next trap.

Answer these questions
  • Why can't the kernel just use a regular register to save the stack pointer?
  • What value does sscratch hold while the user program is running?
  • What value does sscratch hold after the swap in uservec?
  • Why is csrrw used instead of csrr + csrw?
  • What would happen if sscratch weren't set up before returning to user mode?
Why csrrw?
csrrw sp, sscratch, sp is an atomic swap - it reads sscratch into a temporary, writes sp to sscratch, and puts the old sscratch into sp, all in one instruction. Using separate csrr + csrw would require a temporary register, which we don't have (all registers hold user values).

Common Pattern
All three ISAs follow the same pattern: (1) a special instruction traps to the kernel, (2) the hardware saves the return address and switches privilege, (3) the kernel dispatches based on a syscall number, (4) arguments are passed in registers, (5) a return instruction switches back to user mode. The details differ, but the architecture is the same.
