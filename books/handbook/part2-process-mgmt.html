3.1 Process Concept

A process is a program in execution. While a program is a passive entity (a file on disk containing a list of instructions), a process is an active entity—it has a program counter (tracking the next instruction), a set of registers, a stack (for function calls and local variables), a heap (for dynamically allocated memory), and a data section (for global variables). The same program can be running as multiple processes simultaneously, each with its own memory and state.

A process can be in one of several states as it executes. The basic states are: New (being created), Ready (waiting to be assigned to a CPU), Running (executing on a CPU), Waiting (or Blocked, waiting for an event like I/O), and Terminated (finished execution). The OS moves processes between these states: a new process becomes Ready, the scheduler picks a Ready process to Run, a Running process may be preempted (back to Ready) or may block on I/O (to Waiting), and when I/O completes, a Waiting process becomes Ready.

ℹ️ Process States

The five states and their transitions:
New → Ready (admission) · Ready → Running (dispatch) · Running → Ready (preemption / timeout) · Running → Waiting (I/O or event wait) · Waiting → Ready (I/O or event completion) · Running → Terminated (exit)

The OS represents each process with a process control block (PCB), also called a task control block. The PCB is the data structure that stores all information the OS needs about a process: its state, program counter, CPU registers, CPU scheduling information (priority, queue pointers), memory management information (page tables, base/limit registers), accounting information (CPU time used, time limits), and I/O status (open files, allocated devices). When the OS switches from one process to another (a context switch), it saves the current process's state into its PCB and loads the next process's state from its PCB.

/* xv6 process control block (simplified from proc.h) */ enum procstate { UNUSED, USED, SLEEPING, RUNNABLE, RUNNING, ZOMBIE }; struct proc { enum procstate state; // process state int pid; // process ID struct proc *parent; // parent process void *chan; // sleep channel int killed; // killed flag struct trapframe *trapframe; // saved user registers struct context context; // saved kernel registers (for swtch) pagetable_t pagetable; // user page table struct file *ofile[NOFILE]; // open files char name[16]; // process name (for debugging) };

Each process has a unique process identifier (PID), a positive integer. The first process created by the OS (PID 1 on UNIX, called init) is the ancestor of all other processes. In xv6, the first process is created by userinit() in proc.c and runs the init program, which forks a shell. Every subsequent process is created by fork(), which makes a copy of the calling process. The parent-child relationship forms a process tree.

3.2 Process Scheduling

The OS maintains queues of processes. The most important is the ready queue, which holds processes that are ready to run but waiting for a CPU. There are also device queues for processes waiting on specific I/O devices. A process moves between these queues as it changes state: when it blocks on I/O, it leaves the ready queue and joins the device queue; when I/O completes, it returns to the ready queue.

The component of the OS that selects the next process to run is the short-term scheduler (or CPU scheduler). It runs frequently—every few milliseconds—and must be fast. The long-term scheduler (or job scheduler) selects which processes are admitted to the system (from a pool of new jobs) and runs infrequently. Its goal is to maintain a good process mix of CPU-bound processes (long CPU bursts) and I/O-bound processes (short CPU bursts, frequent I/O), keeping both the CPU and I/O devices busy.

💡 CPU-Bound vs. I/O-Bound

A CPU-bound process spends most of its time computing (e.g., a scientific simulation). An I/O-bound process spends most of its time waiting for I/O (e.g., a word processor). A good scheduler keeps a mix: while an I/O-bound process waits, a CPU-bound process can use the CPU. If all processes are CPU-bound, I/O devices sit idle; if all are I/O-bound, the CPU sits idle.

Processes alternate between CPU bursts (periods of computation) and I/O bursts (periods of waiting for I/O). The CPU-I/O burst cycle characterizes a process's behavior. CPU-bound processes have a few long CPU bursts; I/O-bound processes have many short CPU bursts. The histogram of CPU burst durations is typically exponential—most bursts are short, with a long tail of longer bursts. This distribution informs scheduling algorithm design.

The context switch is the mechanism by which the CPU switches from one process to another. The OS saves the state of the currently running process (registers, program counter) into its PCB and loads the state of the next process from its PCB. This is pure overhead—no useful work is done during a context switch—so minimizing context switch time is important. In xv6, the swtch() function in swtch.S saves and restores callee-saved registers to perform the switch. The time for a context switch is typically a few microseconds, but it can be significant if it happens frequently.

/* xv6 context switch (swtch.S, simplified) */ // Save current context, load new context // 'old' = pointer to current context struct // 'new' = pointer to new context struct swtch: sd ra, 0(a0) // save return address sd sp, 8(a0) // save stack pointer sd s0, 16(a0) // save s0-s11 (callee-saved) // ... save s1-s11 ... ld ra, 0(a1) // restore return address ld sp, 8(a1) // restore stack pointer ld s0, 16(a1) // restore s0-s11 // ... restore s1-s11 ... ret // jump to restored ra

Some systems also have a medium-term scheduler that performs swapping: removing processes from memory (and writing them to disk) when memory is full, and bringing them back later. This reduces the degree of multiprogramming (the number of processes in memory) and can improve response time. Swapping is the precursor to modern virtual memory paging, which moves individual pages rather than entire processes.

3.3 Operations on Processes

Processes can be created, terminated, and made to wait for each other. The most fundamental operations are process creation and process termination.

Most operating systems create processes using a fork operation. The fork() system call creates a new process that is a copy of the calling process (the parent). The new process (the child) gets its own memory space (a copy of the parent's), its own PID, and its own open file descriptors (copies of the parent's). The only difference is the return value of fork(): it returns the child's PID to the parent and 0 to the child. This allows the parent and child to execute different code after the fork.

/* fork() example (xv6 / UNIX) */ int pid = fork(); if (pid < 0) { // fork failed exit(1); } else if (pid == 0) { // child process exec("/bin/ls", argv); // replace with new program exit(1); // only reached if exec fails } else { // parent process wait(0); // wait for child to finish }

The exec() system call replaces the current process image with a new program. It loads a new program from a file, initializes its memory (text, data, stack), and starts it running. The PID does not change—exec replaces the program, not the process. The typical pattern is fork() followed by exec() in the child: the parent continues running, while the child runs a different program. This is how shells run commands.

ℹ️ fork() + exec() Pattern

The fork() + exec() pattern is the UNIX way to start a new program. fork() duplicates the process; exec() replaces the program. Separating these allows the parent to modify the child's environment (redirect file descriptors, change directory) between fork and exec. This is more flexible than a single "create process" call.

A process terminates when it calls exit(), when it returns from main(), or when it receives a fatal signal. The exit() system call closes all file descriptors, releases memory, and sets the process's state to zombie. A zombie process has terminated but still has an entry in the process table, waiting for its parent to call wait() to retrieve its exit status. If the parent never calls wait(), the zombie remains, wasting a process table entry. This is a zombie process—a resource leak.

If a parent terminates before its children, the children become orphan processes. On UNIX systems, orphans are reparented to the init process (PID 1), which periodically calls wait() to reap them. This ensures that no process remains a zombie forever. In xv6, the wait() function in sysproc.c scans the process table for children of the calling process, and if any are zombies, reaps one and returns its PID and exit status.

⚠️ Zombie and Orphan Processes

Zombie: A process that has exited but whose parent hasn't called wait(). It retains its PID and exit status. Too many zombies can exhaust the process table.
Orphan: A process whose parent has exited. It is reparented to init (PID 1), which reaps it when it exits.

3.4 Interprocess Communication

Interprocess communication (IPC) is the set of mechanisms by which processes communicate with each other and synchronize their actions. Processes may be independent (not affecting or being affected by other processes) or cooperating (sharing data or coordinating execution). Cooperating processes need IPC for several reasons: information sharing (multiple programs accessing the same data), computation speedup (splitting work across processes/cores), modularity (dividing a system into cooperating modules), and convenience (a user running multiple programs simultaneously).

There are two fundamental models of IPC: shared memory and message passing. In the shared-memory model, processes establish a region of shared memory that they both can read and write. Communication is fast (no kernel involvement after setup) but requires explicit synchronization to avoid races. In the message-passing model, processes communicate by sending and receiving messages through the kernel. This is slower (each message involves a system call) but works across machines and avoids synchronization issues.

The choice between shared memory and message passing depends on the application. For high-performance local communication (e.g., a database and its clients on the same machine), shared memory is preferred. For distributed systems or when simplicity matters, message passing is preferred. Many systems use both: shared memory for local communication, message passing for remote. The producer-consumer problem (also called the bounded-buffer problem) is the classic example used to illustrate IPC: a producer produces data items and a consumer consumes them, with a shared buffer in between.

3.5 IPC in Shared-Memory Systems

In a shared-memory IPC system, cooperating processes establish a region of shared memory that both can access. On UNIX systems, this is done with shmget() (allocate a shared memory segment) and shmat() (attach it to the process's address space), or with mmap() with the MAP_SHARED flag. Once attached, the shared region behaves like regular memory—both processes can read and write it without kernel involvement.

/* Shared memory IPC (POSIX shmget/shmat) */ // Process 1 (Producer): create and write int shmid = shmget(IPC_PRIVATE, sizeof(buffer), IPC_CREAT | 0666); char *shared = (char*)shmat(shmid, NULL, 0); strcpy(shared, "Hello from producer!"); // Process 2 (Consumer): attach and read int shmid = shmget(IPC_PRIVATE, sizeof(buffer), 0666); char *shared = (char*)shmat(shmid, NULL, 0); printf("Got: %s\n", shared); // prints "Hello from producer!"

The classic shared-memory problem is the bounded-buffer (producer-consumer) problem. A producer puts items into a buffer; a consumer takes them out. The buffer has a fixed size, so the producer must wait when the buffer is full, and the consumer must wait when it is empty. The shared buffer is typically implemented as a circular array with in and out indices. The producer writes at in and advances it; the consumer reads at out and advances it. When in catches up to out, the buffer is full; when out catches up to in, it is empty.

⚠️ Race Conditions in Shared Memory

Shared memory requires synchronization. Without it, the producer and consumer can race: if both access in or out simultaneously, updates can be lost. Solutions use semaphores or mutexes (covered in Part 3). The buffer also needs a count or empty/full semaphores to track available slots and items.

A subtle issue is cache coherence on multiprocessor systems. Even if two processes share memory, each CPU core may have its own cache, and writes by one core may not be immediately visible to another. Hardware cache coherence protocols (like MESI) handle this at the hardware level, but software must use memory barriers (or fences) to ensure that memory operations are visible in the correct order. This is especially important for lock-free data structures.

3.6 IPC in Message-Passing Systems

In a message-passing IPC system, processes communicate by sending and receiving messages. The send() operation sends a message to a process or mailbox; the receive() operation waits for and receives a message. The kernel handles the actual data transfer, copying data from the sender's address space to the kernel and then to the receiver's address space (or using zero-copy techniques for large messages).

Message passing can be direct or indirect. In direct communication, each process explicitly names the recipient or sender: send(P, message) sends to process P, receive(Q, message) receives from process Q. This creates a direct link between two processes. In indirect communication, messages are sent to and received from mailboxes (or ports): a mailbox can be shared by multiple processes, allowing one-to-many and many-to-one communication. A process can own a mailbox (only it can receive) or share it.

PropertyDirectIndirect (Mailbox)

Communication can be synchronous or asynchronous. In synchronous (or blocking) communication, send() blocks until the message is received, and receive() blocks until a message is available. This is also called a rendezvous. In asynchronous (or non-blocking) communication, send() returns immediately (the message is buffered by the OS), and receive() can return immediately with a status indicating whether a message was available. Most systems provide both options, or a combination (blocking receive, non-blocking send).

ℹ️ Blocking vs. Non-Blocking

Blocking send: Sender waits until message is received (rendezvous).
Non-blocking send: Sender continues; message is buffered.
Blocking receive: Receiver waits until a message arrives.
Non-blocking receive: Receiver gets a message or a "no message" status.

Buffering is another consideration. A communication link can have zero capacity (no buffering—send blocks until receive), bounded capacity (finite queue—send blocks only if full), or unbounded capacity (infinite queue—send never blocks). Zero capacity is the most restrictive but simplest; unbounded is most flexible but can consume unbounded memory. Most practical systems use bounded capacity with a reasonable buffer size.

3.7 Examples of IPC

UNIX-like systems provide several IPC mechanisms. The simplest is the pipe, a unidirectional byte stream between two processes. A pipe is created with pipe(fd), which returns two file descriptors: fd[0] for reading and fd[1] for writing. After fork(), the parent and child share the pipe: one writes, the other reads. Pipes are limited to processes with a common ancestor (they inherit the file descriptors via fork).

/* xv6 pipe example */ int p[2]; pipe(p); // p[0] = read end, p[1] = write end if (fork() == 0) { // child: read from pipe close(p[1]); // close write end char buf[64]; read(p[0], buf, 64); printf("child got: %s\n", buf); } else { // parent: write to pipe close(p[0]); // close read end write(p[1], "hello", 6); }

A named pipe (or FIFO) is a pipe that exists as a file in the file system, created with mkfifo(). Unlike anonymous pipes, FIFOs can be used between unrelated processes—any process with permission can open the FIFO file for reading or writing. Message queues (System V msgget/msgsnd/msgrcv or POSIX mq_open) provide structured messages with types, allowing selective receiving. Shared memory (shmget/shmat or mmap) provides the fastest IPC for large data.

Sockets are a general-purpose IPC mechanism that works both locally and over a network. A socket is an endpoint for communication, identified by an IP address and port number. The BSD socket API (socket, bind, listen, accept, connect, send, recv) is the standard network programming interface on UNIX and Windows. UNIX domain sockets are a variant that uses the file system for naming, providing socket semantics for local IPC with lower overhead than network sockets.

💡 xv6 IPC

xv6 provides pipes (in pipe.c) as its primary IPC mechanism. The shell uses pipes to implement command pipelines (e.g., ls | grep | wc). xv6 does not implement sockets, shared memory, or message queues—these are left as exercises. Studying xv6's pipe implementation is a great way to understand how IPC works at the kernel level.

3.8 Client-Server Communication

In a client-server model, a server process provides services, and client processes request them. Communication typically uses sockets, remote procedure calls (RPC), or remote method invocation (RMI). This model is the basis of network services, web applications, and distributed systems.

A socket is an endpoint for communication. A server creates a socket, binds it to a known address (IP + port), listens for connections, and accepts them. A client creates a socket, connects to the server's address, and then sends and receives data. Sockets support both stream (TCP, reliable, connection-oriented) and datagram (UDP, unreliable, connectionless) communication. The socket API was introduced in BSD UNIX (4.2BSD, 1983) and is now universal.

/* Socket communication (simplified server) */ // Server int server_fd = socket(AF_INET, SOCK_STREAM, 0); bind(server_fd, &server_addr, sizeof(server_addr)); listen(server_fd, 5); // backlog of 5 int client_fd = accept(server_fd, &client_addr, &len); read(client_fd, buffer, 1024); write(client_fd, response, strlen(response)); close(client_fd); // Client int sock = socket(AF_INET, SOCK_STREAM, 0); connect(sock, &server_addr, sizeof(server_addr)); write(sock, request, strlen(request)); read(sock, response, 1024); close(sock);

Remote Procedure Call (RPC) abstracts network communication as a function call. A client calls a local stub function that marshals the arguments into a message, sends it to the server, waits for the reply, and unmarshals the result. On the server side, a skeleton receives the message, unmarshals the arguments, calls the actual function, marshals the result, and sends it back. This makes distributed programming look like local programming. Systems like Sun RPC, DCE RPC, and gRPC implement this pattern. Remote Method Invocation (RMI) is the Java equivalent for remote objects.

ℹ️ Marshalling

Marshalling (or serialization) is the process of converting function arguments into a byte stream for transmission. It must handle different data types, byte ordering (big-endian vs. little-endian), and pointer structures. Formats like Protocol Buffers, JSON, and MessagePack are commonly used for marshalling in modern RPC systems.

Modern client-server communication often uses higher-level protocols built on top of sockets: HTTP (for web services), gRPC (Google's RPC framework using Protocol Buffers), REST APIs (using HTTP verbs like GET, POST, PUT, DELETE), and GraphQL. These provide richer semantics than raw sockets but add overhead. The choice depends on the application's needs for performance, interoperability, and developer convenience.

4.1 Overview

A thread is a basic unit of CPU utilization; it is smaller than a process. A process can contain multiple threads, all sharing the same code, data, and resources (open files, signals), but each having its own program counter, registers, and stack. Threads are sometimes called lightweight processes because creating a thread and switching between threads is much cheaper than creating a process and context switching, since threads share memory and do not require a full context switch.

The motivation for multithreading is responsiveness (a UI thread stays responsive while a worker thread does computation), resource sharing (threads share memory, avoiding IPC), economy (thread creation is cheaper than process creation), and scalability (threads can run in parallel on multiple cores). A single-threaded process can only use one core; a multithreaded process can use all available cores, potentially achieving near-linear speedup on multicore systems.

A single-threaded process has one thread of control: it executes one instruction at a time. A multithreaded process has multiple threads, each executing independently but sharing memory. For example, a web browser might have one thread for the UI, one for rendering, one for network I/O, and one for each open tab. If one thread blocks (e.g., waiting for a network response), the others continue running, keeping the application responsive.

ℹ️ Concurrency vs. Parallelism

Concurrency means multiple threads making progress (possibly interleaved on a single core via time-slicing). Parallelism means multiple threads running simultaneously on multiple cores. Concurrency is about dealing with multiple things; parallelism is about doing multiple things at once. A system can be concurrent without being parallel (single core, time-sliced) or parallel without being concurrent (one thread per core, no sharing).

4.2 Multicore Programming

A multiprocessor or multicore system has multiple processing units. Multicore programming introduces challenges that single-threaded programming does not face. The main challenges are: task identification (dividing work into independent tasks), load balancing (distributing work evenly across cores), data splitting (dividing data so each core works on its portion), data dependency (handling dependencies between tasks), and testing and debugging (concurrency bugs are non-deterministic and hard to reproduce).

On a single-core system, concurrency is simulated by time-slicing: the OS rapidly switches between threads, giving the illusion of simultaneous execution. On a multicore system, threads can run truly in parallel, with multiple threads executing on different cores at the same time. This exposes race conditions that might not manifest on a single core (where time-slicing serializes access). A program that works on a single core may fail intermittently on multiple cores due to races.

⚠️ Amdahl's Law

Amdahl's Law states that the speedup from parallelization is limited by the sequential portion of the program. If 90% of a program can be parallelized and 10% is sequential, the maximum speedup (with infinite cores) is 10÷(1−0.9) = 10×. This means that even a small sequential portion severely limits parallel speedup. This is why optimizing the sequential parts (Amdahl's "critical section") is crucial.

Parallelism can be data parallel (each thread works on a different portion of the data) or task parallel (each thread performs a different task). Data parallelism is common in scientific computing and image processing; task parallelism is common in interactive applications. Many real applications use both: a web server might use task parallelism (one thread per request type) and data parallelism (within a request, processing data in parallel).

Modern programming models for multicore include thread pools (a pool of worker threads that process tasks from a queue), fork-join (split work, process in parallel, merge results), map-reduce (a framework for large-scale data processing), and dataflow (expressing computation as a graph of dependencies). These models abstract away low-level thread management, making parallel programming more manageable.

4.3 Multithreading Models

There are two types of threads: user threads (managed by a user-level library, invisible to the OS) and kernel threads (managed by the OS). The relationship between user threads and kernel threads determines the multithreading model. There are three common models: many-to-one, one-to-one, and many-to-many.

In the many-to-one model, many user threads are mapped to one kernel thread. Thread management is done in user space by a library, so thread creation and switching are fast. However, if one thread blocks (e.g., on a system call), all threads block, because the kernel only sees one thread. Also, only one thread can run at a time (on one core), so there is no parallelism. This model is rarely used today; early Java green threads and some POSIX thread implementations used it.

In the one-to-one model, each user thread is mapped to one kernel thread. This allows true parallelism (multiple threads on multiple cores) and does not block all threads when one blocks. The downside is that creating a kernel thread is more expensive than creating a user thread, and the number of threads is limited by kernel resources. Linux (using clone()) and Windows use this model. Most modern systems prefer one-to-one for its simplicity and parallelism.

ℹ️ Linux Threads

On Linux, threads are implemented as processes that share memory. The clone() system call creates a new process that can share memory, file descriptors, and signal handlers with its parent. The pthread_create() library function uses clone() internally. From the kernel's perspective, each thread is a separate "task" with its own PID (though the top and ps commands group them by thread group ID, or TGID).

In the many-to-many model, many user threads are mapped to a smaller or equal number of kernel threads. This allows parallelism (multiple kernel threads on multiple cores) while allowing many user threads (limited only by user-space resources). If one user thread blocks, the kernel thread can run another user thread. This model is flexible but complex to implement. Some systems (like Solaris before version 9) used it; modern systems generally prefer one-to-one because kernel threads are now lightweight enough. A variant, two-level, allows a user thread to be bound to a kernel thread (for critical tasks) while others share.

4.4 Thread Libraries

A thread library provides the API for creating and managing threads. There are two approaches: a user-level library (thread management in user space, no kernel involvement) and a kernel-level library (thread management via system calls). Most modern systems provide a kernel-level library (like POSIX pthreads on UNIX or the Windows thread API).

The POSIX Pthreads library (pthread) is the standard threading API on UNIX-like systems. It provides functions for thread creation (pthread_create), termination (pthread_exit), joining (pthread_join), and synchronization (mutexes, condition variables, read-write locks, barriers). Pthreads can be implemented as user-level or kernel-level threads; on Linux, it uses the one-to-one model via clone().

/* Pthreads example */ #include <pthread.h> void *worker(void *arg) { int id = *(int*)arg; printf("Thread %d running\n", id); return NULL; } int main() { pthread_t tid[4]; int ids[4] = {1, 2, 3, 4}; for (int i = 0; i < 4; i++) pthread_create(&tid[i], NULL, worker, &ids[i]); for (int i = 0; i < 4; i++) pthread_join(tid[i], NULL); return 0; }

The Windows thread API (CreateThread, WaitForSingleObject, etc.) is similar in concept but uses different function names and conventions. Java threads are managed by the JVM: the Thread class and Runnable interface provide the API, and the JVM maps Java threads to OS threads (historically many-to-one with green threads, now one-to-one). Modern languages often provide higher-level abstractions: Go's goroutines (lightweight user threads with many-to-many mapping), Rust's async/await, and Python's asyncio.

💡 Thread Attributes

When creating a thread, you can specify attributes: stack size (how much stack space to allocate), scheduling policy (e.g., SCHED_FIFO, SCHED_RR), scheduling priority, and detached state (whether the thread can be joined). The default attributes work for most cases, but tuning them can improve performance or correctness for specific applications.

4.5 Implicit Threading

As applications grow more complex, explicitly managing threads (creating, joining, synchronizing) becomes error-prone. Implicit threading shifts the responsibility of thread management from the developer to the compiler or runtime. The developer expresses what to parallelize; the system decides how.

Thread pools are a common form of implicit threading. Instead of creating a new thread per task, a pool of worker threads is created upfront, and tasks are submitted to a queue. A worker thread picks a task from the queue, executes it, and returns to the pool. This avoids the overhead of thread creation and destruction, limits the number of threads (preventing resource exhaustion), and allows the system to balance load. Most modern languages provide thread pools (Java's ExecutorService, Python's concurrent.futures.ThreadPoolExecutor, C++'s std::async).

/* Thread pool pattern (pseudocode) */ // Create a pool of 8 worker threads ThreadPool pool(8); // Submit tasks — workers pick them up automatically for (int i = 0; i < 100; i++) { pool.submit([=] { process_item(i); // runs on some worker thread }); } pool.wait_all(); // wait for all tasks to complete

OpenMP is a set of compiler directives for parallel programming in C/C++/Fortran. A #pragma omp parallel for directive tells the compiler to parallelize a loop: it divides the loop iterations among threads automatically. This is much simpler than manually creating threads and dividing work. OpenMP is widely used in scientific computing.

/* OpenMP example */ #pragma omp parallel for for (int i = 0; i < N; i++) { c[i] = a[i] + b[i]; // iterations run in parallel }

Other implicit threading approaches include Grand Central Dispatch (Apple's dispatch queues), Intel TBB (Threading Building Blocks), and language-level async/await (C#, JavaScript, Python, Rust). The fork-join framework in Java (ForkJoinPool) splits work recursively, processes subtasks in parallel, and merges results. These abstractions make parallel programming accessible to more developers, but understanding the underlying threading model is still important for debugging and performance tuning.

4.6 Threading Issues

Multithreading introduces several issues that single-threaded programs do not face. Understanding these is essential for writing correct concurrent programs.

The fork() and exec() system calls have subtle semantics with threads. When a multithreaded process calls fork(), should the child have one thread (the calling thread) or all threads? POSIX allows both: fork() duplicates only the calling thread, while pthread_atfork() can register handlers to manage state. If the child immediately calls exec() (replacing the program), the issue is moot. But if the child continues without exec, it may have inconsistent state (e.g., locks held by other threads that no longer exist).

Signal handling is complex with threads. A signal (like SIGINT from Ctrl-C) can be delivered to any thread in the process. Which thread should handle it? Options include: deliver to the thread that caused it (synchronous signals like SIGSEGV), deliver to any thread (asynchronous signals), or deliver to a designated thread. POSIX provides pthread_kill() to send a signal to a specific thread and sigwait() to wait for signals synchronously.

⚠️ Thread Cancellation

Cancelling a thread (terminating it before it finishes) is dangerous. If the thread holds locks or is in the middle of updating shared data, cancellation can leave the data in an inconsistent state. Asynchronous cancellation (immediate) is rarely safe. Deferred cancellation (the thread checks at cancellation points) is safer but requires cooperation. POSIX uses pthread_cancel() with cancellation points.

Thread-local storage (TLS) is data that is per-thread: each thread has its own copy. This is useful for variables that should not be shared, like errno (so one thread's error doesn't overwrite another's). TLS can be implemented by the compiler (using a segment register or special allocation) or by the thread library. Reentrant functions (functions that can be safely called by multiple threads, or called recursively) must not use static or global variables without protection, or must use TLS.

Scheduler activations are a mechanism for the kernel to notify a user-level thread library about scheduling events (like a thread blocking or a core becoming available), allowing the library to make informed decisions. This is used in some many-to-many implementations. Activation-based scheduling aims to combine the flexibility of user-level threads with the kernel's knowledge of system events.

4.7 OS Examples

Different operating systems implement threads differently. Windows uses a one-to-one model: each thread is a kernel object, created with CreateThread(). The Windows scheduler is priority-based with preemptive multitasking. Windows supports fibers, which are user-mode, cooperative "lightweight threads" that the application schedules manually—useful for porting cooperative multitasking code.

Linux does not distinguish between processes and threads at the kernel level. Both are created with clone(), which can share or not share memory, file descriptors, and signal handlers. A "process" is a clone() with no sharing; a "thread" is a clone() with sharing. The task_struct structure represents both. The pthread library provides the POSIX API on top of clone().

clone() takes flags that control sharing:
CLONE_VM — share memory
CLONE_FILES — share file descriptors

CLONE_THREAD — put in same thread group (for pthreads)

xv6 does not implement threads—each process has a single thread. However, the process mechanism (fork, exec, context switch) is the same that a thread-based system would use. Adding threads to xv6 is a common advanced exercise: it involves sharing the address space (page table) between processes, adding a thread ID, and modifying the scheduler to treat threads as schedulable entities. Studying xv6's fork() in sysproc.c and copyproc() in proc.c reveals how process creation works, which is the foundation for thread creation.

5.1 Basic Concepts

CPU scheduling is the basis of multiprogrammed operating systems. By switching the CPU among processes, the OS can keep the CPU busy while some processes wait for I/O, increasing overall throughput. The idea is simple: when a process must wait (for I/O or a child), the OS takes the CPU away and gives it to another process. This multiprogramming maximizes CPU utilization.

Whenever the CPU becomes idle, the OS must select a process from the ready queue to run next. The CPU scheduler makes this selection. Scheduling decisions occur when a process: (1) switches from running to waiting (I/O request), (2) switches from running to ready (interrupt/preemption), (3) switches from waiting to ready (I/O completion), or (4) terminates. Scheduling under (1) and (4) is non-preemptive (the process voluntarily yields); scheduling under (2) and (3) is preemptive (the OS forcibly takes the CPU).

ℹ️ Preemptive vs. Non-Preemptive

Non-preemptive: A running process keeps the CPU until it terminates or blocks. Simple, but a CPU-bound process can starve others.
Preemptive: The OS can interrupt a running process (via timer) and give the CPU to another. More complex (requires saving/restoring state, handling races), but ensures fairness and responsiveness. Modern desktop and server OSes are preemptive.

A key concept is the dispatch latency: the time it takes for the scheduler to stop one process and start another. This includes saving the current process's state, running the scheduler, and loading the next process's state. Minimizing dispatch latency is important for responsiveness, especially in real-time systems. The component of the OS that gives control of the CPU to the selected process is the dispatcher.

5.2 Scheduling Criteria

Different scheduling algorithms optimize for different criteria. The main criteria are:

  • CPU utilization: the percentage of time the CPU is busy (should be as high as possible, ideally near 100%).
  • Throughput: the number of processes completed per unit time (higher is better).
  • Turnaround time: the total time from submission to completion (includes waiting, execution, and I/O time). Lower is better.
  • Waiting time: the total time a process spends waiting in the ready queue. Lower is better.
  • Response time: the time from submission to the first response (not completion). Important for interactive systems. Lower is better.

These criteria often conflict. For example, SJF (Shortest Job First) minimizes average waiting time but can cause starvation for long jobs. Round Robin provides good response time but may have higher average turnaround time. The choice of algorithm depends on which criteria matter most for the workload. Interactive systems prioritize response time; batch systems prioritize throughput and CPU utilization; real-time systems prioritize meeting deadlines.

⚠️ Starvation

Starvation occurs when a process is indefinitely denied the resources it needs (like CPU time). Priority scheduling can cause starvation if high-priority processes keep arriving, preventing a low-priority process from ever running. The solution is aging: gradually increasing a process's priority the longer it waits, so eventually it gets to run.

5.3 Scheduling Algorithms

Several classic scheduling algorithms illustrate the trade-offs in CPU scheduling. Each makes different assumptions and optimizes for different criteria.

First-Come, First-Served (FCFS) is the simplest: processes run in the order they arrive, non-preemptively. It is easy to implement (a FIFO queue) and fair in the sense that no process is starved. However, it suffers from the convoy effect: if a long process is at the head of the queue, all shorter processes behind it wait, increasing average waiting time. FCFS is poor for time-sharing systems (no preemption means poor response time) but acceptable for batch systems.

/* FCFS example: processes arrive in order P1, P2, P3 */ // Burst times: P1=24, P2=3, P3=3 // FCFS order: P1 → P2 → P3 // P1: wait=0, turnaround=24 // P2: wait=24, turnaround=27 // P3: wait=27, turnaround=30 // Average wait = (0+24+27)/3 = 17.0 // Average turnaround = (24+27+30)/3 = 27.0 // Convoy effect: P2 and P3 wait 24+ ms for P1

Shortest-Job-First (SJF) runs the process with the shortest expected CPU burst next. It provably minimizes average waiting time (for a given set of processes). The challenge is predicting the burst length, which is not known in advance. Systems use exponential averaging: the predicted burst is a weighted average of the actual last burst and the previous prediction: $\text{predict}_{n+1} = \alpha \cdot \text{actual}_n + (1-\alpha) \cdot \text{predict}_n$, where $\alpha$ is typically 0.5. SJF can be preemptive (Shortest Remaining Time First, SRTF) or non-preemptive. The risk is starvation of long jobs.

Round Robin (RR) gives each process a fixed time quantum (typically 10–100 ms) and then preempts it, moving to the next process in the queue. If the quantum is too large, RR degenerates to FCFS; if too small, context switch overhead dominates. A quantum of 10–100 ms is a good balance. RR provides good response time (every process gets a turn quickly) and is fair (no starvation). It is the standard for interactive and time-sharing systems.

💡 Choosing the Time Quantum

The time quantum should be: (1) large relative to the context switch time (so overhead is small), (2) small relative to the typical CPU burst (so most processes finish within a few quanta), and (3) large relative to the time for a meaningful computation (so a process does useful work each turn). A common rule: 80% of CPU bursts should be shorter than the quantum.

Priority scheduling assigns each process a priority and runs the highest-priority process. Priorities can be static (fixed at creation) or dynamic (changing over time). The risk is starvation of low-priority processes; aging (increasing priority over time) mitigates this. Priorities can be assigned based on process type (system > interactive > batch), user-specified, or computed from past behavior.

Multilevel queue scheduling divides the ready queue into separate queues by priority or type (e.g., system, interactive, batch). Each queue has its own scheduling algorithm (e.g., RR for interactive, FCFS for batch). Scheduling between queues can be fixed priority (all of queue 1 before any of queue 2) or time-sliced (each queue gets a fraction of CPU time). A multilevel feedback queue allows processes to move between queues based on behavior: a process that uses too much CPU is demoted; one that waits a lot is promoted. This adapts to process behavior and is used in many modern systems.

5.4 Thread Scheduling

On systems that distinguish user and kernel threads, the scheduler schedules kernel threads (since they are the schedulable entities). User threads are managed by the thread library, which maps them to kernel threads. In a one-to-one model (Linux, Windows), each user thread is a kernel thread, so the kernel scheduler handles them directly. In a many-to-many model, the library decides which user thread to run on each kernel thread.

Some systems distinguish between process contention scope (PCS) and system contention scope (SCS). With PCS, threads compete for CPU time within their process (user-level scheduling). With SCS, threads compete with all threads system-wide (kernel-level scheduling). Pthreads allows specifying the scope with pthread_attr_setscope(): PTHREAD_SCOPE_PROCESS (PCS) or PTHREAD_SCOPE_SYSTEM (SCS).

ℹ️ Linux Scheduling

Linux uses the Completely Fair Scheduler (CFS) since kernel 2.6.23. CFS aims to give each process a fair share of CPU time, using a red-black tree ordered by "virtual runtime" (how much CPU time the process has used). The process with the least virtual runtime runs next. This approximates ideal fair scheduling and avoids starvation. CFS also supports priority (nice values) and real-time scheduling policies.

Thread scheduling on multicore systems adds complexity. The scheduler must decide not only which thread to run but where (which core). Considerations include cache affinity (keeping a thread on the same core to reuse cached data), load balancing (distributing threads evenly), and power management (consolidating threads on fewer cores to allow others to sleep). Modern schedulers use per-core run queues with periodic load balancing.

5.5 Multi-Processor Scheduling

On a multiprocessor (or multicore) system, the scheduler must decide which core runs which process. This is more complex than single-processor scheduling because of cache affinity (a process runs faster on a core where its data is cached), load balancing (uneven distribution wastes some cores), and cache coherence overhead (moving a process to another core invalidates caches).

Two common approaches are asymmetric multiprocessing (ASMP) and symmetric multiprocessing (SMP). In ASMP, one core is the master that runs the OS and schedules all other cores; the other cores are slaves that run user code. This is simple (no locking needed for scheduler data structures) but creates a bottleneck (all scheduling goes through the master). In SMP, all cores are equal: each runs the OS and schedules its own processes. This requires locking to protect shared scheduler data structures but scales better. Modern systems use SMP.

💡 Per-Core Run Queues

Modern SMP schedulers use per-core run queues: each core has its own queue of runnable threads. This avoids contention on a single global queue. Periodically (usually every few milliseconds), cores check if their queues are unbalanced and migrate threads from busy cores to idle ones. This balances load while preserving cache affinity most of the time.

Processor affinity refers to a thread's tendency to stay on the same core. Soft affinity means the scheduler tries to keep a thread on the same core but may move it. Hard affinity means the scheduler must keep a thread on specified cores (set via sched_setaffinity() on Linux). Hard affinity is useful for real-time tasks or to isolate cores for specific purposes.

Modern CPUs with simultaneous multithreading (SMT, e.g., Intel Hyper-Threading) present multiple logical processors per physical core. The scheduler treats each logical processor as a separate CPU, but two threads on the same physical core share execution resources, so they don't get full parallel speedup. Some schedulers are SMT-aware and try to spread threads across physical cores before using the second logical processor on each core.

5.6 Real-Time Scheduling

Real-time systems require that tasks complete within deadlines. Hard real-time systems guarantee that deadlines are always met (missing a deadline is a system failure—e.g., a pacemaker, airbag controller). Soft real-time systems try to meet deadlines but tolerate occasional misses (e.g., video streaming, where a missed frame is annoying but not catastrophic).

Real-time scheduling uses priority to ensure critical tasks run first. Two common algorithms are Rate Monotonic and Earliest Deadline First. In Rate Monotonic Scheduling (RMS), tasks are assigned static priorities based on their period: shorter period = higher priority. This is optimal among static-priority schemes for preemptive periodic tasks. In Earliest Deadline First (EDF), the task with the nearest deadline gets the highest priority. EDF is optimal among dynamic-priority schemes and can achieve 100% CPU utilization (vs. ~69% for RMS), but it is more complex and requires knowing deadlines.

Real-time systems must also handle priority inversion: a low-priority task holds a lock that a high-priority task needs, and a medium-priority task preempts the low-priority task, indirectly blocking the high-priority task. The priority inheritance protocol solves this: the low-priority task temporarily inherits the high-priority task's priority while holding the lock, so it cannot be preempted by medium-priority tasks. This was famously the cause of the Mars Pathfinder rover resetting on Mars in 1997 due to priority inversion in its VxWorks real-time OS.

⚠️ Priority Inversion

Scenario: High-priority H needs a lock held by low-priority L. Medium-priority M preempts L. Now H waits for L, which waits for M. Effectively, M (medium) blocks H (high). Priority inheritance temporarily raises L's priority to H's, so M cannot preempt it, and L releases the lock sooner.

POSIX real-time scheduling (SCHED_FIFO, SCHED_RR) provides fixed-priority preemptive scheduling. SCHED_FIFO runs the highest-priority ready thread until it blocks or a higher-priority thread becomes ready. SCHED_RR is like SCHED_FIFO but with time-slicing among same-priority threads. Linux also provides SCHED_DEADLINE for EDF-based scheduling.

5.7 OS Examples

Linux uses the Completely Fair Scheduler (CFS) for normal processes. CFS maintains a red-black tree of runnable tasks, ordered by vruntime (virtual runtime—a measure of CPU time received, normalized by priority). The leftmost node (smallest vruntime) runs next. Each task gets a time slice proportional to its priority (nice value). CFS aims for fair scheduling: each task gets an equal share, adjusted by priority. For real-time tasks, Linux uses SCHED_FIFO and SCHED_RR, which have higher priority than CFS tasks.

Windows uses a priority-based preemptive scheduler with 32 priority levels. Levels 0–15 are for normal (variable) priority threads; levels 16–31 are for real-time threads. Within the variable range, the base priority can be boosted temporarily (e.g., for I/O completion or GUI input) to improve responsiveness. Windows uses per-processor queues and distributes threads across processors, with periodic load balancing.

ℹ️ xv6 Scheduler

xv6 uses a simple round-robin scheduler. The scheduler() function in proc.c loops through the process table (proc[NPROC]), and for each RUNNABLE process, it sets it to RUNNING, switches to its page table, and calls swtch() to run it. When the process yields (blocks or time-slice expires), control returns to scheduler(), which continues the loop. This is simple but not fair (a process that blocks often may get more CPU) and not multiprocessor-safe without locks (xv6 uses a single ptable.lock).

Solaris uses a multilevel feedback queue with several scheduling classes (TS for time-sharing, IA for interactive, RT for real-time, FSS for fair-share, FX for fixed-priority). Each class has its own scheduling logic, and the dispatcher selects the highest-priority thread across all classes. This is one of the most sophisticated scheduling designs, combining fairness, responsiveness, and real-time support.

5.8 Algorithm Evaluation

How do we choose a scheduling algorithm? Several methods help evaluate and compare algorithms: analytic evaluation, simulation, and implementation.

Deterministic modeling takes a specific workload (a set of processes with known arrival times and burst lengths) and computes the result of each algorithm. This is useful for understanding how algorithms differ but is not representative of real workloads. For example, given processes P1(6), P2(8), P3(7), P4(3) arriving at time 0, FCFS gives average wait (0+6+14+21)/4 = 10.25, while SJF (order P4, P1, P3, P2) gives (0+3+9+16)/4 = 7.0.

Queueing models treat the system as a queue: processes arrive according to some distribution (often Poisson), and service times follow another distribution (often exponential). Using Little's formula ($n = \lambda \times W$, where $n$ is average queue length, $\lambda$ is arrival rate, $W$ is average waiting time), we can compute performance metrics. This is more general than deterministic modeling but relies on assumptions about distributions that may not hold.

💡 Little's Formula

Little's formula: $L = \lambda W$, where $L$ is the average number of items in the system, $\lambda$ is the average arrival rate, and $W$ is the average time an item spends in the system. This holds for any stable queueing system, regardless of distribution. It's a powerful tool for quick estimates.

Simulation involves programming a model of the scheduler and running it with generated workloads. Workloads can be real (traces from actual systems) or synthetic (generated to match observed distributions). Simulation allows testing many algorithms and parameters without implementing them in a real OS. The challenge is generating realistic workloads; real traces are best but may not represent future workloads.

Implementation is the ultimate test: implement the algorithm in a real OS and measure performance on real workloads. This is the most accurate but also the most expensive—coding, debugging, and benchmarking take time. Most research uses simulation first, then implements the most promising algorithms. Open-source OSes like Linux and FreeBSD allow researchers to experiment with scheduling algorithms in a real system.
