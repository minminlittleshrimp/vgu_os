11.1 Overview

Mass storage is the foundation of persistent data in a computer system. While main memory (RAM) is fast but volatile and limited in size, mass storage provides large, non-volatile capacity for programs, data, and the operating system itself. The two dominant mass-storage technologies are hard disk drives (HDDs) and non-volatile memory (NVM) devices, primarily solid-state drives (SSDs).

A hard disk drive (HDD) stores data on rotating magnetic platters. Data is organized into concentric tracks on each platter surface, and each track is divided into sectors (typically 512 bytes or 4 KB). A read/write head on a movable arm positions over the desired track, and as the platter rotates, the head reads or writes sectors. The performance of an HDD is dominated by three mechanical delays: seek time (moving the arm to the track), rotational latency (waiting for the sector to rotate under the head), and transfer time (reading/writing the data).

Non-volatile memory (NVM) devices, including SSDs based on NAND flash, have no moving parts. Data is stored in electrical cells organized into pages (typically 4–16 KB) and blocks (typically 128–512 pages). NVM has a fundamental constraint: while pages can be written individually, they can only be erased in blocks. This means that overwriting data requires erasing the entire block, which is slow and wears out the flash. The flash translation layer (FTL) in the SSD firmware handles this by writing to new pages and marking old pages as invalid, a process called out-of-place update. The FTL also performs garbage collection to reclaim invalid pages and wear leveling to distribute writes evenly across the device.

ℹ️ HDD vs. NVM

The key difference is that HDD performance depends on physical location (seek time and rotational latency), so disk scheduling algorithms (FCFS, SSTF, SCAN, etc.) are important. NVM has uniform access time regardless of location, so scheduling is less critical, but write amplification and wear leveling become the key concerns. The OS must use different optimization strategies for each.

In xv6, mass storage is represented by a simple virtio disk driver (kernel/virtio_disk.c). The file system (kernel/fs.c) treats the disk as an array of 512-byte sectors and does not distinguish between HDD and SSD. There is no disk scheduling—the requests are processed in FIFO order. This is acceptable for a teaching OS but would be inefficient on a real HDD, where reordering requests could dramatically improve throughput.

11.2 HDD Scheduling

Because HDD performance is dominated by seek time (moving the read/write head to the target track), disk scheduling algorithms aim to minimize head movement. The OS maintains a queue of disk I/O requests, each specifying a target cylinder (track). The scheduler chooses the order in which to service these requests to minimize total seek distance.

FCFS Scheduling

First-Come, First-Served (FCFS) is the simplest algorithm: requests are serviced in the order they arrive. While fair, it can be very inefficient because consecutive requests may be far apart, causing large seek distances.

/* FCFS disk scheduling */ // Queue: 98, 183, 37, 122, 14, 124, 65, 67 // Head starts at 53 FCFS order: 53 → 98 → 183 → 37 → 122 → 14 → 124 → 65 → 67 // Total head movement: // |98-53| + |183-98| + |37-183| + |122-37| // + |14-122| + |124-14| + |65-124| + |67-65| // = 45 + 85 + 146 + 85 + 108 + 110 + 59 + 2 = 640 cylinders

SSTF (Shortest Seek Time First)

Shortest Seek Time First selects the request with the minimum seek distance from the current head position. This minimizes average seek time but can cause starvation: if requests keep arriving near the current position, distant requests may never be serviced.

/* SSTF disk scheduling */ // Queue: 98, 183, 37, 122, 14, 124, 65, 67 // Head starts at 53 SSTF order: 53 → 65 → 67 → 37 → 14 → 98 → 122 → 124 → 183 // From 53: nearest is 65 (dist 12) // From 65: nearest is 67 (dist 2) // From 67: nearest is 37 (dist 30) // ... total = 236 cylinders (much better than FCFS's 640)

SCAN (Elevator) and C-SCAN

The SCAN algorithm (also called the elevator algorithm) moves the head in one direction, servicing requests in that direction until it reaches the last request (or the end of the disk), then reverses direction. This is like an elevator: it services all requests in one direction before turning around. SCAN has good throughput and fairness—no request is starved because the head will eventually reach every position.

Circular SCAN (C-SCAN) is a variant that treats the disk as circular. The head moves in one direction servicing requests, but when it reaches the end, it jumps back to the beginning (seek to 0) and continues in the same direction. This provides more uniform wait times because the maximum wait is one full sweep, not two (as in SCAN).

/* SCAN vs C-SCAN (head at 53, moving toward 0) */ // Queue: 98, 183, 37, 122, 14, 124, 65, 67 SCAN (toward 0, then reverse): 53 → 37 → 14 → [0] → 65 → 67 → 98 → 122 → 124 → 183 // Services 14, 37 going down, then 65,67,98,... going up C-SCAN (toward 0, jump to max, continue): 53 → 37 → 14 → [0] → [199] → 183 → 124 → 122 → 98 → 67 → 65 // Goes down to 0, jumps to 199, continues down

LOOK and C-LOOK

LOOK is a practical optimization of SCAN: instead of going all the way to the end of the disk, the head reverses at the last request in the current direction. C-LOOK does the same for C-SCAN. These are the most commonly implemented variants because they avoid unnecessary travel to the disk edges.

💡 Modern Disk Scheduling

Modern OSes use more sophisticated schedulers. Linux's deadline scheduler sets a time limit for each request to prevent starvation. The CFQ (Completely Fair Queuing) scheduler assigns time slices to processes. Modern NVMe SSDs often bypass OS scheduling entirely because the device has uniform access time and its own internal scheduler. The OS may use a simple FIFO or a minimal scheduler for NVM devices.

In xv6, there is no disk scheduling. The virtio disk driver processes requests in FIFO order. For a teaching OS on a virtual disk, this is fine. On a real HDD, adding a LOOK scheduler would significantly improve performance under load. The implementation would involve maintaining a sorted request queue and reordering requests based on the current head position—a common advanced OS project.

11.3 NVM Scheduling

Non-volatile memory devices (SSDs) have fundamentally different characteristics from HDDs. Because there are no moving parts, access time is uniform regardless of the logical block address (LBA). This means traditional seek-optimizing schedulers (SSTF, SCAN, etc.) provide no benefit. Instead, NVM scheduling focuses on different goals: maximizing throughput, minimizing latency, and reducing write amplification.

The key performance metric for NVM is IOPS (Input/Output Operations Per Second) and queue depth. NVM devices can handle many concurrent I/O operations, so the OS should submit multiple requests in parallel rather than waiting for each to complete. The NVMe (Non-Volatile Memory Express) interface supports up to 65,535 submission queues, each with up to 65,536 entries, allowing massive parallelism. The OS distributes I/O across multiple queues (typically one per CPU core) to maximize throughput.

/* NVM I/O submission (NVMe-style) */ // Each CPU core has its own submission queue submit_io(request, cpu): sq = nvme.submission_queue[cpu] sq.push(request) // add to tail nvme.doorbell[cpu] = sq.tail // notify device // Device processes requests in parallel // and posts completions to completion queue process_completion(cpu): cq = nvme.completion_queue[cpu] while (cq.has_new()): cqe = cq.pop() complete_request(cqe.request, cqe.status)

Write amplification is a critical concern for NVM. Because flash pages cannot be overwritten in place (they must be erased in blocks), a single 4 KB write may cause the FTL to copy an entire 128-page block, erase it, and write it back—amplifying the write by 128×. The OS can reduce write amplification by: (1) aligning writes to page and block boundaries, (2) batching small writes, (3) using TRIM (or DEALLOCATE) to inform the device about freed blocks, and (4) avoiding unnecessary writes (e.g., not writing unchanged data).

⚠️ TRIM/DISCARD

When a file is deleted, the OS should send a TRIM command to the SSD, informing it that the freed blocks no longer contain valid data. This allows the FTL's garbage collector to skip copying those pages during block erasure, reducing write amplification and improving performance. Without TRIM, SSD performance degrades over time as the FTL runs out of free blocks. Linux enables TRIM via fstrim or continuous TRIM (discard mount option).

Wear leveling is handled by the FTL, not the OS, but the OS can help by avoiding write patterns that concentrate writes on a few blocks. For example, a log-structured file system (like f2fs on Android) writes sequentially to the device, allowing the FTL to distribute wear naturally. The OS should also avoid unnecessary metadata writes (e.g., updating access times) on NVM to reduce wear.

For NVM, the OS scheduler is typically much simpler than for HDDs. Linux's None scheduler (or noop in older kernels) simply passes requests to the device in FIFO order, letting the device's internal scheduler handle optimization. This is optimal for NVM because the device has better knowledge of its internal geometry (page and block layout) than the OS.

11.4 Error Detection and Correction

Storage devices are not perfectly reliable. Bits can be corrupted by media degradation, electrical noise, firmware bugs, or cosmic rays. The OS and storage devices use error detection and error correction techniques to ensure data integrity.

The most common error-detection mechanism is the checksum or CRC (Cyclic Redundancy Check). Each sector or page stores a checksum alongside the data. When data is read, the device (or OS) recomputes the checksum and compares it to the stored value. If they differ, an error is detected. A CRC can detect multi-bit errors but cannot correct them. Common CRCs include CRC-32 (4 bytes) and CRC-64 (8 bytes).

Error-Correcting Codes (ECC) go further: they can detect and correct errors. The most common ECC for storage is Hamming code (for single-bit correction) and Reed-Solomon or BCH codes (for multi-bit correction). Modern SSDs store significant ECC data per page (typically 1 byte per 32–128 bytes of data) to correct multiple bit errors. The ECC is computed and verified by the device controller, transparent to the OS.

When an uncorrectable error is detected, the device returns an error status to the OS. The OS may then: (1) retry the read (transient errors may succeed on retry), (2) use redundant data from a RAID array (Section 11.8) to reconstruct the data, or (3) report the error to the application (e.g., EIO on Linux). For critical data, the OS may maintain its own checksums (e.g., ZFS, Btrfs) to detect silent data corruption—errors that the device does not report.

ℹ️ Silent Data Corruption

Sometimes storage devices return data without error but the data is actually corrupted (e.g., due to a firmware bug or a bit flip in the device's buffer). This is called silent data corruption (SDC). File systems with end-to-end checksums (ZFS, Btrfs) detect this by verifying data checksums at every level: device, OS, and application. This is why enterprise storage uses end-to-end data integrity.

Storage devices also report S.M.A.R.T. (Self-Monitoring, Analysis, and Reporting Technology) data, which includes health metrics like reallocated sector count, temperature, and power-on hours. The OS can read S.M.A.R.T. data to predict impending failure and warn the user. Tools like smartctl on Linux expose this data. Enterprise systems use S.M.A.R.T. for predictive maintenance—replacing drives before they fail.

In xv6, there is no error detection or correction beyond what the virtio disk provides. The virtio_disk_rw() function in kernel/virtio_disk.c simply checks the device's status field for errors and panics if an I/O fails. A production OS would retry failed I/O, log errors, and eventually mark the device as failed. Adding checksums to the xv6 file system would be a valuable exercise in understanding data integrity.

11.5 Storage Device Management

Storage device management encompasses the low-level operations the OS performs to prepare and maintain storage devices: formatting, partitioning, and bad-block management.

Low-level formatting (physical formatting) divides the disk into sectors that the disk controller can read and write. Each sector consists of a header, a data area (typically 512 bytes or 4 KB), and a trailer containing the ECC. Low-level formatting is done at the factory for HDDs and is not normally performed by the OS. For NVM, the equivalent is the initial provisioning of the flash translation layer.

Partitioning divides a storage device into logical units called partitions. Each partition appears as a separate device (e.g., /dev/sda1, /dev/sda2 on Linux). The partition table is stored at the beginning of the device. Two common partition table formats are MBR (Master Boot Record, limited to 2 TB and 4 primary partitions) and GPT (GUID Partition Table, supports larger disks and more partitions). The OS treats each partition as an independent storage device and can place a different file system on each.

/* Partition table (MBR layout) */ // Sector 0: Master Boot Record // 446 bytes: bootstrap code // 64 bytes: 4 partition entries (16 bytes each) // 2 bytes: signature (0x55 0xAA) struct partition_entry: status // 0x80 = bootable chs_first // CHS of first sector type // 0x83 = Linux, 0x07 = NTFS, etc. chs_last // CHS of last sector lba_first // LBA of first sector num_sectors // number of sectors // GPT uses 128 entries, 128 bytes each // Supports disks > 2 TB

High-level formatting (logical formatting) creates a file system on a partition. This involves writing the file system's metadata structures: the superblock, inode table, free-space bitmap or list, and root directory. On Linux, this is done by mkfs (e.g., mkfs.ext4, mkfs.xfs). On Windows, it is done by the format command. The file system is then mounted to make it accessible.

Bad-block management handles sectors or pages that become unreliable. For HDDs, the OS or the disk controller maintains a list of bad blocks and avoids using them. When a bad block is detected during operation, the data is relocated (if possible) and the block is marked as bad. For NVM, the FTL handles bad blocks transparently: it maintains a bad-block table and remaps logical blocks to good physical pages. The OS typically does not see bad blocks on NVM devices, but the FTL may eventually run out of spare blocks, at which point the device fails.

⚠️ Bad Blocks in xv6

The xv6 file system (kernel/fs.c) does not handle bad blocks. If a disk sector goes bad, xv6 will either silently corrupt data or panic. A production file system must detect bad blocks (via read errors or checksums), mark them in a bad-block list, and relocate data. This is a significant gap between xv6 and real file systems.

Storage device management also includes mounting and unmounting file systems. When a file system is mounted, the OS reads its superblock, validates the file system structure, and makes it accessible at a mount point (a directory in the existing directory tree). When unmounted, the OS flushes all dirty buffers and metadata to the device, ensuring consistency. If a file system is not cleanly unmounted (e.g., due to a power failure), the OS must run a file system check (fsck) on the next boot to repair any inconsistencies.

11.6 Swap-Space Management

Swap space is the area on a storage device used to hold pages that have been evicted from memory (see Chapter 10, Swapping). The OS manages swap space to provide virtual memory that exceeds physical RAM. Swap-space management involves deciding where to place swap space, how to allocate it, and how to track which pages are where.

Swap space can be a dedicated swap partition (a raw partition used only for swapping) or a swap file (a regular file within a file system). A swap partition is faster because it avoids file-system overhead, but it is inflexible (the size is fixed at partition time). A swap file is more flexible (can be created, resized, and deleted at runtime) but slightly slower. Modern Linux supports both and can use multiple swap areas simultaneously.

/* Swap space management */ // Linux swap area layout: // Page 0: swap header (magic, version, bad blocks) // Page 1..N: swap slots (4 KB each) // Bitmap: tracks free/used slots swap_out(page): slot = swap_alloc_slot() // find free slot write_to_swap(slot, page) // I/O to disk pte.frame = SWAP_MARKER pte.swap_slot = slot pte.valid = false pte.swap = true swap_in(pte): page = alloc_frame() read_from_swap(pte.swap_slot, page) swap_free_slot(pte.swap_slot) pte.frame = page pte.valid = true pte.swap = false

The OS tracks the mapping between virtual pages and swap slots. When a page is swapped out, the PTE is updated to indicate that the page is on swap (the valid bit is cleared and the swap slot index is stored in the PTE). When the page is referenced, a page fault occurs, and the OS reads the page from the swap slot back into a free frame. The swap slot is then freed for reuse.

ℹ️ Swap on SSD vs. HDD

Swap performance depends heavily on the storage device. On an HDD, swap I/O is very slow (5–10 ms per page), so the OS must minimize swapping. On an NVMe SSD, swap is much faster (10–50 μs per page), making it more practical. However, swapping on flash wears the device, so mobile OSes avoid it. macOS and Windows 10+ use memory compression before swapping to reduce I/O.

Swap-space size is a trade-off. Too little swap limits the total virtual memory; too much wastes disk space. A common rule of thumb is to set swap to 1–2× the physical RAM, but modern systems with large RAM may use less. Linux's swappiness parameter (0–200) controls how aggressively the OS swaps: a low value prefers keeping anonymous pages in memory; a high value swaps more eagerly to free memory for file cache.

In xv6, there is no swap space. All process pages are in memory, and sbrk() allocates physical frames eagerly. Adding swap to xv6 would require: (1) a swap area on the virtio disk, (2) a swap-slot allocator, (3) modifying the page-fault handler to swap in pages, (4) a page-replacement algorithm to select victims, and (5) modifying sbrk() to support lazy allocation. This is a common advanced xv6 lab.

11.7 Storage Attachment

Storage devices are attached to a computer via various interfaces or buses. The interface determines the protocol, performance characteristics, and management model. Understanding storage attachment is important for OS design because the driver and I/O subsystem must adapt to the interface.

The most common storage interfaces are:

Direct-attached storage (DAS) is connected directly to the computer (SATA, SAS, NVMe, USB). The OS communicates with the device through a device driver that understands the interface protocol. The driver translates OS I/O requests into interface-specific commands (e.g., SATA READ DMA EXT, NVMe READ).

Network-attached storage (NAS) is accessed over a network using a file protocol (NFS, SMB/CIFS). The OS's NFS or SMB client translates file operations into network requests to a remote server. The server's OS handles the actual storage I/O. NAS appears to the user as a network drive.

Storage-area networks (SAN) provide block-level access over a network using protocols like iSCSI (SCSI over TCP/IP) or Fibre Channel (FC). The OS sees a SAN LUN (Logical Unit Number) as a local block device and can put a file system on it. SANs are used in enterprise data centers for centralized storage management, snapshots, and replication.

💡 Hot-Plug and Hot-Swap

Modern storage interfaces support hot-plug—connecting and disconnecting devices while the system is running. The OS must detect the change (via an interrupt or event), update its device list, and notify affected applications. For NVMe, hot-plug is handled via PCIe hot-plug events. For USB, the udev daemon on Linux automatically mounts new devices. This dynamic device management is a significant complexity in modern OS I/O subsystems.

In xv6, storage attachment is simplified: the virtio disk is present at boot and never changes. The virtio_disk_init() function in kernel/virtio_disk.c sets up the device during boot, and there is no hot-plug support. A real OS must handle dynamic device arrival and departure, which requires a device manager (like Linux's udev or Windows's PnP manager) that can load and unload drivers at runtime.

11.8 RAID Structure

RAID (Redundant Array of Independent Disks) is a technique that uses multiple physical disks to improve performance, reliability, or both. Data is striped across disks to increase throughput, and redundancy is added to tolerate disk failures. RAID can be implemented in hardware (a RAID controller) or in software (the OS's RAID subsystem, like Linux's md).

RAID levels define different trade-offs between performance, redundancy, and capacity:

LevelNameDescriptionMin DisksCapacityFault Tolerance
RAID 0StripingData split across disks, no redundancy2100%None (failure = total loss)
RAID 1MirroringData duplicated on each disk250%1 disk
RAID 4Parity diskStriping + dedicated parity disk3(N−1)/N1 disk
RAID 5Distributed parityStriping + parity distributed across disks3(N−1)/N1 disk
RAID 6Double parityStriping + 2 parity blocks per stripe4(N−2)/N2 disks
RAID 101+0Mirrored stripes (RAID 1 of RAID 0 arrays)450%1 per mirror

RAID 0 (striping) splits data across all disks. A stripe of size S bytes is written as S/N bytes to each of N disks. This increases throughput N-fold for large sequential I/O. However, if any disk fails, all data is lost. RAID 0 is used for performance-critical, non-critical data (e.g., scratch space, cache).

RAID 1 (mirroring) writes identical data to two (or more) disks. Read performance can be improved by reading from either disk; write performance is limited by the slower disk. If one disk fails, the other continues to provide data. RAID 1 is simple and reliable but wastes 50% of capacity. It is used for boot disks and small critical volumes.

/* RAID 4/5 parity calculation */ // Parity is XOR of all data blocks in a stripe compute_parity(blocks[]): parity = 0 for b in blocks: parity = parity XOR b return parity // If one block is lost, it can be reconstructed: // lost = XOR of all remaining blocks (including parity) reconstruct(remaining_blocks[]): lost = 0 for b in remaining_blocks: lost = lost XOR b return lost

RAID 4 uses a dedicated parity disk. Every write must update the parity disk, making it a bottleneck. RAID 5 distributes parity across all disks, eliminating the bottleneck. RAID 5 can tolerate one disk failure. RAID 6 uses two independent parity blocks (typically Reed-Solomon) and can tolerate two disk failures, which is important during rebuild (a second failure during rebuild would lose data in RAID 5).

⚠️ RAID Write Penalty

RAID 4/5/6 have a write penalty for small random writes. A 4 KB write requires: (1) read old data, (2) read old parity, (3) compute new parity, (4) write new data, (5) write new parity. This is 4 I/Os for 1 write—a 4× penalty. For large sequential writes (full stripe), the penalty is lower because parity is computed once for the whole stripe. This is why RAID 5 is good for read-heavy workloads but poor for write-heavy ones.

RAID rebuild is the process of reconstructing data after a disk failure. A new disk is inserted, and the RAID controller reads all surviving disks to recompute the missing data. Rebuild can take hours or days for large arrays, during which the array is vulnerable (no redundancy). During rebuild, performance is degraded because the controller is busy reading all disks. RAID 6 reduces the risk of data loss during rebuild by tolerating a second failure.

Modern systems often use hybrid RAID levels like RAID 10 (mirrored stripes) for performance and reliability, or erasure coding (a generalization of RAID 6) for large-scale storage systems. Cloud storage systems (Amazon S3, Azure Blob) use erasure coding to achieve 11 nines of durability with minimal storage overhead.

In xv6, there is no RAID support—the file system uses a single virtio disk. Implementing RAID in xv6 would involve: (1) a multi-disk driver that manages several virtio disks, (2) a striping layer for RAID 0, (3) a mirroring layer for RAID 1, and (4) a parity layer for RAID 5. This is a significant project but would demonstrate the core concepts of redundant storage.

12.1 Overview

The I/O system is the part of the OS that manages input/output devices. It provides a uniform interface to a wide variety of devices—disks, network cards, keyboards, displays, GPUs—hiding their differences from applications and most of the kernel. The I/O system is one of the largest and most complex parts of a modern OS, often comprising the majority of the kernel source code (Linux has millions of lines of driver code).

The I/O system has three main components: (1) I/O hardware—the devices themselves and their controllers; (2) the kernel I/O subsystem—the OS code that provides services like buffering, caching, and scheduling; and (3) the application I/O interface—the system calls and library functions that applications use to perform I/O.

ℹ️ I/O System Goals

The I/O system aims to: (1) provide uniformity—all devices should have a similar interface; (2) provide efficiency—minimize CPU involvement and maximize throughput; (3) provide correctness—handle errors gracefully; and (4) provide device independence—applications should not need to know device-specific details. These goals often conflict, and the OS must balance them.

A key challenge is the speed mismatch between CPUs and I/O devices. A CPU executes billions of instructions per second, while a disk I/O takes milliseconds. The OS uses interrupts to avoid making the CPU wait: it starts an I/O operation, continues executing other code, and is notified by an interrupt when the I/O completes. This enables concurrency—the CPU can do useful work while I/O is in progress.

In xv6, the I/O system is minimal. The console driver (kernel/console.c) handles keyboard input and screen output. The virtio disk driver (kernel/virtio_disk.c) handles disk I/O. Both use interrupts to notify the kernel of completion. The uart.c driver handles serial I/O. These drivers are simple but demonstrate the core concepts: device registers, interrupts, and memory-mapped I/O.

12.2 I/O Hardware

I/O hardware consists of devices and their controllers. A device controller is a hardware component that manages one or more devices. It has a set of registers that the CPU reads and writes to control the device: a control register (to issue commands), a status register (to check device state), a data-in register (to read data), and a data-out register (to write data). The CPU communicates with the controller through these registers.

There are two ways the CPU accesses device registers: port I/O and memory-mapped I/O. In port I/O (used by x86), device registers are in a separate I/O address space, accessed by special instructions (in and out on x86). In memory-mapped I/O (used by ARM, RISC-V, and most modern architectures), device registers are mapped into the physical address space, and the CPU accesses them using normal load/store instructions. Memory-mapped I/O is more flexible and is the dominant approach in modern systems.

/* Memory-mapped I/O (RISC-V / xv6) */ // UART (16550) registers at physical address 0x10000000 #define UART0 0x10000000 #define RHR 0 // Receive Holding Register (data-in) #define THR 0 // Transmit Holding Register (data-out) #define LSR 5 // Line Status Register // Write a character to the UART uartputc(c): while ((*(UART0 + LSR) & 0x20) == 0) ; // wait for transmit ready *(UART0 + THR) = c // Read a character from the UART uartgetc(): if (*(UART0 + LSR) & 0x01) return *(UART0 + RHR) return -1 // no data

Polling is the simplest I/O method: the CPU repeatedly reads the device's status register until the device is ready, then reads or writes data. Polling is simple but wastes CPU cycles and prevents the CPU from doing other work. It is used for simple devices or when interrupts are not available.

Interrupts are more efficient: the CPU issues an I/O command and continues executing. When the device completes, it raises an interrupt, and the CPU jumps to an interrupt service routine (ISR) that handles the completion. Interrupts allow the CPU to do other work while waiting for I/O, dramatically improving throughput. However, interrupt handling has overhead (saving/restoring registers, context switch), so for very fast devices, polling may be more efficient.

💡 Interrupt vs. Polling

For slow devices (disks, network), interrupts are better because the wait time is long and the CPU can do other work. For fast devices (high-speed network cards), the overhead of interrupt processing may exceed the benefit, so NAPI (New API) in Linux uses a hybrid: switch to polling when the interrupt rate is high, and back to interrupts when it drops. This avoids livelock under high load.

Direct Memory Access (DMA) is used for bulk data transfers. Instead of the CPU copying each byte between the device and memory, the DMA controller transfers data directly between the device and RAM. The CPU sets up the DMA transfer (source, destination, length), starts it, and is notified by an interrupt when it completes. DMA dramatically reduces CPU load for large transfers. Modern devices (NVMe, network cards) have built-in DMA engines and can perform scatter-gather DMA, transferring data to/from multiple memory regions in a single operation.

In xv6, the virtio disk driver uses DMA. The virtio_disk_rw() function in kernel/virtio_disk.c sets up a descriptor with the buffer address and length, adds it to the virtqueue, and notifies the device. The device performs the DMA transfer and raises an interrupt when done. The interrupt handler (virtio_disk_intr()) wakes up the waiting process. This is a simplified version of how real DMA-based drivers work.

12.3 Application I/O Interface

The application I/O interface is the set of system calls and library functions that applications use to perform I/O. The OS provides a uniform interface that hides device-specific details. The most important interface is the file descriptor abstraction: in Unix-like systems, all I/O devices are represented as files, and I/O is performed using open(), read(), write(), close(), and ioctl().

Devices are categorized into classes, each with a common interface:

Device ClassExamplesKey OperationsCharacteristics
Block devicesDisk, SSD, USB driveread(), write(), seek()Random access, fixed-size blocks
Character devicesKeyboard, serial, terminalgetchar(), putchar()Sequential, byte stream
Network devicesEthernet, Wi-Fisend(), recv(), socket()Packet-based, no seek
Clock/timerSystem timergettimeofday(), sleep()Generates interrupts

The block device interface provides random access to fixed-size blocks (typically 512 bytes or 4 KB). The OS uses this interface for file systems: the file system reads and writes blocks via the block device driver. The character device interface provides sequential byte-stream access. Terminals, keyboards, and serial ports use this interface. The network device interface is different: it uses sockets and packet-based I/O rather than read/write.

/* Unix I/O interface (POSIX) */ // Block/character device: open, read, write, close int fd = open("/dev/sda", O_RDONLY); read(fd, buffer, 4096); close(fd); // Network: socket, send, recv int sock = socket(AF_INET, SOCK_STREAM, 0); connect(sock, &addr, sizeof(addr)); send(sock, data, len, 0); recv(sock, buf, len, 0); // ioctl: device-specific control ioctl(fd, IOCTL_GET_SIZE, &size);

The ioctl() (I/O control) system call is the escape hatch for operations that do not fit the read/write model. It takes a device-specific command code and an argument, allowing drivers to implement custom operations. For example, a disk driver might use ioctl() to get the disk size, eject the media, or perform a low-level format. The ioctl() interface is powerful but unstructured—each driver defines its own commands, making it a source of bugs and security issues.

ℹ️ Everything Is a File

The Unix philosophy of "everything is a file" means that the same read()/write() interface works for disks, terminals, pipes, and network sockets (via /dev/tcp in some shells). This uniformity simplifies application programming and enables powerful composition (e.g., piping the output of one program to the input of another). However, network devices break this model (they use socket() instead of open()), which is a historical compromise.

In xv6, the I/O interface follows the Unix model. The open(), read(), write(), and close() system calls work on both files and devices. The console is accessed via file descriptor 0 (stdin), 1 (stdout), and 2 (stderr). The file system is accessed via open() on a path like "/file.txt". xv6 does not have ioctl() or socket interfaces, keeping the system simple.

12.4 Kernel I/O Subsystem

The kernel I/O subsystem provides services that are common to all I/O devices, independent of the specific hardware. These services include buffering, caching, spooling, scheduling, and error handling. By providing these in the kernel, device drivers can be simpler and more uniform.

Buffering is the practice of holding data in memory while it is being transferred between a device and a process. Buffers serve several purposes: (1) they decouple producer and consumer speeds (a fast producer can fill a buffer while a slow consumer drains it); (2) they enable batching (many small writes can be coalesced into one large write); (3) they support copy semantics (if a process writes from a buffer and then modifies the buffer before the I/O completes, the OS must copy the data to a kernel buffer to ensure the correct data is written).

/* Buffering in the kernel I/O subsystem */ // Single buffer: data passes through one kernel buffer write(fd, user_buf, len): copy_from_user(kernel_buf, user_buf, len) start_io(kernel_buf, len) // async // Double buffer: one for reading, one for writing // While device reads into buf A, CPU processes buf B // Then swap. Used for streaming I/O (audio, video). // Circular buffer: ring of buffers // Producer fills slots, consumer empties them. // Used for serial I/O, network packets.

Caching is related to buffering but has a different goal: a cache keeps recently used data in memory to avoid re-reading it from the device. The OS maintains a buffer cache (or page cache) for disk blocks: when a block is read, it is stored in the cache; subsequent reads of the same block are served from memory. Writes may be write-through (written to both cache and device) or write-back (written to cache only, flushed to device later). Write-back is faster but risks data loss on crash.

⚠️ Write-Back Caching Risk

With write-back caching, data in the cache may not be on disk for seconds or minutes. If the system crashes, this data is lost. The OS periodically flushes dirty buffers to disk (e.g., every 5 seconds on Linux). File systems with journaling (ext4, NTFS) reduce the risk by writing metadata changes to a journal first, allowing recovery after a crash. Applications can force a flush with fsync().

Spooling is a specialized form of buffering for devices that cannot accept interleaved data streams. The classic example is a printer: if two processes try to print simultaneously, their output would interleave on the page. Instead, each process writes its output to a spool file (a temporary file on disk), and a spooler daemon sends the files to the printer one at a time. Spooling is also used for email (mail spool) and batch processing.

The kernel I/O subsystem also provides device reservation (exclusive access to a device), error reporting (standardized error codes), and I/O scheduling (reordering requests for efficiency, as discussed in Section 11.2). These services make device drivers simpler: a driver only needs to handle device-specific commands, while the kernel handles buffering, caching, and scheduling.

In xv6, the kernel I/O subsystem is minimal but present. The buf structure in kernel/buf.h represents a buffered disk block. The bget() and brelse() functions in kernel/bio.c implement a simple buffer cache: recently accessed blocks are kept in a linked list, and reads check the cache before accessing the disk. This is a simplified version of the buffer cache described by Silberschatz. There is no write-back caching—xv6 writes blocks to disk immediately (write-through), which is simpler but slower.

12.5 Transforming I/O Requests

When an application performs an I/O operation, the request passes through several layers of the I/O subsystem before reaching the hardware. Understanding this I/O request lifecycle is essential for understanding OS I/O performance and debugging.

The typical lifecycle of a read() request is:

/* I/O request lifecycle (read example) */ // 1. Application calls read() read(fd, buf, len): // 2. System call enters kernel syscall_read(fd, buf, len) // 3. VFS resolves fd to file object file = fd_table[fd] // 4. VFS calls file system's read method file->f_op->read(file, buf, len, offset): // 5. File system maps offset to disk block(s) block = inode_block(inode, offset) // 6. File system requests block from I/O subsystem bh = bread(dev, block): // 7. Check buffer cache if (cache_has(block)) return cache[block] // 8. Cache miss: submit to device driver submit_bio(dev, block, READ): // 9. Driver builds device command cmd = build_read_cmd(block) // 10. Driver writes to device registers (or DMA) write_dev_reg(CMD, cmd) // 11. Process sleeps waiting for interrupt sleep_on(&wait_queue) // 12. Device completes, raises interrupt interrupt_handler(): // 13. ISR reads status, wakes process wake_up(&wait_queue) // 14. Data copied from kernel buffer to user space copy_to_user(buf, bh->data, len) // 15. read() returns to application

Each layer adds functionality: the VFS (Virtual File System) provides a uniform interface; the file system translates file offsets to disk blocks; the I/O subsystem provides caching and scheduling; the device driver translates to device-specific commands; and the hardware performs the actual I/O. This layering allows new file systems and devices to be added without changing the application interface.

ℹ️ Layered I/O

The layered I/O architecture is a classic example of separation of concerns. Each layer has a well-defined interface and can be replaced independently. For example, Linux can read ext4, XFS, and FAT file systems through the same VFS, and can access SATA, NVMe, and USB storage through the same block layer. This modularity is essential for supporting the vast diversity of I/O devices.

The write path is similar but may involve additional steps: the data is copied from user space to a kernel buffer, the buffer is marked dirty, and the I/O may be deferred (write-back caching). The fsync() system call forces all dirty buffers for a file to be written to disk, ensuring durability. The sync() system call flushes all dirty buffers system-wide.

In xv6, the I/O request path is simpler but follows the same pattern. A read() system call goes through sysfile.c → file.c → fs.c (which calls bread()) → bio.c (buffer cache) → virtio_disk.c (device driver). The bread() function checks the buffer cache and, on a miss, calls virtio_disk_rw() to read from disk. The driver submits the request and sleeps until the interrupt handler wakes it. This is a clear, teachable example of the layered I/O architecture.

12.6 STREAMS

STREAMS is a mechanism, originating in UNIX System V, for building modular, bidirectional data paths between a process and a device driver. A STREAM is a full-duplex pipeline of modules, each of which performs a specific processing function on the data flowing through it. Modules can be pushed and popped at runtime, allowing flexible configuration of I/O processing.

A STREAM consists of: a stream head (the interface to user space), zero or more modules (processing stages), and a stream end (the device driver). Data flows down the STREAM (write) and up the STREAM (read), passing through each module. Each module has a read queue and a write queue. A module can transform, filter, or buffer data as it passes through.

/* STREAMS architecture */ // Process ↔ Stream Head ↔ Module 1 ↔ Module 2 ↔ Driver write(fd, data): stream_head.write_queue.push(data) // Data flows down through modules: module1.write(data) → module2.write(data) → driver.write(data) read(fd): // Data flows up from driver: driver.read() → module2.read() → module1.read() → stream_head return stream_head.read_queue.pop() // Push a module onto a STREAM ioctl(fd, I_PUSH, "module_name") // Pop a module ioctl(fd, I_POP)

Common STREAMS modules include line discipline modules (handling terminal line editing, echo, etc.), protocol modules (implementing network protocols like TCP/IP), and encryption modules. The modular design allows protocols to be composed: for example, a TCP module can be stacked on an IP module, which is stacked on an Ethernet driver module.

ℹ️ STREAMS in Practice

STREAMS was widely used in System V UNIX and Solaris for networking (the TCP/IP stack was implemented as STREAMS modules). Linux did not adopt STREAMS for its networking stack, preferring a more tightly integrated design (the sk_buff architecture). However, the concept of modular, stackable processing lives on in Linux's netfilter (iptables) framework and in the BPF (Berkeley Packet Filter) programs that can be attached to various points in the networking stack.

The advantage of STREAMS is modularity: new functionality can be added by pushing a module, without modifying the driver or the application. The disadvantage is overhead: each module adds a context switch and data copy, which can be significant for high-speed networking. Modern systems prefer in-kernel, zero-copy architectures for performance-critical paths.

In xv6, there is no STREAMS mechanism. The console driver handles line editing directly in kernel/console.c. There is no networking stack at all. Implementing a STREAMS-like architecture in xv6 would be a significant project but would demonstrate the concept of modular I/O processing. A simpler exercise would be to add a line-discipline module that can be inserted between the console driver and the user process, handling backspace, arrow keys, and command history.

12.7 Performance

I/O performance is often the bottleneck in system performance because I/O devices are orders of magnitude slower than CPUs. The OS employs many techniques to improve I/O performance, and understanding these is crucial for system design and tuning.

The key strategies for improving I/O performance are:

  • Buffering and caching: Keep recently accessed data in memory to avoid re-reading from the device. The buffer cache (or page cache) can satisfy 90%+ of reads from memory for workloads with good locality.
  • Asynchronous I/O: Allow the process to continue executing while I/O is in progress. POSIX aio_read() and aio_write(), or Linux's io_uring, enable this. The process is notified when the I/O completes.
  • I/O scheduling: Reorder I/O requests to minimize seek time (for HDDs) or maximize parallelism (for NVM). See Section 11.2.
  • DMA and zero-copy: Use DMA to transfer data directly between devices and memory, avoiding CPU copies. sendfile() and splice() on Linux enable zero-copy file-to-network transfers.
  • Interrupt coalescing: Instead of raising an interrupt for every I/O completion, the device raises one interrupt for a batch of completions, reducing interrupt overhead.

💡 io_uring: Modern Async I/O

Linux's io_uring (introduced in 2019) is a high-performance async I/O interface that uses shared-memory ring buffers between user space and kernel. It avoids system calls for submission and completion, enabling millions of I/O operations per second. io_uring has become the standard for high-performance I/O in databases, storage engines, and network servers, replacing older interfaces like aio and epoll.

Network I/O performance deserves special attention. Network packets are small and frequent, so the per-packet overhead (interrupt, context switch, copy) can dominate. Techniques to improve network performance include: (1) NAPI (hybrid interrupt/polling), (2) receive-side scaling (RSS, distributing packets across CPU cores), (3) zero-copy (avoiding data copies between kernel and user space), (4) TCP offload (letting the NIC handle TCP segmentation and checksums), and (5) BPF/XDP (executing packet-processing programs in the kernel or even on the NIC).

In xv6, I/O performance is not optimized. The buffer cache (kernel/bio.c) provides basic caching, but there is no async I/O, no I/O scheduling, no zero-copy, and no interrupt coalescing. The virtio disk driver processes one request at a time, sleeping until it completes. This is adequate for a teaching OS but would be far too slow for production. Adding a request queue with batching and async completion would be a valuable exercise in I/O performance optimization.
