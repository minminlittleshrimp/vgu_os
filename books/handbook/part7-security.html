16.1 The Security Problem

Security is the set of mechanisms and policies that protect a computer system's resources—data, programs, CPU, memory, network, and devices—from unauthorized access, modification, or destruction. While protection (Chapter 17) is about internal mechanisms that enforce access rules, security is the broader goal of defending the system against deliberate attacks and accidental threats. The two concepts are deeply intertwined: a system cannot be secure without robust protection mechanisms, and protection mechanisms are designed with security goals in mind.

The security problem arises because computer systems are shared by multiple users and connected to networks. A threat is a potential security violation, and an attack is an actual attempt to breach security. Threats can be categorized as intentional (malicious attacks by hackers, insiders, or nation-states) or accidental (bugs, misconfigurations, human error). The classic security goals are summarized by the CIA triad:

PropertyMeaningExample Threat
ConfidentialityData is accessible only to authorized partiesEavesdropping, data theft
IntegrityData is not modified without authorizationTampering, unauthorized writes
AvailabilitySystem and data are available when neededDenial-of-service (DoS)

An attacker may try to intercept data (read confidential information), modify data (alter files or messages), fabricate data (create fake records), or interrupt service (crash the system). The attacker's goals map directly to violations of the CIA triad. For example, a man-in-the-middle attack violates confidentiality and integrity, while a DDoS attack violates availability.

Security is fundamentally a weakest-link problem: a system is only as secure as its most vulnerable component. A perfectly encrypted network connection is useless if the endpoint has a keylogger. A hardened kernel is irrelevant if users choose weak passwords. This is why security must be defense in depth—multiple layers of protection, so that if one layer fails, others still defend the system.

⚠️ Security Is Never Perfect

No system is 100% secure. The goal is risk management: reducing the probability and impact of attacks to an acceptable level. Security measures always involve trade-offs with convenience, performance, and cost. The most secure computer is one that is turned off, disconnected, and locked in a vault—but it is also completely useless.

In xv6, the security model is minimal but illustrative. The kernel runs in supervisor mode (RISC-V S-mode) and user processes run in user mode (U-mode). The hardware enforces that user processes cannot directly access kernel memory or execute privileged instructions. However, xv6 has no file permissions, no encryption, and no authentication—any user process can read or write any file. This is acceptable for a teaching OS but would be catastrophic in production. Studying xv6 helps you understand the foundation of protection (hardware-enforced privilege levels) upon which real security systems are built.

16.2 Program Threats

Program threats are attacks that exploit vulnerabilities in programs to gain unauthorized access, escalate privileges, or damage data. The most common program threat is malware—malicious software designed to harm or co-opt a system. Malware categories include viruses, worms, Trojan horses, spyware, ransomware, and rootkits. Each has a different propagation mechanism and payload, but all exploit the fact that programs run with the privileges of the user who executes them.

A virus is a program that attaches itself to a legitimate program and replicates by infecting other programs. When the infected program runs, the virus code executes first, spreads to other files, and then (optionally) delivers its payload. Viruses can be boot-sector viruses (infecting the boot sector), file viruses (infecting executables), macro viruses (infecting documents with embedded macros), or polymorphic viruses (mutating their code to evade detection). The key characteristic is self-replication requiring a host program.

A worm, by contrast, is a standalone program that replicates itself across network connections without needing a host file. Famous worms include the Morris worm (1988, one of the first Internet worms), Code Red (2001, exploited IIS buffer overflow), and Stuxnet (2010, targeted Iranian nuclear centrifuges). Worms spread by exploiting network vulnerabilities—buffer overflows, default passwords, or unpatched services—and can infect millions of systems within hours.

ℹ️ Code Injection Attacks

A code injection attack occurs when an attacker provides malicious input that is executed as code by the target program. Common variants include:

  • Buffer overflow: Writing past the end of an array to overwrite return addresses or function pointers, redirecting execution to attacker-controlled code (the classic "stack smashing" attack).
  • SQL injection: Injecting SQL commands through user input fields that are concatenated into database queries.
  • Command injection: Injecting shell commands through input that is passed to system() or similar.
  • Cross-site scripting (XSS): Injecting JavaScript into web pages viewed by other users.

The buffer overflow deserves special attention because it is the most common and dangerous program threat in C/C++ systems. When a program writes more data to a stack buffer than it can hold, the excess data overwrites adjacent memory. If the overwritten region contains the saved return address, the attacker can redirect execution to arbitrary code—often a sequence called shellcode that spawns a shell with the program's privileges.

/* Classic stack-smashing buffer overflow */ // Vulnerable function: no bounds checking void vulnerable(char *input) { char buf[64]; strcpy(buf, input); // overflow if input > 64 bytes! printf("%s\n", buf); } // Attack: input is crafted to overwrite return address // [64 bytes padding][saved ebp][return addr → shellcode] // When vulnerable() returns, CPU jumps to shellcode

Modern defenses against buffer overflows include: stack canaries (compiler-inserted values that detect stack corruption before return), ASLR (Address Space Layout Randomization, which randomizes code and stack addresses), DEP/NX bit (marking stack and heap as non-executable), and stack protectors like -fstack-protector in GCC. In xv6, none of these are implemented—the system trusts all code. This makes xv6 a good platform for understanding the vulnerability, but also a reminder of why production systems need these protections.

A Trojan horse is a program that appears legitimate but contains hidden malicious functionality. For example, a "free game" that also installs a keylogger. Unlike viruses, Trojans do not self-replicate—they rely on social engineering to trick users into running them. Spyware secretly monitors user activity (keystrokes, browsing habits) and reports it to a third party. Ransomware encrypts the victim's files and demands payment for the decryption key—WannaCry (2017) and NotPetya (2017) caused billions in damage worldwide.

💡 Rootkits and Persistence

A rootkit is malware designed to maintain privileged access while hiding its presence. Kernel-mode rootkits modify the kernel itself (e.g., hooking system calls) so that ls, ps, and other tools do not show the malicious process or files. Detecting rootkits often requires comparing the system's view of itself against an external, trusted view (e.g., booting from a clean rescue disk). This is why secure boot and measured boot are important: they establish a chain of trust from firmware to OS.

16.3 System and Network Threats

While program threats target individual applications, system and network threats target the operating system and network infrastructure. These threats exploit weaknesses in system configuration, network protocols, or the sheer interconnectedness of systems. A compromised system can become a stepping stone for attacking other systems, making network security a chain that is only as strong as its weakest link.

Network intrusions occur when an attacker gains unauthorized access to a system over a network. Common intrusion vectors include: exploiting known vulnerabilities in network services (e.g., a vulnerable SSH daemon), brute-forcing weak passwords, exploiting misconfigured services (e.g., an open Samba share), or using port scanning to find exposed services. Once inside, the attacker may install a backdoor for persistent access, escalate privileges to root/admin, and exfiltrate data or pivot to other systems on the network.

Denial-of-service (DoS) attacks aim to make a system unavailable to legitimate users. A flood attack overwhelms the target with more requests than it can handle. A SYN flood exploits the TCP handshake by sending SYN packets without completing the handshake, exhausting the server's connection table. A Distributed DoS (DDoS) uses thousands of compromised machines (a botnet) to amplify the attack. The amplification attack uses services like DNS or NTP that respond with much larger packets than the request, multiplying the attacker's bandwidth.

Attack TypeMechanismMitigation
SYN FloodHalf-open TCP connections exhaust server resourcesSYN cookies, connection rate limiting
DDoS (volumetric)Botnet floods target with trafficCDN, traffic scrubbing, BGP blackholing
AmplificationExploits UDP services that send large responsesDisable UDP services, rate-limit responses

Man-in-the-middleIntercepts and possibly alters trafficTLS/SSL, certificate pinning

Worms are both program threats and network threats: they exploit program vulnerabilities but spread via network connections. The Morris worm (1988) used multiple vectors: a buffer overflow in fingerd, weak passwords, and trust relationships via rsh. It infected roughly 6,000 machines (10% of the Internet at the time) and led to the creation of CERT (Computer Emergency Response Team). Modern worms like Conficker and WannaCry use similar multi-vector strategies, demonstrating that network interconnectedness amplifies the impact of any single vulnerability.

Port scanning is a reconnaissance technique where an attacker probes a range of ports on a target to identify open services. Tools like nmap can fingerprint the OS and service versions, helping the attacker identify known vulnerabilities. Intrusion detection systems (IDS) like Snort or Suricata monitor network traffic for suspicious patterns and alert administrators. Firewalls filter traffic based on rules (allow/deny by IP, port, protocol), reducing the attack surface. A stateful firewall tracks connection state, while a deep packet inspection (DPI) firewall examines packet contents.

ℹ️ The Threat Landscape

Modern threats are often multi-stage: reconnaissance → initial access → privilege escalation → lateral movement → data exfiltration → persistence. This is formalized in frameworks like the MITRE ATT&CK matrix. Defenders use zero-trust architecture (never trust, always verify), network segmentation (limiting lateral movement), and endpoint detection and response (EDR) to detect and contain attacks at each stage.

In the context of xv6, there is no networking stack, so network threats do not apply directly. However, the principle is relevant: xv6's lack of authentication means that if it were networked, any connection would effectively be root access. This illustrates why real operating systems invest heavily in network security—without it, a single exposed port can compromise the entire system.

16.4 Cryptography as a Security Tool

Cryptography is the science of encoding information so that only authorized parties can read it. It is the backbone of modern computer security, enabling confidentiality (encryption), integrity (hashing), authentication (digital signatures), and non-repudiation (proof of origin). The OS uses cryptography for secure communication (TLS), password storage (hashing), disk encryption (full-disk encryption), code signing (verifying executable integrity), and secure boot (verifying firmware).

Symmetric encryption uses the same key for encryption and decryption. It is fast and suitable for bulk data. Common algorithms include AES (Advanced Encryption Standard, 128/192/256-bit keys), ChaCha20, and the older DES/3DES (now deprecated). The challenge with symmetric encryption is key distribution: how do two parties securely share the secret key? This is solved by asymmetric cryptography.

Asymmetric encryption (public-key cryptography) uses a pair of keys: a public key that can be freely shared and a private key that is kept secret. Data encrypted with the public key can only be decrypted with the private key (and vice versa). RSA (Rivest-Shamir-Adleman) and ECC (Elliptic Curve Cryptography) are the most common algorithms. Asymmetric encryption is computationally expensive, so it is typically used to exchange a symmetric session key, which is then used for bulk encryption. This is exactly how TLS works: the handshake uses RSA/ECC to agree on an AES session key, then all subsequent data is encrypted with AES.

/* Simplified TLS 1.3 handshake (conceptual) */ // 1. Client sends supported cipher suites + random number Client → Server: ClientHello(ciphers, client_random) // 2. Server responds with chosen cipher + certificate + random Server → Client: ServerHello(cipher, server_random), Certificate // 3. Client verifies certificate, generates pre-master secret // Encrypts with server's public key (RSA) or uses ECDHE Client → Server: KeyExchange(encrypted_pre_master) // 4. Both derive session key from pre_master + randoms session_key = HKDF(pre_master, client_random, server_random) // 5. All subsequent traffic encrypted with AES-GCM(session_key) Client ↔ Server: ApplicationData(encrypted)

Hash functions produce a fixed-size digest from arbitrary input. A cryptographic hash must be one-way (infeasible to reverse), collision-resistant (infeasible to find two inputs with the same hash), and avalanche (small input change → large output change). Common hashes: SHA-256, SHA-3, BLAKE2/3. Hashes are used for password storage (store hash(password), not the password itself), file integrity (compare hash before and after transfer), and digital signatures (sign the hash, not the full message).

⚠️ Never Store Plaintext Passwords

Storing passwords in plaintext is a critical security failure. Even storing hash(password) is insufficient—attackers can use rainbow tables (precomputed hash databases) or brute-force common passwords. The correct approach is to use a salted, slow hash function like bcrypt, scrypt, or Argon2. These functions are deliberately slow and memory-hard, making brute-force attacks computationally expensive.

Digital signatures combine hashing and asymmetric encryption to provide authentication (proof of identity), integrity (proof the message was not altered), and non-repudiation (the signer cannot deny signing). To sign a message, the sender computes hash(message) and encrypts it with their private key. The recipient decrypts the signature with the sender's public key and compares it to hash(message). If they match, the signature is valid. This is how code signing works: the OS verifies that an executable was signed by a trusted publisher before running it.

Key management is often the hardest part of cryptography. Keys must be generated securely (using a cryptographically secure random number generator), stored safely (hardware security modules, TPMs), distributed securely (PKI, certificate authorities), rotated periodically, and revoked when compromised. A certificate authority (CA) is a trusted third party that issues digital certificates binding public keys to identities. The X.509 certificate format is used in TLS, S/MIME, and code signing. The chain of trust flows from root CAs (pre-installed in the OS/browser) through intermediate CAs to end-entity certificates.

💡 Cryptography in xv6

xv6 has no cryptography—no encryption, no hashing, no authentication. This is a deliberate simplification for a teaching OS. However, the concepts are directly relevant: if you were to add file encryption to xv6, you would need to (1) generate or accept a key, (2) encrypt file blocks with AES, (3) store the key securely (perhaps in a keyring file protected by a password hash), and (4) decrypt on read. Each step involves the cryptographic primitives discussed above.

16.5 User Authentication

Authentication is the process of verifying a user's identity. It is the first line of defense in system security: before granting access to resources, the system must confirm who is requesting access. Authentication is based on one or more of three factors: something you know (password, PIN), something you have (smart card, token, phone), and something you are (biometric: fingerprint, face, iris). Multi-factor authentication (MFA) combines two or more factors, dramatically increasing security.

Passwords remain the most common authentication method despite their weaknesses. A good password should be long, random, and unique per service. In practice, humans choose weak, predictable passwords, reuse them across sites, and write them down. The system stores not the password itself but a hash of the password (ideally salted and slow-hashed). When the user logs in, the system hashes the entered password and compares it to the stored hash. In Linux, this is stored in /etc/shadow (readable only by root), using formats like $6$ (SHA-512 with salt) or $2b$ (bcrypt).

/* /etc/shadow entry format (Linux) */ // username:$algorithm$salt$hash:lastchanged:min:max:warn:inactive:expire alice:$6$$salt$$long_sha512_hash:19000:0:99999:7::: // $6$ = SHA-512, $2b$ = bcrypt, $y$ = yescrypt // salt is random, prevents rainbow table attacks // hash is computed as: hash = SHA512(salt + password), iterated

Password cracking techniques include dictionary attacks (trying common passwords and variations), brute-force (trying all possible combinations), rainbow tables (precomputed hash chains), and credential stuffing (reusing passwords leaked from other breaches). Defenses include rate limiting (lockout after N failed attempts), password complexity rules, password managers (generating and storing strong, unique passwords), and passwordless authentication (WebAuthn, passkeys) that replaces passwords with cryptographic keys stored on a device.

One-time passwords (OTP) generate a new password for each login, defeating replay attacks. TOTP (Time-based OTP, RFC 6238) generates codes from a shared secret and the current time—this is what Google Authenticator and similar apps use. HOTP (HMAC-based OTP, RFC 4226) uses a counter instead of time. Hardware tokens like YubiKey implement FIDO U2F or FIDO2/WebAuthn, using public-key cryptography: the token signs a challenge with a private key that never leaves the device. This is resistant to phishing because the signature is bound to the origin domain.

MethodFactorStrengthsWeaknesses
PasswordSomething you knowSimple, no hardwareWeak, reused, phishable
SMS OTPSomething you haveWidely availableSIM swap, interception
TOTP (Authenticator app)Something you haveNo SMS neededPhishable (code can be relayed)
Hardware key (FIDO2)Something you havePhishing-resistantCost, availability
BiometricSomething you areConvenient, no memorizationCannot be changed if stolen

Biometric authentication uses physiological or behavioral characteristics: fingerprints, facial recognition, iris scans, voice, or typing patterns. Biometrics are convenient (no password to remember) but have unique risks: they cannot be changed if compromised, they can have false positives/negatives, and they raise privacy concerns. Modern systems like Windows Hello and Touch ID store biometric templates locally (not raw biometric data) and use them to unlock a cryptographic key, combining the convenience of biometrics with the security of hardware-backed keys.

ℹ️ Authentication vs. Authorization

Authentication answers "who are you?" while authorization answers "what are you allowed to do?" A user may authenticate successfully but still be denied access to a file (authorization). In xv6, there is no authentication (anyone can log in as any user) and no authorization (any user can access any file). Real systems combine both: authenticate the user, then check their permissions (see Chapter 17 on access control).

16.6 Implementing Security Defenses

Securing an operating system requires a layered, defense-in-depth approach. No single mechanism is sufficient; instead, multiple independent controls must work together so that the failure of one does not compromise the system. The key categories of defense are: prevention (stopping attacks before they succeed), detection (identifying attacks in progress or after the fact), and response (containing and recovering from attacks).

Security policies define what is allowed and what is prohibited. A policy might state: "only the database service may access the customer database; all other network connections to port 5432 are denied." Policies are implemented through mechanisms: firewalls (network-level), access control lists (file-level), and application sandboxing (process-level). The principle of least privilege states that every process, user, or program should have only the minimum privileges needed to perform its function—and no more.

Firewalls are a primary network defense. A packet-filtering firewall examines each packet's source/destination IP, port, and protocol, applying allow/deny rules. A stateful firewall tracks connection state (e.g., allowing return traffic for an established connection). A proxy firewall (application-level gateway) terminates the connection and re-originates it, inspecting application-layer data. Next-generation firewalls (NGFW) combine these with intrusion prevention, deep packet inspection, and threat intelligence feeds.

/* Example firewall rules (iptables-style) */ // Allow established connections iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT // Allow SSH from trusted subnet only iptables -A INPUT -s 10.0.0.0/24 -p tcp --dport 22 -j ACCEPT // Allow HTTP/HTTPS from anywhere iptables -A INPUT -p tcp --dport 80 -j ACCEPT iptables -A INPUT -p tcp --dport 443 -j ACCEPT // Drop everything else iptables -A INPUT -j DROP iptables -P INPUT DROP // default deny

Intrusion detection complements firewalls by detecting attacks that bypass perimeter defenses. A host-based IDS (HIDS) monitors system logs, file integrity, and process behavior on a single host. A network-based IDS (NIDS) inspects network traffic for attack signatures or anomalies. SIEM (Security Information and Event Management) systems aggregate logs from across the organization and use correlation rules and machine learning to detect sophisticated attacks.

Sandboxing restricts what a program can do, limiting the damage if it is compromised. Examples include: chroot (changes the apparent root directory), seccomp (filters system calls), AppArmor/SELinux (mandatory access control), containers (namespace + cgroup isolation), and virtual machines (full hardware-level isolation). Browsers sandbox each tab in a separate process with restricted privileges, so a compromised tab cannot access the user's files or other tabs.

💡 Defense in Depth Layers

A well-defended system has multiple independent layers:

  1. Network perimeter: Firewall, DDoS protection, VPN
  2. Host hardening: Patching, disabling unused services, host firewall
  3. Access control: Authentication, authorization, least privilege
  4. Application security: Input validation, ASLR, DEP, stack canaries
  5. Data protection: Encryption at rest, encryption in transit
  6. Monitoring: IDS, SIEM, audit logging
  7. Response: Incident response plan, backups, disaster recovery

Each layer must be independently effective. If an attacker breaches one layer, the next layer should still stop them.

Patching and vulnerability management are critical. New vulnerabilities are discovered constantly—CVE (Common Vulnerabilities and Exposures) entries document known issues. The CVSS (Common Vulnerability Scoring System) rates severity. Systems must be patched promptly, but patching can introduce regressions, so organizations balance speed with testing. Zero-day vulnerabilities (unknown to the vendor) cannot be patched and are especially dangerous—defense in depth is the only mitigation until a patch is available.

Audit logging records security-relevant events: logins (successful and failed), privilege escalations, file access, configuration changes, and policy violations. Logs must be tamper-resistant (an attacker who compromises the system should not be able to erase their tracks) and retained for forensic analysis. In Linux, auditd provides detailed auditing; in Windows, the Event Log and Sysmon serve similar purposes. The challenge is volume: a busy system generates gigabytes of logs, requiring automated analysis to find the signal in the noise.

16.7 Windows 10 Example

Windows 10 (and its successors Windows 11) implements a comprehensive security architecture that illustrates many of the concepts in this chapter. Microsoft adopted a security development lifecycle (SDL) in the early 2000s after repeated vulnerabilities in Windows XP and earlier. The SDL mandates threat modeling, secure coding practices, fuzzing, and security testing throughout the development process.

Windows security fundamentals include: user accounts with distinct Security Identifiers (SIDs), access tokens that encode the user's identity and group memberships, security descriptors on securable objects (files, registry keys, processes), and privileges that grant specific capabilities (e.g., SeDebugPrivilege allows inspecting other processes). The Local Security Authority (LSA) manages authentication, and the Security Reference Monitor (SRM) enforces access checks in the kernel.

User Account Control (UAC) is a key Windows security feature introduced in Windows Vista. Even administrators run with standard user privileges by default; when an action requires elevation, UAC prompts the user to confirm. This reduces the impact of malware: even if a malicious program runs, it cannot modify system files or install services without the user explicitly consenting. UAC is an application of the principle of least privilege—administrators do not need admin powers for most tasks.

ℹ️ Windows Access Control Model

Every securable object in Windows has a security descriptor containing:

  • Owner SID: who owns the object (can change permissions)
  • DACL (Discretionary ACL): who is allowed/denied access
  • SACL (System ACL): what access attempts to audit

When a thread accesses an object, the SRM checks the thread's access token against the DACL. If an explicit deny entry matches, access is denied. If an allow entry matches and grants the requested access, access is granted. If no entry matches, access is denied by default.

Windows Defender (now Microsoft Defender) provides built-in antivirus, anti-malware, and endpoint detection and response (EDR). It uses signature-based detection, heuristic analysis, behavioral monitoring, and cloud-delivered protection. Controlled Folder Access (ransomware protection) restricts which applications can modify files in protected folders. Exploit Protection enables DEP, ASLR, and other mitigations per application, even for legacy software that was not compiled with them.

BitLocker is Windows' full-disk encryption feature. It encrypts the entire system volume using AES, protecting data at rest if the device is lost or stolen. BitLocker can use a TPM (Trusted Platform Module) to verify boot integrity (measured boot): the TPM records measurements of boot components, and if the measurements have changed (e.g., due to a bootkit), the TPM refuses to release the encryption key. This ties disk encryption to hardware-level boot security.

Windows Hello provides passwordless authentication using biometrics (facial recognition, fingerprint) or a PIN. The biometric data is processed locally and never leaves the device. Windows Hello for Business uses certificate-based authentication, eliminating passwords entirely for domain login. Credential Guard isolates the LSA in a virtualization-based security (VBS) container, protecting credentials from pass-the-hash and pass-the-ticket attacks even if the kernel is compromised.

💡 Comparing Windows and xv6 Security

Windows 10 represents the state of the art in commercial OS security, while xv6 represents the bare minimum. The contrast is instructive: xv6 has no authentication, no access control, no encryption, and no auditing. Windows has all of these plus UAC, Defender, BitLocker, Secure Boot, and Credential Guard. The gap between them illustrates how much real-world security engineering goes into a production operating system—and why studying xv6 (which exposes the raw mechanisms) helps you appreciate what those features are built upon.

17.1 Goals of Protection

While security (Chapter 16) is about defending against external threats, protection is about the internal mechanisms that enforce rules governing how processes access resources. Protection ensures that programs behave according to a defined policy, preventing accidental or intentional misuse of resources. The goal is not to prevent all errors (impossible) but to ensure that when errors or attacks occur, their blast radius is limited.

The primary goals of protection are: (1) isolation—preventing processes from interfering with each other's memory, files, or execution; (2) controlled sharing—allowing processes to share resources when authorized, but only when authorized; (3) least privilege—granting each process only the privileges it needs; and (4) accountability—ensuring that actions can be attributed to the responsible principal (user or process).

Protection mechanisms are the foundation upon which security is built. Without hardware-enforced memory protection (user/kernel mode, page tables, privilege levels), no amount of software can make a system secure. The hardware provides the mechanism; the OS provides the policy. This separation of mechanism and policy is a fundamental OS design principle: mechanisms should be general and flexible, while policies should be specific and adaptable.

ℹ️ Mechanism vs. Policy

Mechanism = how to enforce rules (e.g., page tables, privilege levels, access control lists). Policy = what rules to enforce (e.g., "only root can read /etc/shadow"). Good OS design separates the two: the mechanism should support any reasonable policy, and the policy should be changeable without rewriting the mechanism. In xv6, the hardware (RISC-V privilege levels) is the mechanism; the kernel's code that checks permissions (minimal in xv6) is the policy.

Protection is also about fault containment. If one process crashes or misbehaves, protection ensures that other processes are unaffected. This is why modern OSes give each process its own address space: a bug in your browser cannot corrupt the memory of your text editor. Without this isolation, a single buggy program could crash the entire system—as was common in early single-address-space systems like MS-DOS.

In xv6, the fundamental protection mechanism is the hardware privilege levels. RISC-V has three modes: U-mode (user), S-mode (supervisor, where xv6 kernel runs), and M-mode (machine, for firmware). User processes run in U-mode and cannot execute privileged instructions or access kernel memory. The sstatus register's SPP bit tracks the previous privilege level, and the satp register (only accessible in S-mode) controls page tables. This hardware foundation is what makes protection possible.

17.2 Principles of Protection

The principle of least privilege is the cornerstone of protection design: every program, process, and user should operate with the minimum set of privileges needed to accomplish its task, and no more. This limits the damage from bugs, misconfiguration, and attacks. If a web server runs with only the privileges needed to serve web pages, a compromise cannot spread to the rest of the system.

Least privilege is implemented through privilege separation: splitting a system into components with different privilege levels. For example, a web server might run as a low-privilege user, while a separate privileged helper process handles tasks that require elevated permissions (like binding to port 80). The helper validates each request, reducing the attack surface of the privileged component. Privilege dropping is a related technique: a program starts with elevated privileges, performs the privileged operations it needs, then permanently drops those privileges before handling untrusted input.

/* Privilege dropping pattern (C, Unix-like) */ int main() { // 1. Start as root (e.g., to bind port 80) int fd = bind_port(80); // 2. Drop to unprivileged user setgid(UNPRIV_GID); setuid(UNPRIV_UID); // 3. Now running as unprivileged user // Even if exploited, attacker has no root serve(fd); }

The need-to-know principle extends least privilege to information access: a process should only have access to the information it needs to perform its function. A payroll system needs access to salary data but not to source code repositories. This principle motivates compartmentalization: dividing information and resources into compartments, with strict access controls between them.

The principle of separation of privilege states that a system should not grant access based on a single condition. For example, two-person control requires two authorized users to approve a sensitive action. In software, this means requiring multiple independent checks (e.g., authentication and authorization and audit logging) rather than relying on any single one.

⚠️ The Confused Deputy Problem

A confused deputy is a privileged program that is tricked by an unprivileged caller into misusing its privileges. The classic example: a compiler with write access to a system log file is tricked by a malicious user into writing to /etc/passwd instead. The solution is capability-based security (Section 17.10): pass the specific capability (file descriptor) the caller is authorized to use, rather than letting the deputy open files by name.

The principle of complete mediation requires that every access to every resource be checked against the access control policy—not just the first time. A common mistake is to check permissions once and cache the result; if permissions change between checks, the cached result is stale. Complete mediation is expensive (checking on every access) but necessary for correctness. Capability systems make this efficient: holding a capability is the authorization, so no separate check is needed.

17.3 Protection Rings

Protection rings are a hardware-enforced privilege hierarchy introduced by Multics and later adopted (in simplified form) by x86 and other architectures. The idea is to organize privilege levels into concentric rings, where inner rings have more privilege than outer rings. The most privileged code (the kernel) runs in ring 0, and user programs run in ring 3. Intermediate rings (1, 2) can be used for device drivers or system services, though most modern OSes only use rings 0 and 3.

RingTypical UsePrivileges
Ring 0KernelFull hardware access
Ring 1Device drivers (rarely used)I/O, some system calls
Ring 2System services (rarely used)Limited I/O
Ring 3User applicationsNo direct hardware access

On x86, the Current Privilege Level (CPL) is stored in the CS register (2 bits, giving 4 rings). When code in ring 3 attempts a privileged operation (e.g., executing hlt, accessing an I/O port, or writing to a page marked supervisor-only), the CPU raises a general protection fault. The transition from ring 3 to ring 0 happens through gates: system call gates, interrupt gates, or (on modern x86) the SYSCALL/SYSRET instructions, which atomically switch privilege level and jump to a kernel entry point.

RISC-V uses a simpler model: U-mode (user), S-mode (supervisor), and M-mode (machine). There are no intermediate rings. xv6 runs its kernel in S-mode and user processes in U-mode. The sstatus register's SPP bit records the previous mode, and the scause register indicates the trap cause. The ecall instruction triggers an environment call (system call) that transitions from U-mode to S-mode.

/* RISC-V privilege levels and xv6 */ // M-mode: Machine mode (firmware, SBI) — highest privilege // S-mode: Supervisor mode (xv6 kernel) — can access satp, sstatus // U-mode: User mode (xv6 processes) — restricted // User → Kernel transition (system call): user_code: li a7, 64 // syscall number (SYS_write) ecall // trap to S-mode // Kernel entry point (trampoline): uservec: csrr a0, scause // read trap cause // ... save user registers, switch to kernel stack ... call usertrap // dispatch to C handler

The hypervisor ring (sometimes called "ring -1") extends the ring model for virtualization. A hypervisor runs at a privilege level below ring 0, managing multiple guest operating systems that each think they have ring 0. On x86, this is implemented with VMX root (hypervisor) and VMX non-root (guest) modes, controlled by Intel VT-x or AMD-V extensions. RISC-V has the H-extension for the same purpose. This is covered in more detail in Chapter 18 (Virtual Machines).

💡 Why Only Two Rings in Practice?

Although x86 supports 4 rings, Linux and Windows only use rings 0 and 3. The intermediate rings (1, 2) were intended for device drivers and system services, but experience showed that the complexity of managing multiple privilege levels outweighed the benefit. Instead, modern OSes put drivers in ring 0 (kernel space) or in ring 3 (user space, via frameworks like Linux's VFIO or Windows' User-Mode Driver Framework). The trend is toward more code in user space, not more rings.

17.4 Domain of Protection

A protection domain is the set of resources (memory, files, devices, capabilities) that a process (or a component within a process) is authorized to access. The concept of a domain generalizes the idea of a user or a privilege level: a domain is an execution context with a specific set of access rights. A process may execute in different domains at different times—for example, switching from a user domain to a kernel domain when making a system call.

In its simplest form, a domain corresponds to a user identity: all processes running as user "alice" share the same access rights. This is the model used by traditional Unix: each process has a UID (user ID), GID (group ID), and supplementary groups, and file permissions are checked against these. However, this model is coarse: all of alice's processes have the same rights, even if they perform very different functions.

A more fine-grained model associates a domain with a process or even a thread. Each process has its own address space (memory protection) and its own set of open file descriptors. In xv6, each process has its own page table, so processes cannot access each other's memory. The kernel is a separate domain with access to all physical memory. When a process makes a system call, it temporarily enters the kernel domain, performs the requested operation (with kernel privileges), and returns to the user domain.

ℹ️ Domain Switching

A domain switch occurs when execution moves from one protection domain to another. The most common example is a system call: user process (domain A) → kernel (domain B) → back to user process (domain A). The hardware ensures that this transition is controlled: you cannot jump directly into the middle of kernel code; you must enter through a defined entry point (trap vector) that saves state and sets up the kernel stack. In xv6, the trampoline page handles this transition.

Capability-based addressing is an alternative to traditional addressing where a memory reference is not a raw address but a capability—a token that both names the object and carries the rights to access it. In a capability system, you cannot access an object unless you hold a capability for it. This makes protection automatic: the hardware checks the capability on every access. The classic capability-based systems (Hydra, CAP—see Section 17.10) demonstrated this approach, though it has not been widely adopted in mainstream hardware.

The principle of context-dependent access recognizes that access rights may depend on the context of execution. For example, a process may have the right to read a file when running normally, but not when running in a debugger. Or a process may have different rights depending on which network interface it is using. This is implemented through security contexts that can be switched at well-defined points, such as entering a sandbox or connecting to a network.

In modern systems, namespaces (Linux) and job objects (Windows) provide a form of domain isolation: processes in different namespaces see different sets of resources (different process IDs, network interfaces, mount points). Containers combine namespaces with cgroups (resource limits) to create lightweight isolated environments. This is a software-level implementation of the domain concept, built on top of the hardware's privilege levels.

17.5 Access Matrix

The access matrix is an abstract model of protection that captures the relationships between domains (subjects), objects (resources), and rights (permissions). The matrix has domains as rows, objects as columns, and access rights as entries. The entry M[i][j] lists the rights that domain i has on object j. This model is general enough to express most protection policies.

File F1File F2PrinterProcess P1
Domain D1 (alice)read, writereadprint—
Domain D2 (bob)readread, write—signal
Domain D3 (root)read, write, ownread, write, ownprint, ownsignal, kill, own

The access rights in the matrix can include: read (examine the object), write (modify the object), execute (run the object if it is a program), append (add data but not modify existing), own (the owner can grant or revoke rights to others), and control (can modify the rights of other domains on this object). The own right is special: it allows the holder to change the access rights of other domains on that object, enabling discretionary access control.

The access matrix is a conceptual model, not a practical implementation. A real system with thousands of users and millions of files would have an enormous, mostly empty matrix. Instead, the matrix is decomposed into more efficient structures (Section 17.6). However, the matrix is valuable as a specification: any protection policy that can be expressed as an access matrix can be implemented, and the matrix provides a framework for reasoning about protection.

ℹ️ Rights as Capabilities and ACLs

The access matrix can be decomposed in two ways:

  • By row (access control lists): For each object, store the list of domains and their rights. This is the ACL approach used by Windows and (optionally) Linux.
  • By column (capability lists): For each domain, store the list of objects and the rights held. This is the capability approach.

Both are valid decompositions of the same matrix; they differ in efficiency and semantics for specific operations.

The access matrix also supports the concept of copy rights and transfer rights. A copy right (often denoted *) allows a domain to copy its access right to another domain. A transfer right allows a domain to transfer (move) its right to another domain, losing it itself. These rights control how access propagates through the system, which is critical for maintaining the integrity of the protection policy.

In xv6, there is no access matrix—there are no file permissions at all. Every process can read and write every file. This makes xv6 unsuitable for multi-user scenarios but keeps the code simple for teaching. The concept of the access matrix is still relevant: if you were to add permissions to xv6, you would need to decide whether to use ACLs (per-file lists of allowed UIDs) or capabilities (per-process lists of accessible files), and how to store and check them efficiently.

17.6 Implementation of Access Matrix

Since the full access matrix is too large to store directly, real systems decompose it into one of two structures: access control lists (ACLs) (column-wise decomposition) or capability lists (row-wise decomposition). Each has trade-offs in efficiency, expressiveness, and ease of management.

Access Control Lists (ACLs) associate with each object a list of (domain, rights) pairs. When a domain attempts to access an object, the system checks the object's ACL for an entry matching the domain and the requested right. ACLs are used by Windows (security descriptors with DACLs) and, in extended form, by Linux (POSIX ACLs in addition to the traditional owner/group/other model).

/* Unix file permissions (simplified ACL) */ // Traditional Unix: 3 classes × 3 bits = 9 permission bits // owner | group | other // rwx | rwx | rwx $ ls -l /etc/passwd -rw-r--r-- 1 root root ... /etc/passwd // owner(root): rw-, group(root): r--, other: r-- // POSIX ACL (extended): more granular per-user/group entries // getfacl /etc/passwd // user::rw- // user:alice:r-- ← specific user grant // group::r-- // other::r--

ACLs are efficient for answering "who can access this object?" (just read the ACL) but inefficient for "what can this domain access?" (must scan all objects). They make revocation easy (just edit the ACL) but make it hard to enumerate all of a user's permissions. ACLs are the natural choice when objects are the primary unit of management (e.g., file systems).

Capability lists associate with each domain a list of (object, rights) pairs—essentially, a list of capabilities the domain holds. A capability is a token that both names an object and confers specific rights on it. To access an object, a domain must present a valid capability. Capabilities are efficient for answering "what can this domain access?" (just read the capability list) but inefficient for "who can access this object?" (must scan all domains). They make delegation easy (pass the capability) but make revocation harder (must find and invalidate all copies of the capability).

In practice, file descriptors are capabilities. When a process opens a file, it receives a file descriptor—a small integer that serves as a capability for that file with specific rights (read, write). The process can pass this descriptor to child processes (via fork or Unix domain sockets), delegating access. The kernel checks the capability (file descriptor) on each read/write, not the original path or permissions. This is a form of capability-based protection embedded within an ACL-based system.

💡 xv6 File Descriptors as Capabilities

In xv6, file descriptors are implemented as indices into a per-process file table (proc->ofile[]). Each entry points to a struct file that tracks the file, the offset, and the mode (readable/writable). When a process calls read(fd, buf, n), the kernel uses fd to look up the struct file and checks the mode. The process cannot access a file it has not opened—this is capability-based protection, even though xv6 has no file permissions. The capability (file descriptor) is the authorization.

Lock-and-key is a hybrid approach combining aspects of ACLs and capabilities. Each object has a unique lock (a bit pattern), and each domain has a set of keys. A domain can access an object if it holds a key matching the object's lock. This model is rarely used directly but appears in some forms of capability hardware and in memory keys (where each memory page has an associated key, and the CPU checks the key on access).

17.7 Revocation of Access Rights

Revocation is the process of withdrawing a previously granted access right. It is essential for security: when an employee leaves, a password is compromised, or a policy changes, the system must be able to remove access. The difficulty of revocation depends on the protection model: in ACL-based systems, revocation is straightforward (edit the ACL); in capability-based systems, it is harder (find and invalidate all copies of the capability).

The key requirements for revocation are: immediacy (the revocation should take effect quickly, ideally immediately), completeness** (all copies of the right should be revoked, not just some), and selectivity (it should be possible to revoke a right from one domain without affecting others). These requirements can conflict: immediate, complete revocation is easy with ACLs but hard with capabilities; selective revocation is easy with ACLs but may require indirection with capabilities.

In ACL-based systems, revocation is simple: remove the entry from the object's ACL. The next access check will fail. However, there is a subtlety: if a process has already opened a file (holding a file descriptor/capability), revoking the ACL entry does not close the file descriptor. The process can continue to use the open descriptor until it closes it or exits. To achieve immediate revocation, the system must also invalidate open descriptors—this is rarely done in practice, creating a window where revoked users retain access.

⚠️ The Open File Descriptor Problem

When you revoke a user's read permission on a file, any file descriptors they already have open for that file remain valid. The user can continue reading until they close the descriptor. This is a fundamental limitation of capability-based access (file descriptors are capabilities). Some systems provide a revoke system call that forces all open descriptors to a file to be closed, but this is rarely implemented and can cause application crashes.

In capability-based systems, revocation is harder because capabilities can be copied and passed around. The standard solution is indirection: instead of giving a domain a direct capability for an object, give it a capability for an indirection object (sometimes called a "capability locker" or "revoke capability"). The indirection object points to the real object. To revoke, the owner changes the indirection object to point nowhere (or to a different object). All holders of the indirection capability lose access simultaneously.

Back-pointers are another approach: each object maintains a list of all domains that hold capabilities for it. To revoke, the system traverses this list and invalidates each capability. This is expensive in space (the back-pointer lists can be large) and time (traversal is O(n)), but it provides complete, immediate revocation. Few systems implement this due to the overhead.

Time-limited capabilities (or expiring capabilities) are a proactive approach: capabilities include an expiration time, after which they are automatically invalid. The holder must periodically renew the capability, and if the owner stops renewing, access is revoked. This is used in systems like Kerberos (where tickets expire) and in some distributed capability systems. The trade-off is that renewal adds overhead and that there is a window (until expiration) during which a revoked capability remains valid.

ℹ️ Revocation in Practice

In Linux, revoking a user's access typically involves: (1) changing file permissions or ownership (chmod, chown), (2) killing the user's processes (pkill -u username), and (3) disabling the account (usermod -L or passwd -l). Step 2 is necessary because open file descriptors remain valid after permission changes. In Windows, revoking access from a user involves modifying the DACL on each object and, if necessary, terminating the user's processes.

17.8 Role-Based Access Control

Role-Based Access Control (RBAC) is a protection model that associates access rights with roles rather than individual users. Users are assigned to roles, and roles are granted permissions. This indirection simplifies administration: instead of managing permissions for each user individually, administrators manage roles, and users inherit permissions from their roles. When a user's job changes, the administrator changes their role assignment, not dozens of individual permissions.

For example, in a hospital system, roles might include doctor, nurse, pharmacist, and administrator. A doctor role might have permission to read and write patient records, prescribe medication, and order tests. A nurse role might have read access to records and permission to administer medication but not to prescribe. When a new doctor joins, they are assigned the doctor role and immediately have all the appropriate permissions—no need to configure each permission individually.

RolePermissionsExample Users

RBAC supports role hierarchies: a senior role can inherit the permissions of a junior role. For example, a senior developer role might inherit all developer permissions and add the ability to approve pull requests and deploy to production. This reduces redundancy: the senior role does not need to re-list all developer permissions; it simply inherits them and adds its own.

RBAC also supports constraints that enforce separation of duties. For example, a constraint might state that no user can hold both the requester and approver roles for the same transaction. This prevents a single user from both requesting and approving a purchase, reducing fraud. Cardinality constraints limit how many users can hold a role (e.g., at most 2 users can be super-admin). Prerequisite roles require a user to hold one role before being assigned another (e.g., must be employee before being manager).

ℹ️ RBAC vs. DAC vs. MAC

There are three major access control models:

  • DAC (Discretionary Access Control): The owner of an object decides who can access it (e.g., Unix file permissions, Windows ACLs). Flexible but can lead to inconsistent policies.
  • MAC (Mandatory Access Control): The system enforces a central policy that users cannot override (e.g., SELinux, classified data handling). Secure but inflexible.
  • RBAC (Role-Based Access Control): Access is granted through roles, combining the flexibility of DAC with the central management of MAC. Most common in enterprise systems.

In Linux, RBAC is implemented through groups (users belong to groups, and file permissions include group rights) and through frameworks like sudo (which grants specific commands to specific users or groups). More sophisticated RBAC is provided by SELinux roles and AppArmor profiles. In Windows, RBAC is implemented through security groups and role assignments in Active Directory, where group membership determines access to resources.

The NIST RBAC standard (INCITS 359) defines four levels of increasing complexity: flat RBAC (basic user-role-permission), hierarchical RBAC (role inheritance), constrained RBAC (separation of duties), and symmetric RBAC (permission review). Most real-world systems implement at least hierarchical RBAC, and enterprise systems often implement constrained RBAC for compliance.

17.9 Mandatory Access Control

Mandatory Access Control (MAC) is a protection model where access decisions are enforced by the system based on a central policy, not by the discretion of individual users. Unlike DAC, where a file owner can grant access to anyone, MAC policies cannot be overridden by users. This makes MAC suitable for environments with strict security requirements: military systems, government classified data, healthcare (HIPAA), and financial systems (PCI-DSS).

The classic MAC model is Bell-LaPadula, designed for military multi-level security. It assigns each subject (process) and object (file) a security level: Unclassified < Confidential < Secret < Top Secret. The rules are:

  • No read up (simple security): A subject can only read objects at or below its security level. A Secret process cannot read a Top Secret file.
  • No write down (*-property): A subject can only write to objects at or above its security level. A Top Secret process cannot write to a Secret file (to prevent leaking classified information downward).
/* Bell-LaPadula rules */ // Security levels: U < C < S < TS // Rule 1: No Read Up (Simple Security) // subject_level >= object_level → read allowed // subject_level < object_level → read DENIED // Rule 2: No Write Down (*-Property) // subject_level <= object_level → write allowed // subject_level > object_level → write DENIED // Result: information can flow UP but never DOWN // This protects confidentiality but not integrity

The dual of Bell-LaPadula is Biba, which protects integrity rather than confidentiality. Biba's rules are the mirror image: no read down (a high-integrity process cannot read low-integrity data, which might be corrupted) and no write up (a low-integrity process cannot write to high-integrity data, which would corrupt it). Together, Bell-LaPadula and Biba can protect both confidentiality and integrity, though combining them is restrictive.

⚠️ The Conflict Between Confidentiality and Integrity

Bell-LaPadula (confidentiality) says "no write down" (information flows up). Biba (integrity) says "no write up" (information flows down). If you apply both simultaneously, information can only flow between subjects and objects at the same level—making the system nearly unusable. Real systems that need both use more nuanced models, such as Clark-Wilson (which focuses on well-formed transactions and separation of duties) or Type Enforcement (which assigns types to subjects and objects and specifies allowed interactions in a matrix).

In Linux, MAC is implemented by SELinux (Security-Enhanced Linux), developed by the NSA. SELinux uses type enforcement: every subject (process) and object (file, socket, etc.) has a type, and a policy specifies which subject-object-type combinations are allowed. For example, a policy might state that httpd_t (the Apache process type) can read httpd_sys_content_t (web content files) but cannot read shadow_t (password hashes). Even if Apache is compromised, it cannot read /etc/shadow because the SELinux policy forbids it—regardless of Unix file permissions.

/* SELinux policy example (type enforcement) */ // Allow httpd to read web content allow httpd_t httpd_sys_content_t:file { read getattr }; // Deny httpd access to shadow passwords (implicit deny) // No allow rule → access denied, even if Unix perms allow it // Allow httpd to connect to network allow httpd_t http_port_t:tcp_socket { name_connect }; // Check status: getenforce → Enforcing / Permissive / Disabled

AppArmor is an alternative MAC system used in Ubuntu and SUSE. Unlike SELinux (which labels objects by type), AppArmor uses path-based profiles: a profile specifies which file paths a program can access and with what permissions. AppArmor is simpler to configure than SELinux but less expressive. Both are examples of MAC: the policy is enforced by the kernel and cannot be overridden by users.

Comparison with xv6: xv6 has no MAC (or DAC, or RBAC). All processes have full access to all files. Adding MAC to xv6 would require: (1) assigning security labels to processes and files, (2) checking labels on every file access in the kernel (in sys_open, sys_read, sys_write), and (3) defining a policy (which labels can access which). This would be a significant but instructive extension to the teaching OS.

17.10 Capability-Based Systems

A capability is a token that both names a resource and confers specific access rights to it. Unlike an ACL entry (which is checked separately from the access), a capability is the authorization: holding the capability is sufficient to access the resource. This eliminates the confused deputy problem (Section 17.2) because the caller passes the specific capability they are authorized to use, and the callee cannot use capabilities the caller did not provide.

Capabilities can be implemented in software or hardware. Software capabilities are typically unforgeable tokens managed by the kernel. The kernel ensures that user processes cannot create or modify capabilities—only receive them through legitimate channels (e.g., opening a file, receiving a message). File descriptors are the most common example: a file descriptor is a capability for an open file, and the kernel ensures processes cannot forge file descriptors.

/* File descriptors as capabilities */ // Opening a file creates a capability int fd = open("/tmp/data", O_RDONLY); // fd is a capability: names the file, confers read right // Using the capability (no separate permission check) read(fd, buf, 1024); // kernel checks fd is valid + readable // Passing the capability to a child process if (fork() == 0) { // Child inherits fd — can read /tmp/data read(fd, buf, 1024); } // Cannot access a file without a capability // No fd → no access, even if path is known

The Hydra operating system (1970s, Carnegie Mellon) was a pioneering capability-based system. In Hydra, every resource is an object, and access to objects is mediated by capabilities. Capabilities are stored in a capability list associated with each protection domain. Hydra introduced the concept of rights amplification: a procedure can be given a capability that grants more rights than the caller has, but only for the duration of the call and only through a verified code path. This allows trusted procedures to perform privileged operations on behalf of untrusted callers without giving the callers the underlying privileges.

The CAP computer (Cambridge, 1970s) implemented capabilities in hardware. The CPU had special capability registers, and memory access required a valid capability in a register. Capabilities were tagged in memory (using a tag bit) so they could not be forged by user programs. The CAP system demonstrated that hardware capability support could provide fine-grained, efficient protection, but the hardware complexity limited its adoption.

ℹ️ Modern Capability Systems

While pure capability hardware is rare, capabilities appear in many modern systems:

  • File descriptors (Unix): capabilities for open files, sockets, pipes
  • SeL4: a formally verified microkernel that uses capabilities for all resource access—every kernel operation requires a capability
  • WebAssembly (WASM): capabilities for memory, tables, and functions
  • Android: intents and content providers use capability-like tokens for inter-app communication
  • Cloud: API tokens and IAM roles are capability-like

The seL4 microkernel is a modern example of a capability-based system. seL4 is formally verified: mathematical proofs guarantee that the kernel implementation matches its specification, and that the specification enforces the intended security properties. All access in seL4 is mediated by capabilities: to send a message, you need a capability for the endpoint; to map memory, you need a capability for the frame. This makes seL4 one of the most secure general-purpose kernels ever built.

Capability-based addressing extends the capability concept to memory. Instead of addressing memory by virtual address, a program addresses memory by capability: a (capability, offset) pair. The hardware checks the capability on each access, ensuring that the program can only access memory for which it holds valid capabilities. This provides fine-grained memory protection without page tables. The Plessey System 250 and the Intel iAPX 432 experimented with this approach, but it was too complex and slow for mainstream adoption.

💡 Capabilities vs. ACLs: The Confused Deputy

The confused deputy problem (Section 17.2) illustrates the key advantage of capabilities. A compiler (the deputy) has write access to a log file. A malicious user asks the compiler to compile a file named /etc/passwd and output to the log file path. In an ACL system, the compiler checks the user's permissions on the output file—but the compiler has write access, not the user, so the check passes, and the compiler overwrites /etc/passwd. In a capability system, the user passes a capability for the specific output file they are authorized to use. The compiler can only write to that file—it cannot write to /etc/passwd because it has no capability for it. The deputy cannot be confused because it can only act on the capabilities it is given.

17.11 Language-Based Protection

Language-based protection uses programming language features to enforce protection policies, rather than (or in addition to) OS-level mechanisms. The idea is that the compiler and runtime can enforce access rules at a finer granularity than the OS, because they understand the semantics of the program. For example, a language can enforce that a variable is only accessible within a certain module, or that a function can only be called by certain callers.

The type system is the most common form of language-based protection. A type-safe language (like Java, Rust, or Go) guarantees that a program cannot access memory outside of its allocated objects. This eliminates entire classes of vulnerabilities: buffer overflows, use-after-free, and type confusion are impossible in a type-safe language (assuming the language runtime is correct). In contrast, C and C++ are not type-safe: a pointer cast or buffer overflow can access arbitrary memory.

/* Type safety prevents buffer overflows */ // C (not type-safe): buffer overflow possible char buf[64]; strcpy(buf, user_input); // overflow if > 64! // Java (type-safe): bounds checked byte[] buf = new byte[64]; System.arraycopy(input, 0, buf, 0, input.length); // throws ArrayIndexOutOfBoundsException if input > 64 // No memory corruption — the runtime enforces bounds // Rust (type-safe + ownership): no overflow, no use-after-free let mut buf = [0u8; 64]; buf[..input.len()].copy_from_slice(input); // panics if input > 64, but no memory corruption

Access modifiers (public, private, protected) in object-oriented languages are a form of language-based protection. They control which code can access a class's fields and methods. private members are only accessible within the class, protected within the class and its subclasses, and public from anywhere. The compiler enforces these rules, preventing accidental or intentional access from outside the intended scope. This is analogous to OS-level access control but at the language/object level.

Java's security model is a comprehensive example of language-based protection. Java programs run in a Java Virtual Machine (JVM) that enforces type safety, memory safety, and a security manager that can restrict what code can do (read files, open network connections, etc.). Signed code can be granted different permissions based on the signer's identity. Applets (now deprecated) ran in a sandbox with no access to the local file system. While applets are gone, the principles live on in WebAssembly, Android's app sandbox, and container runtimes.

ℹ️ Rust's Ownership System

Rust takes language-based protection further with its ownership and borrowing system. The compiler enforces that:

  • Each value has exactly one owner
  • When the owner goes out of scope, the value is dropped (no leaks, no double-free)
  • References must always point to valid data (no dangling pointers, no use-after-free)
  • Mutable and immutable references cannot coexist (no data races)

These rules are checked at compile time, eliminating memory safety bugs without runtime overhead. Rust demonstrates that language-level protection can replace some OS-level protection mechanisms—at least for memory safety.

Proof-carrying code is an advanced form of language-based protection where the code producer provides a proof that the code satisfies certain safety properties, and the consumer (or the runtime) verifies the proof before running the code. This allows untrusted code to run safely without a full sandbox: if the proof checks out, the code is guaranteed to be safe. Typed assembly language and WebAssembly validation are practical applications of this idea.

The relationship between language-based and OS-based protection is complementary, not competitive. Language-based protection is fine-grained and efficient but only works within a single language runtime. OS-based protection is coarser and has more overhead but works across all programs and languages. A secure system uses both: the OS provides the foundation (process isolation, privilege levels), and language-based protection adds fine-grained, type-safe access control within each process. For example, a web browser uses OS-level sandboxing to isolate tabs (process-level) and language-level sandboxing to isolate JavaScript from the browser's native code (language-level).

💡 The Future: Capability-Safe Languages

Modern research in object-capability languages (like E, Pony, and some extensions of JavaScript) combines language-level safety with capability-based access control. In these languages, the only way to access a resource is to hold a reference (capability) to it—there is no global namespace or ambient authority. This makes the principle of least privilege automatic: a module can only access what it is explicitly given. This is the language-level analog of seL4's capability-based kernel architecture.
