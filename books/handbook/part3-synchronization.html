6.1 Background

When multiple threads or processes access shared data concurrently, the final result can depend on the order of execution. Without synchronization, this leads to race conditions—situations where the outcome depends on the timing of thread execution. Consider a simple counter increment: counter++ looks like one operation, but it is actually three: (1) read counter into a register, (2) increment the register, (3) write the register back to counter. If two threads do this simultaneously, one thread's update can be lost.

/* Race condition: counter++ is not atomic */ // Thread 1 and Thread 2 both execute counter++ // counter++ expands to three instructions: // Thread 1 Thread 2 ld t0, counter | addi t0, t0, 1 | sd t0, counter | | ld t1, counter // reads OLD value! | addi t1, t1, 1 | sd t1, counter // Result: counter incremented by 1, not 2!

A race condition occurs when multiple threads access shared data and at least one is writing, and the result depends on the order of access. Race conditions are notoriously hard to debug because they are non-deterministic: the bug may appear only under specific timing conditions, and may not reproduce on every run. A program that passes all tests may still have a race condition that manifests only in production under load.

⚠️ Race Conditions Are Dangerous

Race conditions can cause: lost updates (one thread's write is overwritten), inconsistent reads (a read sees a partially-updated data structure), and data corruption (a data structure is left in an invalid state). They are among the hardest bugs to find because they may not reproduce reliably and may only appear under specific load or timing conditions.

To prevent race conditions, we need synchronization—mechanisms that ensure only one thread at a time can access shared data, or that coordinate access so the result is correct regardless of execution order. The fundamental concept is the critical section: a section of code that accesses shared data and must not be executed by more than one thread at a time. By protecting critical sections, we prevent races.

In xv6, race conditions are a real concern because the kernel is multiprocessor-capable. Multiple CPUs can execute kernel code simultaneously, accessing shared data structures like the process table. xv6 uses spinlocks (in spinlock.c) to protect these structures. The ptable.lock protects the process table; the kmem.lock protects the memory allocator. Without these locks, concurrent access would corrupt the data structures.

6.2 The Critical-Section Problem

The critical-section problem is: design a protocol that threads can use to coordinate access to shared data. Each thread has a critical section of code where it accesses shared data. The protocol must satisfy three requirements:

  1. Mutual exclusion: If thread $T_i$ is executing in its critical section, no other thread can be executing in its critical section.
  2. Progress: If no thread is in a critical section and some threads want to enter, the selection of which thread enters cannot be postponed indefinitely.
  3. Bounded waiting: There must be a bound on how many times other threads can enter their critical sections after a thread has requested entry and before it is granted entry (prevents starvation).
ℹ️ The Three Requirements

Mutual exclusion: only one at a time.
Progress: if the critical section is free and someone wants in, someone gets in (no deadlock).
Bounded waiting: a waiting thread eventually gets in (no starvation).

A general structure for a solution is:

/* Critical section structure */ do { // entry section — request access acquire_lock(); // critical section — access shared data shared_data++; // exit section — release access release_lock(); // remainder section — other work } while (1);

The challenge is implementing acquire_lock() and release_lock() correctly. The solution must work on multiprocessor systems (where threads truly run in parallel) and must handle the case where a thread is preempted at any point. Solutions fall into two categories: software solutions (like Peterson's algorithm) that use only shared variables, and hardware solutions that use special CPU instructions.

A key assumption is that shared variables are not reordered by the compiler or hardware. In practice, compilers and CPUs reorder instructions for performance, which can break software-only solutions. This is why modern solutions use memory barriers (or fences) and atomic operations provided by the hardware.

6.3 Peterson's Solution

Peterson's solution is a classic software-only solution to the critical-section problem for two threads. It uses two shared variables: int flag[2] (indicating each thread's interest in entering) and int turn (indicating whose turn it is). The algorithm is elegant and satisfies all three requirements—assuming that memory accesses are not reordered.

/* Peterson's solution for two threads */ int flag[2] = {0, 0}; int turn = 0; // Thread 0 (i = 0, j = 1) do { flag[0] = 1; // I want to enter turn = 1; // but give priority to the other while (flag[1] && turn == 1); // wait if other wants in and it's their turn // critical section flag[0] = 0; // I'm done // remainder section } while (1);

The key insight is the turn variable: even if both threads set their flags simultaneously, only one can set turn last, and that determines who enters first. If thread 0 sets turn = 1 last, then turn == 1 is true, so thread 0 waits while thread 1 (for which turn != 1 from its perspective) can enter. This guarantees mutual exclusion.

ℹ️ How Peterson's Works

Thread $i$ sets flag[i] = 1 (I want in) and turn = j (but you go first). Then it waits while the other wants in and it's the other's turn. The turn variable breaks the tie when both want in: the last writer of turn defers to the other.

Limitations: Peterson's solution assumes that loads and stores are atomic and not reordered. On modern CPUs, this is not guaranteed: compilers may reorder the flag[i] = 1 and turn = j writes, or the CPU may reorder them at runtime. This can break the algorithm. To make it work on modern hardware, you need memory barriers after each write. In practice, Peterson's is mainly of historical and pedagogical interest; real systems use hardware-supported locks.

Peterson's can be generalized to $n$ threads, but the generalization (the Bakery algorithm by Leslie Lamport) is more complex. The Bakery algorithm assigns each thread a "ticket number" (like a deli), and the thread with the lowest number enters first. Ties are broken by thread ID. This satisfies all three requirements for $n$ threads, but again assumes atomic, unordered memory access.

6.4 Hardware Support for Synchronization

Software-only solutions like Peterson's are fragile on modern hardware. To provide robust synchronization, CPU designers include special atomic instructions that execute indivisibly. These are the foundation of all practical synchronization primitives.

The most fundamental is test-and-set (or tas): it atomically reads a memory location, sets it to true, and returns the old value. Using test-and-set, we can implement a simple lock: acquire by looping until test-and-set returns false (meaning we set it to true); release by setting it to false.

/* Lock using test-and-set */ boolean lock = false; // Acquire lock (spin until we get it) while (test_and_set(&lock)) // returns old value ; // spin (busy-wait) // Critical section // Release lock lock = false;

Another common instruction is compare-and-swap (CAS): compare_and_swap(ptr, expected, new) atomically compares *ptr to expected; if they match, it sets *ptr = new and returns true; otherwise it returns false. CAS is more powerful than test-and-set and is the basis for many lock-free data structures. On x86, it is the cmpxchg instruction; on RISC-V, it is the lr (load-reserved) / sc (store-conditional) pair.

/* RISC-V atomic exchange: lr (load-reserved) + sc (store-conditional) */ // Atomically: old = *addr; *addr = new; return old atomic_swap: lr.w t0, (a0) // load-reserved: t0 = *a0 sc.w t1, a1, (a0) // store-conditional: *a0 = a1, t1 = 0 if success bnez t1, atomic_swap // retry if store failed mv a0, t0 // return old value ret

Other atomic instructions include fetch-and-add (atomically add a value and return the old value) and atomic exchange (swap two values). Modern CPUs also provide memory barriers (or fences) to prevent instruction reordering: a fence instruction ensures that all memory operations before it complete before any after it. On x86, these are mfence, lfence, and sfence; on RISC-V, fence and fence.i.

💡 xv6 Spinlock Implementation

xv6's spinlock.c uses RISC-V's amoswap (atomic swap) instruction to implement acquire() and release(). The acquire() function spins on amoswap until the lock is free. It also disables interrupts on the current CPU (via push_off()) to prevent a deadlock if a timer interrupt triggers while holding the lock.

6.5 Mutex Locks

A mutex lock (short for mutual exclusion) is the simplest synchronization primitive. It has two states: locked and unlocked. A thread acquires the lock before entering a critical section and releases it after. Only one thread can hold the lock at a time; others must wait. The name "mutex" reflects its purpose: it ensures mutual exclusion.

/* Mutex lock (using test-and-set) */ typedef struct { boolean locked; } mutex; void mutex_acquire(mutex *m) { while (test_and_set(&m->locked)) // spin or block ; // busy-wait (spinlock) or sleep (blocking) } void mutex_release(mutex *m) { m->locked = false; // release } // Usage: mutex_acquire(&m); shared_counter++; // critical section mutex_release(&m);

There are two ways to wait for a lock: spinning (busy-waiting in a loop, re-checking the lock) and blocking (putting the thread to sleep and waking it when the lock is free). A spinlock spins; a blocking mutex blocks. Spinning wastes CPU cycles but has low latency (no context switch); blocking saves CPU but has higher latency (context switch overhead). Spinlocks are used for short critical sections (where the wait is likely short); blocking mutexes are used for long critical sections (where spinning would waste too much CPU).

PropertySpinlockBlocking Mutex
Wait methodBusy-wait (spin)Sleep (block)
CPU usageWastes CPU while waitingFrees CPU while waiting
LatencyLow (no context switch)Higher (context switch)
Best forShort critical sectionsLong critical sections
Used inKernel, low-levelUser-space, high-level
⚠️ Contention and Fairness

Under high contention (many threads trying to acquire the same lock), spinlocks waste CPU and blocking mutexes cause many context switches. Neither is fair: a thread that just released the lock may immediately re-acquire it, starving others. Some locks provide fairness (FIFO ordering) using a ticket lock, but this adds overhead. The xv6 spinlock is not fair; Linux's mutex can be configured for fairness.

In xv6, the spinlock structure (in spinlock.h) has a locked field and a cpu field (to track which CPU holds the lock, for debugging). The acquire() function uses __sync_test_and_fetch (a GCC builtin that compiles to amoswap) to atomically acquire the lock, and release() uses a simple store (with a memory barrier). The push_off()/pop_off() functions manage interrupt disabling to prevent deadlocks with interrupt handlers.

6.6 Semaphores

A semaphore is a more general synchronization tool than a mutex. Invented by Edsger Dijkstra, a semaphore $S$ is an integer variable with two atomic operations: wait(S) (also called P or down) and signal(S) (also called V or up). wait decrements $S$ and blocks if $S$ becomes negative; signal increments $S$ and wakes a waiting thread if any.

/* Semaphore operations */ typedef struct { int value; struct process *wait_queue; // blocked processes } semaphore; void wait(semaphore *S) { S->value--; if (S->value < 0) { add_to_queue(current_process, S->wait_queue); block(); // sleep until signaled } } void signal(semaphore *S) { S->value++; if (S->value <= 0) { process *p = remove_from_queue(S->wait_queue); wakeup(p); // wake one waiting process } }

Semaphores come in two types. A counting semaphore can have any value and is used to control access to a resource with multiple instances (e.g., a pool of $N$ printers: initialize to $N$, wait to acquire, signal to release). A binary semaphore has values 0 or 1 and is essentially a mutex (though without an "owner" concept). The key difference from a mutex is that a semaphore can be signaled by any thread, while a mutex should only be released by its owner.

ℹ️ Semaphore vs. Mutex

A mutex is for mutual exclusion: one thread acquires, the same thread releases. It has an "owner."
A binary semaphore is similar but can be signaled by any thread (no owner).
A counting semaphore generalizes to $N$ resources. Use a mutex for protecting critical sections; use a counting semaphore for resource pools.

Semaphores are powerful but error-prone. A missed signal leads to deadlock; a missed wait leads to a race. A signal without a corresponding wait is a bug. Because semaphores are low-level, they require discipline. Higher-level constructs like monitors (Section 6.7) encapsulate synchronization to prevent these errors.

A classic use of semaphores is the bounded-buffer (producer-consumer) problem. We use three semaphores: empty (counts empty slots, initialized to $N$), full (counts filled slots, initialized to 0), and mutex (protects the buffer, initialized to 1). The producer waits on empty (wait for a free slot), then waits on mutex (enter critical section), adds an item, signals mutex, and signals full (announce a new item). The consumer does the reverse.

/* Bounded buffer with semaphores */ semaphore empty = N; // N empty slots semaphore full = 0; // 0 full slots semaphore mutex = 1; // buffer lock // Producer while (1) { item = produce(); wait(&empty); // wait for empty slot wait(&mutex); // enter critical section add_item(buffer, item); signal(&mutex); // leave critical section signal(&full); // announce item available } // Consumer while (1) { wait(&full); // wait for item wait(&mutex); // enter critical section item = remove_item(buffer); signal(&mutex); // leave critical section signal(&empty); // announce slot free consume(item); }
⚠️ Deadlock with Semaphores

If the producer (or consumer) acquires mutex before empty (or full), a deadlock can occur: the producer holds mutex and waits for empty (buffer full), while the consumer waits for mutex to consume. The rule: always acquire the resource semaphore (empty/full) before the mutex.

6.7 Monitors

A monitor is a high-level synchronization construct that encapsulates shared data and the operations on it. A monitor is like a class: it has private data (accessible only through its methods) and public methods. Only one thread can be executing inside the monitor at a time, so the data is automatically protected. This prevents the errors that arise from manually using semaphores.

/* Monitor example (pseudocode) */ monitor BankAccount { int balance = 0; condition sufficient_funds; void deposit(int amount) { balance += amount; signal(sufficient_funds); // wake a waiter if any } void withdraw(int amount) { while (balance < amount) wait(sufficient_funds); // release monitor, wait balance -= amount; } } // Only one thread in deposit() or withdraw() at a time. // No explicit lock needed — monitor enforces mutual exclusion.

Monitors use condition variables for threads to wait for specific conditions. A condition variable has two operations: wait() (release the monitor lock, block until signaled, then re-acquire) and signal() (wake one waiting thread). A third operation, broadcast(), wakes all waiting threads. The key is that wait() atomically releases the lock and blocks, preventing a race where a signal is missed.

ℹ️ Condition Variables

A condition variable is always associated with a lock. The pattern is: lock(); while (!condition) wait(cv); /* do work */ signal(cv); unlock();. The while (not if) is important: after waking, the condition may no longer be true (another thread may have changed it), so we must re-check. This is called a loop invariant check.

There are two semantics for signal(): signal-and-wait (the signaling thread waits until the signaled thread exits the monitor) and signal-and-continue (the signaling thread continues, and the signaled thread must wait to re-enter). Most implementations use signal-and-continue, which is more flexible. The choice affects how conditions must be checked (always use a while loop with signal-and-continue).

Monitors are a language-level construct: they are supported by some languages (Java's synchronized is monitor-like; Mesa, Modula, and Java have native support). In C, monitors are simulated using mutexes and condition variables (the POSIX pthread_mutex_t and pthread_cond_t). The advantage of monitors is that the compiler or runtime enforces mutual exclusion, reducing the chance of programmer error.

💡 Why Monitors?

Monitors encapsulate synchronization: the lock is implicit, and condition variables are tied to the monitor. This makes code easier to write and maintain—you can't forget to acquire the lock, and you can't signal the wrong condition variable. The trade-off is less flexibility: you can't, for example, hold two locks at once (which is sometimes needed for complex data structures).

6.8 Liveness

Liveness refers to a set of properties that require a system to make progress. While safety properties (like mutual exclusion) ensure that "bad things don't happen," liveness properties ensure that "good things eventually happen." The main liveness failures are deadlock, starvation, and priority inversion.

Deadlock occurs when threads are waiting for each other indefinitely. For example, thread A holds lock 1 and waits for lock 2, while thread B holds lock 2 and waits for lock 1. Neither can proceed. Deadlocks are covered in detail in Chapter 8. The key is that deadlocks involve a cycle of waiting: each thread in the cycle holds a resource that the next thread needs.

Starvation occurs when a thread is indefinitely denied access to resources. For example, in priority scheduling without aging, a low-priority thread may never run if higher-priority threads keep arriving. Starvation is a liveness failure: the thread is not deadlocked (it could run if given the chance), but it never gets the chance. Solutions include aging (gradually increasing priority) and fair locking (FIFO order).

⚠️ Priority Inversion

Priority inversion occurs when a high-priority thread is forced to wait for a low-priority thread that holds a resource it needs. If a medium-priority thread preempts the low-priority thread, the high-priority thread is effectively blocked by a lower-priority thread. The Mars Pathfinder mission (1997) experienced this: a low-priority data-gathering thread held a lock that a high-priority communications thread needed, and a medium-priority thread preempted the low-priority thread, causing the system to reset repeatedly. The fix was the priority inheritance protocol.

The priority inheritance protocol solves priority inversion: when a low-priority thread holds a lock that a high-priority thread needs, the low-priority thread temporarily inherits the high priority, preventing medium-priority threads from preempting it. Once it releases the lock, it returns to its original priority. This ensures that the high-priority thread gets the resource as soon as possible. Some systems also use the priority ceiling protocol, which assigns each lock a priority ceiling (the highest priority of any thread that may lock it), and a thread holding a lock runs at that ceiling priority.

6.9 Evaluation

Choosing the right synchronization tool depends on the situation. The main options are spinlocks, blocking mutexes, semaphores, monitors, and lock-free (atomic) approaches. Each has trade-offs in performance, ease of use, and applicability.

ToolBest forProsCons
SpinlockShort critical sections, kernelLow latencyWastes CPU, no fairness
Blocking mutexLong critical sectionsFrees CPUContext switch overhead
SemaphoreResource counting, signalingFlexibleError-prone
MonitorEncapsulated dataSafe, easyLess flexible
Lock-free (CAS)High-contention, low-latencyNo blockingComplex, ABA problem

Under low contention (few threads competing), all approaches perform similarly—the lock is usually free, so acquire is fast. Under high contention, the choice matters: spinlocks waste CPU, blocking mutexes cause context switches, and lock-free approaches may have high retry rates. The optimal choice depends on the hold time (how long the lock is held) and the wait time (how long threads wait). For very short critical sections, spinlocks are best; for long ones, blocking mutexes; for simple operations (like a counter increment), lock-free atomics.

💡 Adaptive Locks

Some systems use adaptive locks (or hybrid locks) that spin for a short time and then block if the lock doesn't become free. This combines the low latency of spinlocks (for short waits) with the CPU efficiency of blocking mutexes (for long waits). Solaris and Linux use adaptive mutexes for kernel locks.

Lock-free approaches use atomic operations (like CAS) to update data without locks. This avoids deadlocks and can be faster under low contention, but is harder to write correctly. The ABA problem is a classic pitfall: a thread reads value A, another thread changes it to B then back to A, and the first thread's CAS succeeds (it sees A), but the data structure may have changed in ways the CAS doesn't detect. Solutions include hazard pointers, epoch-based reclamation, and versioned pointers (using the high bits of a pointer for a version counter).

7.1 Classic Problems of Synchronization

Several classic problems illustrate the challenges of synchronization and are used to evaluate synchronization mechanisms. The three most famous are the bounded-buffer (producer-consumer) problem, the readers-writers problem, and the dining-philosophers problem.

The Bounded-Buffer Problem (Producer-Consumer): A set of producers generates items and places them in a buffer of size $N$; a set of consumers removes items. The buffer is shared, so access must be synchronized. Producers must wait if the buffer is full; consumers must wait if it is empty. The solution uses three semaphores (as shown in Section 6.6): empty (counts empty slots), full (counts filled slots), and mutex (protects the buffer). This is the basis for many real-world systems: message queues, logging (producer = application, consumer = logger), and streaming (producer = camera, consumer = encoder).

The Readers-Writers Problem involves a shared data structure accessed by two types of processes: readers (which only read) and writers (which read and write). Multiple readers can read simultaneously (no conflict), but a writer needs exclusive access (no other readers or writers). There are three variants: (1) first readers-writers (no reader waits unless a writer has permission—can starve writers), (2) second readers-writers (writers have priority once they request—can starve readers), and (3) third readers-writers (fair—no starvation). The choice depends on the application: databases often favor readers (more reads than writes), while logging may favor writers (to ensure logs are written promptly).

/* Readers-Writers (first variant, no writer starvation) */ // Shared state semaphore rw_mutex = 1; // for writers semaphore mutex = 1; // protects read_count int read_count = 0; // Writer wait(&rw_mutex); // write data signal(&rw_mutex); // Reader wait(&mutex); read_count++; if (read_count == 1) wait(&rw_mutex); // first reader locks writers signal(&mutex); // read data wait(&mutex); read_count--; if (read_count == 0) signal(&rw_mutex); // last reader unlocks writers signal(&mutex);

The Dining Philosophers Problem (Dijkstra, 1965): Five philosophers sit around a table with five chopsticks (one between each pair). Each philosopher needs two chopsticks to eat. If each philosopher picks up the left chopstick and waits for the right, they all deadlock (each holds one chopstick and waits for another). Solutions include: (1) allow at most 4 philosophers to sit simultaneously (breaks the cycle), (2) asymmetric: odd philosophers pick left first, even pick right first (breaks symmetry), (3) use a waiter (a monitor that grants permission), or (4) require both chopsticks to be picked up atomically (using a mutex). This problem models resource allocation where processes need multiple resources.

ℹ️ Dining Philosophers in Practice

The dining philosophers problem models real situations: processes needing multiple resources (e.g., a transaction locking multiple database rows). The deadlock in the naive solution (all pick left first) is a circular wait, one of the four conditions for deadlock (Section 8.3). Breaking any of the four conditions prevents deadlock.

7.2 Synchronization within the Kernel

Kernel synchronization is more complex than user-space synchronization because the kernel runs on multiple CPUs, handles interrupts, and must not block in certain contexts. Different operating systems use different strategies.

In Linux, the kernel is fully preemptive (since 2.6), so kernel code can be interrupted at almost any point. Linux uses several synchronization primitives: spinlocks (for short critical sections, especially on multiprocessors), mutexes (for longer critical sections, can sleep), semaphores (counting, can sleep), RCU (Read-Copy-Update, for read-mostly data), and per-CPU variables (data that is per-CPU, so no locking needed). The choice depends on whether the critical section can sleep (if so, use mutex/semaphore; if not, use spinlock) and the contention level.

⚠️ Sleeping in the Kernel

In the kernel, some contexts cannot sleep (block): interrupt handlers and atomic contexts (holding a spinlock). If you sleep while holding a spinlock, you can deadlock (another CPU spinning on the lock will spin forever, and if that CPU is the one that would wake you, you're stuck). This is why interrupt handlers use spinlocks, not mutexes, and do minimal work (often just queuing work for a "bottom half" that can sleep).

Windows uses spinlocks for multiprocessor synchronization and dispatcher objects (events, semaphores, mutexes, timers) for higher-level synchronization. Windows uses IRQLs (Interrupt Request Levels) to manage interrupt priority: code at a higher IRQL cannot be preempted by a lower IRQL. Spinlocks raise the IRQL to DISPATCH_LEVEL, preventing preemption by most interrupts.

In xv6, synchronization is simple: spinlocks are the only primitive. The acquire() function disables interrupts on the current CPU (via push_off()) and then spins on the lock. This prevents deadlocks with interrupt handlers on the same CPU (if an interrupt fired while holding a lock, and the handler tried to acquire the same lock, it would deadlock). The sleep() and wakeup() functions in proc.c provide a condition-variable-like mechanism for processes to wait for events.

💡 xv6 sleep()/wakeup()

xv6's sleep(chan, lock) atomically releases lock, puts the process to sleep on channel chan, and reacquires lock when woken. wakeup(chan) wakes all processes sleeping on chan. The atomic release-sleep prevents the lost wakeup problem: if wakeup is called between the release and the sleep, the wakeup would be lost. By holding the lock, sleep ensures that wakeup cannot run in between.

7.3 POSIX Synchronization

The POSIX standard (IEEE 1003.1) defines a set of synchronization primitives for C programs, provided by the pthread library. These are the standard synchronization tools on UNIX-like systems.

POSIX mutexes (pthread_mutex_t) provide mutual exclusion. pthread_mutex_lock() acquires the lock (blocks if held), pthread_mutex_unlock() releases it, and pthread_mutex_trylock() attempts to acquire without blocking. Mutexes can have attributes: type (normal, error-check, recursive), protocol (priority inheritance, priority ceiling), and robustness (what happens if the holder dies).

/* POSIX mutex example */ #include <pthread.h> pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER; int counter = 0; void *increment(void *arg) { for (int i = 0; i < 1000000; i++) { pthread_mutex_lock(&lock); counter++; // protected pthread_mutex_unlock(&lock); } return NULL; }

POSIX semaphores come in two types: named semaphores (sem_open, identified by a name like a file, usable across processes) and unnamed semaphores (sem_init, in memory, usable within a process or shared memory). Operations are sem_wait() (decrement, block if negative) and sem_post() (increment, wake a waiter). sem_trywait() is non-blocking.

POSIX condition variables (pthread_cond_t) allow threads to wait for a condition. They are always used with a mutex. The pattern is: lock the mutex, check the condition in a while loop, pthread_cond_wait() if not met (atomically unlocks and waits), and pthread_cond_signal() or pthread_cond_broadcast() to wake waiters. The while loop handles spurious wakeups (waking without a signal) and races (another thread may change the condition between the signal and the wake).

/* POSIX condition variable */ pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER; pthread_cond_t cond = PTHREAD_COND_INITIALIZER; int ready = 0; // Waiter pthread_mutex_lock(&mutex); while (!ready) // MUST use while, not if pthread_cond_wait(&cond, &mutex); // atomically unlock + wait // ready is true, do work pthread_mutex_unlock(&mutex); // Signaler pthread_mutex_lock(&mutex); ready = 1; pthread_cond_signal(&cond); // wake one waiter pthread_mutex_unlock(&mutex);

POSIX also provides read-write locks (pthread_rwlock_t) that allow multiple readers or one writer, and barriers (pthread_barrier_t) that cause threads to wait until a set of threads reach a point. These higher-level primitives simplify common patterns.

7.4 Java Synchronization

Java provides built-in synchronization at the language level, making it easier to write correct concurrent code than in C. Every Java object has an intrinsic lock (also called a monitor lock), and the synchronized keyword uses it.

A synchronized method acquires the object's lock before executing and releases it after. Only one thread can execute a synchronized method on the same object at a time. A synchronized block (synchronized(obj) { ... }) is more fine-grained: it locks a specific object, allowing different methods to use different locks for less contention.

/* Java synchronization */ class Counter { private int count = 0; private final Object lock = new Object(); // Synchronized method: locks 'this' public synchronized void increment() { count++; } // Synchronized block: locks 'lock' public void decrement() { synchronized (lock) { count--; } } public int get() { synchronized (this) { return count; } } }

Java also provides wait(), notify(), and notifyAll() methods (on Object) for condition synchronization, used within synchronized blocks. wait() releases the lock and blocks; notify() wakes one waiting thread; notifyAll() wakes all. As with POSIX, the while loop pattern is essential to handle spurious wakeups and races.

ℹ️ Java's java.util.concurrent

Modern Java (since 5.0) provides the java.util.concurrent package with higher-level tools: ReentrantLock (a more flexible lock with tryLock() and fairness), Semaphore, CountDownLatch, CyclicBarrier, ConcurrentHashMap (a thread-safe map), BlockingQueue (a thread-safe queue for producer-consumer), and AtomicInteger/AtomicReference (lock-free atomics). These are preferred over raw synchronized for new code.

Java's volatile keyword ensures that reads and writes to a variable are visible to all threads (prevents caching in registers or per-CPU caches) and prevents reordering. However, volatile does not make compound operations (like ++) atomic. For atomic operations, use the Atomic* classes, which use hardware CAS instructions internally.

7.5 Alternative Approaches

Beyond traditional locks, several alternative approaches to synchronization have been developed to address their limitations (deadlocks, contention, complexity).

Transactional memory applies the concept of database transactions to memory access. A thread executes a block of code speculatively: the runtime tracks all reads and writes. If no conflict occurs (no other thread modified the same data), the transaction commits (changes become visible). If a conflict occurs, the transaction aborts and retries. This avoids the need for explicit locks and can be more composable (transactions can nest). Hardware transactional memory (HTM) is supported by some CPUs (Intel TSX, IBM POWER); software transactional memory (STM) is implemented in software. The std::experimental::atomic in C++ and Haskell's STM are examples.

/* Transactional memory (pseudocode) */ atomic { // All reads and writes are tracked if (account.balance >= amount) { account.balance -= amount; target.balance += amount; } // If another thread touched account or target, // this whole block aborts and retries. }

OpenMP provides compiler directives for parallelism, including synchronization: #pragma omp critical (a critical section), #pragma omp barrier (a barrier), #pragma omp atomic (an atomic operation), and #pragma omp single (only one thread executes a block). These are higher-level than explicit locks and integrate with the compiler's parallelization.

Functional programming offers a different approach: avoid shared mutable state entirely. In functional languages (Haskell, Erlang, Clojure) or functional styles (immutable data in Rust, Scala), data is immutable, so there are no races. When state must change, it is done through controlled mechanisms (software transactional memory, actors, or single-threaded event loops). The actor model (used in Erlang and Akka) has independent actors that communicate only by message passing, with no shared memory—eliminating the need for locks.

💡 Choose the Right Tool

For simple mutual exclusion: use a mutex or synchronized. For producer-consumer: use a blocking queue or semaphores. For read-heavy data: use a read-write lock or RCU. For simple counters: use atomic operations. For complex data structures with high contention: consider lock-free or transactional memory. For distributed systems: use message passing (actors). The best approach depends on the specific problem.

8.1 System Model

A deadlock occurs when a set of processes are blocked, each holding a resource and waiting for a resource held by another process in the set. None can proceed, and none can release its resource until it gets the one it's waiting for. To understand deadlocks, we model a system as having resources (of various types) and processes that request, use, and release resources.

A resource type $R_i$ has $W_i$ instances. For example, if a system has 3 printers, the resource type "printer" has 3 instances. A process requests instances of a resource type; if available, the OS grants them; if not, the process waits. A process can request more than it holds (e.g., hold 1 printer, request another). The resource-allocation graph visualizes this: processes are circles, resources are rectangles with dots for instances, request edges point from process to resource, assignment edges from resource instance to process.

/* Resource-allocation graph example */ // Processes: P1, P2, P3 // Resources: R1 (1 instance), R2 (2 instances), R3 (1 instance) // Current allocations: // P1 holds R1, requests R2 // P2 holds R2 (one instance), requests R3 // P3 holds R3, requests R1 // Graph: P1 → R2 → P2 → R3 → P3 → R1 → P1 (a cycle!) // This is a deadlock: each waits for the next.

A key theorem: if the resource-allocation graph has no cycles, the system is not deadlocked. The converse is not always true: if each resource type has only one instance, a cycle implies deadlock; but if a resource type has multiple instances, a cycle does not necessarily mean deadlock (a process outside the cycle might release an instance). However, cycles are a useful indicator—most deadlocks involve cycles.

ℹ️ Deadlock vs. Starvation

Deadlock: processes are blocked forever, each waiting for a resource held by another in the set. No process can make progress.
Starvation: a process is indefinitely denied resources but could proceed if given them. Other processes make progress; the starved one does not. Deadlock implies starvation (for all in the cycle), but starvation can occur without deadlock.

Resources can be preemptable (can be taken away—e.g., memory, via swapping) or non-preemptable (cannot—e.g., a printer mid-print). Deadlock mainly concerns non-preemptable resources. For preemptable resources, the OS can resolve deadlock by preempting and reallocating. The classic deadlock scenarios involve non-preemptable resources like locks, file locks, and I/O devices.

8.2 Deadlock in Multithreaded Applications

Deadlocks are common in multithreaded programs that use multiple locks. The classic scenario is the lock ordering deadlock: thread 1 acquires lock A then lock B, while thread 2 acquires lock B then lock A. If thread 1 gets A and thread 2 gets B, both wait for the other—deadlock.

/* Deadlock from lock ordering */ // Thread 1 Thread 2 lock(&A); lock(&B); lock(&B); lock(&A); // deadlock! // ... ... unlock(&B); unlock(&A); unlock(&A); unlock(&B); // Thread 1 holds A, waits for B // Thread 2 holds B, waits for A // Neither can proceed.

The standard solution is a lock ordering protocol: all threads acquire locks in the same global order. If both threads acquire A before B, no deadlock can occur. This is simple but can be hard to enforce in large codebases: a function may not know what locks its caller holds, leading to violations. Tools like lock linters (Clang's Thread Safety Analysis) can help enforce ordering at compile time.

⚠️ Lock Ordering Is Hard

Enforcing a global lock order is difficult in practice: (1) the order may not be obvious (what if A and B are in different modules?), (2) the order may conflict with other constraints (e.g., you need B to check a condition before acquiring A), (3) the codebase may be too large to audit. Alternative: use trylock with back-off (try to acquire, if fail, release all and retry), or use a single lock (simpler but less concurrent).

Another common deadlock is the lock-with-sleep deadlock: a thread holds a lock and then calls a function that sleeps (e.g., I/O, or another lock that blocks). If the sleep waits for a thread that needs the lock, deadlock. This is why kernel code must be careful not to sleep while holding a spinlock. The rule: never sleep while holding a spinlock.

Deadlocks can also occur with non-lock resources: file locks, database locks, network connections. A database transaction that locks rows in different orders can deadlock with another transaction. Databases detect this and abort one transaction (a victim), which the application must retry. This is an example of deadlock detection and recovery (Section 8.7–8.8).

8.3 Deadlock Characterization

A deadlock can only occur if all four of the following conditions hold simultaneously. This is the Coffman conditions (1971):

  1. Mutual exclusion: At least one resource is held in non-shareable mode (only one process can use it at a time).
  2. Hold and wait: A process holding at least one resource is waiting to acquire additional resources held by other processes.
  3. No preemption: Resources cannot be preempted (taken away); they must be released voluntarily by the holding process.
  4. Circular wait: There exists a set $\{P_0, P_1, ..., P_n\}$ such that $P_0$ waits for a resource held by $P_1$, $P_1$ waits for $P_2$, ..., $P_n$ waits for $P_0$.
ℹ️ The Four Conditions

For deadlock to occur, all four must hold. Breaking any one prevents deadlock. This is the basis for deadlock prevention (Section 8.5): design the system so that at least one condition cannot hold.

The resource-allocation graph is a tool for analyzing deadlocks. Nodes are processes (circles) and resources (rectangles with dots for instances). Edges are request (process → resource) and assignment (resource instance → process). A cycle in the graph is necessary for deadlock (if each resource has one instance, it is also sufficient). If there is no cycle, there is no deadlock. If there is a cycle and each resource has one instance, there is deadlock. If there is a cycle but some resources have multiple instances, there may be deadlock (need further analysis).

/* Detecting a cycle in the resource-allocation graph */ // If all resource types have 1 instance: // cycle ⟺ deadlock // If some resource types have multiple instances: // cycle ⟹ possible deadlock (not certain) // no cycle ⟹ no deadlock (certain) // Algorithm (for single-instance resources): // 1. Build a wait-for graph: P_i → P_j if P_i waits for a resource held by P_j // 2. Check for a cycle (DFS) // 3. If cycle found, deadlock exists

Understanding the four conditions helps in designing deadlock-free systems. For example, spooling (using a shared spool directory for printers) breaks mutual exclusion (multiple processes can write to the spool; only the printer daemon uses the printer exclusively). Acquiring all locks at once breaks hold-and-wait. Allowing preemption (e.g., rollback) breaks no-preemption. Lock ordering breaks circular wait. Each prevention strategy has costs, which is why most systems do not prevent deadlocks but instead detect and recover (or ignore them).

8.4 Methods for Handling Deadlocks

There are three main approaches to dealing with deadlocks: (1) prevention (ensure the system can never enter a deadlock state), (2) avoidance (allow the possibility of deadlock but avoid it by careful allocation), and (3) detection and recovery (let deadlocks occur, detect them, and recover). A fourth approach, common in practice, is to ignore deadlocks (pretend they don't happen and let the user deal with them if they do).

ApproachStrategyCostUsed by
PreventionBreak one of the 4 conditionsLow resource utilizationSome RTOS
AvoidanceBanker's AlgorithmOverhead, needs max needsRare (some DBs)
Detection & RecoveryPeriodic check, abortRecovery costDatabases
IgnoreDo nothingManual recoveryMost desktop OSes

Deadlock prevention ensures that at least one of the four conditions cannot hold. This is done by system design: for example, requiring all resources to be acquired at once (breaks hold-and-wait), imposing a lock order (breaks circular wait), or making resources preemptable (breaks no-preemption). Prevention is simple but can be inefficient: acquiring all resources at once may hold them longer than needed, reducing concurrency.

Deadlock avoidance is more flexible: the system allows the possibility of deadlock but checks each resource request to ensure it cannot lead to deadlock. The classic algorithm is Dijkstra's Banker's Algorithm (Section 8.6), which requires knowing each process's maximum resource needs in advance. The system only grants a request if the resulting state is safe (there exists a sequence in which all processes can complete). Avoidance is more efficient than prevention but requires advance knowledge of needs, which is often unavailable.

Deadlock detection and recovery lets deadlocks occur but periodically checks for them (using the resource-allocation graph or an algorithm). When a deadlock is detected, the system recovers by aborting one or more processes (victims) or preempting resources. This is used in database systems (which detect transaction deadlocks and abort a victim) and some operating systems. The cost is the detection overhead and the recovery (aborting a process loses work).

ℹ️ The Ostrich Algorithm

Most general-purpose operating systems (Windows, Linux, macOS) ignore deadlocks. This is humorously called the ostrich algorithm (stick your head in the sand). The rationale: deadlocks are rare in practice, prevention/avoidance is expensive, and the user can kill a deadlocked process. This is acceptable for desktop and server systems where occasional deadlocks are tolerable, but not for critical systems (medical, aerospace) where deadlock prevention is mandatory.

8.5 Deadlock Prevention

Deadlock prevention ensures that at least one of the four Coffman conditions cannot hold. Each strategy breaks one condition, with associated costs.

Breaking mutual exclusion: Make resources shareable. For some resources, this is possible: read-only files can be shared by multiple readers. A printer can be shared via spooling (processes write to a spool directory; a daemon prints sequentially). But some resources are inherently non-shareable (a printer mid-print, a writable file being modified). For these, mutual exclusion is unavoidable.

Breaking hold-and-wait: Require a process to request all resources at once, before it begins. If it gets all, it proceeds; if not, it waits (holding nothing). This prevents hold-and-wait (a process either holds all or none). The cost: a process may hold resources it doesn't yet need, reducing availability for others. Also, a process may not know all its needs in advance. A variant: require a process to release all held resources before requesting new ones.

⚠️ Cost of Breaking Hold-and-Wait

Acquiring all resources upfront can cause starvation: a process that needs many popular resources may wait forever while others acquire and release them one at a time. It also reduces concurrency: resources are held longer than necessary. This is why most systems don't use this strategy.

Breaking no-preemption: Allow resources to be preempted. If a process holding resources requests another and cannot get it, it must release all its held resources (and later request them again). This is practical for some resources (e.g., a database transaction can roll back) but not others (a printer mid-print cannot be preempted without wasting paper). For locks, this means: if you can't get a lock, release all locks you hold and retry. This is the trylock-with-back-off approach.

Breaking circular wait: Impose a total ordering on resource types and require processes to request resources in increasing order. If all processes acquire resources in the same order, no cycle can form. For example, if locks are numbered 1, 2, 3, and all code acquires them in ascending order, a process holding lock 2 can only request lock 3 (not lock 1), so no cycle. This is the most practical prevention strategy and is widely used (e.g., in the Linux kernel, lock ordering is documented and enforced by tools).

/* Breaking circular wait with lock ordering */ // Assign each lock a global order: A=1, B=2, C=3 // Always acquire in ascending order. // Correct: A then B lock(&A); // order 1 lock(&B); // order 2 // ... unlock(&B); unlock(&A); // WRONG: B then A — violates ordering, may deadlock // lock(&B); // order 2 // lock(&A); // order 1 — VIOLATION
💡 Lock Ordering in Practice

Lock ordering is the most practical deadlock prevention. The Linux kernel documents lock ordering in comments and uses tools (like lockdep) to detect violations at runtime. The rule: if you hold lock A and need lock B, and A's order is higher than B's, you must release A first. This requires discipline but is effective.

8.6 Deadlock Avoidance

Deadlock avoidance allows the system to be in a state where deadlock is possible but ensures it never reaches a deadlock state. The key concept is the safe state: a state is safe if there exists a sequence of all processes such that each can get its resources, complete, and release them, even if all request their maximum needs. An unsafe state is not necessarily deadlocked, but a deadlock is possible. The system only grants requests that lead to safe states.

The Banker's Algorithm (Dijkstra) is the classic avoidance algorithm. It models the system like a bank: the bank has a certain amount of money (resources), and each customer (process) has a credit limit (maximum need). The bank grants loans (resources) as long as the remaining money is enough to satisfy at least one customer's maximum need (that customer can complete and repay, freeing money for others). The algorithm requires knowing each process's maximum resource needs in advance.

/* Banker's Algorithm data structures */ // n = number of processes, m = number of resource types int Available[m]; // available instances of each resource int Max[n][m]; // max demand of each process int Allocation[n][m]; // currently allocated to each process int Need[n][m]; // remaining need = Max - Allocation // Safety check: is there a sequence where all can finish? boolean is_safe() { int Work[m] = Available; // copy boolean Finish[n] = {false}; while (true) { // Find a process i where Finish[i]=false and Need[i] <= Work int i = find(Finish, Need, Work); if (i == -1) break; // no such process Work += Allocation[i]; // process i finishes, releases resources Finish[i] = true; } return all(Finish); // safe if all finished }

When a process requests resources, the Banker's Algorithm pretends to grant the request, checks if the resulting state is safe, and only actually grants if it is. If unsafe, the process must wait. This ensures the system never enters an unsafe state, hence never deadlocks. The algorithm is $O(m \times n^2)$ per check, which is expensive for large systems.

ℹ️ Safe vs. Unsafe vs. Deadlock

Safe state: the system can definitely avoid deadlock (there's a sequence to finish all processes).
Unsafe state: deadlock is possible (not certain)—the system might still avoid it, but can't guarantee it.
Deadlock state: no process can proceed.
Safe ⟹ not deadlocked. Unsafe ⟏ deadlock (but may not be). Avoidance keeps the system in safe states.

The resource-allocation graph algorithm is a simpler avoidance method for single-instance resources. It adds a claim edge (dashed, from process to resource it may request) in addition to request and assignment edges. A request is granted only if the edge can be converted to an assignment without creating a cycle. This is $O(n^2)$ and works only for single-instance resources. For multiple instances, the Banker's Algorithm is needed.

The main limitation of avoidance is the requirement to know maximum needs in advance. In interactive systems, users don't know how much memory, disk, or CPU a process will need. This is why avoidance is rarely used in general-purpose systems but is used in some database systems (where transactions declare their resource needs) and real-time systems.

8.7 Deadlock Detection

Instead of preventing or avoiding deadlocks, a system can let them occur and detect them, then recover. Detection is practical when deadlocks are rare and the cost of detection is lower than the cost of prevention. The detection algorithm runs periodically (or when resources are low) and checks if a deadlock exists.

For single-instance resources, detection uses a wait-for graph: a graph where nodes are processes, and an edge $P_i \to P_j$ means $P_i$ is waiting for a resource held by $P_j$. A cycle in this graph indicates a deadlock. The algorithm runs a cycle-detection (DFS) on the wait-for graph, which is $O(n^2)$ where $n$ is the number of processes.

/* Deadlock detection (single-instance resources) */ // Build wait-for graph from current state // Edge: P_i → P_j if P_i waits for a resource held by P_j boolean detect_deadlock() { // Run cycle detection (DFS with coloring) for (int i = 0; i < n; i++) { if (dfs_find_cycle(i)) // DFS from each node return true; // deadlock found } return false; }

For multiple-instance resources, the detection algorithm is similar to the Banker's safety check, but instead of checking against maximum needs, it checks against current requests. The algorithm: let Work = Available and Finish[i] = (Allocation[i] == 0) for all $i$. Repeatedly find a process $i$ with Finish[i] == false and Request[i] <= Work; if found, set Work += Allocation[i] and Finish[i] = true. If no such process exists and some Finish[i] is still false, those processes are deadlocked.

ℹ️ When to Run Detection

Detection can run: (1) periodically (e.g., every hour), (2) when resource utilization is low (a sign of deadlock), or (3) when a process waits too long. The trade-off: frequent detection catches deadlocks sooner but uses more CPU; infrequent detection saves CPU but lets deadlocks persist. Databases typically detect on each wait (since transactions are short).

Once a deadlock is detected, the system must recover. The detection algorithm identifies the deadlocked processes; recovery involves breaking the deadlock by aborting processes or preempting resources. The challenge is choosing which process(es) to abort (the victim selection problem) and how to recover the system state.

8.8 Recovery from Deadlock

Once a deadlock is detected, the system must recover. There are three main approaches: aborting processes, resource preemption, and manual intervention.

Aborting processes is the simplest: terminate one or more deadlocked processes, releasing their resources. There are two variants: (1) abort all deadlocked processes (drastic but guaranteed to work—the cost is all the work done by those processes is lost), or (2) abort one at a time until the deadlock is resolved (less wasteful but requires re-running the detection algorithm after each abort). The challenge is victim selection: which process to abort?

⚠️ Victim Selection

Choosing a victim involves trade-offs. Factors: (1) process priority (abort low-priority), (2) work done (abort the one that has done the least, to minimize lost work), (3) resources used (abort the one holding the most resources, to free them), (4) restartability (abort a process that can be safely restarted). The goal is to minimize total cost, but the "right" choice is often unclear.

Resource preemption takes resources away from processes (rather than killing them). This is only possible for preemptable resources (or resources that can be rolled back). The process losing a resource must roll back to a safe state and retry. This is used in database systems (transactions can be rolled back) but is hard for general computation (how do you "roll back" a process that has sent network packets or printed pages?). Preemption also raises starvation concerns: if the same process is always chosen as the victim, it starves. Solutions include tracking how many times a process has been a victim and limiting it.

Rollback requires saving enough state to restore a process to a previous point. Checkpoints are periodic saves of process state; on rollback, the process resumes from the last checkpoint. This is expensive (saving state takes time and space) and is mainly used in database transactions (which have built-in rollback) and long-running computations (scientific simulations). For general processes, rollback is impractical, so abort-and-restart (from the beginning) is more common.

💡 Database Deadlock Recovery

Databases are the prime example of deadlock detection and recovery. When a transaction waits for a lock, the database may detect a deadlock (via wait-for graph cycle) and abort one transaction (the victim). The aborted transaction's changes are rolled back (using the undo log), and the application can retry. This is transparent to the user (the transaction just seems slow). This is why databases can handle deadlocks gracefully while general-purpose OSes often ignore them.

In practice, most general-purpose operating systems do not implement deadlock detection or recovery for general resources. They rely on: (1) careful programming (lock ordering), (2) timeouts (a lock request that times out is aborted), (3) user intervention (the user kills a hung process), and (4) the rarity of deadlocks. For critical resources (like database locks), the application (database) handles detection and recovery. For kernel resources, the kernel uses lock ordering and lockdep (Linux) to prevent deadlocks at development time.
