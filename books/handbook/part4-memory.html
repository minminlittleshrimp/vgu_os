9.1 Background

Memory is central to the operation of a modern computer system. It consists of a large array of bytes, each with its own address. The CPU fetches instructions from memory according to the value of the program counter (PC), and it loads and stores data to memory addresses computed by the running program. The memory unit sees only a stream of addresses and does not care how they were generated or what they represent.

Addresses in a system can be viewed from two perspectives. A logical address (also called a virtual address) is the address generated by the CPU. A physical address is the address seen by the memory unit—that is, the address loaded into the memory-address register. The two are not necessarily the same. The mapping from logical to physical addresses is performed at runtime by the memory-management unit (MMU), a hardware device that sits between the CPU and main memory.

The simplest form of address translation is a base register and a limit register. The base register holds the starting physical address of a process's memory region, and the limit register holds the size of that region. Every logical address A is translated to physical address base + A, provided that A < limit. If A >= limit, the MMU raises a trap to the OS, which terminates the process for a memory-access violation. This is the fundamental mechanism for memory protection.

ℹ️ Key Concept

The separation of logical and physical addresses is the foundation of memory protection and virtual memory. Without it, any process could read or overwrite any memory location, including the kernel's code and data. The MMU enforces this separation in hardware, so the OS does not need to check every memory access in software.

In the xv6 teaching operating system, the MMU is configured during process creation. The function proc_pagetable() in kernel/vm.c sets up the page table for a new process, mapping the kernel's code and data at high addresses and the user's code, data, and stack at lower addresses. When a process makes a system call, the CPU switches to the kernel page table (or a kernel portion of the same table), allowing the kernel to access both its own memory and the user's memory (with proper checks).

Modern systems rarely use a single base/limit pair. Instead, they use paging, which divides memory into fixed-size blocks called pages and frames. Paging eliminates external fragmentation and allows non-contiguous allocation, making it possible to run a process whose logical address space is larger than the available physical memory. We study paging in detail in Section 9.3.

9.2 Contiguous Memory Allocation

Before paging became universal, operating systems allocated memory in contiguous blocks. Each process was given a single, contiguous region of physical memory. The OS maintained a list of free memory holes and allocated a hole large enough for each process. When the process terminated, its memory was returned to the free list and possibly coalesced with adjacent free holes.

Three strategies are commonly used to select a hole for a new process:

StrategyDescriptionAdvantageDisadvantage
First FitAllocate the first hole big enoughFast—stops at first matchMay fragment low addresses
Best FitAllocate the smallest hole big enoughMinimizes wasted space per allocationLeaves many tiny unusable holes
Worst FitAllocate the largest holeLeaves large remnants that are still usableQuickly exhausts large blocks

Both first fit and best fit are generally better than worst fit in terms of storage utilization. First fit is usually the fastest. Simulations show that first fit and best fit are comparable in overall performance, but first fit is simpler and faster, so it is preferred in practice.

The main problem with contiguous allocation is external fragmentation: as processes are loaded and removed, the free memory becomes broken into small, non-contiguous pieces. Even if the total free memory is sufficient to satisfy a request, no single hole may be large enough. One solution is compaction—moving all processes to one end of memory to create one large free block. However, compaction is expensive (it requires copying large amounts of data) and is only possible if all addresses are dynamically relocatable (i.e., the base register can be updated).

⚠️ Fragmentation

External fragmentation occurs when there is enough total free memory but no single hole is large enough. Internal fragmentation occurs when memory is allocated in fixed-size blocks and the last block is partially unused. Contiguous allocation suffers from external fragmentation; paging (Section 9.3) eliminates external fragmentation but introduces a small amount of internal fragmentation.

Another issue is that contiguous allocation makes it difficult to grow a process's memory. If a process needs more heap space and the adjacent memory is occupied by another process, the OS must either move the process or swap it out. Paging solves this by allowing non-contiguous allocation: a process's pages can be scattered across any free frames in physical memory.

9.3 Paging

Paging is a memory-management scheme that permits the physical address space of a process to be non-contiguous. It avoids external fragmentation and allows the logical address space to be larger than the physical memory (when combined with virtual memory). Paging is the dominant memory management technique in modern operating systems, including Linux, Windows, macOS, and xv6.

Physical memory is divided into fixed-size blocks called frames, and logical memory is divided into blocks of the same size called pages. When a process needs to run, its pages are loaded into any available frames—no contiguity required. The page size is typically 4 KB, though larger pages (2 MB, 1 GB) are supported by modern CPUs for performance reasons (see huge pages).

The CPU generates a logical address, which is divided into two parts: a page number (p) and a page offset (d). The page number is used as an index into a page table, which contains the base address of each frame in physical memory. The physical address is computed as frame_base + offset.

/* Logical to physical address translation */ // Logical address: 32 bits (example) // Page size: 4 KB = 2^12, so offset = 12 bits // Page number = 32 - 12 = 20 bits logical_address: page_number = logical_address >> 12 offset = logical_address & 0xFFF // Look up page table frame_base = page_table[page_number].frame // Physical address physical_address = (frame_base << 12) | offset

The page table is maintained by the OS and stored in main memory. A hardware register called the page-table base register (PTBR) points to the page table. On each memory access, the MMU must first read the page table to find the frame number, then access the actual data. This doubles the number of memory accesses, so modern CPUs use a translation lookaside buffer (TLB)—a small, fast cache of recent page-table entries—to speed up translation.

💡 TLB: The Speed Multiplier

Without a TLB, every memory access would require two memory accesses (one for the page table, one for the data). The TLB caches recently used page-table entries, so most translations complete in a single cycle. TLB hit rates are typically 95–99% for well-behaved programs. A TLB miss triggers a page-table walk to fetch the entry from memory.

Each page-table entry (PTE) contains several control bits in addition to the frame number. The most important are: valid/invalid bit (whether the page is in memory), read/write bits (access permissions), user/supervisor bit (whether the page is accessible in user mode), dirty bit (whether the page has been modified), and reference bit (whether the page has been accessed recently, used by replacement algorithms).

In xv6, the page table is a three-level structure on RISC-V (Sv39). The walk() function in kernel/vm.c traverses the three levels to find the PTE for a given virtual address. The mappages() function creates mappings by writing frame addresses and permission bits into the page table. This is the same mechanism described by Silberschatz, implemented in a real (teaching) kernel.

9.4 Structure of the Page Table

For a 32-bit system with 4 KB pages, a single-level page table would require 2^20 entries (about 1 million), each 4 bytes, totaling 4 MB per process. This is wasteful, especially for small processes. Modern systems solve this with hierarchical paging, hashed page tables, or inverted page tables.

Hierarchical paging (also called multilevel paging) breaks the page table into multiple levels. A two-level scheme divides the page number into a page directory index and a page table index. Only the page directory is always in memory; the second-level tables are allocated on demand. If a process uses only a small portion of its address space, most page-table entries are never created, saving memory.

/* Two-level page table (32-bit example) */ // Logical address: 32 bits // [ page_dir_index (10) | page_table_index (10) | offset (12) ] translate(addr): dir_index = addr >> 22 // top 10 bits tbl_index = (addr >> 12) & 0x3FF // middle 10 bits offset = addr & 0xFFF // bottom 12 bits dir_entry = page_directory[dir_index] if (!dir_entry.valid) fault tbl_entry = dir_entry.table_ptr[tbl_index] if (!tbl_entry.valid) fault return (tbl_entry.frame << 12) | offset

For 64-bit systems, two levels are insufficient. A 64-bit address with 4 KB pages requires 52 bits of page number, which would need five or six levels of paging. In practice, most 64-bit architectures (x86-64, ARMv8) use four-level page tables, supporting 48 bits of virtual address space (256 TB). Five-level paging (57 bits, 128 PB) is available on newer Intel CPUs. The unused high bits must be zero or all-ones (canononical address form).

Hashed page tables are used for address spaces larger than 32 bits. A virtual page number is hashed, and the hash value indexes into a hash table of page-table entries. Each entry contains the virtual page number, the mapped page frame, and a pointer to the next entry (chaining for collisions). This works well for sparse address spaces.

Inverted page tables take a different approach: instead of one entry per virtual page, there is one entry per physical frame. The table is indexed by physical frame number, and each entry stores the process ID and virtual page number that maps to that frame. This keeps the page table size proportional to physical memory, not virtual memory. The drawback is that looking up a virtual address requires searching the table (or using a hash), which is slower. PowerPC, UltraSPARC, and IA-64 use inverted page tables.

ℹ️ Trade-off

Standard (forward) page tables are fast to look up (direct indexing) but can be huge for large address spaces. Inverted page tables are compact (proportional to physical memory) but slower to search. Hashed page tables are a compromise. Modern x86 and ARM use multilevel forward page tables with TLBs to get the best of both worlds.

In xv6 on RISC-V (Sv39), the page table has three levels, each with 512 entries (9 bits per level). The virtual address is 39 bits: 27 bits for the three page-table indices (9+9+9) and 12 bits for the offset. This supports 512 GB of virtual address space per process. The SATP register holds the physical address of the root page table, and the hardware walks the three levels on a TLB miss.

9.5 Swapping

Swapping is a technique that allows the total logical address space of all processes to exceed the physical memory. A process (or parts of it) can be swapped out—copied from memory to a backing store (usually disk)—and later swapped in when it is needed again. This creates the illusion of more memory than physically exists.

In early systems, swapping moved entire processes between memory and disk. When the OS needed to run a process that was swapped out, it would swap in the entire process before scheduling it. This was simple but slow: moving a 100 MB process to and from disk takes significant time. Modern systems use paging instead, swapping individual pages rather than entire processes. This is called demand paging and is covered in Chapter 10.

The backing store for swapped data is typically a dedicated swap partition or swap file on disk. The OS maintains metadata to track which pages of which processes are on the swap device and where they are located. When a process references a page that is not in memory (a page fault), the OS finds the page on the swap device, reads it into a free frame, updates the page table, and restarts the instruction.

⚠️ Swap Performance

Swapping is slow because disk I/O is orders of magnitude slower than memory access. A system that swaps too much suffers from thrashing (Section 10.6), where it spends more time swapping than executing. Modern systems with large RAM may disable swapping entirely, but this means out-of-memory conditions cause immediate process termination rather than graceful degradation.

In xv6, there is no swapping mechanism—the teaching kernel keeps all process pages in memory. However, the page-fault trap handler in kernel/trap.c does kill processes that access invalid addresses. A real OS would extend this handler to check whether the faulting page is on the swap device and, if so, bring it in. The sbrk() system call in xv6 grows the process's heap by allocating new pages, but it does not support lazy allocation or swapping.

Mobile operating systems (iOS, Android) typically do not use disk-based swapping. Instead, they ask applications to free memory voluntarily, and if memory pressure persists, they terminate background applications. This is because flash storage has limited write endurance, and swapping would wear it out quickly. macOS uses memory compression (Section 10.7) as an alternative to swapping to disk.

9.6 Intel 32/64-bit Architecture

The Intel x86 architecture has evolved from 16-bit (8086) to 32-bit (80386+) to 64-bit (x86-64 / AMD64). Each generation introduced new memory management features. Understanding the Intel architecture is important because it is the most widely used desktop and server architecture and is the target of many OS textbooks.

In 32-bit mode (IA-32), Intel uses a two-level page table: a page directory (1024 entries) and a page table (1024 entries each). With 4 KB pages, this supports 4 GB of virtual address space (1024 × 1024 × 4 KB = 4 GB). The CR3 register holds the physical address of the page directory. Intel also supports PAE (Physical Address Extension), which adds a third level and allows up to 64 GB of physical memory (though each process is still limited to 4 GB virtual).

In 64-bit mode (x86-64 / IA-32e), Intel uses a four-level page table structure called IA-32e paging. Each level has 512 entries (9 bits). With 4 KB pages, this supports 48 bits of virtual address space (256 TB). A newer five-level paging mode (LA57) extends this to 57 bits (128 PB). The CR3 register still holds the root, and the hardware performs a four-level (or five-level) walk on a TLB miss.

FeatureIA-32 (32-bit)x86-64 (64-bit)
Virtual address width32 bits (4 GB)48 or 57 bits (256 TB / 128 PB)
Page table levels2 (or 3 with PAE)4 (or 5 with LA57)
Entries per level1024 (10 bits)512 (9 bits)
Page sizes4 KB, 4 MB4 KB, 2 MB, 1 GB
Root registerCR3CR3
TLBYes (L1 data + instruction)Yes (multi-level TLB)

Intel CPUs also support huge pages: 2 MB and 1 GB pages in 64-bit mode. A 2 MB page uses a single PDE (page directory entry) with the PS (page size) bit set, eliminating one level of translation. This reduces TLB pressure for applications with large working sets (databases, virtual machines). Linux exposes huge pages via the hugetlbfs filesystem and transparent huge pages (THP).

💡 TLB and PCID

On context switch, the TLB must be flushed (or partially flushed) because entries from the old process are invalid. Intel CPUs support PCID (Process Context ID), which tags TLB entries with a process identifier, allowing multiple processes' TLB entries to coexist. This avoids flushing the entire TLB on every context switch, significantly improving performance for workloads with frequent context switches.

The Intel architecture also includes NX bit (No eXecute, also called the XD bit—eXecute Disable), which marks pages as non-executable. This is a security feature that prevents code execution from data pages, mitigating buffer-overflow attacks. The OS sets the NX bit on stack and heap pages to prevent shellcode injection. This is an example of how hardware features support OS-level security policies.

9.7 ARMv8 Architecture

The ARMv8 architecture is a 64-bit RISC architecture used in most smartphones, tablets, and increasingly in servers (e.g., AWS Graviton). It has a memory management unit similar to x86-64 but with different terminology and structure. Understanding ARMv8 is important for mobile and embedded OS development.

ARMv8 (AArch64) uses a multilevel page table with 4 KB pages. The virtual address is 48 bits (or 52 bits with ARMv8.2-LPA), supporting 256 TB of virtual address space. The page table has up to four levels: Level 0 (root), Level 1, Level 2, and Level 3 (leaf). Each level has 512 entries (9 bits). The TTBR0_EL1 register holds the physical address of the root page table for user-space, and TTBR1_EL1 holds the root for kernel-space. This split simplifies kernel address translation and avoids flushing kernel TLB entries on context switch.

/* ARMv8 (AArch64) address translation */ // Virtual address: 48 bits (with 4 KB pages) // [ L0 (9) | L1 (9) | L2 (9) | L3 (9) | offset (12) ] translate(va): l0_idx = (va >> 39) & 0x1FF l1_idx = (va >> 30) & 0x1FF l2_idx = (va >> 21) & 0x1FF l3_idx = (va >> 12) & 0x1FF off = va & 0xFFF l0 = TTBR[l0_idx] // TTBR0 or TTBR1 l1 = l0.table[l1_idx] l2 = l1.table[l2_idx] // L2 can be a block descriptor (2 MB) or table pointer if (l2.is_block) return (l2.base << 21) | (va & 0x1FFFFF) l3 = l2.table[l3_idx] return (l3.base << 12) | off

ARMv8 supports block descriptors at intermediate levels: 1 GB blocks at Level 1 and 2 MB blocks at Level 2. These are equivalent to x86 huge pages. Using blocks reduces the number of page-table levels traversed and reduces TLB pressure. The OS can choose between 4 KB pages, 2 MB blocks, and 1 GB blocks depending on the application's memory access patterns.

ℹ️ ARM vs. x86 Page Tables

Both ARMv8 and x86-64 use four-level page tables with 4 KB base pages and 9 bits per level. The key difference is that ARM uses separate page tables for user and kernel (TTBR0 and TTBR1), while x86 uses a single page table with the kernel mapped at the top of the address space. ARM's approach avoids kernel TLB flushes on context switch, while x86's approach allows the kernel to access user memory without switching tables.

ARMv8 also includes the ASID (Address Space ID) feature, similar to Intel's PCID. Each process is assigned an 8-bit or 16-bit ASID, and TLB entries are tagged with it. On context switch, the OS sets the new ASID in the TTBR0 register, and the hardware automatically uses only TLB entries matching the current ASID. This avoids flushing the TLB on every context switch, improving performance for workloads with many short-lived processes.

Security extensions in ARMv8 include TrustZone, which provides two execution environments: the Secure World (trusted OS, trusted applications) and the Normal World (regular OS, regular applications). Each world has its own virtual address space and page tables, and hardware enforces isolation between them. This is used for secure boot, DRM, biometric authentication, and mobile payments. The OP-TEE project provides an open-source trusted OS that runs in the Secure World alongside a Linux kernel in the Normal World.

10.1 Background

Virtual memory is a technique that allows the execution of a process that may not be completely in memory. The main advantage is that programs can be larger than physical memory. Further, virtual memory abstracts physical memory into a large, uniform array of storage, separating the programmer's view of memory from the actual hardware. This makes programming easier and enables memory protection.

The concept of virtual memory builds on paging (Chapter 9). In a virtual memory system, a process's pages are loaded into physical frames on demand. If a process references a page that is not in memory, a page fault occurs, and the OS brings the page in from disk. This is called demand paging and is the most common form of virtual memory.

Virtual memory also enables memory-mapped files, where a file on disk is mapped into a process's virtual address space. Reading and writing the mapped memory transparently reads and writes the file. This is more efficient than explicit read() and write() calls because the OS handles paging and caching. The mmap() system call in POSIX provides this feature.

ℹ️ Virtual Memory Benefits

Virtual memory provides: (1) larger address space—a process can use more memory than physically available; (2) protection—each process has its own address space, isolated from others; (3) memory sharing—pages can be shared between processes (e.g., shared libraries, copy-on-write fork); (4) efficient I/O—demand paging loads only the pages actually used.

In xv6, virtual memory is implemented via the RISC-V Sv39 page table. Each process has its own page table, created by proc_pagetable(). The kernel is mapped at high addresses (starting at 0x80000000), and user code, data, and stack are mapped at lower addresses. The uvmalloc() and uvmdealloc() functions grow and shrink the user address space. However, xv6 does not implement demand paging—all pages are allocated eagerly when sbrk() is called. A real OS would implement lazy allocation: allocate the page table entry but mark it invalid, and only allocate the physical frame when the page is first accessed.

The performance of virtual memory depends on the locality of reference principle. Programs tend to access a small set of pages at any given time (the working set). If the working set fits in physical memory, the page-fault rate is low and performance is good. If the working set exceeds physical memory, the system thrashes (Section 10.6), spending most of its time moving pages between memory and disk.

10.2 Demand Paging

Demand paging is a method of virtual memory where pages are loaded only when they are demanded (referenced) by the executing process. When a process starts, only the first page (containing the entry point) is loaded. As the process executes and references more pages, each missing page is brought in on demand. This is analogous to demand-driven inventory: stock is replenished only when needed.

The key mechanism is the valid/invalid bit in each page-table entry. When a page is allocated but not yet loaded, the PTE is marked invalid. When the CPU references such a page, the MMU raises a page fault (a type of trap). The OS page-fault handler checks whether the reference is valid (within the process's logical address space) and, if so, locates the page on disk, finds a free frame, reads the page into the frame, updates the PTE to point to the frame and mark it valid, and restarts the faulting instruction.

/* Page fault handler (simplified) */ page_fault_handler(addr): // 1. Check if address is valid (within process VMA) if (!is_valid_address(addr)) kill(process, SIGSEGV) // 2. Find a free frame (or evict one) frame = get_free_frame() if (frame == NULL) { victim = select_victim_page() if (victim.dirty) write_page_to_disk(victim) frame = victim.frame victim.pte.valid = false } // 3. Read page from disk into frame read_page_from_disk(addr.page, frame) // 4. Update PTE pte = get_pte(addr) pte.frame = frame pte.valid = true pte.dirty = false // 5. Restart the faulting instruction return to_user_mode

The performance of demand paging is measured by the effective access time. If the page-fault rate is p (0 ≤ p ≤ 1), the memory access time is ma, and the page-fault service time is pft, then:

EAT = (1 − p) × ma + p × pft

If p = 0, there are no page faults and EAT = ma. If p = 1, every access faults and EAT = pft (very slow). Even a small page-fault rate can be devastating: if ma = 100 ns and pft = 10 ms, then a 1% fault rate gives EAT = 0.99 × 100 + 0.01 × 10,000,000 = 100,099 ns—over 1000× slower than a no-fault access. This is why the OS must keep the page-fault rate very low.

⚠️ Page Fault Cost

A page fault is extremely expensive because it involves disk I/O. Even with NVMe SSDs (~100 μs), a page fault is 1000× slower than a memory access. The OS must minimize faults by keeping the working set in memory and choosing good replacement algorithms. A high fault rate leads to thrashing.

In xv6, demand paging is not implemented—pages are allocated eagerly. However, the trap handler in kernel/trap.c does handle page faults (by killing the process). To add demand paging to xv6, one would: (1) modify sbrk() to only grow the page table, not allocate frames; (2) add a page-fault handler that allocates a frame on first access; (3) implement a swap area on disk for evicted pages; (4) add a page-replacement algorithm. This is a common advanced xv6 lab exercise.

10.3 Copy-on-Write

Copy-on-Write (CoW) is an optimization that avoids copying pages until they are modified. When a process forks, instead of duplicating all the parent's pages, the child shares the parent's pages. Both parent and child page-table entries are marked read-only and copy-on-write. When either process writes to a shared page, a protection fault occurs, and the OS creates a private copy of the page for the writing process.

CoW dramatically speeds up fork(). Without CoW, forking a process with 1 GB of memory would require copying 1 GB of data, which takes tens of milliseconds. With CoW, fork() only copies the page table (a few MB), and pages are copied lazily only if written. In practice, many forked processes immediately call exec(), which replaces the address space entirely, so most pages are never copied.

/* Copy-on-Write fork flow */ fork(): child = new_process() child.pagetable = copy_pagetable(parent.pagetable) // Mark all writable pages as read-only + CoW for each page p in child.pagetable: if (p.writable): p.writable = false p.cow = true p.refcount++ // shared reference count // Same for parent's pages for each page p in parent.pagetable: if (p.writable): p.writable = false p.cow = true cow_fault_handler(addr): pte = get_pte(addr) if (!pte.cow) kill(process) if (pte.refcount == 1): // Only this process uses it; just make writable pte.writable = true pte.cow = false else: // Create a private copy new_frame = alloc_frame() copy_page(pte.frame, new_frame) pte.frame = new_frame pte.refcount-- pte.writable = true pte.cow = false

CoW requires hardware support: the MMU must distinguish between a "real" protection violation (accessing a page the process should not access) and a CoW fault (accessing a page that is temporarily read-only but should be writable). On x86, the CR2 register holds the faulting address, and the error code indicates whether it was a write fault. On RISC-V, the scause register indicates a store page fault.

💡 CoW in Practice

Linux uses CoW extensively: fork() is nearly free, and mmap() with MAP_PRIVATE uses CoW to share file-backed pages until modified. The vfork() system call goes further: it shares the entire address space without even copying the page table, but the child must not modify anything and must call exec() or _exit() immediately.

In xv6, fork() does not use CoW—it eagerly copies all user pages via uvmcopy() in kernel/vm.c. This is simple but slow. Implementing CoW in xv6 is a common lab exercise: one must (1) add a reference count to each physical frame, (2) modify uvmcopy() to share pages and clear the PTE_W bit, (3) handle write page faults in trap.c by copying the page and restoring PTE_W, and (4) handle the case where the last reference to a page is freed.

10.4 Page Replacement

When a page fault occurs and no free frame is available, the OS must evict a page from memory to make room. The choice of which page to evict is the page replacement problem. A good replacement algorithm minimizes the number of page faults, keeping the page-fault rate low and performance high.

The reference bit (also called the use bit or access bit) in each PTE helps the OS track page usage. The hardware sets this bit to 1 whenever the page is accessed. The OS can read and clear it to determine which pages are being used. Some architectures also provide a modify bit (dirty bit) that is set when the page is written. A dirty page must be written back to disk before eviction; a clean page can be evicted without I/O.

FIFO Page Replacement

The simplest algorithm is First-In, First-Out (FIFO). The OS maintains a queue of pages in memory, ordered by arrival time. When a page must be evicted, the oldest page (the one at the front of the queue) is removed. FIFO is easy to implement but can perform poorly: it may evict a frequently used page simply because it was loaded long ago.

/* FIFO page replacement */ // Reference string: 7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2 // 3 frames FIFO trace (3 frames): 7 → [7] fault 0 → [7, 0] fault 1 → [7, 0, 1] fault 2 → [0, 1, 2] evict 7 fault 0 → [0, 1, 2] hit 3 → [1, 2, 3] evict 0 fault 0 → [2, 3, 0] evict 1 fault 4 → [3, 0, 4] evict 2 fault 2 → [0, 4, 2] evict 3 fault 3 → [4, 2, 3] evict 0 fault 0 → [2, 3, 0] evict 4 fault 3 → [2, 3, 0] hit 2 → [2, 3, 0] hit // Total: 10 faults out of 13 references

FIFO suffers from Belady's anomaly: increasing the number of frames can increase the number of page faults. For the reference string above with 3 frames, there are 10 faults; with 4 frames, there are 10 faults (no improvement); but for some reference strings, adding frames actually increases faults. This is counterintuitive and shows that FIFO is not a stack algorithm.

Optimal Page Replacement

The optimal algorithm (OPT or MIN) replaces the page that will not be used for the longest time in the future. It has the lowest possible fault rate for a fixed number of frames and is used as a benchmark. Unfortunately, it requires knowledge of the future reference string, which is impossible in practice. However, it is useful for comparison and for offline analysis.

ℹ️ Why Optimal Matters

The optimal algorithm is not implementable, but it provides a theoretical lower bound on page faults. Researchers use it to evaluate practical algorithms: if an algorithm's fault rate is close to optimal, it is considered good. LRU approximates optimal well in practice because programs tend to exhibit temporal locality—pages used recently are likely to be used again soon.

LRU Page Replacement

The Least Recently Used (LRU) algorithm replaces the page that has not been used for the longest time. It is based on the principle of temporal locality: if a page has not been used recently, it is unlikely to be used in the near future. LRU is a good approximation of optimal and does not suffer from Belady's anomaly (it is a stack algorithm).

True LRU requires the hardware to timestamp every memory access or maintain a stack of page references, which is expensive. In practice, the OS uses LRU approximations:

  • Reference bit (second-chance) algorithm: Pages are arranged in a circular list (like FIFO). When a page must be evicted, the OS checks the reference bit. If it is 1, the bit is cleared and the page is given a "second chance" (moved to the back of the queue). If it is 0, the page is evicted. This approximates LRU using only the 1-bit reference bit.
  • Enhanced second-chance: Uses both the reference bit and the modify bit. Pages are classified into four classes: (0,0), (0,1), (1,0), (1,1). The OS evicts the first page in the lowest class, preferring clean pages (no write-back needed).
  • Aging: Maintains a history of reference bits over time. Each page has an 8-bit counter, shifted right each interval, with the current reference bit shifted into the MSB. The page with the smallest counter is the least recently used.

Counting-Based Algorithms

Counting-based algorithms maintain a reference count for each page. The LFU (Least Frequently Used) algorithm evicts the page with the smallest count. The MFU (Most Frequently Used) algorithm evicts the page with the largest count, based on the heuristic that a page with a high count has been used a lot and may be done. Both are rarely used in practice because they require expensive counter maintenance and do not adapt well to changing access patterns.

💡 What Real Systems Use

Linux uses a variant of LRU called the active/inactive list (or second-chance in older kernels, MGLRU in newer ones). Windows uses a clock algorithm (a variant of second-chance). Most systems use approximations rather than true LRU because maintaining exact access order is too expensive. The key insight is that any LRU approximation is much better than FIFO.

10.5 Allocation of Frames

When multiple processes compete for physical memory, the OS must decide how to allocate frames among them. Two extremes are equal allocation (every process gets the same number of frames) and proportional allocation (frames are distributed in proportion to process size). Proportional allocation is generally better because larger processes need more frames to maintain a low fault rate.

A minimum allocation is necessary: each process needs at least enough frames to hold the pages referenced by a single instruction. For example, on x86, a single instruction may span two pages (if it straddles a page boundary) and may reference two operands in two other pages. So the minimum is typically 3–4 frames. If a process has fewer frames than this minimum, it cannot execute a single instruction without faulting, leading to an infinite loop of faults.

⚠️ Minimum Frames

If a process has too few frames, it may not be able to complete a single instruction. For example, an instruction that fetches from one page, reads a source operand from another, and writes a destination to a third needs at least 3 frames. If only 2 are available, the OS evicts one of the needed pages to load another, causing an immediate re-fault. This is a thrashing condition.

Global allocation allows a process to select a replacement frame from the set of all frames (any process's page). This is flexible: a process that needs more memory can take frames from other processes. Local allocation restricts replacement to the process's own frames. Global allocation is more common because it adapts to changing memory demands, but it can cause one process to steal frames from another, increasing the victim's fault rate.

With global allocation, the number of frames allocated to a process can vary over time. The OS may use a page-fault frequency (PFF) strategy: if a process's fault rate is too high, it gets more frames; if too low, it gives up frames. This is a feedback control system that keeps fault rates within a target range and prevents thrashing.

10.6 Thrashing

Thrashing occurs when a process spends more time paging than executing. If a process does not have enough frames, it page-faults frequently. Each fault evicts a page that will be needed soon, causing another fault. The CPU utilization drops, and the OS may respond by scheduling more processes (thinking the CPU is idle), which makes the problem worse. The system enters a downward spiral of decreasing performance.

The cause of thrashing is that the total working set of all processes exceeds the available physical memory. The working set is the set of pages a process is actively using. If the OS loads too many processes, each gets fewer frames than its working set, and every process thrashes.

/* Thrashing scenario */ // System has 100 frames // Process A working set: 40 pages // Process B working set: 35 pages // Process C working set: 30 pages // Total working set: 105 pages > 100 frames // Each process faults constantly because it cannot // keep its full working set in memory. // CPU utilization drops to near zero. // OS sees low CPU → schedules MORE processes → worse!

The working-set model addresses thrashing by tracking each process's working set and ensuring that the total does not exceed physical memory. The working set is estimated using a window of Δ references: the working set W(t, Δ) is the set of pages referenced in the last Δ memory accesses. If Σ W_i > m (total working sets exceed memory m), the OS suspends a process (swaps it out entirely) until memory is available.

ℹ️ Working Set vs. Page-Fault Frequency

The working-set model is proactive: it estimates each process's needs and prevents overcommitment. The page-fault frequency (PFF) approach is reactive: it monitors fault rates and adjusts allocations. Both aim to keep each process's allocation above its working set size. PFF is simpler to implement and is used in practice.

The working-set size depends on the program's locality. A program with good locality has a small working set; a program with poor locality (e.g., randomly accessing a large array) has a large working set. Compilers and programmers can improve locality by: (1) accessing data sequentially (cache-friendly loops), (2) grouping frequently used data together, (3) using smaller data structures, and (4) avoiding pointer chasing. These optimizations reduce the working set and improve virtual memory performance.

In xv6, thrashing is not a concern because there is no demand paging—all pages are in memory. However, xv6 limits the number of processes (NPROC, typically 64) and the size of each process's address space. A real OS must carefully manage the trade-off between multiprogramming level (more processes = better CPU utilization) and memory pressure (more processes = more thrashing risk).

10.7 Memory Compression

Memory compression is an alternative to swapping pages to disk. Instead of writing a cold (infrequently used) page to the swap device, the OS compresses it and stores the compressed version in a reserved area of RAM. When the page is needed again, it is decompressed. Since compression and decompression in RAM are much faster than disk I/O, this can significantly improve performance under memory pressure.

macOS has used memory compression since OS X 10.9 (Mavericks). When memory pressure rises, the kernel compresses the least-recently-used pages and stores them in a compressed memory region. If pressure continues to rise, compressed pages are eventually written to disk. This two-tier approach (compress first, swap second) reduces disk I/O and improves responsiveness.

ℹ️ Compression Trade-offs

Compression trades CPU time for I/O time. Compressing a 4 KB page takes a few microseconds; writing it to an SSD takes ~100 μs, to an HDD ~10 ms. So compression is a net win for HDDs and a marginal win for SSDs. The downside is increased CPU usage and the need for a compressed memory region. Modern algorithms (LZ4, zstd) are fast enough that the trade-off is favorable for most workloads.

Linux added zswap and zram as compressed swap backends. zswap is a compressed cache in RAM for pages that would otherwise go to the swap device. zram creates a compressed block device in RAM that can be used as swap. Both reduce disk I/O at the cost of CPU. Android uses zram extensively because mobile devices have limited flash endurance and no traditional swap partition.

The compression algorithm matters. LZ4 is fast (decompression at several GB/s) but has a modest compression ratio. zstd (Zstandard) offers a better ratio with reasonable speed and is used by default in recent Linux and Windows. The OS must balance compression ratio (saves more memory) against speed (faster decompression on page-in). Adaptive algorithms that choose the compression level based on memory pressure are an active research area.

10.8 Allocating Kernel Memory

Kernel memory has different allocation requirements than user memory. User pages are uniformly sized (4 KB) and allocated/freed in bulk. Kernel memory, by contrast, needs to allocate objects of varying sizes: small structures (e.g., a 64-byte task_struct), medium buffers (e.g., 2 KB network buffers), and large contiguous regions (e.g., for DMA). The kernel cannot use the same page-based allocator for all of these.

Most kernels use a slab allocator (or its successor, the slub allocator in Linux). The slab allocator manages caches of pre-initialized objects of specific types. When the kernel needs a new inode or file structure, it gets one from the appropriate slab cache—already initialized and ready to use. When freed, the object returns to the cache for reuse. This avoids the overhead of initialization and reduces fragmentation.

/* Slab allocator concept (Linux) */ // Each kernel object type has a dedicated cache struct kmem_cache: name // e.g., "inode_cache" object_size // e.g., 608 bytes slabs // list of slab pages // Allocation kmalloc(size, flags): cache = find_cache_for_size(size) obj = cache.alloc() // from free list return obj // Common caches: // kmalloc-32, kmalloc-64, ..., kmalloc-8192 // inode_cache, dentry_cache, task_struct, ...

The buddy system is used for allocating power-of-two-sized blocks of pages. It maintains free lists for blocks of size 1, 2, 4, 8, ... pages. When a block of size n is requested, the allocator finds the smallest power of two ≥ n that has a free block. If the block is larger than needed, it is split into two buddies, one of which is returned and the other added to a smaller free list. When a block is freed, the allocator checks if its buddy is also free; if so, they are merged into a larger block. This provides fast allocation and coalescing but can cause internal fragmentation (rounding up to the next power of two).

💡 Two-Level Allocation

Most kernels use a two-level strategy: the buddy system for page-sized (or larger) allocations, and the slab/slub allocator for sub-page objects. The buddy system manages physical pages; the slab allocator carves objects out of pages obtained from the buddy system. This combines the simplicity of the buddy system with the efficiency of object caching.

In xv6, kernel memory allocation is simpler. The kalloc() and kfree() functions in kernel/kalloc.c manage a free list of 4 KB pages. There is no slab allocator—kernel code that needs smaller objects either wastes a full page or manages sub-allocations manually. This is acceptable for a teaching OS but would be inefficient in a production system. The kalloc() implementation uses a per-CPU free list with a global fallback, which is a simplified version of Linux's approach.

10.9 Other Considerations

Several additional factors affect virtual memory performance and design beyond the core algorithms discussed above.

Prepaging is the opposite of demand paging: instead of loading pages on demand, the OS preloads pages that it predicts will be needed. For example, when a process starts, the OS may preload the first few pages of the executable and the first few pages of shared libraries. This reduces the number of page faults at startup. The trade-off is that if the preloaded pages are not used, the I/O was wasted. Prepaging is beneficial when the cost of faults outweighs the cost of unnecessary I/O, which is often the case for HDDs.

Page size is a critical design decision. Larger pages (e.g., 2 MB, 1 GB) reduce the number of PTEs, reduce TLB pressure, and reduce page-table memory. However, they also increase internal fragmentation (a 1 GB page wastes up to 1 GB if partially used) and make fine-grained protection impossible. Most systems use 4 KB as the default and offer huge pages as an option for large-workload applications (databases, JVMs, virtual machines). The OS may use transparent huge pages (THP), which automatically coalesce 4 KB pages into 2 MB pages when possible.

Program structure affects paging performance. Consider two loops that access a 2D array: one row-by-row, one column-by-column. The row-by-row access is sequential and cache-friendly; the column-by-column access jumps across pages, causing many faults. Compilers and programmers should arrange data and code to maximize locality. For example, storing frequently used global variables together, keeping functions small, and using array layouts that match access patterns all improve virtual memory performance.

/* Locality example: row-major vs column-major */ // C arrays are row-major: a[i][j] and a[i][j+1] are adjacent // GOOD: sequential access, good locality for (i = 0; i < N; i++) for (j = 0; j < N; j++) a[i][j] = 0; // BAD: striding across rows, poor locality for (j = 0; j < N; j++) for (i = 0; i < N; i++) a[i][j] = 0;

I/O interlock and page locking are needed when pages are involved in I/O. If a page is being written to by a DMA controller, it must not be evicted or modified by another process. The OS marks such pages as locked (pinned) so the replacement algorithm skips them. This is also important for memory-mapped I/O, where device registers are mapped into the kernel's address space and must not be paged out.

⚠️ DMA and Paging

If a page is evicted and its frame is reused while a DMA transfer is in progress, the DMA will write to the wrong page, corrupting data. The OS must pin (lock) pages involved in DMA transfers. This is why get_user_pages() in Linux pins user pages before passing them to device drivers.

10.10 OS Examples

Different operating systems implement virtual memory with different strategies. This section compares the approaches used by Linux, Windows, and mobile OSes.

Linux

Linux uses a four-level page table on x86-64 (PGD, P4D, PUD, PMD, PTE—actually five levels with P4D, but conceptually four). The page replacement algorithm is based on the active/inactive list model: pages are on an "active" or "inactive" list. Pages are promoted from inactive to active when accessed, and demoted when not. The kswapd daemon runs in the background, evicting pages from the inactive list when memory is low. Linux also supports zswap (compressed cache) and zram (compressed swap in RAM).

Linux's mmap() system call supports memory-mapped files, anonymous mappings (not backed by a file), and shared memory. The fork() system call uses copy-on-write. Transparent Huge Pages (THP) automatically coalesce 4 KB pages into 2 MB pages for large allocations. The madvise() system call lets programs hint about their access patterns (e.g., MADV_SEQUENTIAL, MADV_RANDOM), allowing the kernel to optimize paging.

Windows

Windows uses a two-level page table on x86 (32-bit) and four-level on x86-64. The page replacement algorithm is a clock algorithm (a variant of second-chance). Windows supports memory-mapped files via MapViewOfFile() and copy-on-write for fork()-like operations (though Windows does not have a traditional fork()). Windows also supports large pages (2 MB, 1 GB) and memory compression (since Windows 10).

Mobile OSes (iOS, Android)

Mobile operating systems avoid traditional disk-based swapping because flash storage has limited write endurance and swapping would wear it out. Instead, they use memory compression and application termination. When memory pressure rises, the OS asks background apps to free memory (via callbacks like onTrimMemory() on Android). If pressure persists, the OS terminates background apps, saving their state for later restoration. iOS uses a similar approach with UIApplicationDelegate methods.

ℹ️ Mobile Memory Strategy

Mobile OSes prioritize foreground responsiveness over background multitasking. Rather than swapping (which would wear flash and drain battery), they compress memory and terminate background apps. This is acceptable on mobile because users typically interact with one app at a time, and apps can save/restore state quickly. The trade-off is that background apps may be killed without warning, so they must be designed to handle termination gracefully.

In xv6, the virtual memory system is minimal but functional. Each process has a page table (Sv39 on RISC-V), the kernel is mapped at high addresses, and user pages are mapped at low addresses. There is no demand paging, no swapping, no compression, and no slab allocator. The sbrk() system call grows the heap eagerly. Despite these limitations, xv6 demonstrates the core concepts: page tables, address translation, TLB management, and memory protection. Extending xv6 with demand paging, CoW, and a slab allocator are common advanced lab exercises that bridge the gap between the teaching OS and production systems.
