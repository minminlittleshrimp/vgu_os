13.1 File Concept

A file is a named collection of related information recorded on secondary storage. From the user's perspective, a file is the smallest logical unit of data that the OS manages. The OS maps files to physical blocks on the storage device, hiding the details of sectors, tracks, and cylinders from the user. Files are used to store programs (source code, executables), data (documents, databases, images), and metadata (configuration, logs).

A file has attributes (also called metadata) that describe it. These attributes are stored in the file's directory entry or inode and are managed by the OS. Common attributes include:

AttributeDescriptionExample
NameHuman-readable namereport.pdf
IdentifierUnique file ID (inode number)12345
TypeFile type (extension or magic number)PDF, ELF, JPEG
SizeCurrent size in bytes1,048,576
ProtectionAccess permissionsrwxr-xr-x
TimestampsCreation, modification, access time2026-08-16 14:30
OwnerUser who owns the filealice
LocationPhysical location on deviceBlock 1024–2048

File types are often indicated by the file extension (e.g., .txt, .c, .jpg). Windows relies heavily on extensions to determine how to handle files. Unix-like systems use extensions as a hint but also examine the file's magic number—a specific byte sequence at the beginning of the file that identifies its format. For example, an ELF executable starts with 0x7f ELF, a JPEG starts with 0xFF 0xD8, and a PDF starts with %PDF. The file command on Linux uses a database of magic numbers to identify file types.

ℹ️ File Structure

Some OSes (notably older systems like VMS and some mainframe OSes) support structured files with records and fields. Unix and Windows use unstructured files—a file is simply a sequence of bytes, and the application is responsible for interpreting the structure. This is more flexible: a text file, a database, and an image are all just byte sequences. The OS does not need to understand the format.

File operations are the basic actions the OS provides for manipulating files: create (make a new file), open (prepare a file for access, returning a file descriptor), read (read data from the file), write (write data to the file), seek (move the file position), close (release the file descriptor), and delete (remove the file). The open() operation is important: it loads the file's metadata into memory, checks permissions, and returns a file descriptor (a small integer) that subsequent operations use to refer to the file.

In xv6, files are represented by the struct file in kernel/file.h. The filealloc(), fileread(), filewrite(), and fileclose() functions in kernel/file.c implement the basic file operations. The sysfile.c file contains the system call implementations (sys_open, sys_read, etc.). Files are unstructured byte sequences, following the Unix model.

13.2 Access Methods

File access methods define how a process reads from and writes to a file. The two primary methods are sequential access and direct access (also called random access).

Sequential access is the simplest: information in the file is processed in order, one record (or byte) after another. A read operation reads the next portion of the file and advances the file pointer automatically. A write appends to the end of the file. This model is natural for text files, logs, and tape storage. Early file systems (and tape drives) supported only sequential access.

Direct access (random access) allows a process to read or write any block of the file directly, without reading all preceding blocks. The process specifies a block number (or byte offset), and the file system reads or writes that block. This is essential for databases, indexed files, and any application that needs to access specific records quickly. Modern file systems support both sequential and direct access via the lseek() system call, which moves the file pointer to an arbitrary position.

/* Sequential vs. direct access */ // Sequential: read file from start to end fd = open("log.txt", O_RDONLY); while (read(fd, buf, 1024) > 0) process(buf); // Direct: read block 42 fd = open("database.db", O_RDONLY); lseek(fd, 42 * BLOCK_SIZE, SEEK_SET); // jump to block 42 read(fd, buf, BLOCK_SIZE); // Direct: read record at offset 0x1A000 lseek(fd, 0x1A000, SEEK_SET); read(fd, &record, sizeof(record));

Some systems support an indexed access method, where an index is maintained for the file, allowing the process to look up a record by key. The index maps keys to block numbers, enabling fast lookup. This is the basis of indexed sequential access method (ISAM), used in early database systems. Modern databases build their own indexes on top of the file system's direct access capability, so the OS does not need to provide indexed access directly.

💡 lseek() and Random Access

The lseek() system call is the key to random access. It sets the file offset to a specified position, and subsequent read() or write() operations start from that position. lseek(fd, 0, SEEK_SET) rewinds to the beginning; lseek(fd, 0, SEEK_END) moves to the end. lseek(fd, -100, SEEK_END) moves 100 bytes before the end. This enables efficient access to any part of the file.

In xv6, both sequential and direct access are supported. The sys_lseek system call (if implemented) or the file offset in struct file allows random access. The fileread() and filewrite() functions in kernel/file.c use the file offset to determine where to read or write, and they advance the offset after each operation. This is the standard Unix model.

13.3 Directory Structure

A directory (or folder) is a collection of directory entries, each describing a file or subdirectory. The directory structure organizes files into a hierarchy, making it easier for users to find and manage files. Without directories, all files would be in a single flat namespace, which is unmanageable for systems with thousands or millions of files.

The simplest directory structure is the single-level directory: all files are in one directory. This is simple but does not scale: file names must be unique, and there is no way to group related files. Early personal computers (CP/M) used this model.

A two-level directory has a separate directory for each user. The master file directory (MFD) lists user directories, and each user file directory (UFD) lists that user's files. This solves the naming conflict problem (two users can have a file named report.txt) but does not allow users to organize files into subdirectories.

The tree-structured directory is the most common: directories can contain files and subdirectories, forming a tree. The root directory is at the top, and each file has a path name that describes its location, such as /home/alice/docs/report.pdf. This allows users to organize files hierarchically and avoids naming conflicts (two files can have the same name if they are in different directories).

/* Tree-structured directory */ // Path: /home/alice/docs/report.pdf // / // ├── home/ // │ ├── alice/ // │ │ ├── docs/ // │ │ │ └── report.pdf // │ │ └── photos/ // │ └── bob/ // │ └── ... // └── etc/ // └── passwd // Absolute path: starts from root (/) // Relative path: relative to current directory // "docs/report.pdf" (if cwd is /home/alice) // "../bob" (parent directory) // "." (current directory)

Path names can be absolute (starting from the root, e.g., /home/alice/docs) or relative (relative to the current working directory, e.g., docs/report.pdf). The special names . (current directory) and .. (parent directory) allow navigation. The OS maintains the current working directory (cwd) for each process, used as the base for relative paths.

ℹ️ Acyclic-Graph vs. Tree

A tree structure does not allow a file or directory to appear in two places. An acyclic-graph directory structure allows shared files and directories via links. Unix supports two types of links: hard links (multiple directory entries pointing to the same inode) and symbolic links (a special file containing the path to another file). Hard links cannot cross file systems or link to directories; symbolic links can. Windows supports symbolic links and junctions (similar to hard links for directories).

The directory operations include: create (create a new directory), delete (remove an empty directory), opendir / readdir (enumerate directory entries), rename, link (create a hard link), unlink (remove a directory entry), and symlink (create a symbolic link). The readdir() operation is used by commands like ls to list directory contents.

In xv6, the directory structure is a tree. Directories are represented as special files containing struct dirent entries (defined in kernel/fs.h), each with an inode number and a name. The namei() function in kernel/fs.c resolves a path name to an inode, traversing the directory tree. The dirlink() function creates a directory entry (hard link). xv6 does not support symbolic links. The root directory is inode 1 (the ROOTINO constant).

13.4 Protection

Protection in the context of file systems refers to the mechanisms that control which users can access which files and what operations they can perform. Protection is essential in multi-user systems to ensure that users cannot read or modify each other's files without permission, and that system files are protected from unauthorized modification.

The most common protection model is access control based on permissions. In Unix-like systems, each file has an owner (a user), a group, and a set of permission bits for three classes: owner (user), group, and others (world). For each class, there are three permissions: read (r), write (w), and execute (x). This is represented as a 9-bit mode, displayed as rwxr-xr-x (owner: rwx, group: r-x, others: r-x).

PermissionFor FilesFor Directories
Read (r)Read file contentsList directory contents
Write (w)Modify file contentsCreate/delete files in directory
Execute (x)Run as programEnter directory (cd, access by name)
⚠️ Directory Permissions

Directory permissions are subtle. Read permission on a directory allows listing its contents (e.g., ls). Execute permission allows accessing files in the directory by name (e.g., cat dir/file) and using it as a working directory (cd dir). A directory with --x permissions allows accessing known files by name but not listing the directory. This is used for "blind drop" directories where users can deposit files but not see what others have deposited.

Unix also supports setuid, setgid, and sticky bits. The setuid bit on an executable means it runs with the privileges of the file's owner, not the user who runs it. This is how passwd works: it runs as root to modify /etc/passwd. The setgid bit on a directory means new files in it inherit the directory's group. The sticky bit on a directory (e.g., /tmp) means only the file's owner (or root) can delete files, even if the directory is world-writable.

An alternative to permission bits is Access Control Lists (ACLs). An ACL is a list of entries, each specifying a user or group and the permissions granted to them. ACLs are more fine-grained than the owner/group/other model: you can grant specific permissions to specific users. POSIX ACLs (on Linux) and NTFS ACLs (on Windows) support this. For example, an ACL can grant user bob read-write access to a file owned by alice, without giving access to the entire group.

/* Permission models */ // Unix permission bits (9 bits) rwxr-xr-- // owner: rwx (7), group: r-x (5), other: r-- (4) // chmod 754 file // ACL (POSIX) user::rwx group::r-x other::r-- user:bob:rwx // extra: bob gets rwx group:devs:rw- // extra: devs group gets rw // Windows NTFS ACL ACL: Alice: FullControl Bob: ReadAndExecute Everyone: Read

Another model is capability-based protection, where a process holds a capability (an unforgeable token) that grants specific rights to a file. Capabilities are more flexible than ACLs (a process can pass a capability to another process) but are more complex to implement. The file descriptor in Unix is a simple form of capability: it grants the holder the right to perform the operations allowed at open() time.

In xv6, protection is minimal. The file system stores permission bits in the inode (struct dinode in kernel/fs.h), but xv6 does not enforce them—there is no concept of users or groups. All processes run with full privileges. The chmod system call exists but does not restrict access. Adding user-based protection to xv6 would require: (1) a user database, (2) a current-user field in the process structure, (3) permission checks in open(), read(), and write(), and (4) a setuid mechanism. This is a common advanced xv6 exercise.

13.5 Memory-Mapped Files

Memory-mapped I/O (or memory-mapped files) is a technique that maps a file into a process's virtual address space. Instead of using read() and write() system calls to access the file, the process accesses the file's data by reading and writing memory. The OS handles paging file data in and out of memory transparently, using the virtual memory system.

The mmap() system call (POSIX) creates a memory mapping. It takes a file descriptor, an offset, a length, and protection flags, and returns a pointer to the mapped region. After mapping, the process can read and write the mapped memory as if it were an array, and the OS ensures that the memory reflects the file's contents. Changes can be written back to the file with msync() or when the mapping is removed with munmap().

/* Memory-mapped file (POSIX mmap) */ int fd = open("data.bin", O_RDWR); void *map = mmap(NULL, file_size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0); // Access file data as memory struct record *rec = (struct record *)map; for (int i = 0; i < n; i++) { printf("%d: %s\n", rec[i].id, rec[i].name); rec[i].modified = 1; // writes to file } // Flush changes to file msync(map, file_size, MS_SYNC); // Unmap munmap(map, file_size); close(fd);

Memory-mapped files have several advantages over read()/write():

  • No system call overhead: After the initial mmap(), accessing the file is a simple memory access—no system call is needed for each read or write.
  • No data copy: The file data is mapped directly into the process's address space. With read(), data is copied from the kernel buffer cache to the user buffer; with mmap(), the same physical page is used.
  • Lazy loading: The OS loads only the pages that are actually accessed (demand paging), not the entire file. This is efficient for large files where only a small portion is used.
  • Sharing: Multiple processes can map the same file with MAP_SHARED, enabling efficient inter-process communication. Writes by one process are visible to others.
ℹ️ MAP_SHARED vs. MAP_PRIVATE

MAP_SHARED means changes to the mapped memory are written back to the file and are visible to other processes mapping the same file. MAP_PRIVATE uses copy-on-write: changes are not written to the file and are private to the process. MAP_PRIVATE is useful for loading executables (the code segment is shared, but data modifications are private) and for using a file as a template.

Memory-mapped files are used extensively in modern systems. The dynamic linker (ld.so) maps shared libraries into a process's address space. Database engines (e.g., SQLite, LMDB) use mmap() to access database files. The exec() system call uses mmap() to load the executable and its libraries. The sendfile() system call is related: it transfers data between file descriptors without copying through user space, using a similar zero-copy mechanism.

⚠️ mmap Pitfalls

mmap() has some pitfalls: (1) alignment—the offset must be page-aligned; (2) file growth—if the file grows beyond the mapped region, accessing the new area causes a fault; (3) signal—if the file is truncated, accessing the truncated region raises a SIGBUS signal; (4) consistency—with MAP_SHARED, there is no guarantee of when writes are flushed to disk; use msync() for durability.

In xv6, mmap() is not implemented. All file access is via read() and write(), which copy data between kernel buffers and user space. Implementing mmap() in xv6 would require: (1) a system call that creates a VMA (virtual memory area) mapping a file, (2) modifying the page-fault handler to load file pages on demand, (3) handling MAP_SHARED write-back, and (4) munmap() to remove mappings. This is a significant but instructive project that ties together the file system and virtual memory subsystems.

14.1 File-System Structure

A file system is organized into layers, each providing a specific abstraction. The layered design allows each layer to be implemented and modified independently, as long as it respects the interface of the layer below. The typical layers are:

LayerFunctionExample
ApplicationUser programscp, ls, text editor
System callsopen(), read(), write()POSIX API
VFSUniform interface to multiple FSLinux VFS
File systemMaps files to blocksext4, NTFS, FAT
I/O subsystemBuffering, caching, schedulingbuffer cache
Device driverDevice-specific commandsNVMe, SATA driver
HardwarePhysical deviceSSD, HDD

At the lowest level, the file system sees the storage device as a sequence of blocks (or sectors). The file system organizes these blocks into a structure that supports files and directories. A typical on-disk layout includes:

  • Boot block: Contains bootstrap code (at a fixed location, e.g., sector 0). The BIOS/UEFI loads this and transfers control to it.
  • Superblock: Contains metadata about the file system: type, size, block size, number of free blocks, location of the inode table, etc. This is the "master record" of the file system.
  • Inode table: An array of inodes (index nodes), each describing a file. An inode contains file metadata (size, timestamps, permissions) and pointers to data blocks.
  • Data blocks: The bulk of the device, holding file data. These are allocated to files as needed.
  • Free-space management: A bitmap or list tracking which blocks are free.
/* Typical file system on-disk layout */ // +-----------+-----------+---------+----------+---------+ // | Boot blk | Superblk | Inodes | Free map | Data | // | (1 blk) | (1 blk) | (N blk) | (M blk) | (rest) | // +-----------+-----------+---------+----------+---------+ // xv6 layout (kernel/fs.h): #define BSIZE 512 #define SBLOCK 1 // superblock at block 1 #define ROOTINO 1 // root directory inode struct superblock: magic // file system magic number size // size of file system in blocks nblocks // number of data blocks ninodes // number of inodes nlog // log blocks for crash recovery logstart // block number of log inodestart // block number of inode table bmapstart // block number of free bitmap
ℹ️ Inode vs. Directory Entry

An inode describes a file's metadata and data block locations. A directory entry (dirent) maps a name to an inode number. Multiple directory entries (hard links) can point to the same inode. The inode has a link count that tracks how many directory entries point to it; the file is deleted when the link count reaches zero. This separation of name (directory entry) from file (inode) is a key design of Unix file systems.

The file system must maintain consistency despite crashes. If the system crashes while the file system is updating metadata (e.g., allocating a block), the file system may be left in an inconsistent state. Modern file systems use journaling (a write-ahead log) to ensure consistency: metadata changes are first written to a journal, then applied to the file system. If a crash occurs, the journal is replayed to complete or undo the operation. xv6 uses a simple log (kernel/log.c) for this purpose.

In xv6, the file system structure is defined in kernel/fs.h. The superblock is at block 1, followed by the log, the inode table, the free bitmap, and data blocks. The readsb() function reads the superblock, and iget() reads an inode. The balloc() and bfree() functions manage the free bitmap. This is a classic Unix-like file system layout, simplified for teaching.

The inode is the central data structure. It contains the file's metadata (type, size, permissions, timestamps, link count) and pointers to data blocks. The block pointers may be direct (pointing directly to data blocks), indirect (pointing to a block of pointers), or double-indirect / triple-indirect (pointing to blocks of pointers to pointers). This allows small files to be accessed quickly (via direct pointers) while supporting very large files (via indirect pointers).

💡 Direct vs. Indirect Pointers

A typical inode has 12 direct pointers, 1 single-indirect, 1 double-indirect, and 1 triple-indirect pointer. With 4 KB blocks and 4-byte pointers: direct pointers cover 48 KB; single-indirect covers 4 MB; double-indirect covers 4 GB; triple-indirect covers 4 TB. This means small files (most files) are accessed with a single disk read, while large files can grow to terabytes. This is the design used by ext2/ext3 and xv6.

Directory operations are similar but operate on directory files. A directory is a special file containing directory entries (dirents), each mapping a name to an inode number. The dirlookup() function searches a directory for a name and returns the corresponding inode. The dirlink() function adds a new entry. Directories are typically stored as a linear list of entries (simple but slow for large directories) or as a hash table or B-tree (fast lookup but more complex).

In xv6, the file system operations are in kernel/fs.c. The ialloc() and ifree() functions manage inodes; balloc() and bfree() manage data blocks; bmap() translates a logical block number within a file to a physical block number on disk, traversing the direct and indirect pointers in the inode. The dirlookup() and dirlink() functions manage directory entries. These functions are the building blocks for the system calls in kernel/sysfile.c.

14.3 Directory Implementation

The directory implementation determines how directory entries are stored and searched. The choice of data structure affects the performance of file creation, deletion, and lookup, especially for directories with many entries.

The simplest implementation is a linear list of directory entries. Each entry contains a file name and an inode number. To look up a file, the file system scans the list linearly. This is simple to implement but O(n) in the number of entries, which is slow for large directories. xv6 uses this approach.

/* Linear list directory (xv6) */ struct dirent: ushort inum; // inode number (0 = free) char name[DIRSIZ]; // file name (14 or 255 bytes) // Directory is a file containing an array of dirents dirlookup(dp, name, poff): for (off = 0; off < dp->size; off += sizeof(dirent)): read_dirent(dp, off, &de) if (de.inum != 0 && strcmp(de.name, name) == 0): return iget(dp->dev, de.inum) return NULL // not found

A hash table implementation uses a hash function to map file names to buckets, each containing a list of entries. Lookup is O(1) on average (if the hash function is good and the load factor is reasonable). This is much faster for large directories. The downside is the overhead of the hash table structure and the need to handle collisions. Some file systems (e.g., ReiserFS) use hash-based directories.

A B-tree or B+ tree implementation stores directory entries in a balanced tree, keeping entries sorted by name. Lookup, insertion, and deletion are O(log n). B-trees are also efficient for range queries (e.g., listing all files starting with "a"). Modern file systems like ext4 (with htree), XFS, Btrfs, and NTFS use B-tree-based directories for large directories. This avoids the performance cliff that linear lists hit when a directory has thousands of entries.

ℹ️ Large Directories

With a linear list, a directory with 100,000 files takes O(100,000) comparisons per lookup, which can be hundreds of milliseconds. With a B-tree, the same lookup takes O(log 100,000) ≈ 17 comparisons, which is microseconds. This is why modern file systems use B-trees for directories. The ext4 htree is a specialized B-tree for directories that is enabled automatically when a directory grows beyond a threshold.

Directory entries also need to handle deletion. In a linear list, a deleted entry can be marked as free (inum = 0) and reused later. In a B-tree, the entry is removed and the tree is rebalanced. Some file systems compact directories periodically to reclaim space from deleted entries. The unlink() system call removes a directory entry and decrements the inode's link count; if the count reaches zero, the inode and its data blocks are freed.

In xv6, directories use a linear list of struct dirent entries. The dirlookup() function in kernel/fs.c scans the directory linearly. Deleted entries have inum == 0 and are skipped. This is simple but would be slow for directories with many files. Implementing a hash table or B-tree for xv6 directories would be a valuable exercise in data structure design for file systems.

14.4 Allocation Methods

The allocation method determines how the file system allocates disk blocks to files. The choice affects performance (sequential access, random access, file growth) and fragmentation (wasted space). The three main methods are contiguous, linked, and indexed allocation.

Contiguous Allocation

Contiguous allocation assigns each file a set of consecutive blocks. The directory entry stores the starting block and the length. This is simple and efficient for sequential access (the disk head reads consecutive blocks without seeking) and random access (block n is at start + n). However, it suffers from external fragmentation: as files are created and deleted, free space becomes fragmented into small, non-contiguous holes. Compaction (moving files to consolidate free space) is expensive. Contiguous allocation is used in CD-ROMs and some embedded systems but is rare in general-purpose file systems.

/* Contiguous allocation */ // Directory entry: struct dirent: name start_block // e.g., 100 length // e.g., 50 blocks // Access block n of file: physical = start_block + n // Problem: external fragmentation // [File A: 0-49] [free: 50-99] [File B: 100-199] // If A is deleted: [free: 0-49] [free: 50-99] [B: 100-199] // A 100-block file cannot fit in 0-99 if not coalesced

Linked Allocation

Linked allocation represents each file as a linked list of blocks. Each block contains data and a pointer to the next block. The directory entry stores the starting block and (optionally) the ending block. This eliminates external fragmentation (any free block can be used) and supports efficient file growth (just append a block). However, random access is inefficient: to read block n, the file system must traverse n pointers, reading each block. Linked allocation is used in FAT (File Allocation Table) file systems.

/* Linked allocation (FAT-style) */ // Each block has data + next pointer struct block: data[BSIZE - 4] next_block // 0 = end of file // FAT: an array mapping block → next block FAT[block] = next_block // Directory entry: struct dirent: name first_block // e.g., 5 // Traverse to block n: block = first_block for (i = 0; i < n; i++) block = FAT[block] // follow link // Now 'block' is the physical block // FAT caches the entire table in memory, so traversal is fast

The FAT (File Allocation Table) file system, used in MS-DOS and Windows (FAT12, FAT16, FAT32, exFAT), is a variant of linked allocation. Instead of storing the next-block pointer in each data block, FAT stores all pointers in a separate table (the FAT). This table is small enough to be cached in memory, making traversal fast. FAT is simple and widely supported (USB drives, cameras) but lacks journaling, ACLs, and large file support.

Indexed Allocation

Indexed allocation stores all block pointers for a file in a single index block (the inode). The directory entry points to the index block, which contains an array of block pointers. This supports both sequential and random access efficiently: block n is at index_block[n]. The challenge is that the index block has a fixed size, limiting the maximum file size. This is solved with multi-level indexes (direct, indirect, double-indirect, triple-indirect pointers), as described in Section 14.2. Indexed allocation is used by Unix file systems (ext2, ext3, ext4, UFS) and is the basis of the inode-based design.

💡 Extents

Some modern file systems (ext4, XFS, Btrfs) use extents instead of individual block pointers. An extent is a contiguous range of blocks, represented as (start, length). A file with 1000 contiguous blocks needs one extent instead of 1000 pointers. This reduces metadata size, improves sequential performance, and supports very large files. Ext4 uses a hybrid: extents for large files, falling back to traditional indirect blocks for compatibility.

In xv6, the allocation method is indexed with multi-level pointers. The inode (defined in kernel/fs.h) has 12 direct pointers (addrs[0..11]), 1 single-indirect pointer (addrs[12]), and 1 double-indirect pointer (addrs[13]). With 512-byte blocks and 4-byte pointers, this supports files up to about 32 MB. The bmap() function in kernel/fs.c traverses these pointers to find the physical block for a given logical block number, allocating new blocks as needed.

14.5 Free-Space Management

The file system must track which disk blocks are free (available for allocation) and which are used. The free-space management method determines how this information is stored and how free blocks are found. The choice affects allocation speed, space overhead, and the ability to find contiguous free regions.

Bit Vector (Bitmap)

The bit vector (or bitmap) uses one bit per block: 1 means the block is free, 0 means it is used (or vice versa). For a 1 TB disk with 4 KB blocks, the bitmap is 32 MB—small enough to keep in memory. Finding a free block is a matter of scanning the bitmap for a 1 bit. Finding n contiguous free blocks requires scanning for n consecutive 1 bits. The bitmap is simple, compact, and supports contiguous allocation, making it the most common method.

/* Bitmap free-space management */ // 1 bit per block: 1 = free, 0 = used // For 1 TB disk, 4 KB blocks: 2^38 blocks → 2^35 bytes = 32 GB bitmap // Wait, 1 TB / 4 KB = 2^28 blocks → 2^25 bytes = 32 MB bitmap alloc_block(): for (i = 0; i < bitmap_size; i++): if (bitmap[i] != 0): bit = find_first_set(bitmap[i]) block = i * 8 + bit clear_bit(bitmap, block) return block return -1 // disk full free_block(block): set_bit(bitmap, block)

Linked List

A linked list of free blocks stores each free block's address in the previous free block. The superblock points to the first free block, which points to the next, and so on. This uses no extra space (the pointers are stored in the free blocks themselves) but makes it hard to find contiguous free regions. A variant is the grouped list: the first free block stores the addresses of the next n free blocks, reducing the number of disk reads.

Other Methods

Other methods include counting (store the starting block and count of each contiguous free region) and grouping (store addresses of free blocks in groups). These are less common. The space map used by ZFS is a more sophisticated approach: it uses a log-structured structure that records all allocations and frees, allowing efficient free-space tracking for very large file systems.

⚠️ Bitmap Size

For a 1 TB disk with 4 KB blocks, the bitmap is 32 MB. For a 100 TB disk, it is 3.2 GB. This is too large to keep entirely in memory for very large disks. Modern file systems address this by using block groups (ext2/3/4): the disk is divided into groups, each with its own bitmap. Only the bitmaps for active groups need to be in memory. ZFS and Btrfs use more sophisticated structures (space maps, extent trees) that scale better to very large file systems.

In xv6, free-space management uses a bitmap. The balloc() function in kernel/fs.c scans the bitmap for a free bit, sets it, and returns the block number. The bfree() function clears the bit. The bitmap starts at block bmapstart (defined in the superblock) and covers all data blocks. This is the standard bitmap approach, simplified for the small xv6 file system.

14.6 Efficiency and Performance

File-system efficiency refers to how effectively the file system uses disk space, and performance refers to how fast I/O operations complete. Several design choices affect both.

Block size is a critical parameter. Larger blocks improve throughput for large files (fewer I/O operations, better sequential access) but increase internal fragmentation (the last block of a file is partially unused). With 4 KB blocks, a 1-byte file wastes 4095 bytes. With 64 KB blocks, it wastes 65535 bytes. The optimal block size depends on the workload: large blocks for large files (databases, media), small blocks for many small files (source code, email). Most file systems use 4 KB as a compromise. Some (XFS, Btrfs) support variable block sizes or sub-block allocation to reduce fragmentation for small files.

1 KBLowLowLargeMany tiny files
4 KBMediumMediumMediumGeneral purpose
64 KBHighHighSmallLarge files, databases

Caching is the most important performance optimization. The OS maintains a buffer cache (or page cache) in memory that holds recently accessed disk blocks. Reads check the cache first; if the block is there (a cache hit), no disk I/O is needed. Writes may be write-through (written to both cache and disk) or write-back (written to cache, flushed to disk later). Write-back caching dramatically improves write performance but risks data loss on crash. The cache is managed with an LRU-like algorithm: when the cache is full, the least recently used blocks are evicted.

💡 Read-Ahead (Prefetch)

When the file system detects sequential access (reading blocks in order), it can read ahead—pre-fetching the next few blocks into the cache before they are requested. This overlaps disk I/O with computation, significantly improving sequential read performance. The OS tracks access patterns and enables read-ahead when sequential access is detected. Random access disables read-ahead to avoid wasting I/O.

Write buffering and batching improve write performance. Instead of writing each block immediately, the OS buffers writes in the cache and flushes them in batches. This allows the disk scheduler to reorder writes for efficiency (Section 11.2) and coalesces multiple writes to the same block. The sync() system call forces a flush of all dirty buffers; fsync() flushes a specific file. The OS also runs a periodic flush (e.g., every 5 seconds on Linux) to limit the window of data loss.

File-system tuning involves choosing parameters that match the workload. For a database, use a larger block size, disable access-time updates (noatime), and align partitions to block boundaries. For a home directory, use the default settings. For a web server, increase the cache size and enable read-ahead. Modern file systems (ext4, XFS) support online resizing, defragmentation, and tuning via mount options.

In xv6, performance is not optimized. The buffer cache (kernel/bio.c) provides basic caching with a fixed number of buffers (defined by NBUF). There is no read-ahead, no write batching, and no write-back caching—writes are synchronous (write-through). The block size is 512 bytes, which is small. These choices make xv6 simple and reliable but slow. Adding read-ahead, write-back caching, and a larger block size would be valuable performance exercises.

14.7 Recovery

File systems must recover from crashes and power failures. If the system crashes while the file system is updating metadata (allocating a block, creating a file, deleting a file), the file system may be left in an inconsistent state: blocks may be marked as used but not belong to any file (lost), or marked as free but still referenced by a file (corruption). Recovery techniques ensure the file system returns to a consistent state after a crash.

Consistency Checking (fsck)

The traditional recovery method is consistency checking, performed by a tool like fsck (Unix) or chkdsk (Windows). After a crash, the tool scans the entire file system, checking for consistency:

  • Each block should be either allocated to exactly one file or free (not both, not neither). Blocks allocated to no file are lost; blocks allocated to multiple files are cross-linked.
  • Each inode's link count should match the number of directory entries pointing to it.
  • Directory entries should point to valid inodes.
  • Free-space counts should match the actual free blocks.

The tool repairs inconsistencies by freeing lost blocks, fixing link counts, and removing invalid directory entries. However, fsck is slow (it scans the entire disk) and may not recover all data (it ensures consistency, not correctness). For large file systems, fsck can take hours, which is unacceptable for production systems.

Journaling (Write-Ahead Logging)

Journaling (or write-ahead logging) is the modern approach to recovery. Before modifying the file system, the OS writes a description of the intended changes to a journal (a circular log on disk). After the journal entry is committed (written to disk), the OS applies the changes to the actual file system. If a crash occurs during the apply phase, the journal entry is replayed on the next boot, ensuring the changes are completed. If a crash occurs before the journal entry is committed, the changes are discarded (the file system remains in its pre-change state).

/* Journaling (write-ahead log) */ journal_write(changes): // 1. Write changes to journal (log) log_write(begin_txn) for change in changes: log_write(change) log_write(commit_txn) flush_log() // ensure on disk // 2. Apply changes to file system for change in changes: apply(change) // 3. Mark journal entry as done log_write(done_txn) recover(): for entry in journal: if (entry.committed && !entry.done): replay(entry) // re-apply else if (!entry.committed): discard(entry) // undo

Journaling can be metadata-only (journaling only metadata changes, like block allocation and directory updates) or full data (journaling both metadata and file data). Metadata-only journaling (used by ext3, ext4 by default) is faster but does not protect file data (a crash may leave a file with old or partially written data). Full-data journaling (ext4 with data=journal) is slower but protects both metadata and data. XFS and Btrfs use copy-on-write (never overwriting data in place) as an alternative to journaling for data consistency.

ℹ️ Journaling Levels

Journaling modes in ext4: (1) data=journal — all data and metadata are journaled (safest, slowest); (2) data=ordered — metadata is journaled, data is written before metadata (default, good balance); (3) data=writeback — metadata is journaled, data is not ordered (fastest, may expose old data after crash). Most systems use data=ordered.

Copy-on-Write (CoW) File Systems

Copy-on-write file systems (Btrfs, ZFS, ReFS, APFS) never overwrite data in place. When a block is modified, a new block is written elsewhere, and the metadata is updated to point to it. This means a crash never leaves a file in a partially overwritten state—the old version is intact until the new version is fully written and the metadata is atomically updated. CoW file systems also support snapshots (point-in-time copies) and checksums (detecting silent data corruption) naturally.

In xv6, recovery is handled by a simple log (kernel/log.c). The begin_op() and end_op() functions bracket file system operations. Changes are written to the log first, then applied to the file system. On boot, recover_from_log() replays committed but unapplied log entries. This is a simplified version of journaling: it journals both metadata and data, and it does not support concurrent transactions. Despite its simplicity, it demonstrates the core concept of write-ahead logging for crash recovery.

14.8 WAFL File System

WAFL (Write Anywhere File Layout) is a file system designed by Network Appliance (NetApp) for their storage appliances. It is a copy-on-write file system that uses write-anywhere allocation: new data can be written to any free block on disk, not necessarily near the existing data. This maximizes write performance by eliminating seek time for writes (the disk head writes to wherever it currently is).

WAFL is designed for NAS (Network-Attached Storage) appliances, where the primary workload is serving files over a network (NFS, CIFS). The key insight is that in a NAS environment, writes are often random (many clients writing different files), and read performance is less critical (clients cache). WAFL optimizes for this by writing all new data sequentially to a write-aside log, then periodically consolidating it into the main file system.

/* WAFL concepts */ // Write-anywhere: new blocks go to any free location write(file, offset, data): // Don't overwrite existing block new_block = find_any_free_block() // anywhere on disk write_to(new_block, data) // Update metadata to point to new block update_inode(file, offset, new_block) // Snapshots: copy-on-write makes this trivial snapshot(): // Just save the root of the file system tree // Old blocks are preserved until snapshot is deleted save_root(snapshot_id)

WAFL's snapshot feature is a direct consequence of copy-on-write. Because WAFL never overwrites data, taking a snapshot is as simple as saving the root pointer of the file system tree. The old blocks remain until the snapshot is deleted. WAFL can maintain thousands of snapshots with minimal overhead, allowing users to recover deleted files or revert to previous states. This is a major feature of NetApp storage appliances.

ℹ️ WAFL vs. Traditional FS

Traditional file systems (ext4, NTFS) overwrite data in place, which is efficient for in-place updates but makes snapshots expensive (requires copying all modified blocks). WAFL (and other CoW file systems like Btrfs, ZFS) never overwrite, making snapshots nearly free but requiring more space (old versions of blocks are kept until snapshots are deleted). The trade-off is between write amplification (CoW writes more) and snapshot efficiency (CoW snapshots are cheap).

WAFL also uses NVRAM (non-volatile RAM) as a write cache. Incoming writes are stored in NVRAM and acknowledged immediately (low latency). The data is later flushed to disk in batches. If the system crashes, the NVRAM contents are replayed on reboot, ensuring no acknowledged writes are lost. This is similar to journaling but faster because NVRAM is much faster than disk.

WAFL's design influenced later file systems. Btrfs and ZFS on Linux, APFS on macOS/iOS, and ReFS on Windows all use copy-on-write and support efficient snapshots. The log-structured file system (LFS) concept, where all writes are sequential (like a log), is a related idea that influenced f2fs (Flash-Friendly File System) on Android.

In xv6, there is no WAFL-like functionality. The file system overwrites blocks in place (via bwrite()), and there are no snapshots. The log (kernel/log.c) provides crash recovery but not snapshot capability. Implementing a copy-on-write file system on top of xv6 would be a major project, but it would demonstrate the power of the CoW model for snapshots and data integrity.

15.1 File Systems

A computer system typically has multiple file systems: the root file system, separate file systems for /home, /var, /tmp, and removable media (USB drives, SD cards). Each file system may use a different format (ext4, FAT, NTFS, ISO 9660). The OS must provide a unified view of all these file systems, allowing users and applications to access files without knowing which file system they are on.

The Virtual File System (VFS) is the OS layer that provides this unified interface. VFS defines a common API (open, read, write, close, etc.) that all file systems implement. When an application calls open(), VFS determines which file system contains the file and dispatches the call to that file system's implementation. This allows the OS to support multiple file systems simultaneously and transparently.

ℹ️ Why Multiple File Systems?

Different file systems are optimized for different purposes: ext4 for general Linux use, NTFS for Windows, FAT for removable media (compatibility), ISO 9660 for optical discs, tmpfs for in-memory temporary storage, procfs for process information. The OS supports all of them via VFS, allowing applications to use a single API regardless of the underlying file system.

Each file system has its own on-disk format (how data is laid out on the storage device) and its own in-memory structures (how the OS represents open files, directories, etc.). VFS abstracts these differences by defining common objects: superblock (file system metadata), inode (file metadata), dentry (directory entry), and file (open file). Each file system provides operations on these objects, and VFS dispatches calls to the appropriate implementation.

In xv6, there is only one file system (the xv6 file system), so there is no VFS layer. The file system code in kernel/fs.c directly implements all operations. However, the struct file in kernel/file.h is a simple VFS-like abstraction: it can represent a file, a device (like the console), or a pipe, with different read and write function pointers. This is a simplified version of the VFS object model.

15.2 File-System Mounting

Before a file system can be used, it must be mounted. Mounting attaches a file system to the directory tree at a specified mount point (a directory). After mounting, the file system's root appears at the mount point, and files on the mounted file system are accessible via paths through the mount point.

/* Mounting a file system */ // Before mounting /dev/sdb1 at /mnt/usb: // /mnt/usb/ (empty directory on root FS) // Mount command: mount("/dev/sdb1", "/mnt/usb", "ext4", 0, NULL); // After mounting: // /mnt/usb/ → root of /dev/sdb1 (ext4 FS) // /mnt/usb/file.txt → file on /dev/sdb1 // Unmount: umount("/mnt/usb"); // /mnt/usb is now an empty directory again

The mount() system call takes a device path, a mount point, a file system type, and flags. The OS reads the superblock from the device, validates the file system, and creates an in-memory mount structure that records the mapping. Subsequent path resolution checks each directory: if a directory is a mount point, the OS crosses into the mounted file system.

⚠️ Mount Point Crossing

When resolving a path like /mnt/usb/file.txt, the OS starts at the root of the root file system, descends to mnt, then to usb. At usb, the OS detects that it is a mount point and switches to the root of the mounted file system. From there, it resolves file.txt. This "crossing" is transparent to applications but is a key part of VFS path resolution.

File systems can be mounted with various options: ro (read-only), noexec (no execution), nosuid (ignore setuid bits), noatime (don't update access times), sync (synchronous writes). These options affect security and performance. For example, mounting /tmp with noexec prevents executing binaries from /tmp, a common security hardening measure.

In xv6, there is no mount() system call. The file system is mounted at boot (the root file system) and cannot be changed. The fsinit() function in kernel/fs.c reads the superblock during boot. Adding mount support to xv6 would require: (1) a mount table, (2) a mount() system call, (3) modifying namei() to cross mount points, and (4) an umount() system call. This is a common advanced xv6 exercise.

15.3 Partitions and Mounting

A storage device is divided into partitions, and each partition can contain a file system. The OS mounts file systems from partitions at boot time (based on /etc/fstab on Linux) or at runtime (via mount command). Understanding the relationship between partitions, file systems, and mount points is essential for system administration.

The partition table (MBR or GPT, see Section 11.5) describes the partitions on a device. Each partition entry specifies the starting sector, size, and type. The OS reads the partition table at boot or when a device is attached, creates device nodes for each partition (e.g., /dev/sda1, /dev/sda2), and allows file systems to be mounted from them.

/* /etc/fstab example (Linux) */ # device mount-point type options dump pass /dev/sda1 / ext4 defaults 1 1 /dev/sda2 /home ext4 defaults 1 2 /dev/sda3 none swap sw 0 0 /dev/sdb1 /mnt/usb vfat noexec,user 0 0 tmpfs /tmp tmpfs defaults 0 0 proc /proc proc defaults 0 0 // "pass" = fsck order (0 = don't check) // "dump" = backup frequency (0 = no dump)

Some partitions are special: swap partitions are used for virtual memory (Section 11.6), not for file systems. EFI System Partition (ESP) contains boot loaders. Recovery partitions contain system recovery tools. The OS treats each partition type differently based on its purpose.

ℹ️ Virtual File Systems

Not all "file systems" are backed by a storage device. Virtual file systems like procfs (/proc on Linux) expose kernel data structures as files. sysfs (/sys) exposes device and driver information. tmpfs stores files in memory (RAM). These are mounted like regular file systems but have no on-disk representation. VFS handles them uniformly, demonstrating the power of the VFS abstraction.

Automounting is a feature where file systems are mounted on demand. When a process accesses a path under an automount point, the OS automatically mounts the appropriate file system. This is used for network file systems (NFS) and removable media (USB drives). On Linux, autofs and systemd provide automounting. On desktop environments, udev detects device insertion and triggers automount.

In xv6, there is a single partition (the entire virtio disk). The fsinit() function reads the superblock from block 1 and initializes the file system. There is no partition table parsing, no /etc/fstab, and no automounting. Adding partition support would involve reading the MBR/GPT, creating per-partition device structures, and allowing multiple file systems to be mounted.

15.4 File Sharing

File sharing allows multiple users or processes to access the same file. The OS must ensure that sharing is safe (no data corruption) and efficient (no unnecessary copying). There are several models for file sharing.

Multiple users on the same system can share files via permissions (Section 13.4). A file's owner can grant read or write permission to other users or groups. The OS enforces these permissions on each open() call. Hard links allow a file to appear in multiple directories, and symbolic links allow a path to refer to another path. These mechanisms enable flexible sharing within a single system.

Concurrent access by multiple processes requires synchronization. If two processes write to the same file simultaneously, their writes may interleave, corrupting the file. The OS provides advisory locks (flock(), fcntl(F_SETLK)) and mandatory locks that prevent concurrent access. Advisory locks require processes to cooperate (check the lock before accessing); mandatory locks are enforced by the OS. Most Unix systems use advisory locks; Windows uses mandatory locking by default.

/* File locking */ // Advisory lock (POSIX) int fd = open("shared.txt", O_RDWR); // Exclusive lock (write lock) struct flock fl = { .l_type = F_WRLCK, .l_whence = SEEK_SET }; fcntl(fd, F_SETLKW, &fl); // blocks until locked // ... critical section ... write(fd, data, len); // Unlock fl.l_type = F_UNLCK; fcntl(fd, F_SETLK, &fl); // flock(): whole-file lock (simpler but less flexible) flock(fd, LOCK_EX); // exclusive flock(fd, LOCK_UN); // unlock

Remote file sharing allows users on different systems to share files. This is done via network file systems (NFS, SMB/CIFS), where files on a remote server are accessed as if they were local. The OS's network file system client translates file operations into network requests. See Section 15.6 for details.

ℹ️ Advisory vs. Mandatory Locks

Advisory locks are only checked if a process explicitly calls fcntl() or flock(). A process that ignores locks can still access the file. This is the Unix model: locks are a cooperative protocol. Mandatory locks are enforced by the OS: any read() or write() that conflicts with a lock blocks or fails. Mandatory locks are rarely used on Unix because they can cause deadlocks and performance problems, but they are the default on Windows.

File sharing semantics define what happens when multiple processes read and write the same file concurrently. Unix semantics (also called session semantics) means that each write() is immediately visible to all processes that have the file open. Immutable shared-file semantics means a file cannot be modified once shared; changes create a new version. Transaction semantics groups operations into atomic transactions. Most local file systems use Unix semantics; distributed file systems may use weaker semantics (see Section 15.7).

In xv6, file sharing is basic. Multiple processes can open the same file, and writes are immediately visible (Unix semantics). There is no file locking—concurrent writes can interleave. The struct file in kernel/file.h has a reference count: when fork() duplicates a file descriptor, both parent and child share the same struct file, including the file offset. This is how shell pipes work: the parent and child share the pipe's read and write ends. Adding file locking to xv6 would be a useful exercise in synchronization applied to the file system.

15.5 Virtual File Systems

The Virtual File System (VFS) is the layer that provides a uniform interface to multiple file systems. It defines a set of objects and operations that each file system must implement. VFS dispatches calls to the appropriate file system based on which file system the operation targets.

The four main VFS objects are:

ObjectRepresentsKey Fields
SuperblockA mounted file systemDevice, block size, operations
InodeA specific fileSize, permissions, data block pointers
DentryA directory entry (name → inode link)Name, parent inode, child inode
FileAn open fileOffset, mode, operations

Each object has an operations table (a struct of function pointers) that the specific file system implements. For example, the inode operations table includes create, lookup, link, unlink, etc. The file operations table includes read, write, llseek, mmap, etc. When VFS needs to read from a file, it calls file->f_op->read(file, ...), which dispatches to the file system's read implementation.

/* VFS object model (Linux-style) */ struct super_block: dev_t s_dev // device unsigned long s_block_size struct super_operations *s_op // FS-specific ops struct dentry *s_root // root dentry struct inode: umode_t i_mode // permissions loff_t i_size // file size struct inode_operations *i_op struct file_operations *i_fop struct file: struct dentry *f_dentry loff_t f_pos // file offset struct file_operations *f_op // Dispatch example: ssize_t vfs_read(file, buf, count): return file->f_op->read(file, buf, count, &file->f_pos);
💡 VFS and Object-Oriented Design

VFS is a classic example of object-oriented design in C. The operations tables are like virtual function tables (vtables) in C++. Each file system "subclasses" the VFS objects by providing its own operations. This allows the kernel to support any file system that implements the VFS interface, without knowing the file system's internal details. New file systems can be added as kernel modules without recompiling the kernel.

VFS path resolution is the process of converting a path name to an inode. The path_lookup() function (or namei() in xv6) traverses the path component by component: it starts at the root (or the current directory for relative paths), looks up each component in the current directory, follows symbolic links, and crosses mount points. The result is the inode of the final component. This traversal involves multiple file systems if the path crosses mount points.

VFS also manages the dentry cache (directory entry cache), which caches recently resolved path components to speed up path lookup. Without the dentry cache, every open() would require multiple disk reads to traverse the directory tree. The dentry cache keeps recently used directory entries in memory, making path lookup fast for frequently accessed files.

In xv6, VFS is minimal. The struct file in kernel/file.h has a type field (FD_FILE, FD_PIPE, FD_INODE) and function pointers for read and write. This is a simplified VFS: different "file system types" (regular files, pipes, devices) implement different read/write functions. The namei() function in kernel/fs.c does path resolution, but it does not support mount points or symbolic links. Extending xv6's VFS to support multiple file systems and mount points would be a significant but instructive project.

15.6 Remote File Systems

A remote file system allows a client to access files on a remote server as if they were local. The client runs a file system client that translates file operations (open, read, write) into network requests, sends them to the server, and receives the results. The server runs a file system server that handles the requests by performing local file I/O. This enables distributed file sharing across multiple machines.

The most common remote file system protocols are:

ProtocolOriginTypical UseTransport
NFSSun MicrosystemsUnix/Linux file sharingTCP/UDP (RPC)

NFS (Network File System) is the standard remote file system for Unix-like systems. It uses RPC (Remote Procedure Call) to send file operations from the client to the server. The client's VFS layer has an NFS implementation that translates VFS operations into RPC calls. The server's NFS daemon (nfsd) receives the RPCs and performs local file I/O. NFS is stateless (in versions 2 and 3): the server does not keep track of open files; each request contains all necessary information (file handle, offset, length). This makes crash recovery simple (the client just retries) but complicates file locking. NFSv4 is stateful and includes built-in security (Kerberos) and locking.

/* NFS client-server interaction */ // Client: open("/nfs/server/file.txt") vfs_open("/nfs/server/file.txt"): // VFS detects /nfs/server is an NFS mount // Calls NFS client handle = nfs_lookup(server, "file.txt") // Returns a file handle (opaque token) // Client: read(fd, buf, 4096) vfs_read(fd, buf, 4096): // NFS client sends RPC to server data = nfs_read(handle, offset, 4096) copy_to_user(buf, data, 4096) // Server side: nfsd_read(handle, offset, len): inode = handle_to_inode(handle) bread(inode, offset / BSIZE) return data
ℹ️ NFS File Handles

An NFS file handle is an opaque token that uniquely identifies a file on the server. It typically contains the file system ID and the inode number. The client receives the handle when it looks up a file and uses it in subsequent operations. Because the handle is opaque, the client does not need to understand the server's file system format. The server can even change its file system (e.g., from ext4 to XFS) without affecting clients, as long as handles remain valid.

Caching is critical for remote file system performance. Without caching, every read and write would require a network round-trip, which is much slower than local disk access. The client caches file data and metadata (attributes) locally. When the cache is valid, reads are served locally. The challenge is cache consistency: if two clients modify the same file, or if the server file changes, the cache may be stale. NFS uses close-to-open consistency (Section 15.7): the client validates its cache when opening a file and flushes changes on close. AFS uses callback-based consistency: the server notifies clients when a cached file changes.

Security in remote file systems involves authentication (proving the client's identity) and authorization (checking permissions). NFSv2/v3 rely on the client to send the user's UID/GID, which is insecure (a malicious client can forge UIDs). NFSv4 uses RPCSEC_GSS with Kerberos for strong authentication. SMB uses NTLM or Kerberos. The server must trust the client's authentication or perform its own. In high-security environments, all traffic is encrypted and authenticated.

In xv6, there is no network file system. All files are on the local virtio disk. Implementing a simple network file system in xv6 would require: (1) a network stack (Ethernet, IP, TCP/UDP), (2) an RPC layer, (3) a client VFS implementation, and (4) a server daemon. This is a large project but would demonstrate the power of the VFS abstraction: the same open() / read() / write() API can access both local and remote files transparently.

15.7 Consistency Semantics

Consistency semantics define what guarantees the file system provides when multiple processes or clients access the same file concurrently. This is especially important for distributed file systems, where network delays and caching make consistency harder to achieve.

Unix Semantics (Session Semantics)

Unix semantics (also called session semantics) means that each write() is immediately visible to all processes that have the file open. If process A writes to a file and process B reads it, B sees A's write immediately (after the write returns). This is the strongest consistency model and is what local Unix file systems provide. It is easy to understand but hard to achieve in distributed systems because it requires invalidating all caches on every write.

Close-to-Open Consistency

Close-to-open consistency (used by NFSv3) is weaker: changes to a file are only guaranteed to be visible to other clients when the file is closed. While the file is open, the client may cache it and serve reads from the cache. On close, the client flushes changes to the server. On open, the client checks with the server for a newer version. This means that if two clients have the same file open simultaneously, they may see different versions. This is acceptable for most workloads (files are rarely modified concurrently) and is much more efficient than Unix semantics over a network.

/* Consistency models */ // Unix semantics (local FS): // A writes "hello" → B reads "hello" immediately // Close-to-open (NFSv3): // A opens file, writes "hello" (cached locally) // B opens file, reads old content (from server) // A closes file → "hello" flushed to server // B reopens file → reads "hello" // Immutable file semantics: // File cannot be modified once created // "Modifications" create a new version // Old version remains until explicitly deleted

Immutable Shared-File Semantics

Immutable shared-file semantics means that once a file is shared, it cannot be modified. Any "write" creates a new version of the file, and the old version remains accessible. This eliminates consistency problems (there is no concurrent modification) but is restrictive. Some distributed file systems (e.g., AFS with immutable volumes) and versioning file systems use this model. It is also the model used by copy-on-write file systems (Btrfs, ZFS) for snapshots.

⚠️ Distributed Consistency Challenges

In a distributed file system, achieving Unix semantics is very expensive: every write must invalidate caches on all clients, requiring network communication. Close-to-open consistency is a practical compromise: it provides good performance for the common case (one client modifies a file at a time) while ensuring eventual consistency. Applications that need stronger consistency (e.g., databases) should use explicit locking or a distributed coordination service.

Transaction semantics is the strongest model: operations are grouped into transactions that are atomic (all or nothing), consistent, isolated, and durable (ACID). If two transactions conflict, one is aborted. This is the model used by databases and some specialized file systems. It is too expensive for general-purpose file systems but is used in applications that need strict consistency (e.g., financial systems, distributed databases).

In xv6, the file system provides Unix semantics for local access: writes are immediately visible to all processes. There is no caching that would delay visibility (writes are synchronous). Since xv6 has no distributed file system, consistency is not a concern. If a network file system were added, the designer would need to choose a consistency model—likely close-to-open for simplicity and performance.

15.8 NFS

NFS (Network File System) is the most widely used distributed file system in Unix-like environments. Developed by Sun Microsystems in the 1980s, it allows clients to mount directories exported by a server and access them as if they were local. NFS has gone through several versions, each adding features and improving security and performance.

NFS Architecture

NFS uses a client-server architecture. The server exports directories (specified in /etc/exports). Clients mount the exported directories using the mount command with the nfs file system type. Once mounted, the NFS client in the kernel translates VFS operations into RPC (Remote Procedure Call) requests, sends them to the server, and returns the results. The server's nfsd daemon handles the requests by performing local file I/O.

/* NFS setup */ // Server: export /home in /etc/exports /home 192.168.1.0/24(rw,sync,no_subtree_check) // Server: start nfsd exportfs -a systemctl start nfs-server // Client: mount mount -t nfs server:/home /mnt/nfs // Now /mnt/nfs/* are files on the server ls /mnt/nfs/alice // lists server's /home/alice

NFS Protocol and RPC

NFS uses ONC RPC (Open Network Computing Remote Procedure Call, originally Sun RPC) as its transport. RPC allows a client to call a function on the server as if it were local. The client stub marshals the arguments into a network message, sends it, receives the reply, and unmarshals the result. The server stub receives the message, unmarshals the arguments, calls the local function, marshals the result, and sends it back. NFS defines procedures like NFSPROC_READ, NFSPROC_WRITE, NFSPROC_LOOKUP, etc.

ℹ️ NFS Versions

NFSv2 (1989): the original, over UDP, stateless, 32-bit file sizes. NFSv3 (1995): supports TCP, larger files, async writes. NFSv4 (2003): stateful, integrated security (Kerberos/RPCSEC_GSS), file delegation, compound operations (multiple ops in one RPC). NFSv4.1 (2010): pNFS (parallel NFS) for high-performance storage. NFSv4 is the recommended version for modern deployments.

NFS File Handles and Operations

NFS identifies files by file handles—opaque tokens that the server generates and the client uses in subsequent operations. A file handle typically encodes the file system ID and the inode number. The client obtains a handle via LOOKUP (resolve a name in a directory) and uses it in READ, WRITE, GETATTR, etc. The handle is valid as long as the file exists; if the file is deleted, the handle becomes stale, and the client gets a ESTALE error.

NFS Caching and Consistency

NFS clients cache file data and attributes to reduce network traffic. The dentry cache caches directory lookups; the page cache caches file data; the attribute cache caches file metadata. Caching dramatically improves performance but introduces consistency challenges. NFSv3 uses close-to-open consistency: when a client opens a file, it checks with the server for a newer version; when it closes the file, it flushes changes. While the file is open, the client may serve reads from its cache, which may be stale if another client modified the file.

⚠️ NFS Stale File Handles

If a file is deleted on the server while a client has it open, the client's file handle becomes stale. Subsequent operations return ESTALE. The client must re-resolve the path to get a new handle. This can happen if another client deletes the file, or if the server reboots and loses the file (if the handle was in memory only). NFSv4 uses volatile file handles for some files to avoid this, but it remains a common issue.

NFSv4 Features

NFSv4 introduced several improvements over NFSv3: (1) Stateful operation—the server tracks open files and locks, enabling proper file locking and lease-based delegation; (2) Integrated security—RPCSEC_GSS with Kerberos provides authentication, integrity, and privacy; (3) Compound operations—multiple operations can be sent in a single RPC, reducing round-trips; (4) File delegation—the server can delegate a file to a client for exclusive caching, reducing server load; (5) pNFS (NFSv4.1)—separates metadata and data paths, allowing direct client-to-storage access for high performance.

In xv6, there is no NFS support. Adding NFS would require a network stack, an RPC implementation, and a VFS NFS client. This is a large project but would demonstrate how VFS enables transparent remote file access. A simpler exercise would be to implement a 9P client (used by QEMU's virtio-9p), which is simpler than NFS and is used in virtualization to share host directories with guests.
