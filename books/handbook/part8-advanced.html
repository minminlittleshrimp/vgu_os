18.1 Overview

A virtual machine (VM) is a software emulation of a computer system that provides a complete, isolated environment in which an operating system (or application) can run as if it had its own dedicated hardware. The software that creates and manages VMs is called a virtual machine monitor (VMM) or hypervisor. The VMM runs on the physical hardware (or on a host OS) and allocates resources—CPU, memory, I/O devices—to one or more guest operating systems. Each guest believes it is running on real hardware and is unaware that it is virtualized.

The fundamental idea of virtualization is abstraction: the VMM presents each guest with a virtual machine—a virtual CPU, virtual memory, virtual disks, and virtual network interfaces. The guest OS uses these virtual resources exactly as it would use physical ones. The VMM intercepts the guest's hardware accesses and translates them to operations on the real hardware. This indirection allows multiple guests to share the same physical hardware safely and efficiently.

ℹ️ Key Virtualization Concepts
  • Host: the physical machine (or the OS running the VMM)
  • Guest: the OS running inside a VM
  • Hypervisor / VMM: the software that creates and manages VMs
  • Virtual hardware: the emulated CPU, memory, and devices presented to the guest
  • Trap: the mechanism by which the guest's privileged operations are caught by the VMM

Virtualization relies on the same privilege levels that protect the kernel from user processes (see Chapter 17). In a virtualized system, the hypervisor runs at the highest privilege level (sometimes called "ring -1"), and the guest OS runs at a lower level. When the guest OS attempts a privileged operation (like modifying page tables or disabling interrupts), the hardware traps to the hypervisor, which emulates the operation. This is the trap-and-emulate model, the foundation of classical virtualization.

The relationship to xv6 is direct: xv6 runs in RISC-V S-mode (supervisor mode) and user processes run in U-mode. A hypervisor would run in a new H-mode (RISC-V Hypervisor Extension) above S-mode, and xv6 would run as a guest in a modified S-mode that traps privileged operations to the hypervisor. The same trap mechanism that xv6 uses to catch user-mode system calls (ecall) is extended one level up to catch guest-OS privileged operations.

💡 Virtualization vs. Containers

Virtual machines virtualize the hardware: each VM has its own kernel and full OS. Containers (like Docker) virtualize the OS: all containers share the host kernel but have isolated user spaces. VMs provide stronger isolation (a VM compromise does not affect the host) but are heavier (each VM runs a full OS). Containers are lighter and faster to start but provide weaker isolation (a kernel vulnerability can affect all containers). Many systems use both: containers inside VMs for defense in depth.

18.2 History

Virtualization is not a new idea—it predates personal computers by decades. The concept originated in the 1960s at IBM with the CP-40 and CP-67 systems, which evolved into VM/370 (1972). The IBM VM family allowed multiple users to each have their own virtual machine running a copy of the CMS operating system. This was remarkable: in an era when a mainframe cost millions of dollars, VM/370 let dozens of users share it while each believing they had their own machine.

The key innovation was the CP (Control Program), the hypervisor that ran directly on the IBM System/370 hardware. CP created virtual machines by intercepting the guest's privileged instructions and emulating them. The System/370 architecture was designed to support this: it had a start interpretive execution (SIE) instruction that allowed the CPU to run a guest in a virtualized mode, trapping privileged operations to CP. This is an early example of hardware-assisted virtualization.

After the mainframe era, virtualization fell out of favor in the 1980s and 1990s as personal computers became cheap enough that each user could have their own machine. The x86 architecture, designed for single-user PCs, was not virtualizable using the trap-and-emulate model because certain privileged instructions did not trap in user mode—they failed silently or had different behavior. This made x86 virtualization seem impossible.

The breakthrough came in 1999 with VMware, which used binary translation to virtualize x86. Instead of relying on hardware traps, VMware scanned the guest's code at runtime and rewrote privileged instructions into calls to the VMM. This was slow but worked, enabling x86 virtualization for the first time. In 2005–2006, Intel (VT-x) and AMD (AMD-V) introduced hardware-assisted virtualization extensions that made x86 properly virtualizable, eliminating the need for binary translation in most cases and dramatically improving performance.

⚠️ Popek and Goldberg Requirements

In 1974, Gerald Popek and Robert Goldberg formalized the requirements for virtualization. A architecture is virtualizable if:

  1. Equivalence: programs running in a VM behave identically to running on bare hardware (except for timing).
  2. Resource control: the VMM has complete control over virtual resources.
  3. Efficiency: most guest instructions execute directly on hardware without VMM intervention.

The key technical requirement is that all sensitive instructions must trap. The original x86 violated this (some sensitive instructions did not trap), which is why binary translation was needed until VT-x/AMD-V.

The modern era of virtualization began with the cloud. Amazon EC2 (2006) offered virtual machines as a service, enabling companies to rent computing power by the hour. This would not have been possible without efficient x86 virtualization. Today, virtualization is the foundation of cloud computing: every cloud instance is a VM, and technologies like serverless (AWS Lambda) build on VMs (often using micro-VMs like Firecracker for fast startup and strong isolation).

18.3 Benefits and Features

Virtualization offers numerous benefits that have made it ubiquitous in data centers, cloud computing, and development. The most important is consolidation: running multiple VMs on a single physical server. Before virtualization, servers typically ran at 5–15% CPU utilization (one application per server). With virtualization, a single physical server can run 10–50 VMs, each running a different application, raising utilization to 60–80% and dramatically reducing hardware costs, power consumption, and data-center footprint.

Isolation is a critical benefit. Each VM is completely isolated from others: a crash, security breach, or misconfiguration in one VM does not affect others on the same host. This is stronger than process-level isolation (a kernel bug can affect all processes) because each VM has its own kernel. This makes virtualization ideal for multi-tenant cloud environments, where different customers' workloads run on the same physical hardware.

ℹ️ Key Benefits of Virtualization
  • Consolidation: run many VMs on one server, improving utilization
  • Isolation: each VM is independent; faults don't spread
  • Encapsulation: a VM is a file (or set of files) that can be copied, moved, backed up
  • Snapshots: save VM state and roll back if needed
  • Migration: move a running VM to another host (live migration)
  • Testing: run multiple OS versions or configurations on one machine
  • Legacy support: run old OSes on new hardware
  • Disaster recovery: replicate VMs to a remote site

Encapsulation is a powerful feature: a VM is represented as a set of files (disk image, configuration, memory state). This means a VM can be copied, cloned, backed up, and moved like any other file. A snapshot captures the VM's complete state (CPU, memory, disk) at a point in time, allowing rollback if something goes wrong. This is invaluable for testing: take a snapshot, install a risky update, and if it breaks, revert to the snapshot in seconds.

Live migration allows a running VM to be moved from one physical host to another with minimal or no downtime. The hypervisor copies the VM's memory to the destination while the VM continues running, then briefly pauses to transfer the final state and switch execution. This enables load balancing (move VMs off busy hosts), maintenance (evacuate a host before servicing it), and power saving (consolidate VMs onto fewer hosts and power down idle servers). VMware vMotion, KVM live migration, and Xen live migration all implement this.

/* Live migration (conceptual) */ // 1. Pre-copy phase: copy memory pages to destination while VM runs while (dirty_pages > threshold) { copy_dirty_pages(dest, src); // VM continues running; pages may be re-dirtied } // 2. Stop-and-copy: brief pause to transfer final state pause_vm(); copy_remaining_pages(dest, src); copy_cpu_state(dest, src); // 3. Resume on destination resume_vm(dest); // Total downtime: typically 50-500 ms

Hardware independence is another benefit: the VM sees virtual hardware, so it can run on any physical host that the hypervisor supports. A VM created on an Intel server can be migrated to an AMD server (if the hypervisor presents the same virtual CPU). This decouples the OS from the hardware, enabling flexible resource allocation and avoiding vendor lock-in. In the cloud, this means a workload can run on whatever hardware is available, with the hypervisor abstracting the differences.

💡 Virtualization in Development

For developers, virtualization is invaluable. Tools like Vagrant and VirtualBox let developers create reproducible development environments as VMs. A new team member can vagrant up and have the exact same environment as everyone else. CI/CD pipelines use VMs to run tests in clean, isolated environments. And if you're studying xv6, you're likely running it in QEMU—a virtual machine emulator—which lets you develop and debug an OS without dedicated hardware.

18.4 Building Blocks

Virtualization is implemented using three primary techniques: trap-and-emulate, binary translation, and hardware assistance. Different hypervisors use different combinations of these, depending on the architecture and performance requirements.

Trap-and-emulate is the classical virtualization model, described by Popek and Goldberg. The guest OS runs in a de-privileged mode (e.g., ring 1 on x86, or a guest mode on RISC-V). When the guest executes a privileged instruction (like modifying page tables or disabling interrupts), the hardware traps to the hypervisor. The hypervisor examines the trapped instruction, emulates its effect on the virtual machine, and resumes the guest. Non-privileged instructions (most of the guest's code) execute directly on the hardware at native speed.

/* Trap-and-emulate flow */ // Guest OS tries to disable interrupts guest_kernel: cli // clear interrupt flag (privileged!) // → TRAP to hypervisor // Hypervisor handles the trap hypervisor_trap_handler: if (trap_cause == PRIVILEGED_INSTRUCTION) { if (instruction == "cli") { guest_vm.eflags.IF = 0; // emulate: disable vIRQs advance_guest_pc(); // skip the instruction } } resume_guest(); // return to guest

The challenge with trap-and-emulate is that it requires all sensitive instructions to trap. The original x86 violated this: instructions like POPF (pop flags) and SGDT (store GDT) did not trap in user mode—they silently ignored the privileged bits or returned different values. This meant a guest OS running in ring 1 could detect it was virtualized (by executing SGDT and seeing a different value) or could bypass the hypervisor's control. This is why x86 was not classically virtualizable.

Binary translation solves this by rewriting the guest's code at runtime. The hypervisor scans the guest's instruction stream, identifies sensitive instructions, and replaces them with calls to emulation routines. The translated code is cached for reuse. This was VMware's breakthrough: it made x86 virtualization possible without hardware support. The downside is overhead: translation adds latency, especially for code that executes many sensitive instructions (like kernel code). VMware optimized this by translating only kernel code and letting user code run natively.

⚠️ Binary Translation Overhead

Binary translation can slow down guest code by 2–10× for instruction-heavy workloads. The overhead is worst for code that frequently executes sensitive instructions (kernel code, drivers). User-mode code (applications) runs at near-native speed because it rarely uses sensitive instructions. This is why early VMware was fast for I/O-bound workloads but slow for CPU-bound kernel operations. Modern hardware-assisted virtualization (VT-x/AMD-V) largely eliminates this overhead.

Hardware assistance is the modern solution. Intel VT-x (2005) and AMD-V (2006) added a new CPU mode—VMX root (hypervisor) and VMX non-root (guest)—and instructions to switch between them: VMLAUNCH (enter guest) and VMRESUME (resume guest). In VMX non-root mode, all sensitive instructions trap to the hypervisor, satisfying the Popek-Goldberg requirements. The hardware also provides a VMCS (Virtual Machine Control Structure) that stores the guest and host state, making context switches efficient. RISC-V has the Hypervisor Extension (H-mode) for the same purpose.

Paravirtualization is a fourth approach where the guest OS is modified to cooperate with the hypervisor. Instead of executing sensitive instructions and trapping, the guest makes explicit hypercalls to the hypervisor, like a system call. This avoids the overhead of trapping and emulation. The original Xen hypervisor used paravirtualization: Linux was modified to run as a Xen guest, replacing sensitive instructions with hypercalls. The downside is that the guest must be modified, so closed-source OSes (like Windows) could not run unmodified. Modern Xen supports hardware-assisted virtualization (HVM) for unmodified guests, making paravirtualization optional.

💡 Memory Virtualization

Virtualizing memory is a key challenge. The guest OS has its own page tables (guest virtual → guest physical). The hypervisor must translate guest physical to host physical. This is done with shadow page tables (hypervisor-maintained tables that map guest virtual → host physical directly) or nested page tables / EPT (Extended Page Tables, Intel; NPT, AMD—hardware that walks two levels of page tables). Shadow page tables are software-intensive (the hypervisor must intercept guest page table updates); EPT is hardware-assisted and faster but adds latency to each memory access. In RISC-V, the two-stage page table (Stage 1: guest virtual → guest physical; Stage 2: guest physical → host physical) provides the same functionality.

18.5 Types of Virtual Machines

Virtual machines come in several types, differing in what they virtualize and how. The main categories are system virtual machines (virtualize the hardware), process virtual machines (virtualize the OS API), and containers (OS-level virtualization). Each has different isolation, performance, and use-case characteristics.

System virtual machines virtualize the complete hardware. A Type 1 hypervisor (bare-metal) runs directly on the hardware with no host OS: examples include VMware ESXi, Microsoft Hyper-V, Xen, and KVM (which is built into the Linux kernel). A Type 2 hypervisor (hosted) runs on top of a host OS: examples include VMware Workstation, VirtualBox, and QEMU. The distinction is blurred in practice—KVM is a Linux kernel module (Type 2?) that runs directly on hardware (Type 1?)—but the key point is whether the hypervisor has direct hardware access.

Process virtual machines do not virtualize the hardware; instead, they provide a virtual instruction set and runtime environment for a single process. The Java Virtual Machine (JVM) is the canonical example: it executes Java bytecode and provides a runtime with garbage collection, security, and cross-platform portability. The .NET CLR and V8 (JavaScript engine) are similar. A process VM starts when the application starts and terminates when it exits. The "virtual machine" is the runtime, not a full OS.

Containers (OS-level virtualization) are a middle ground. A container shares the host kernel but has its own isolated user space: its own filesystem namespace, process namespace, network namespace, and user namespace. Because there is no second kernel, containers start in milliseconds (vs. seconds for VMs) and have near-zero overhead. The isolation is weaker than VMs (a kernel vulnerability affects all containers), but sufficient for most use cases. Docker popularized containers; Kubernetes orchestrates them at scale.

/* Container isolation via Linux namespaces */ // Docker run creates a container with isolated namespaces // Each namespace gives the container its own view: // PID namespace: container sees only its own processes // (PID 1 in container ≠ PID 1 on host) // Mount namespace: container has its own filesystem root // (can't see host files unless explicitly mounted) // Network namespace: container has its own network stack // (own IP, routing table, firewall rules) // User namespace: container UID 0 ≠ host UID 0 // (root in container is unprivileged on host) // cgroups: limit CPU, memory, I/O per container

Emulation is a related but distinct concept. An emulator interprets the guest's instructions one at a time, simulating a different architecture. QEMU can emulate ARM on x86, or x86 on ARM, by interpreting each instruction. This is much slower than virtualization (10–100×) but allows running software for a different architecture. QEMU/KVM combines QEMU's device emulation with KVM's hardware-assisted CPU virtualization: KVM handles the CPU, QEMU handles I/O devices, giving near-native speed for same-architecture guests.

ℹ️ QEMU and xv6

If you're running xv6, you're almost certainly using QEMU. QEMU emulates a RISC-V (or x86) system, including the CPU, memory, and virtual devices (UART, virtio disk, virtio network). xv6's Makefile invokes QEMU with a configuration that sets up the virtual hardware. When xv6 executes a csrw satp instruction (set page table), QEMU updates its emulated satp register. When xv6 writes to the UART, QEMU displays the character. This is full-system emulation—slower than KVM, but essential for OS development where you need to control the entire virtual machine.

Unikernels are a specialized type of VM that runs a single application directly on a hypervisor, with no OS. The application is compiled with a minimal library OS (like MirageOS or IncludeOS) that provides just enough OS functionality (network stack, file system) to run. The result is a tiny, specialized VM that boots in milliseconds, has a minimal attack surface, and is ideal for microservices and serverless functions. Unikernels blur the line between process VMs and system VMs: they are system VMs (they run on a hypervisor) but contain only one application (like a process VM).

18.6 Virtualization and OS Components

Virtualizing each OS component presents unique challenges. The CPU, memory, and I/O each require different techniques, and the hypervisor must handle all of them correctly and efficiently. Understanding how each component is virtualized illuminates both the power and the complexity of virtualization.

CPU virtualization is the core: the hypervisor must present each guest with one or more virtual CPUs (vCPUs) that behave like real CPUs. The guest OS schedules its processes on vCPUs as if they were physical cores. The hypervisor time-shares the physical CPUs among vCPUs: when a vCPU is "running," the hypervisor has scheduled it on a physical core. The guest is unaware of this scheduling—it believes its vCPU is always running. When the hypervisor needs the physical core for another vCPU, it preempts the current vCPU (using a timer interrupt) and schedules a different one.

/* CPU virtualization (conceptual) */ // Physical CPU has 4 cores; 3 VMs each want 2 vCPUs // Hypervisor time-shares: each vCPU gets a time slice while (true) { for each vcpu in runqueue { // Load vCPU state into physical core load_vmcs(vcpu); // Enter guest mode (VMLAUNCH / VMRESUME) // ... guest runs until trap or timer ... // Exit guest mode (VMEXIT) save_vmcs(vcpu); // Handle exit reason (I/O, page fault, timer) handle_exit(vcpu); } }

Memory virtualization is the most performance-critical component. The guest OS believes it has contiguous physical memory starting at address 0. In reality, its "physical" memory is allocated from the host's memory, possibly scattered across different host physical pages. The hypervisor must translate every guest physical address to a host physical address. As discussed in Section 18.4, this is done with shadow page tables (software) or nested page tables / EPT (hardware). The overhead of memory virtualization is significant: with EPT, each memory access requires walking two page tables (guest and host), increasing TLB miss penalties.

⚠️ The Memory Virtualization Challenge

Memory virtualization is the single biggest performance bottleneck in virtualized systems. With shadow page tables, the hypervisor must intercept every guest page table update (writing to CR3 on x86, or satp on RISC-V), which is frequent during process creation and context switching. With EPT, the TLB must store entries that map guest virtual → host physical, and a TLB miss requires walking two page tables (4 levels each on x86-64 = up to 8 memory accesses). Modern CPUs add VPID (Virtual Processor ID) to avoid TLB flushes on VM transitions, and large pages (2 MB, 1 GB) to reduce TLB pressure.

I/O virtualization is the most complex component because I/O devices are diverse and have complex interfaces. There are three main approaches:

  • Emulation: the hypervisor emulates a real device (e.g., an Intel e1000 NIC). The guest uses the standard device driver; the hypervisor intercepts device register writes and emulates the device behavior. This is slow (each I/O operation traps) but works with unmodified guests. QEMU uses this for its default devices.
  • Paravirtualization: the hypervisor provides a simplified, virtual device (e.g., virtio) that is designed for virtualization. The guest uses a special virtio driver that communicates with the hypervisor via shared memory and hypercalls, avoiding most traps. This is much faster than emulation. Virtio is the standard for KVM/QEMU.
  • Pass-through / SR-IOV: a physical device is assigned directly to a VM, bypassing the hypervisor. The guest has direct access to the device hardware, achieving near-bare-metal performance. SR-IOV (Single Root I/O Virtualization) allows a single physical device (like a NIC) to present multiple virtual functions, each assigned to a different VM. This is used for high-performance networking and storage in cloud environments.
MethodPerformanceGuest ModificationExample
EmulationSlow (traps per I/O)None (standard driver)QEMU e1000, IDE disk

Network virtualization deserves special mention. In a virtualized environment, VMs need to communicate with each other, with the host, and with the external network. The hypervisor provides a virtual switch (vSwitch) that connects VMs' virtual NICs. VM-to-VM traffic on the same host never touches the physical network—it is handled entirely in memory by the vSwitch. For external traffic, the hypervisor performs NAT or bridging. Technologies like Open vSwitch and VMware NSX provide advanced features like VLANs, QoS, and distributed switching across hosts.

💡 Virtualization and xv6

xv6 runs in QEMU, which uses emulation for I/O. When xv6 writes to the virtio disk controller, QEMU intercepts the register writes and translates them to reads/writes on the disk image file. When xv6 writes to the UART, QEMU displays the character. If you wanted to run xv6 under a real hypervisor (like KVM), you would need to either (1) use QEMU's emulation (slow but works) or (2) port xv6 to use virtio drivers and run under KVM (fast but requires modifying xv6). The virtio driver in xv6 is already a paravirtualized driver—it's designed to work with QEMU's virtio backend, not a real disk controller.

18.7 Examples: VMware and JVM

VMware is the most influential commercial virtualization product. Founded in 1998, VMware released VMware Workstation in 1999, the first x86 virtualization product. It used binary translation to virtualize the x86 architecture, which was not classically virtualizable. VMware's key innovation was a dynamic binary translator that scanned guest kernel code, identified sensitive instructions, and replaced them with calls to the VMM. User-mode code ran natively, so application performance was near-native; only kernel operations were translated.

VMware's product line evolved: VMware ESXi (2001) is a Type 1 hypervisor that runs directly on hardware (no host OS), designed for data centers. VMware Workstation and VMware Fusion (for Mac) are Type 2 hypervisors for desktop use. VMware vSphere is the enterprise platform, adding management, live migration (vMotion), high availability, and resource scheduling. With hardware-assisted virtualization (VT-x/AMD-V), modern VMware uses hardware support instead of binary translation for most operations, achieving near-native performance.

ℹ️ VMware Architecture

VMware ESXi architecture:

  • VMkernel: the hypervisor kernel (microkernel-like), manages CPU, memory, and I/O scheduling
  • VMX process: each VM is a VMX process that runs the guest, with VMkernel handling traps
  • VMM: the virtual machine monitor within each VMX, handles CPU virtualization (binary translation or VT-x)
  • vmxnet3, pvscsi: paravirtualized drivers for network and storage
  • vSphere Client: management interface for creating and configuring VMs

KVM (Kernel-based Virtual Machine) is the open-source alternative, integrated into the Linux kernel since 2007. KVM turns the Linux kernel into a Type 1 hypervisor: each VM is a regular Linux process, scheduled by the Linux scheduler, and KVM provides the CPU virtualization via VT-x/AMD-V. I/O is handled by QEMU, which runs in user space and provides device emulation. The combination QEMU/KVM is the standard open-source virtualization stack: KVM for CPU/memory, QEMU for devices. KVM is used by cloud platforms like OpenStack and underlies Google Compute Engine and other cloud services.

The Java Virtual Machine (JVM) is a fundamentally different kind of virtual machine: a process virtual machine that executes Java bytecode. The JVM is not a hypervisor; it does not virtualize hardware. Instead, it provides a platform-independent runtime: Java source is compiled to bytecode (architecture-neutral), and the JVM interprets or JIT-compiles the bytecode to native code. This "write once, run anywhere" model means the same Java program runs on any platform with a JVM.

/* JVM architecture (simplified) */ // Java source → bytecode → JVM // 1. Compiler: Hello.java → Hello.class (bytecode) javac Hello.java // 2. JVM loads Hello.class // Class loader reads .class, verifies bytecode // 3. Execution engine runs bytecode // - Interpreter: executes bytecode one instruction at a time // - JIT compiler: compiles hot methods to native code // - GC: automatic memory management // 4. Runtime data areas: // - Method area: class metadata, bytecode // - Heap: objects (GC-managed) // - Stack: method frames (per thread) // - PC register: current instruction (per thread)

The JVM provides several OS-like services: memory management (garbage collection), thread scheduling (maps Java threads to OS threads), security (security manager, class loaders), and I/O (file, network, via native methods). In this sense, the JVM is a language-level operating system—it manages resources for Java applications the way an OS manages resources for processes. The comparison is not accidental: the JVM's designers drew on OS concepts (processes, threads, memory protection, security) in designing the runtime.

Other notable virtualization examples include Microsoft Hyper-V (Type 1 hypervisor for Windows, uses paravirtualized "enlightened" guests), Xen (open-source hypervisor, originally paravirtualization, now supports HVM), Docker (containers using Linux namespaces and cgroups), and WebAssembly (WASM) (a portable bytecode for the web, increasingly used outside browsers via WASI, the WebAssembly System Interface). Each represents a different point in the design space of virtualization and isolation.

19.1 Advantages of Distributed Systems

A distributed system is a collection of independent computers that appears to its users as a single coherent system. The computers (nodes) are connected by a network and cooperate to achieve a common goal. Unlike a single computer, a distributed system has no shared memory—nodes communicate by passing messages over the network. The operating system (or middleware) presents a unified view, hiding the distribution from users and applications.

The primary advantages of distributed systems are resource sharing, scalability, fault tolerance, and geographic distribution. Resource sharing allows users on one node to access files, printers, databases, and computing power on other nodes. Scalability means the system can grow by adding more nodes, rather than replacing a single machine with a bigger one. Fault tolerance means the system can continue operating (perhaps with reduced capacity) if some nodes fail. Geographic distribution allows data and computation to be placed near the users who need them, reducing latency.

ℹ️ Key Advantages of Distributed Systems
  • Resource sharing: share files, printers, databases, CPU across nodes
  • Scalability: add nodes to increase capacity (horizontal scaling)
  • Fault tolerance: system survives node failures (redundancy)
  • Performance: parallel processing, load distribution
  • Geographic distribution: data near users, disaster recovery
  • Cost-effectiveness: many cheap nodes vs. one expensive mainframe
  • Data accessibility: data available from any location

However, distributed systems also introduce significant challenges. The most fundamental is partial failure: in a distributed system, some nodes may fail while others continue. This is qualitatively different from a single computer, which either works or doesn't. Handling partial failure requires detecting failures, reconfiguring the system, and ensuring consistency—problems that are notoriously difficult (the Byzantine generals problem, the consensus problem, CAP theorem).

Another challenge is latency: network communication is orders of magnitude slower than memory access. A local memory read takes ~100 ns; a network round trip in a data center takes ~500 μs (5000× slower); across continents, ~150 ms (1,500,000× slower). This latency fundamentally shapes distributed system design: operations that are fast locally (like reading a file) become slow remotely, requiring caching, replication, and asynchronous communication.

⚠️ The CAP Theorem

The CAP theorem (Brewer, 2000) states that a distributed system can provide at most two of three guarantees:

  • Consistency: all nodes see the same data at the same time
  • Availability: every request receives a response (no timeout)
  • Partition tolerance: the system operates despite network partitions

Since network partitions will happen (cables get cut, switches fail), real systems must choose between C and A during a partition. CP systems (like HBase, MongoDB with strong consistency) reject requests during a partition to maintain consistency. AP systems (like Cassandra, DynamoDB) accept requests and reconcile later, risking temporary inconsistency. There is no "CA" system that ignores partitions—partitions are a fact of network life.

Transparency is a key design goal: the distributed system should hide its distributed nature from users and applications. Types of transparency include access transparency (same operations for local and remote resources), location transparency (resources are accessed without knowing their location), replication transparency (users don't know about replicas), failure transparency (failures are hidden), and migration transparency (resources can move without affecting access). Achieving full transparency is extremely difficult; real systems make trade-offs.

19.2 Network Structure

A distributed system is built on a network that connects the nodes. Networks are classified by scale: LAN (Local Area Network, within a building or campus, ~1 km), MAN (Metropolitan Area Network, ~10 km), WAN (Wide Area Network, ~100+ km, e.g., the Internet), and PAN (Personal Area Network, ~10 m, e.g., Bluetooth). The network's characteristics—bandwidth, latency, reliability—fundamentally affect the distributed system built on top of it.

Networks are organized in layers, following the OSI model (7 layers) or the simpler TCP/IP model (4 layers). From bottom to top, the TCP/IP layers are: Link (Ethernet, Wi-Fi—physical and data link), Internet (IP—networking, routing), Transport (TCP, UDP—end-to-end communication), and Application (HTTP, DNS, SMTP—user protocols). Each layer builds on the one below, adding functionality.

LayerProtocolsFunction

Local Area Networks (LANs) typically use Ethernet (IEEE 802.3) or Wi-Fi (IEEE 802.11). Ethernet uses switches to connect devices; each device has a MAC address (hardware address). Switches forward frames based on MAC addresses, creating a point-to-point network. Wide Area Networks (WANs) use routers to forward packets between networks based on IP addresses. The Internet is a global WAN composed of thousands of interconnected networks, using BGP (Border Gateway Protocol) for inter-domain routing.

Network topology describes how nodes are connected. Common topologies include bus (all nodes on a shared wire, obsolete), star (all nodes connected to a central switch), ring (nodes in a circle), mesh (nodes connected to multiple peers), and tree (hierarchical). Modern data centers use spine-leaf topologies for low-latency, high-bandwidth any-to-any connectivity. The topology affects performance (latency, bandwidth), reliability (single points of failure), and cost.

ℹ️ Network Performance Metrics
  • Bandwidth: data rate (bits per second). Ethernet: 1–400 Gbps. Wi-Fi: 0.1–10 Gbps. Internet: variable.
  • Latency: time for a bit to travel. LAN: ~0.5 ms. Same data center: ~0.5 ms. Cross-continent: ~50–150 ms. Satellite: ~600 ms.
  • Jitter: variation in latency. Affects real-time applications (VoIP, gaming).
  • Packet loss: percentage of packets lost. Internet: 0.01–1%. Wi-Fi: higher, variable.
  • Throughput: actual data delivered per second (≤ bandwidth, reduced by overhead, loss, congestion).

Network protocols define the rules for communication. The Internet Protocol (IP) provides unreliable, connectionless packet delivery: packets may be lost, duplicated, or delivered out of order. TCP (Transmission Control Protocol) adds reliability: it numbers packets, acknowledges receipt, retransmits lost packets, and orders them, providing a reliable byte stream. UDP (User Datagram Protocol) is a thin layer over IP that adds port numbers but no reliability—useful for applications that can tolerate loss (video streaming, DNS, gaming) or implement their own reliability (QUIC, used by HTTP/3, implements reliability over UDP).

💡 xv6 and Networking

xv6 has a minimal networking stack. It includes a network interface card (NIC) driver (for the QEMU virtio-net device) and a basic network stack that can send and receive Ethernet frames. However, xv6 does not implement TCP/IP—there is no socket API, no TCP state machine, no IP routing. Adding networking to xv6 would require implementing: (1) an IP layer (packet forwarding, fragmentation), (2) a TCP layer (connection management, reliable delivery, congestion control), (3) a socket API (like socket(), bind(), listen(), accept()), and (4) network applications (a simple web server or chat client). This is a substantial project but illustrates how much functionality a real OS networking stack provides.

19.3 Communication Structure

Distributed systems communicate using various communication structures, each with different trade-offs. The fundamental choice is between message passing (explicit send/receive) and remote procedure call (RPC) (making a remote function call look like a local one). Higher-level abstractions like distributed shared memory and publish-subscribe build on these foundations.

Message passing is the most basic form: one process sends a message to another, which receives it. The send and receive operations may be blocking (synchronous: sender waits until the message is received) or non-blocking (asynchronous: sender continues immediately). Message passing is flexible but low-level: the programmer must explicitly marshal data, handle failures, and manage message ordering. The sockets API (Berkeley sockets) is the standard message-passing interface in Unix and Windows.

/* Socket communication (simplified) */ // Server side int server_fd = socket(AF_INET, SOCK_STREAM, 0); bind(server_fd, &addr, sizeof(addr)); listen(server_fd, 5); int client_fd = accept(server_fd, NULL, NULL); read(client_fd, buf, 1024); // receive message write(client_fd, reply, n); // send reply // Client side int sock = socket(AF_INET, SOCK_STREAM, 0); connect(sock, &addr, sizeof(addr)); write(sock, request, n); // send message read(sock, buf, 1024); // receive reply

Remote Procedure Call (RPC) is a higher-level abstraction that makes a call to a remote function look like a local function call. The caller invokes a function; the RPC runtime marshals the arguments into a message, sends it to the server, the server unmarshals the arguments, calls the function, marshals the result, and sends it back. The caller's function call returns the result as if it were local. This abstraction is powerful but hides important realities: network latency, partial failure, and the fact that a "local" call and a "remote" call have very different performance and failure characteristics.

⚠️ A Note on Distributed Computing

There is a famous fallacy in distributed computing, articulated by L. Peter Deutsch: "The network is reliable." Other fallacies: "Latency is zero," "Bandwidth is infinite," "The network is secure," "Topology doesn't change," "There is one administrator," "Transport cost is zero." These fallacies lead to broken distributed systems. RPC, in particular, hides the network so well that developers treat remote calls like local ones, leading to chatty protocols (many small calls) that are devastated by latency. Good distributed system design acknowledges the network's limitations and minimizes round trips.

RPC implementations include gRPC (Google, uses Protocol Buffers and HTTP/2), Apache Thrift (Facebook), JSON-RPC, and XML-RPC. Each defines an Interface Definition Language (IDL) for specifying the remote interface, and generates client stubs and server skeletons. The stub/skeleton handle marshaling, so the programmer writes code that looks like local function calls. REST (Representational State Transfer) is an architectural style (not RPC) that uses HTTP verbs (GET, POST, PUT, DELETE) on resources identified by URLs; it is simpler but less type-safe than RPC.

Distributed Shared Memory (DSM) is an abstraction that provides a shared memory model over a distributed system. Processes on different nodes can read and write shared variables as if they were in the same address space; the DSM runtime handles replication and consistency. DSM is appealing because it extends the familiar shared memory programming model to distributed systems. However, implementing DSM efficiently is extremely difficult: maintaining consistency across nodes with network latency leads to poor performance, and the abstraction hides the cost of remote access, leading to unpredictable performance. DSM is mostly of research interest; few production systems use it.

ℹ️ Marshaling and Serialization

Marshaling (or serialization) is the process of converting in-memory data structures into a byte stream for transmission. The receiver unmarshals (deserializes) the byte stream back into data structures. Challenges include: byte order (big-endian vs. little-endian), data types (integers, floats, strings, arrays, structs), pointers (must be replaced with identifiers), and versioning (handling schema changes). Common formats: JSON (human-readable, slow), Protocol Buffers (binary, fast, schema), MessagePack (binary JSON), Apache Avro (schema-based).

Publish-subscribe (pub/sub) is a communication pattern where publishers send messages to topics, and subscribers receive messages from topics they subscribe to. Publishers and subscribers are decoupled: publishers don't know who subscribes, and subscribers don't know who publishes. This is useful for event-driven architectures, IoT, and microservices. Apache Kafka, RabbitMQ, and Redis Pub/Sub are popular implementations. Pub/sub is asynchronous and scalable but introduces challenges in ordering, durability, and exactly-once delivery.

19.4 Network and Distributed Operating Systems

A network operating system (NOS) provides services that allow users on one machine to access resources on other machines, but each machine runs its own OS and users are aware of the network. Examples: users know they are logging in to a remote machine via SSH, or mounting a remote file system via NFS. The NOS provides the tools for network access, but the network is visible to users and applications.

A distributed operating system goes further: it presents a single system image. Users and applications see a single, coherent system, even though it spans multiple machines. The OS automatically places processes, files, and other resources across the network, transparently. Users do not know (or need to know) which machine their process runs on or where their files are stored. True distributed operating systems are rare: Amoeba, Plan 9, and LOCUS are research examples. Most "distributed systems" in practice are built on network operating systems (Linux + middleware) rather than true distributed operating systems.

The distinction matters because it affects how the system is designed and used. In a network OS, each machine runs a complete OS kernel and manages its own resources. Network protocols (NFS for files, SSH for remote login, SMTP for email) provide inter-machine services. The system is a federation of independent machines. This is the model of the Internet: each host is autonomous, and protocols enable cooperation.

In a distributed OS, the kernel itself is distributed: it runs across multiple machines and manages all resources globally. Process scheduling, memory management, and file systems are distributed—the OS decides where to run a process, where to store a file, and how to balance load. This requires sophisticated algorithms for distributed scheduling, distributed consensus, and distributed locking. The benefit is transparency; the cost is complexity and the difficulty of handling partial failure.

ℹ️ Middleware

In practice, most distributed systems use middleware—software that sits between the OS and the application, providing distributed services. Middleware includes: RPC frameworks (gRPC, Thrift), message queues (Kafka, RabbitMQ), distributed file systems (NFS, Ceph, HDFS), distributed databases (Cassandra, MongoDB), and coordination services (ZooKeeper, etcd). Middleware provides a distributed system abstraction without requiring a distributed operating system. This is the dominant approach: Linux (network OS) + middleware = distributed system.

Cluster computing is a common architecture: a set of identical machines (a cluster) connected by a high-speed LAN, running a network OS with middleware for coordination. Grid computing extends this across organizations and geographic boundaries, with heterogeneous machines. Cloud computing provides virtualized resources (VMs, containers, functions) on demand, with the cloud provider managing the infrastructure. All of these are built on network operating systems, not distributed operating systems—the transparency is provided by middleware and management software, not the OS kernel.

💡 Plan 9: A Distributed OS

Plan 9 from Bell Labs (1980s–1990s) is the most influential distributed operating system. Its key idea: everything is a file, and files can be remote. Plan 9 uses the 9P protocol to access resources on remote machines as if they were local files. A Plan 9 user can run a CPU-intensive computation on a remote CPU server, read files from a remote file server, and display output on a local terminal—all transparently. Plan 9 influenced Linux (the /proc filesystem, UTF-8) and modern distributed systems, but never achieved commercial success. It remains a touchstone for distributed OS design.

19.5 Design Issues

Designing a distributed system involves several fundamental issues that have no counterpart in single-machine systems. These include naming, consistency, replication, fault tolerance, and security. Each involves trade-offs, and the "right" choice depends on the application's requirements.

Naming is the problem of mapping human-readable names to resources (files, services, machines) in a distributed system. A name service (like DNS) translates names to addresses. Challenges include: scalability (the name space is global), latency (name resolution requires network access), caching (cached entries may be stale), and updates (propagating name changes). DNS uses a hierarchical, distributed database with caching and time-to-live (TTL) to balance freshness and performance. Service discovery (Consul, etcd, Kubernetes DNS) is a related problem: finding the address of a service that may move or scale.

Consistency is the problem of ensuring that all nodes agree on the state of shared data. Strong consistency (linearizability) guarantees that every read returns the latest write—this is easy on a single machine but expensive in a distributed system (requires coordination on every write). Eventual consistency allows replicas to diverge temporarily, with the guarantee that they will eventually converge. This is faster and more available but allows stale reads. Causal consistency and session consistency are intermediate points. The CAP theorem (Section 19.1) formalizes the trade-off: during a network partition, you must choose between consistency and availability.

Consistency ModelGuaranteeCostExample
Strong (linearizable)Read = latest writeHigh (coordination)Spanner, etcd

Replication is the practice of storing multiple copies of data on different nodes. Replication improves availability (data survives node failure), performance (read from a nearby replica), and scalability (distribute read load). The challenge is consistency: when data is updated, all replicas must be updated. Primary-backup replication has one primary that handles writes and forwards to backups; if the primary fails, a backup takes over. Multi-master replication allows writes to any replica, with conflict resolution. Quorum-based replication requires a majority of replicas to agree, balancing consistency and availability.

⚠️ The Consensus Problem

Consensus is the fundamental problem of distributed systems: how do nodes agree on a value? It sounds simple but is remarkably hard because nodes can fail and the network can delay or drop messages. The Paxos algorithm (Lamport, 1998) solves consensus but is notoriously complex. Raft (2014) is a more understandable consensus algorithm, used by etcd, Consul, and others. Consensus is the foundation of state machine replication: if all nodes agree on a sequence of operations, they can maintain identical state. This is how distributed systems like ZooKeeper and etcd provide consistent metadata.

Fault tolerance is the ability to continue operating despite failures. Distributed systems must handle: node crashes (a machine stops), network partitions (the network splits), byzantine failures (nodes behave maliciously), and storage failures (disk corruption). Techniques include replication (multiple copies), checkpointing (save state periodically), heartbeat monitoring (detect failed nodes), failover (switch to a backup), and Byzantine fault tolerance (tolerate malicious nodes, used in blockchain systems). The two-army problem shows that reliable communication over an unreliable channel is impossible with certainty; practical systems use timeouts and heuristics.

Security in distributed systems adds the challenge of securing communication over an untrusted network. Every message may be intercepted, modified, or replayed. TLS/SSL provides encryption, authentication, and integrity for network communication. Kerberos provides ticket-based authentication in distributed environments. Public Key Infrastructure (PKI) provides trust through certificate authorities. The zero-trust model assumes the network is hostile and authenticates every request, regardless of network location.

ℹ️ Distributed System Design Patterns
  • Load balancer: distribute requests across servers
  • Sharding: partition data across nodes (by key)
  • Replication: copy data for availability/performance
  • Caching: store frequently accessed data closer to consumers
  • Circuit breaker: stop calling a failing service (prevent cascading failures)
  • Leader election: choose one node to coordinate (via consensus)
  • Saga: distributed transaction as a sequence of compensating actions
  • Service mesh: sidecar proxy for service-to-service communication

19.6 Distributed File Systems

A distributed file system (DFS) allows files stored on remote servers to be accessed as if they were local. The DFS presents a unified file namespace that spans multiple machines, hiding the physical location of files. Users and applications access files using the same API (open, read, write) as local files, without knowing whether a file is local or remote. This is a key example of transparency in distributed systems.

The Network File System (NFS), developed by Sun Microsystems in 1984, is the most widely used DFS. NFS allows a client to mount a directory exported by a server, making the remote directory appear as part of the local file tree. When a process opens a file in the mounted directory, the NFS client sends requests to the NFS server over the network. NFS uses Sun RPC for communication and supports both UDP and TCP as transports. NFSv4 added strong security (Kerberos), stateful operation, and improved performance over WANs.

/* NFS mount and access */ // Server exports a directory // /etc/exports: // /home *(rw,sync,no_subtree_check) // Client mounts the remote directory mount server.example.com:/home /mnt/home // Now /mnt/home/* is the server's /home/* ls /mnt/home/alice // reads from server cat /mnt/home/alice/file.txt // file served over network // NFS protocol operations (over Sun RPC): // NFSPROC3_READ → read file by handle + offset // NFSPROC3_WRITE → write file by handle + offset // NFSPROC3_LOOKUP → resolve path component to file handle

Server Message Block (SMB) / Common Internet File System (CIFS) is the Microsoft equivalent, used for file sharing in Windows environments. SMB provides file, printer, and named pipe sharing over the network. Like NFS, it allows remote files to appear local. Samba is an open-source implementation of SMB for Unix, enabling Linux servers to share files with Windows clients. SMB 3.0 added features like SMB Direct (RDMA), encryption, and multi-channel.

Cloud distributed file systems are designed for data-center and cloud scale. HDFS (Hadoop Distributed File System) stores large files (100s of GB to TBs) by splitting them into blocks (128 MB) and replicating each block across multiple nodes (typically 3). HDFS is optimized for sequential reads of large files and is the storage layer for Hadoop. Ceph provides a unified storage system with object, block, and file interfaces, using CRUSH for data placement. Amazon S3 is an object store (not a file system) that provides essentially unlimited storage with 99.999999999% (11 nines) durability through replication and erasure coding.

The Andrew File System (AFS), developed at Carnegie Mellon in the 1980s, was a pioneering DFS that introduced several influential concepts. AFS uses whole-file caching: when a file is opened, the entire file is copied to the client's local cache, and subsequent reads and writes operate on the cache. The file is written back to the server only when closed. This dramatically reduces network traffic for files that are read or written repeatedly. AFS also introduced location independence: files are identified by name, not by server, and can be moved between servers without changing paths.

ℹ️ DFS Architecture: Client-Server

Most DFS use a client-server architecture: clients (user machines) request file operations from servers (file servers). The client typically has a cache to reduce network traffic: recently accessed file blocks are kept locally, and the client checks the cache before contacting the server. The consistency of the cache is a key issue: if another client modifies the file, the cached copy is stale. NFS uses attribute caching with time-based validation (check the server every N seconds); AFS uses callback promises (the server promises to notify the client of changes).

Google File System (GFS) and its successor Colossus are internal Google DFS designed for Google's workloads: large files, append-mostly access, and high failure rates (commodity hardware). GFS splits files into 64 MB chunks, replicates each chunk 3 times, and uses a single master for metadata (chunk locations) and chunkservers for data. The design assumes failures are common and optimizes for Google's specific access patterns. GFS influenced HDFS, which is the open-source equivalent.

💡 xv6 and Distributed File Systems

xv6 has a local file system (the "log-structured" file system on the virtio disk) but no network file system. Adding NFS-like functionality to xv6 would require: (1) a network stack (see Section 19.2), (2) an RPC layer (for NFS protocol messages), (3) a client-side VFS layer that redirects file operations to the network, and (4) a server-side handler that processes NFS requests. The xv6 file system interface (sys_open, sys_read, sys_write) would remain the same—the distribution would be transparent. This is exactly how NFS works on Linux: the VFS layer decides whether a file is local or remote, and dispatches accordingly.

19.7 DFS Naming and Transparency

Naming in a distributed file system is the mapping from file names to file locations. The naming scheme determines how users refer to files and how the system locates them. There are three levels of transparency in naming:

  • Location transparency: the name does not reveal the file's location. A path like /home/alice/file.txt does not indicate which server stores the file. The file can be moved to a different server without changing the path.
  • Location independence: the name remains valid even if the file moves. This is stronger than location transparency: not only does the name not reveal the location, but the file can be migrated while in use. AFS and Ceph support this; NFS (with static mounts) does not.
  • Access transparency: local and remote files are accessed using the same operations. The user does not need to use different commands for local and remote files. NFS and SMB achieve this through the VFS layer.
ℹ️ Naming Schemes
  • Host-based naming: the name includes the host (e.g., server:/path). NFS mounts use this. Not location-transparent.
  • Mount-based naming: a remote directory is mounted into the local namespace (e.g., /mnt/server/home). The local path hides the server, but the mount point reveals it. Semi-transparent.
  • Global naming: all files are in a single global namespace, and the system locates them automatically (e.g., AFS's /afs/cell/path). Fully location-transparent.

Symbolic links are a common mechanism for naming: a symbolic link is a file that contains a path to another file (which may be on a remote server). When the link is accessed, the OS follows it to the target. Symbolic links provide flexibility but can create dangling references (if the target is deleted) and do not provide location independence (the link contains the location).

Hard links and inodes are the Unix mechanism for file naming. An inode is a data structure that describes a file's contents and location on disk. A directory entry maps a name to an inode number. Multiple directory entries (hard links) can point to the same inode. In a DFS, the inode may be on a remote server; the client must resolve the name to a file handle (a unique identifier for the file on the server) before accessing it.

/* NFS file handle and name resolution */ // NFS uses file handles (opaque identifiers) to refer to files // A handle is: { server_ip, filesystem_id, inode_number, generation } // Name resolution: /home/alice/file.txt // 1. Start with root handle (from mount) // 2. LOOKUP "home" → handle for /home // 3. LOOKUP "alice" → handle for /home/alice // 4. LOOKUP "file.txt" → handle for /home/alice/file.txt // 5. READ(handle, offset, count) → file data // Each LOOKUP is an RPC to the server // Client caches handle→name mappings (directory cache)

Replication transparency means that users do not know (or need to know) that a file has multiple copies. When a user reads a file, the DFS may serve it from any replica; when a user writes, the DFS updates all replicas. The challenge is consistency: if two users write to different replicas simultaneously, the writes may conflict. DFS use various consistency models: read-your-writes (you see your own writes), monotonic reads (once you see a value, you never see an older one), and strong consistency (all replicas agree at all times, expensive).

⚠️ The Stale Cache Problem

In a DFS with client caching, a client may cache a file and continue reading from the cache while another client modifies the file on the server. The first client's cache is stale: it contains an outdated version. NFSv3 uses attribute caching with a timeout: the client periodically checks the file's modification time on the server and invalidates the cache if it changed. This reduces staleness but does not eliminate it—there is always a window where the cache may be stale. NFSv4 with delegations allows the server to "delegate" a file to a client, guaranteeing that the client will be notified of any changes—eliminating staleness for that file.

Failure transparency means that the DFS continues to operate despite failures. If a server crashes, the DFS should failover to a replica. If the network partitions, the DFS should either continue (accepting the risk of inconsistency) or refuse operations (maintaining consistency). High availability is achieved through replication: if one replica is unavailable, another can serve requests. The quorum approach requires a majority of replicas to agree on writes, ensuring that a single partition cannot make conflicting decisions.

Migration transparency allows files to be moved between servers without affecting access. This is useful for load balancing (move files from busy servers to idle ones) and server maintenance (evacuate a server before shutting it down). AFS supports file migration: the volume (a collection of files) is the unit of migration, and the volume location database tracks the current location. Clients consult the database to find the current server, then access the file directly.

💡 Transparency Trade-offs

Full transparency is the ideal but is expensive. Real DFS make trade-offs:

  • NFS: access transparency (yes), location transparency (partial—mount points), location independence (no—static mounts), consistency (weak—cache staleness).
  • AFS: access transparency (yes), location transparency (yes—global namespace), location independence (yes—volume migration), consistency (session—callbacks).
  • Ceph: access transparency (yes), location transparency (yes), location independence (yes—dynamic placement), consistency (strong—via metadata server).

The more transparency you provide, the more complex the implementation. NFS's simplicity (stateless server, weak consistency) is why it has survived for 40+ years.

19.8 Remote File Access Methods

Remote file access in a DFS involves several mechanisms that determine how data is transferred between client and server. The key design decisions are caching, consistency, statefulness, and failure handling. Each choice involves trade-offs between performance, consistency, and complexity.

Caching is the primary performance optimization in a DFS. Without caching, every read and write would require a network round trip, making the DFS unusable. The client caches recently accessed data (file blocks, attributes, directory entries) and serves subsequent accesses from the cache. The cache granularity matters: block-level caching (cache disk blocks, like NFS) is fine-grained but may require many requests to read a file; whole-file caching (cache the entire file, like AFS) is coarse but efficient for files that are read or written in full.

Caching StrategyGranularityProsCons
Block caching (NFS)4–8 KB blocksMemory efficient, random accessMany requests for large files
Whole-file caching (AFS)Entire fileFew requests, local-speed accessWasteful for large, rarely-read files
Hybrid (Ceph)ConfigurableFlexibleComplex implementation

Cache consistency is the problem of ensuring that cached data is not stale. There are two main approaches: client-initiated validation and server-initiated invalidation. In client-initiated validation (NFSv3), the client periodically checks with the server whether the cached data is still valid (by comparing modification times). This is simple but allows staleness between checks. In server-initiated invalidation (AFS callbacks, NFSv4 delegations), the server keeps track of which clients have cached a file and notifies them when the file changes. This eliminates staleness but requires the server to maintain state (which clients have cached what).

/* Cache consistency approaches */ // 1. Client-initiated (NFSv3): periodic validation read(file) { if (cache_valid(file) && !expired(cache_time)) { return cache[file]; // fast path } attr = GETATTR(file); // RPC to server if (attr.mtime == cached_mtime) { renew_cache(file); // still valid return cache[file]; } // Stale: re-read from server cache[file] = READ(file, 0, size); return cache[file]; } // 2. Server-initiated (AFS callback): push invalidation // Server maintains: file → list of clients with callbacks // On write: server sends CB_REVOKE to all listed clients // Client invalidates cache on receiving CB_REVOKE // No polling needed; no staleness window

Stateful vs. stateless servers is a fundamental design choice. A stateless server (NFSv3) does not maintain any state about clients: each request is self-contained, and the server can be restarted without affecting clients. A stateful server (NFSv4, SMB, AFS) maintains state about open files, locks, and client sessions. Stateful servers enable features like file locking (prevent concurrent writes) and delegations (server guarantees to notify of changes), but require session recovery if the server crashes.

⚠️ Stateless vs. Stateful: The Recovery Problem

A stateless server can crash and restart without clients noticing (they just retry requests). But it cannot support file locking (which requires the server to track who holds locks). A stateful server can support locking and delegations, but if it crashes, all state is lost. Clients must detect the crash and recover (re-establish locks, re-open files). NFSv4 uses lease-based locking: locks are granted for a limited time (a lease), and the client must renew them periodically. If the server crashes and restarts, it waits for all leases to expire before granting new locks, ensuring no stale locks survive. This is a clever compromise between statelessness and statefulness.

File locking in a distributed system is challenging because locks must be consistent across all clients and must survive failures. Advisory locking (locks are not enforced by the system; applications must check) is simpler but relies on cooperation. Mandatory locking (the system enforces locks) is safer but can cause deadlocks and performance problems. In a DFS, locking requires a distributed lock manager that tracks locks across all nodes. The lock revocation problem (Section 17.7) is acute: if a client holds a lock and crashes, the server must detect the failure (via lease expiry or heartbeat) and revoke the lock.

Failure handling in remote file access must deal with: server crashes (the server stops), network failures (the network drops or delays packets), client crashes (the client stops), and byzantine failures (the server behaves incorrectly). The standard approach is at-least-once semantics: the client retries a request until it receives a response. This works for idempotent operations (like reading a file at a given offset—repeating the read returns the same data) but is dangerous for non-idempotent operations (like appending to a file—repeating the append writes twice). Exactly-once semantics requires the server to track which requests have been processed, typically using request IDs and a reply cache.

ℹ️ Semantics of Remote File Operations
  • At-least-once: the operation is performed one or more times. Safe for idempotent operations (read, set attribute). Unsafe for non-idempotent (append, increment).
  • At-most-once: the operation is performed zero or one times. The client may not know if it was performed. Used when the client can tolerate uncertainty.
  • Exactly-once: the operation is performed exactly one time. Requires the server to deduplicate requests (using request IDs) and handle crashes carefully. Most expensive but safest.

NFSv3 provides at-least-once for most operations (the client retries). NFSv4 improves this with session trunking and exactly-once semantics for session-based operations.

Performance optimization in remote file access includes: read-ahead (prefetch the next blocks of a file, anticipating sequential access), write-behind (buffer writes and flush asynchronously), batching (combine multiple operations into one RPC), and compression (compress data before transmission). NFSv4 introduced compound procedures that combine multiple operations (like LOOKUP + OPEN + READ) into a single RPC, reducing round trips. pNFS (parallel NFS) separates metadata and data: clients access data servers directly (bypassing the metadata server for bulk I/O), enabling parallel access and higher throughput.

💡 Remote File Access and xv6

xv6's file system is entirely local. If you wanted to add remote file access (like NFS), you would need to: (1) add a network stack, (2) implement an RPC layer, (3) modify the file system to support remote operations (a VFS-like layer that dispatches to local or remote handlers), (4) implement caching with a consistency protocol, and (5) handle failures (retry, timeout). The xv6 file system code (file.c, fs.c, sysfile.c) would need to be generalized to support both local and remote backends. This is a significant project, but it illustrates how a real OS supports distributed file access—and how much complexity the "transparent" remote access actually involves.
