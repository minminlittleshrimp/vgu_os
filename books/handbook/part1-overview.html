1.1 What Operating Systems Do

An operating system is software that manages a computer's hardware and provides a convenient environment for running application programs. It acts as an intermediary between the user and the hardware, abstracting away low-level details such as disk sectors, interrupt controllers, and memory addresses. From the perspective of a user, the OS provides a virtual machine that is easier to use than the bare hardware; from the perspective of the hardware, the OS is a resource manager that allocates CPU time, memory, I/O devices, and storage among competing programs.

The two primary goals of an operating system are: (1) convenience—making the computer convenient to use—and (2) efficiency—ensuring that hardware resources are used efficiently. In early batch systems, efficiency was paramount because hardware was expensive. In modern interactive systems, convenience and responsiveness are equally important. A third goal, increasingly emphasized in the 21st century, is security: the OS must protect one user's programs and data from interference by others.

Consider what happens when you run a simple C program that reads a file and prints its contents. The program does not directly access the disk controller; instead, it calls library functions that eventually invoke system calls—protected routines provided by the kernel. The OS validates the request, locates the file on disk, reads the data into a kernel buffer, copies it to user space, and returns control to the program. Every step involves the OS acting as a gatekeeper and resource manager.

ℹ️ Key Insight

The OS is the only software that runs in kernel mode (also called supervisor mode or privileged mode). All other programs—compilers, browsers, text editors—run in user mode, where direct hardware access is forbidden. The transition from user mode to kernel mode happens via a trap or system call.

In the xv6 teaching operating system (used at MIT and elsewhere), this separation is visible in the source code. User processes execute in a lower privilege level, and the syscall() function in syscall.c dispatches to kernel handlers based on a system call number. This mirrors the design described by Silberschatz: the kernel provides a system-call interface that user programs use to request services.

1.2 Computer-System Organization

A modern computer system can be viewed as having four main components: the CPU (processor), the main memory (RAM), the I/O devices, and the system bus that interconnects them. The operating system manages all of these. A key architectural feature is the interrupt mechanism, which allows I/O devices to signal the CPU when they need attention, freeing the CPU from polling.

When an I/O device needs to notify the CPU—for example, when a key is pressed or a disk transfer completes—it raises an interrupt. The CPU suspends its current execution, saves its state (program counter, registers), and transfers control to an interrupt service routine (ISR) in the OS. After the ISR completes, the CPU resumes the interrupted program. This mechanism is fundamental to how operating systems achieve concurrency and responsiveness.

/* Simplified interrupt handling flow (xv6-style) */ // 1. Device raises interrupt signal // 2. CPU finishes current instruction, saves PC to mepc (RISC-V) // 3. CPU jumps to trap vector (mtvec register) trap_vector: csrrw sp, mscratch, sp // swap to kernel stack call trap_handler // dispatch to C handler csrrw sp, mscratch, sp // restore user stack mret // return to user mode

Modern systems use DMA (Direct Memory Access) controllers to offload bulk data transfers. Instead of the CPU copying each byte from a disk to memory, the DMA controller transfers data directly between the device and RAM, raising an interrupt only when the entire transfer is complete. This dramatically improves throughput and frees the CPU for other work.

Storage structure is layered: registers (fastest, smallest, inside the CPU) → cache (SRAM, L1/L2/L3) → main memory (DRAM) → solid-state drives (SSD) → hard disk drives (HDD) → tape (slowest, cheapest). The OS manages this hierarchy, deciding what to keep in cache, what to swap to disk, and how to schedule I/O. The speed gap between registers and disk can be over 10 million times, making the OS's memory management decisions critical to performance.

1.3 Computer-System Architecture

Computer systems are classified by how many CPUs they have and how they share memory. A single-processor system has one main CPU that executes a single instruction stream. Most embedded devices and older personal computers fall into this category. A multiprocessor system (also called a parallel system or tightly coupled system) has two or more CPUs that share the same memory and I/O devices, communicating via shared variables.

Multiprocessor systems offer several advantages: increased throughput (doing more work in less time), economy of scale (sharing peripherals and memory), and increased reliability (if one CPU fails, others can continue). Two common multiprocessor designs are SMP (Symmetric Multiprocessing), where all processors are equal and each runs its own copy of the OS, and ASMP (Asymmetric Multiprocessing), where one master processor runs the OS and slave processors run user code. Modern systems almost exclusively use SMP.

💡 Multicore vs. Multiprocessor

A multicore CPU has multiple processing cores on a single chip, sharing L2/L3 cache. A multiprocessor system has multiple CPU chips. Both are forms of parallel processing. The OS must be designed to schedule threads across cores and manage cache coherence.

A clustered system is a type of loosely coupled multiprocessor where multiple independent computers (nodes) are connected via a network or high-speed interconnect. Clusters provide high availability—if one node fails, others take over. Asymmetric clustering has one node in standby mode ready to take over; symmetric clustering has all nodes actively running and monitoring each other. Clusters are the backbone of modern cloud computing and data centers.

Modern CPUs also support simultaneous multithreading (SMT, called Hyper-Threading on Intel CPUs), where a single physical core can execute two or more threads concurrently by sharing functional units. From the OS's perspective, an SMT core appears as multiple logical processors, but performance gains are typically 15–30% per additional thread, not the 100% a true second core would provide.

1.4 Operating-System Operations

Operating systems are designed to run in two modes: user mode and kernel mode (also called supervisor, system, or privileged mode). This dual-mode operation is implemented in hardware via a mode bit in the CPU's status register. In user mode, certain instructions (such as directly accessing I/O ports or manipulating memory management registers) are prohibited. In kernel mode, all instructions are allowed. This separation protects the OS and other programs from buggy or malicious user code.

When a user program needs a privileged service—reading a file, allocating memory, creating a process—it executes a system call. The system call causes a trap (a software-generated interrupt), which switches the CPU to kernel mode and transfers control to a fixed location in the OS. The OS validates the request, performs the operation, and returns to user mode. This is the fundamental mechanism by which the OS maintains control.

/* Dual-mode operation: user → kernel transition */ // User program calls: fd = open("file.txt", O_RDONLY); // The C library translates this to a system call: user_mode: li a7, 56 // syscall number for sys_open (RISC-V Linux) ecall // trap into kernel — mode bit → 0 (kernel) kernel_mode: // OS saves user registers, checks syscall number, // validates arguments, performs the operation, // then returns via sret (mode bit → 1, user) sret

On startup, the OS begins executing in kernel mode as the bootstrap program (or bootloader) initializes the system: it loads the kernel into memory, initializes device drivers, sets up the page tables, and then starts the first user process (often called init on UNIX systems, PID 1). In xv6, the boot sequence starts at entry.S (assembly) which sets up the stack and calls main() in main.c, which initializes subsystems and starts the first user process via userinit().

Modern operating systems also support timers to prevent a single process from monopolizing the CPU. The OS sets a hardware timer to interrupt after a fixed interval (the time quantum or time slice). When the timer fires, control returns to the OS, which can then preempt the current process and schedule another. This is the basis of preemptive multitasking.

⚠️ Timer Interrupts Are Essential

Without timer interrupts, a CPU-bound process in an infinite loop would never yield. Cooperative multitasking (used in early Mac OS) relied on programs voluntarily yielding, which was unreliable. Preemptive multitasking via timer interrupts is now universal.

1.5 Resource Management

The operating system is fundamentally a resource manager. The resources it manages include the CPU, memory, storage, I/O devices, and—on multi-user systems—access to shared data. Each resource type requires its own management strategy, and the OS must balance fairness, efficiency, and protection.

CPU management is the domain of the process scheduler. The OS maintains a ready queue of processes waiting for CPU time and uses a scheduling algorithm (round-robin, priority, multilevel feedback) to decide which process runs next. The scheduler must ensure that every process gets a fair share of CPU time while keeping the system responsive. On multiprocessor systems, the scheduler must also balance load across cores and manage cache affinity.

Memory management involves keeping track of which parts of memory are in use (by which processes), allocating and freeing memory as needed, and providing virtual memory—the illusion that each process has its own large, contiguous address space. The OS uses paging and segmentation to map virtual addresses to physical addresses, and can swap inactive pages to disk to free up RAM. In xv6, the functions in kalloc.c manage physical memory as a free list of 4 KB pages, while vm.c manages page tables.

/* xv6 physical page allocator (simplified) */ struct run { struct run *next; }; struct { struct run *freelist; // linked list of free 4KB pages } kmem; // Allocate one 4KB page void *kalloc(void) { struct run *r = kmem.freelist; if (r) kmem.freelist = r->next; return (void*)r; }

Storage management (file systems) organizes data on disks and SSDs into files and directories, providing a convenient abstraction over raw blocks. The OS maintains a file allocation table or inode structure to track which blocks belong to which file. I/O device management provides device drivers that present a uniform interface to diverse hardware—disks, network cards, keyboards, displays—so that applications can use them without knowing hardware-specific details.

1.6 Security and Protection

Protection is a mechanism for controlling the access of programs, processes, or users to system resources. Security is a broader concept that defends the system from external and internal attacks, including unauthorized access, denial-of-service, and data corruption. The OS must ensure that a process can only access resources within its authorized domain.

The dual-mode (user/kernel) separation is the first line of defense: user programs cannot directly access hardware or other processes' memory. Memory protection ensures that each process's address space is isolated—process A cannot read or write process B's memory. This is enforced by the memory management unit (MMU) and page tables, which map virtual addresses to physical addresses and raise a fault if a process accesses an unmapped or protected region.

On multi-user systems, the OS implements access control through user identifiers (UIDs) and permission bits. Each file has an owner, a group, and a set of permission bits (read, write, execute) for the owner, group, and others. The OS checks these permissions on every file access. In UNIX-like systems, the root user (UID 0) bypasses most permission checks, which is both powerful and dangerous.

⚠️ Principle of Least Privilege

Every program and every user should operate using the least set of privileges necessary to complete the job. Running a web server as root is a classic security mistake—if the server is compromised, the attacker gets full system access. Modern systems use capabilities, sandboxing, and containerization to enforce this principle.

Security threats include malware (viruses, worms, trojans, ransomware), buffer overflow attacks (overwriting return addresses to hijack control flow), and side-channel attacks (inferring secrets from timing or power consumption). The OS defends against these through address space layout randomization (ASLR), stack canaries, non-executable stacks (NX bit), and privilege separation. Recent hardware vulnerabilities like Meltdown and Spectre have shown that even hardware-level protections can be circumvented, requiring OS-level mitigations.

1.7 Virtualization

Virtualization is a technology that allows a single physical machine to host multiple virtual machines (VMs), each running its own operating system. The software layer that creates and manages VMs is called a hypervisor or virtual machine monitor (VMM). There are two types: Type 1 (bare-metal, like VMware ESXi, Xen, Hyper-V) runs directly on hardware; Type 2 (hosted, like VirtualBox, VMware Workstation) runs on top of a host operating system.

Virtualization works by trapping and emulating privileged operations. When a guest OS (running in a VM) attempts a privileged instruction—such as modifying a page table or accessing an I/O port—the CPU traps to the hypervisor, which emulates the operation on behalf of the guest. This allows multiple guest OSes to share the same hardware safely. Modern CPUs provide hardware-assisted virtualization (Intel VT-x, AMD-V, ARM virtualization extensions) that makes this process much more efficient.

ℹ️ Virtualization vs. Containers

VMs virtualize the hardware, each running a full OS kernel. Containers (Docker, Kubernetes) virtualize at the OS level—sharing one kernel but isolating processes and their file systems. Containers are lighter and faster to start, but provide weaker isolation than VMs.

Virtualization enables server consolidation (running many small servers on one physical machine), live migration (moving a running VM to another physical host), and cloud computing (renting VMs on demand from providers like AWS, Azure, GCP). It also supports sandboxing—running untrusted code in an isolated VM to limit damage if it misbehaves. The concept of virtualization extends beyond CPUs: memory virtualization (virtual memory), storage virtualization (RAID, logical volumes), and network virtualization (VLANs, SDN) all follow the same principle of abstracting physical resources.

In the context of this course, xv6 itself can be run as a guest under QEMU, which emulates a RISC-V machine. This is a form of system-level emulation—the QEMU VMM translates xv6's RISC-V instructions and emulates its devices, allowing students to develop and test OS code without dedicated hardware.

1.8 Distributed Systems

A distributed system is a collection of physically separate computers connected by a network, appearing to the user as a single coherent system. Unlike multiprocessor systems (which share memory), distributed systems have no shared memory—each node has its own memory, and communication happens via message passing over the network. The network may be a LAN (local area network), WAN (wide area network), or even the internet.

Distributed systems offer several advantages: resource sharing (accessing remote files, printers, databases), computation speedup (splitting a large task across nodes), reliability (if one node fails, others continue), and communication (email, chat, web). However, they introduce challenges: latency (network delays), partial failure (some nodes may crash while others continue), concurrency (multiple nodes accessing shared data simultaneously), and heterogeneity (different hardware and OS types).

💡 Key Challenge: Partial Failure

In a distributed system, the network can partition—some nodes become unreachable. The system must decide: do we stop serving requests (sacrificing availability) or risk serving stale data (sacrificing consistency)? This is the CAP theorem: you can have at most two of Consistency, Availability, and Partition tolerance.

The OS support for distributed computing includes network protocols (TCP/IP, RPC—Remote Procedure Call), distributed file systems (NFS, AFS, CIFS/SMB), and distributed shared memory (DSM) systems that simulate shared memory over a network. Cloud computing platforms (AWS, Azure, GCP) are large-scale distributed systems that provide on-demand computing resources. Modern distributed system designs include microservices (small, independently deployable services), container orchestration (Kubernetes), and serverless computing (AWS Lambda).

1.9 Kernel Data Structures

The kernel uses a variety of data structures to track processes, memory, files, and devices. Understanding these is essential for reading kernel source code. The most common structures include linked lists, queues, hash maps, trees, and bitmaps.

A process control block (PCB) is the central data structure for process management. It stores the process's state (running, ready, blocked), program counter, CPU registers, memory limits, open file descriptors, scheduling priority, and accounting information. In xv6, the PCB is the struct proc defined in proc.h. The kernel maintains an array of these structures (proc[NPROC]) and uses a linked list to track active processes.

/* xv6 process control block (simplified from proc.h) */ enum procstate { UNUSED, USED, SLEEPING, RUNNABLE, RUNNING, ZOMBIE }; struct proc { enum procstate state; // process state int pid; // process ID struct proc *parent; // parent process void *chan; // sleep channel (for waiting) int killed; // flag: has been killed? struct trapframe *trapframe; // saved registers struct context context; // for context switching pagetable_t pagetable; // process page table struct file *ofile[NOFILE]; // open files };

Other key kernel data structures include: page tables (multi-level trees mapping virtual to physical addresses), file tables (tracking open files and their offsets), inode tables (tracking file metadata and block lists), device tables (tracking I/O devices and their drivers), and ready queues (lists of runnable processes). The choice of data structure affects performance: hash tables provide O(1) lookup, balanced trees provide O(log n), and linked lists provide O(n) but are simple and flexible.

1.10 Computing Environments

Operating systems span a wide range of computing environments, each with different requirements. Traditional computing refers to desktop and laptop computers running general-purpose OSes like Windows, macOS, or Linux. These systems prioritize user interactivity, support for diverse applications, and backward compatibility.

Mobile computing (smartphones, tablets) runs OSes like Android and iOS. These systems emphasize power efficiency (battery life), touch interfaces, and app sandboxing (each app runs in an isolated environment with limited permissions). Mobile OSes often aggressively kill background apps to save power, unlike desktop OSes that let processes run indefinitely.

Embedded systems are specialized computers within larger devices—car engine controllers, medical devices, IoT sensors, smart appliances. They often run real-time operating systems (RTOS) like FreeRTOS, VxWorks, or QNX that guarantee deterministic timing: critical tasks must complete within a deadline. A pacemaker that responds 50 ms late could be fatal; a game that drops a frame is merely annoying.

ℹ️ Real-Time Systems

Hard real-time systems guarantee that deadlines are always met (medical, aerospace). Soft real-time systems try to meet deadlines but tolerate occasional misses (streaming video, games). RTOSes use priority-based preemptive scheduling and avoid unpredictable delays (like garbage collection or disk I/O).

Cloud computing provides on-demand access to shared pools of configurable computing resources over the internet. Service models include IaaS (Infrastructure as a Service—virtual machines, e.g., AWS EC2), PaaS (Platform as a Service—managed runtimes, e.g., Heroku, Google App Engine), and SaaS (Software as a Service—applications, e.g., Gmail, Office 365). Cloud OSes must handle massive scale, multi-tenancy, and rapid provisioning. Edge computing pushes computation closer to data sources (IoT devices, 5G base stations) to reduce latency.

1.11 Open-Source Operating Systems

Open-source software is software whose source code is freely available for anyone to view, modify, and redistribute. In the OS world, open-source systems have become dominant, especially in servers, supercomputers, and embedded devices. The most prominent example is Linux, created by Linus Torvalds in 1991 and now developed by thousands of contributors worldwide.

Open-source OSes offer several advantages: transparency (anyone can audit the code for bugs and backdoors), customizability (you can modify the kernel for your specific needs), community support (large communities provide patches, drivers, and documentation), and cost (typically free). The GNU project (started by Richard Stallman in 1983) provides many of the user-space tools (compiler, shell, utilities) that complement the Linux kernel, forming what is commonly called "GNU/Linux."

💡 xv6 Is Open Source Too

The xv6 teaching operating system used in this course is open source, derived from UNIX Version 6 (1975) and modernized for RISC-V. Its source code is small enough (~10,000 lines) to read in a semester, yet implements all major OS concepts: processes, virtual memory, file system, and system calls. Studying xv6 is one of the best ways to understand how a real OS works.

Beyond Linux, notable open-source OSes include FreeBSD (a direct descendant of BSD UNIX, known for its network stack and ZFS support), Android (open-source mobile OS based on the Linux kernel), and ReactOS (an open-source Windows-compatible OS). The GNU General Public License (GPL) used by Linux requires that derivative works also be open source, while more permissive licenses like BSD and MIT allow proprietary derivatives. The choice of license has significant implications for how the software can be used and distributed.

The open-source development model—distributed contributors, public version control (Git), and meritocratic review—has proven remarkably effective. The Linux kernel receives thousands of patches per release from hundreds of companies. This collaborative approach has made open-source OSes the foundation of modern computing infrastructure, from Android phones to the servers running most of the internet.

2.1 Operating-System Services

An operating system provides a set of services to programs and users. These services make the computer usable and efficient. Silberschatz organizes them into two categories: services that are helpful to the user and services that ensure efficient system operation.

User-facing services include: user interface (GUI, command-line, or touch), program execution (loading programs into memory and running them), I/O operations (reading from and writing to files and devices), file-system manipulation (creating, deleting, searching files and directories), communications (between processes, possibly on different machines), and error detection (catching hardware failures, software bugs, and resource exhaustion).

System-efficiency services include: resource allocation (managing CPU, memory, and I/O allocation among competing processes), accounting (tracking which users and processes use how much of which resources), and protection and security (ensuring that all access to resources is controlled and that processes cannot interfere with each other or the OS).

A well-designed system call interface is stable (programs written decades ago still compile and run), consistent (naming conventions, error codes), and minimal (only the essential operations are in the kernel; the rest are in libraries).

2.2 User and Operating-System Interface

There are two primary ways users interact with an operating system: through a command-line interface (CLI) or a graphical user interface (GUI). Some systems also provide a touch-screen interface for mobile devices. Each has its strengths and target audience.

A command interpreter (or shell) is a program that reads commands from the user and executes them. On UNIX-like systems, common shells include bash, zsh, and fish. The shell can execute built-in commands directly or run external programs by forking a child process and calling exec(). In xv6, the shell is a user-level program (sh.c) that demonstrates how a shell works using fork(), exec(), and wait().

/* xv6 shell: simplified command execution */ int main(void) { char buf[128]; while (getcmd(buf, sizeof(buf)) >= 0) { if (buf[0] == 'c' && buf[1] == 'd' && buf[2] == ' ') { // built-in: cd chdir(buf + 3); continue; } if (fork1() == 0) // child runcmd(parsecmd(buf)); // exec the command wait(0); // parent waits } }

A GUI provides windows, icons, menus, and a pointing device (mouse). The windowing system manages overlapping windows, handles input events (mouse clicks, key presses), and draws graphics. On Linux, the X Window System (X11) or Wayland provides the windowing infrastructure; on macOS, it is Quartz; on Windows, it is the Desktop Window Manager. GUIs are more intuitive for casual users but less efficient for repetitive or scriptable tasks.

Many power users combine both: using a GUI for browsing and email, but a CLI for development, system administration, and automation. The scripting capability of shells—combining commands with pipes (|), redirection (>), and variables—makes them powerful tools for automation. Modern systems also provide system calls via library functions (the C standard library wraps system calls), so programmers rarely need to invoke system calls directly.

2.3 System Calls

System calls are the interface between user processes and the operating system kernel. They provide the only way for a user program to request privileged services such as I/O, process creation, and memory management. When a program makes a system call, execution transfers from user mode to kernel mode via a trap instruction (e.g., ecall on RISC-V, syscall on x86-64).

System calls are typically grouped into categories: process control (fork, exec, exit, wait), file management (open, read, write, close), device management (ioctl, mmap), information maintenance (getpid, time, getrusage), and communications (pipe, shmget, socket).

/* How a system call works (RISC-V / xv6) */ // 1. User program calls the C library wrapper: int fd = open("hello.txt", O_RDONLY); // 2. The wrapper (in usys.pl / ulib.c) does: .globl open open: li a7, 14 // SYS_open = 14 in xv6 ecall // trap to kernel ret // return result in a0 // 3. In the kernel (syscall.c): void syscall(void) { int num = p->trapframe->a7; // get syscall number switch (num) { case SYS_open: p->trapframe->a0 = sys_open(); // dispatch break; // ... other cases ... } }

System calls have parameters that must be passed from user space to kernel space. Three common methods are: (1) passing parameters in registers (fastest, but limited number), (2) passing parameters in a block or table in memory, with the address passed in a register, and (3) pushing parameters onto the stack (flexible, but slower). Most modern systems use a combination of registers for the first few arguments and the stack for the rest, following the calling convention (e.g., RISC-V uses a0– a7 for arguments).

ℹ️ System Call Numbers

Each system call has a unique number that identifies it. The user program places this number in a specific register (e.g., a7 on RISC-V, rax on x86-64) before executing the trap instruction. The kernel reads this number and dispatches to the corresponding handler. This indirection allows the kernel to validate and control all privileged operations.

The standard C library (glibc on Linux) provides wrapper functions for system calls, so programmers rarely write the assembly directly. For example, printf() eventually calls write(), which is a system call. This layering means that a simple printf("Hello\n") involves: formatting the string in user space, calling the write wrapper, executing the ecall/syscall instruction, the kernel copying data from user space to kernel space, the kernel writing to the console device, and returning to user space.

2.4 System Services

Beyond system calls, operating systems provide system services—also called system programs or system utilities—that are not part of the kernel but are essential for a usable system. These programs run in user space and use system calls to perform their tasks. They bridge the gap between the raw kernel interface and what users and administrators need.

Categories of system services include: file management (ls, cp, mv, rm, mkdir), status information (ps, top, du, df, who), file modification (text editors like vi, emacs, nano), programming-language support (compilers like gcc, clang; interpreters like python, node), program loading and execution (the shell, exec, ld), and communications (ssh, ftp, mail, web browsers).

💡 Kernel vs. User Space

The kernel provides the minimal set of mechanisms (system calls). System services build higher-level functionality on top. For example, the kernel provides read() and write(), but the cat command (a system service) uses those to concatenate files. This separation keeps the kernel small and focused, while allowing rich user-space tools.

Most operating systems also provide background services called daemons (UNIX terminology) or services (Windows terminology). These run continuously, handling requests or performing maintenance. Examples include sshd (SSH server), httpd (web server), cron (task scheduler), and syslogd (log collector). On systemd-based Linux distributions, these are managed by systemd, which handles dependencies, restarts, and logging.

2.5 Linkers and Loaders

Before a program can run, its source code must be compiled and linked into an executable file. The process involves several stages: preprocessing (expanding macros and includes), compilation (translating C to assembly), assembly (translating assembly to machine code in an object file), and linking (combining object files and libraries into an executable).

A linker resolves symbol references—when one object file calls a function defined in another, the linker fills in the correct address. There are two types of linking: static linking copies library code directly into the executable (larger files, but self-contained), while dynamic linking (deferred to runtime) leaves references to shared libraries (smaller files, but depends on the library being present at runtime). The .so files on Linux and .dll files on Windows are shared libraries.

/* Compilation pipeline */ // Source: hello.c #include <stdio.h> int main() { printf("Hello\n"); return 0; } // Stages: hello.c ──preprocess──> hello.i // expand #include, #define hello.i ──compile─────> hello.s // C → assembly hello.s ──assemble───> hello.o // assembly → machine code hello.o ──link────────> hello // + libc → executable // Or all at once: $ gcc -o hello hello.c

A loader is the OS component that loads an executable into memory and starts it running. The absolute loader copies the executable to a fixed memory address. A relocating loader can load at any address, adjusting addresses as needed. Modern systems use dynamic loading and position-independent code (PIC), where the loader maps the executable at a random address (ASLR) and resolves dynamic library symbols at runtime via the dynamic linker (ld-linux.so on Linux).

ℹ️ ELF Format

On Linux, executables use the ELF (Executable and Linkable Format). An ELF file contains: a header, program headers (segments for loading), section headers (sections for linking), symbol tables, and relocation entries. The OS loader reads the program headers to determine which segments to map into memory. In xv6, the executable format is simpler (a header followed by segments), but the principle is the same.

The address space of a running process typically has four segments: text (code, read-only), data (initialized global variables), bss (uninitialized globals, zero-filled), and stack (local variables, function calls). The heap grows upward (via malloc), and the stack grows downward. The OS sets up these segments when loading the program, using the information in the executable file's header.

2.6 Operating-System Design

Designing an operating system is one of the most complex software engineering tasks. The designer must balance many competing goals: performance (fast response, high throughput), correctness (no crashes, no data corruption), security (protection from attacks), portability (running on different hardware), extensibility (adding new features without rewriting), and compatibility (running old software).

A key design principle is separation of policy and mechanism. Mechanisms are the how—the tools the OS provides (e.g., a timer interrupt, a priority field in the PCB, a CPU scheduling queue). Policies are the what—the decisions made using those tools (e.g., "give higher priority to interactive processes"). By separating them, the OS can change policies without redesigning mechanisms. For example, the timer mechanism (a hardware countdown) supports many scheduling policies (round-robin, priority, fair share).

💡 Policy vs. Mechanism

Mechanism: "The scheduler can preempt a process after a time quantum."
Policy: "The time quantum is 10 ms, and interactive processes get higher priority."
The mechanism is in the kernel; the policy can be a tunable parameter or even a loadable module.

Another important principle is least privilege: each component of the OS should have only the privileges it needs. This is why modern OSes run device drivers in user space (microkernel design) or in separate protection domains. The end-to-end argument suggests that functions placed at a low level may be redundant or insufficient—some functionality can only be correctly implemented at the highest level (the application). OS designers must decide what belongs in the kernel and what belongs in user space.

Performance considerations include minimizing context switch time (saving and restoring registers), reducing system call overhead (the cost of trapping to kernel mode), optimizing cache usage (keeping frequently accessed data in cache), and avoiding lock contention (too many threads waiting for the same lock). These low-level concerns often drive OS design decisions, sometimes at the expense of clean abstractions.

2.7 Operating-System Structure

As operating systems grew larger and more complex, different architectural structures emerged to organize the code. The main structures are: monolithic, layered, microkernel, modules, and hybrid. Each makes different trade-offs between performance, maintainability, and security.

A monolithic kernel puts all OS services—the scheduler, memory manager, file system, device drivers, network stack—into a single large executable running in kernel mode. Linux is the prime example. Advantages include performance (no overhead for crossing protection boundaries within the kernel) and simplicity of communication (all components share the same address space). Disadvantages include large kernel size (millions of lines of code), security risk (a bug in any component can crash the entire system), and maintainability (the code is hard to understand and modify).

A layered structure organizes the OS into hierarchical layers, where each layer uses services from the layer below and provides services to the layer above. Layer 0 is the hardware; Layer 1 is the scheduler; Layer 2 is memory management; and so on, up to the user interface. This design is clean and modular—each layer can be developed and tested independently—but it can be inefficient because each call must traverse multiple layers. THE operating system (Dijkstra, 1968) was the first layered OS. Few modern systems use pure layering because of the performance overhead.

ℹ️ Microkernel Design

A microkernel keeps the kernel as small as possible—only IPC, basic scheduling, and minimal memory management. All other services (file system, device drivers, network) run as user-space processes and communicate via message passing. Examples: MINIX, QNX, Mach. Advantages: easier to develop, more secure, more reliable. Disadvantage: overhead of message passing makes it slower than monolithic kernels for many operations.

A modular kernel (used by modern Linux and Solaris) has a small core kernel but allows loadable kernel modules (LKMs) to be dynamically loaded and unloaded. This combines the performance of a monolithic kernel with some flexibility of a microkernel: the core is always in memory, but drivers and file systems can be loaded on demand. The insmod and rmmod commands on Linux manage modules.

Most modern commercial OSes use a hybrid structure. Windows NT (the basis of modern Windows) and macOS (XNU kernel) are hybrids: they have a microkernel-like core but run many services in kernel mode for performance. macOS's XNU combines the Mach microkernel with BSD UNIX components and the I/O Kit driver framework. These designs attempt to get the best of both worlds—modularity and performance—but are complex to understand and maintain.

In xv6, the structure is essentially monolithic: all kernel code runs in supervisor mode, and there is no module loading. However, the code is organized into files by function (proc.c for processes, vm.c for virtual memory, fs.c for the file system), which provides some logical separation. 2.8 Building and Booting

The process of building an operating system involves compiling the kernel source code, linking it into a kernel image, and preparing it for booting. For xv6, this means compiling the kernel C and assembly files, linking them with a linker script that specifies the memory layout, and producing a kernel image that can be loaded by QEMU or a bootloader.

The boot process begins when power is applied. The CPU starts executing at a fixed address (often in ROM or flash memory) where the BIOS (Basic Input/Output System) or UEFI (Unified Extensible Firmware Interface) resides. This firmware performs POST (Power-On Self-Test), initializes hardware, and then loads the bootloader (e.g., GRUB on Linux) from a storage device. The bootloader then loads the kernel image into memory and jumps to its entry point.

/* xv6 boot sequence (RISC-V) */ // 1. QEMU starts in machine mode at 0x80000000 // (ROM: boot ROM loads kernel from disk) // 2. Kernel entry: entry.S (assembly) _entry: // Set up stack pointer for each hart (CPU core) la sp, stack0 addi sp, sp, 4096 // 4KB stack call start // call C function start() // 3. start() in start.c: initialize, then call main() // 4. main() in main.c: initialize all subsystems // kinit(), kvminit(), procinit(), trapinit(), // then userinit() → scheduler()

Once the kernel is loaded, it initializes its subsystems: setting up page tables, initializing the interrupt controller, registering trap handlers, initializing the file system, and creating the first user process (the init process, PID 1). On UNIX-like systems, init reads a configuration file (e.g., /etc/inittab or systemd units) and starts login services, network daemons, and other system services. In xv6, init (the init.c user program) simply forks a shell on the console.

ℹ️ Boot Stages

Modern booting often involves multiple stages: Stage 1 (MBR or UEFI boot manager, tiny, in the first sector) loads Stage 2 (the full bootloader, like GRUB), which can read file systems, display a boot menu, and load the kernel with parameters. This multi-stage approach allows a tiny first-stage loader to fit in the 512-byte boot sector while still supporting complex boot configurations.

Building the kernel involves a Makefile that compiles each source file, links them according to a linker script (specifying where the text, data, and bss segments go in memory), and produces a binary image. For xv6, the command make qemu compiles the kernel and user programs, creates a file system image, and launches QEMU with the kernel. The cross-compiler (riscv64-linux-gnu-gcc) is used because the host (x86) and target (RISC-V) architectures differ.

2.9 Operating-System Debugging

Debugging an operating system is significantly harder than debugging a user program because a kernel bug can crash the entire system, making it difficult to run a debugger. OS developers use a variety of techniques to find and fix bugs.

Logging is the simplest technique: the kernel writes diagnostic messages to a log buffer (the dmesg buffer on Linux, or printf in xv6). These messages can be viewed after a crash or during normal operation. In xv6, the printf function in printf.c writes directly to the console, which is invaluable for debugging. However, excessive logging can slow the system or change timing behavior, masking the bug.

Kernel debuggers (like kgdb on Linux) allow setting breakpoints, inspecting memory, and single-stepping through kernel code. These require either a second machine connected via serial cable or a virtual machine with debugger support. Crash dumps save the contents of memory to disk after a kernel panic, allowing post-mortem analysis. On Linux, the crash utility can analyze these dumps.

💡 Debugging xv6

When debugging xv6 under QEMU, you can use make qemu-gdb to start QEMU with GDB server support, then connect with riscv64-linux-gnu-gdb. You can set breakpoints (e.g., in syscall or scheduler), inspect registers and memory, and step through kernel code. This is one of the best ways to understand how the OS works.

Tracing tools (like strace for system calls, ftrace for function calls, and perf for performance profiling) help identify what the system is doing without modifying the code. Static analysis tools (like sparse for the Linux kernel) can find bugs by analyzing source code without running it. Sanitizers (AddressSanitizer, ThreadSanitizer) can detect memory errors and data races, though they are harder to use in kernel code.

Common OS bugs include race conditions (multiple threads accessing shared data without proper synchronization), deadlocks (threads waiting for each other indefinitely), memory leaks (allocating memory without freeing it), buffer overflows (writing past the end of an array), and null pointer dereferences (accessing memory at address 0). The consequences are more severe in the kernel: a null pointer dereference causes a kernel panic, not just a segfault in one process. This is why kernel code must be written with extreme care, with thorough testing and code review.
