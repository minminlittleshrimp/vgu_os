20.1 Linux History

Linux began in 1991 when Linus Torvalds, a Finnish university student, wrote a free operating system kernel for his 386 PC. Frustrated with the limitations of MINIX (a teaching OS by Andrew Tanenbaum) and the high cost of commercial Unix, Torvalds released Linux under the GNU General Public License (GPL), making it free and open source. The first public release, Linux 0.01 (September 1991), was a minimal kernel supporting only the 386 processor. Within a few years, Linux had grown into a full-featured operating system, thanks to contributions from thousands of developers worldwide.

The name "Linux" technically refers only to the kernel—the core that manages CPU, memory, and devices. The complete operating system is more properly called GNU/Linux, because most of the user-space utilities (shell, compilers, core utilities) come from the GNU Project, started by Richard Stallman in 1983 with the goal of creating a free Unix-like operating system. GNU had written the utilities but lacked a kernel; Linux provided the kernel. Together, GNU and Linux formed a complete, free operating system. The distinction is important: when you run "Linux," you are running the Linux kernel with GNU (and other) user-space software.

ℹ️ Linux Timeline
  • 1991: Linus Torvalds announces Linux on comp.os.minix
  • 1992: Linux 0.96, first X Window System port
  • 1994: Linux 1.0, first "stable" release
  • 1996: Linux 2.0, SMP (multiprocessor) support
  • 2001: Linux 2.4, improved SMP, large file support
  • 2003: Linux 2.6, O(1) scheduler, NPTL threads
  • 2011: Linux 3.0 (version number reset, no major change)
  • 2015: Linux 4.0, live kernel patching
  • 2019: Linux 5.0 (version number reset)
  • 2022+: Linux 6.x, Rust support, io_uring, BPF

Linux's success is due in large part to its open-source development model. The kernel is developed by a global community of contributors, coordinated by Torvalds and a team of maintainers. Anyone can contribute: the kernel source is on GitHub (and git.kernel.org), and patches are reviewed on the Linux Kernel Mailing List (LKML). This model, sometimes called bazaar development (as opposed to the cathedral model of closed development), has produced a kernel that supports more hardware architectures, devices, and features than any other operating system. Companies like Intel, AMD, Google, Red Hat, and IBM contribute heavily, ensuring Linux runs well on their hardware and in their environments.

The Linux ecosystem includes distributions (distros) that package the kernel with user-space software: Ubuntu, Debian, Fedora, Red Hat Enterprise Linux (RHEL), Arch Linux, Alpine, and many others. Each distro targets different users: Ubuntu for desktops, RHEL for enterprise, Alpine for containers, OpenWrt for routers. The kernel is the same; the user-space differs. This separation of kernel and user-space is a key Linux design principle, inherited from Unix.

💡 Linux and xv6

xv6 is a simplified, teaching version of Unix. Linux is a production, full-featured Unix-like kernel. Comparing them is instructive: xv6 has ~10,000 lines of code; Linux has over 30 million. xv6 supports one architecture (RISC-V, x86); Linux supports dozens. xv6 has a simple round-robin scheduler; Linux has the Completely Fair Scheduler (CFS). xv6 has a basic file system; Linux supports ext4, XFS, Btrfs, NFS, and dozens of others. But the core concepts are the same: processes, system calls, page tables, file descriptors, inodes. Studying xv6 teaches you the foundation; Linux shows you what happens when that foundation is scaled to production.

20.2 Design Principles

Linux is designed as a monolithic kernel: the entire kernel (scheduler, memory manager, file systems, device drivers, network stack) runs in a single address space in kernel mode. This contrasts with microkernel design (like Mach, seL4), where the kernel is minimal and services run as user-space processes. The monolithic design is faster (no message passing between kernel components) but less modular (a bug in any component can crash the kernel). Linux mitigates this with loadable kernel modules (Section 20.3), which allow code to be loaded and unloaded at runtime, providing some of the flexibility of a microkernel without the performance cost.

The Unix philosophy heavily influences Linux design: everything is a file (devices, processes, network sockets are represented as files), small, composable tools (do one thing well, combine via pipes), text as the universal interface (configuration files, logs, data are text), and policy separation from mechanism (the kernel provides mechanisms; user-space provides policy). These principles make Linux flexible and scriptable: you can combine simple commands into complex pipelines, and configure the system through text files.

ℹ️ Linux Design Principles
  • Monolithic kernel: all kernel services in one address space
  • Loadable modules: dynamically load/unload kernel code
  • Everything is a file: uniform interface for devices, processes, network
  • Multi-user, multitasking: multiple users, preemptive multitasking
  • POSIX compliance: compatible with Unix standards
  • Portable: runs on many architectures (x86, ARM, RISC-V, MIPS, ...)
  • Open source: GPL-licensed, community-developed
  • Stable kernel API: user-space API is stable; internal kernel API can change

Linux is POSIX-compliant: it implements the POSIX standard for operating system interfaces, meaning software written for other POSIX systems (Unix, macOS) can be ported to Linux with minimal changes. The system call interface (open, read, write, fork, exec, wait) is the same as in xv6 and other Unix systems. This is why xv6 is such a good teaching tool: its system calls are a subset of Linux's, so what you learn in xv6 transfers directly to Linux.

A key design decision is the stable user-space API: the system call interface is stable and backward-compatible. A program compiled for Linux 2.0 (1996) will still run on Linux 6.x (2022) without recompilation. This is a deliberate choice: the kernel maintainers refuse to break user-space. In contrast, the internal kernel API (functions and data structures used by kernel code and modules) can change between versions. This means kernel modules (drivers) may need to be updated for new kernel versions, but user-space applications do not. This stability is a major reason for Linux's success in enterprise environments.

⚠️ Monolithic vs. Microkernel: The Tanenbaum-Torvalds Debate

In 1992, Andrew Tanenbaum (creator of MINIX) published a famous critique of Linux's monolithic design, arguing that microkernels were the future. Torvalds defended the monolithic approach, citing performance and simplicity. The debate continues: microkernels (like seL4, Fuchsia's Zircon) offer better isolation and security, while monolithic kernels (Linux, Windows) offer better performance and simpler development. In practice, Linux has incorporated microkernel ideas (loadable modules, user-space drivers via FUSE, VFIO) while remaining fundamentally monolithic. The debate illustrates that OS design involves fundamental trade-offs with no single "right" answer.

Linux is portable: it runs on more CPU architectures than any other operating system, including x86, x86-64, ARM, ARM64, RISC-V, MIPS, PowerPC, SPARC, s390, and many embedded processors. This portability is achieved by separating architecture-independent code (the bulk of the kernel) from architecture-dependent code (in arch/ directory). Porting Linux to a new architecture involves writing the architecture-specific code (boot, page tables, interrupt handling, system call entry) while reusing the architecture-independent code. xv6 follows a similar pattern: the RISC-V and x86 versions share most code but differ in the kernel/ and entry* files.

20.3 Kernel Modules

Kernel modules are pieces of code that can be loaded and unloaded into the kernel at runtime, without rebooting. This provides much of the flexibility of a microkernel (load only the drivers you need) while keeping the performance of a monolithic kernel (modules run in kernel space, not user space). Modules are used for device drivers, file systems, network protocols, and security modules. When you plug in a USB device, Linux loads the appropriate driver module; when you mount an ext4 file system, Linux loads the ext4 module (if not already loaded).

A module is a relocatable object file (.ko) that is linked into the running kernel. The module's code runs in kernel mode with full kernel privileges—it can access any kernel data structure and any hardware. This is powerful but dangerous: a bug in a module can crash the entire kernel. Modules are loaded with insmod (load a specific module) or modprobe (load a module and its dependencies) and unloaded with rmmod. The lsmod command lists loaded modules.

/* Linux kernel module example (simplified) */ #include <linux/module.h> #include <linux/kernel.h> // Called when module is loaded static int __init hello_init(void) { printk("Hello, kernel!\n"); return 0; } // Called when module is unloaded static void __exit hello_exit(void) { printk("Goodbye, kernel!\n"); } module_init(hello_init); module_exit(hello_exit); MODULE_LICENSE("GPL"); MODULE_DESCRIPTION("Hello World module");

Modules interact with the kernel through exported symbols: functions and variables that the kernel makes available to modules. A module can call printk (kernel logging), kmalloc/kfree (kernel memory allocation), register_chrdev (register a character device), and thousands of other kernel functions. The set of exported symbols is the kernel API for modules. Unlike the user-space API, this API can change between kernel versions, so modules may need updates for new kernels.

Device drivers are the most common type of module. A character device driver implements open, read, write, release (and optionally ioctl) functions that the kernel calls when user-space programs access the device file. A block device driver implements request or submit_bio for block I/O. Network drivers implement ndo_start_xmit for packet transmission. The kernel provides frameworks (the driver model) that handle common tasks like device discovery, power management, and hotplugging.

ℹ️ Module Loading and Dependencies

Modules can depend on other modules. For example, the ext4 file system module depends on the jbd2 (journaling block device) module. The modprobe command reads modules.dep (generated by depmod) to find and load dependencies automatically. insmod loads a single module without dependencies—if dependencies are missing, it fails. The kernel can also auto-load modules: when a program requests a feature (like mounting a file system type), the kernel sends a request to modprobe via kmod to load the needed module.

Security modules are a special class of module that implement security policies. SELinux and AppArmor are implemented as Linux Security Modules (LSM): they hook into kernel security decision points and enforce mandatory access control policies. Yama restricts ptrace (debugging). seccomp filters system calls. These modules demonstrate the flexibility of the module system: security policy can be loaded and changed at runtime without modifying the core kernel.

💡 Modules vs. xv6

xv6 has no loadable modules—all drivers and file systems are compiled into the kernel. This is fine for a teaching OS (the kernel is small and the hardware is fixed), but it illustrates why Linux needs modules: a production kernel must support thousands of devices and file systems, and compiling them all in would bloat the kernel and waste memory. Modules let Linux load only what's needed. If you wanted to add modules to xv6, you would need: (1) a way to load .o files into kernel memory, (2) a symbol table for resolving references, (3) init/exit functions called on load/unload, and (4) a registry for drivers to register themselves. This is a significant but instructive extension.

20.4 Process Management

Linux process management follows the Unix model, with some enhancements. A process is an instance of a running program, with its own address space, file descriptors, and execution context. The fork() system call creates a copy of the calling process (the parent); the new process (the child) is an almost-exact duplicate, differing only in its PID, PPID, and some statistics. The exec() family of system calls replaces the current process image with a new program. The wait() system call allows a parent to wait for a child to exit and retrieve its status. This fork-exec-wait model is the same as in xv6.

Internally, Linux represents a process with a task_struct (defined in <sched.h>), which is the Linux equivalent of xv6's struct proc. The task_struct is large (several kilobytes) and contains everything the kernel needs to know about a process: PID, credentials (UID, GID), scheduling information, signal handlers, open file descriptors (pointer to files_struct), memory management information (pointer to mm_struct), parent/child pointers, CPU affinity, and much more. The kernel maintains a linked list of all task_structs, accessible via current (a macro that expands to the current process's task_struct).

/* Linux task_struct (simplified) */ struct task_struct { pid_t pid; // process ID pid_t tgid; // thread group ID (= PID for main thread) struct task_struct *parent; // parent process struct list_head children; // child processes struct mm_struct *mm; // memory descriptor struct files_struct *files; // open files volatile long state; // TASK_RUNNING, TASK_INTERRUPTIBLE, ... int prio; // scheduling priority cpumask_t cpus_allowed; // CPU affinity struct signal_struct *signal; // signal handlers // ... hundreds more fields ... };

A key difference from xv6 is threads. In Linux, a thread is simply a process that shares its address space, file descriptors, and signal handlers with another process. The clone() system call (used by pthread_create) creates a new process that shares selected resources with the parent. By choosing what to share (memory, files, signal handlers), clone() can create a thread (share everything), a process (share nothing), or something in between. This is more flexible than xv6, which has no threads—each process has its own address space.

ℹ️ Linux Threads vs. Processes

In Linux, threads and processes are both represented by task_struct. The difference is what they share:

  • Process (fork): new mm_struct (own address space), new files_struct (own file descriptors)
  • Thread (clone with CLONE_VM | CLONE_FILES): shares mm_struct and files_struct with parent

The tgid (thread group ID) groups threads of the same process: getpid() returns the tgid (the main thread's PID), while gettid() returns the actual thread ID. This design simplifies the kernel (one data structure for both) while presenting the expected process/thread distinction to user-space.

Linux supports namespaces, which provide isolation for various resources. A namespace wraps a global system resource to make it appear as a separate instance to processes within the namespace. Types include: PID namespace (isolated process IDs), mount namespace (isolated file system view), network namespace (isolated network stack), UTS namespace (isolated hostname), IPC namespace (isolated IPC), user namespace (isolated UID/GID mapping), and cgroup namespace. Namespaces are the foundation of containers: a Docker container is a process (or group of processes) in a set of namespaces, isolated from the host.

cgroups (control groups) complement namespaces by limiting and isolating resource usage. A cgroup limits how much CPU, memory, I/O, and network bandwidth a group of processes can use. Combined with namespaces (isolation) and cgroups (limits), this provides lightweight virtualization: containers. The unshare and clone system calls create new namespaces; the cgroup filesystem configures resource limits.

💡 Comparing Linux and xv6 Process Management

xv6's struct proc is a simplified version of Linux's task_struct. Both track the process's PID, parent, state, memory, and open files. The key differences: (1) xv6 has no threads (Linux has clone), (2) xv6 has no namespaces or cgroups (Linux has both, enabling containers), (3) xv6 uses a simple round-robin scheduler (Linux uses CFS or EEVDF), (4) xv6 has a fixed-size process table (Linux dynamically allocates task_structs). But the fundamental model—fork, exec, wait, signals, file descriptors—is the same. Learning xv6's process management gives you the foundation to understand Linux's.

20.5 Scheduling

Linux scheduling has evolved significantly. Early Linux (2.4 and earlier) used a simple O(n) scheduler that scanned the entire run queue to find the next process. Linux 2.6 introduced the O(1) scheduler, which used per-CPU run queues with priority arrays, making scheduling time constant regardless of the number of processes. From Linux 2.6.23 (2007) to 6.5 (2023), Linux used the Completely Fair Scheduler (CFS), which aimed to provide fair CPU sharing using a red-black tree. Linux 6.6+ uses EEVDF (Earliest Eligible Virtual Deadline First), which improves latency for interactive and real-time tasks.

The Completely Fair Scheduler (CFS) models an "ideal, precise multitasking processor" that would give each runnable process an equal share of CPU time. Since this is impossible (a single CPU can run only one process at a time), CFS approximates it by tracking each process's virtual runtime (vruntime): the amount of CPU time the process has received, normalized by its priority. CFS always runs the process with the smallest vruntime, which is the process that has received the least CPU time relative to its priority. Processes are stored in a red-black tree ordered by vruntime, making selection O(log n).

/* CFS scheduling (simplified) */ // Each process has a vruntime (virtual runtime) // Lower vruntime = has received less CPU = should run next // On each scheduling decision: struct task_struct *pick_next() { // Select leftmost node in red-black tree (min vruntime) return rb_tree_leftmost(runqueue); } // As a process runs, its vruntime increases: vruntime += delta_exec * (NICE_0_LOAD / load_weight); // delta_exec = actual CPU time used // load_weight = based on nice value (priority) // Higher priority → lower weight → vruntime grows slower → runs more // Result: each process gets CPU proportional to its priority // No starvation: every process eventually gets CPU

Linux uses nice values for priority, ranging from -20 (highest priority) to +19 (lowest priority), with 0 as the default. The nice value affects the process's weight in CFS: a process with nice -20 has a much higher weight than one with nice +19, so it gets more CPU time. The nice and renice commands adjust nice values. Only root can set negative nice values (higher priority); regular users can only lower priority (increase nice value).

Linux supports SMP (symmetric multiprocessing): multiple CPUs sharing the same memory. Each CPU has its own run queue, and the scheduler tries to keep processes on the same CPU (cache affinity) for performance. Load balancing moves processes between CPUs to keep them balanced. The scheduler also supports CPU affinity (sched_setaffinity): pinning a process to specific CPUs. This is important for performance (cache locality) and real-time applications (avoiding interference).

ℹ️ Scheduling Classes

Linux has multiple scheduling classes, tried in priority order:

  1. Deadline: tasks with explicit deadlines (highest priority)
  2. Real-time (RT): FIFO and round-robin real-time tasks
  3. CFS / EEVDF: normal (time-sharing) tasks
  4. Idle: background tasks (lowest priority)

Within each class, the scheduler picks the highest-priority runnable task. Real-time tasks always preempt normal tasks. This allows Linux to support soft real-time applications (audio, video) alongside normal applications, though it is not a hard real-time system without the PREEMPT_RT patch.

Preemption is a key feature. The Linux kernel can be preempted at most points (with CONFIG_PREEMPTION), meaning a higher-priority process can interrupt the kernel itself, not just user-space code. This reduces scheduling latency for real-time tasks. The PREEMPT_RT patch (merged into mainline in 2024 as CONFIG_PREEMPT_RT) makes the kernel fully preemptible, enabling hard real-time behavior. Without preemption, kernel code runs to completion (or until it voluntarily yields), which can cause latency spikes for real-time tasks.

💡 xv6 Scheduling vs. Linux

xv6 uses a simple round-robin scheduler: it iterates through the process table and runs each runnable process in turn. There are no priorities, no fairness guarantees, and no real-time support. Each process runs until it blocks, yields, or its time slice expires (timer interrupt). This is easy to understand but would be inadequate for a production system. Linux's CFS/EEVDF is far more sophisticated: it provides fairness, priorities, SMP support, and real-time classes. But the concept is the same: the scheduler decides which process runs next, based on some policy. xv6 shows you the simplest possible policy; Linux shows you what a production policy looks like.

20.6 Memory Management

Linux memory management is built on paging: the physical memory is divided into fixed-size pages (typically 4 KB), and each process has a page table that maps virtual addresses to physical addresses. The CPU's MMU (Memory Management Unit) translates virtual addresses to physical addresses using the page table, with a TLB (Translation Lookaside Buffer) cache for speed. This is the same mechanism as in xv6, but Linux adds many optimizations and features.

Each process has a mm_struct (memory descriptor) that describes its address space. The mm_struct contains a list of vm_area_structs (VMAs), each describing a contiguous region of virtual memory with the same attributes (permissions, backing file, etc.). A VMA might represent the code segment, data segment, heap, stack, or a memory-mapped file. When a process accesses an address, the kernel finds the VMA containing that address and checks permissions. If no VMA contains the address (or permissions don't allow the access), a segmentation fault occurs.

/* Linux mm_struct and VMA (simplified) */ struct mm_struct { struct vm_area_struct *mmap; // list of VMAs pgd_t *pgd; // page global directory (top of page table) unsigned long start_code, end_code; // code segment unsigned long start_data, end_data; // data segment unsigned long start_brk, brk; // heap unsigned long start_stack; // stack atomic_t mm_users; // number of users (threads) }; struct vm_area_struct { unsigned long vm_start; // start address unsigned long vm_end; // end address (exclusive) unsigned long vm_flags; // VM_READ, VM_WRITE, VM_EXEC, ... struct file *vm_file; // backing file (if mmap'd) struct vm_area_struct *vm_next; // next VMA };

Page replacement is a critical function. When physical memory is full, the kernel must evict pages to make room. Linux uses a variant of the clock algorithm (also called the "second chance" algorithm). Each page has a referenced bit that the hardware sets when the page is accessed. The kernel periodically scans pages, clearing the referenced bit. Pages whose bit is still clear on the next scan (not recently accessed) are candidates for eviction. The kernel maintains active and inactive lists: pages start on the inactive list and are promoted to active if accessed; pages on the inactive list are evicted first.

Swap allows the kernel to use disk space as overflow for physical memory. When memory is full, the kernel writes inactive pages to a swap area (a disk partition or file) and frees the physical page. When the page is accessed again, a page fault occurs, and the kernel reads the page back from swap. Swap extends the effective memory but is much slower than RAM. Modern systems with large RAM may disable swap or use it mainly for anonymous memory (memory not backed by a file).

⚠️ The OOM Killer

When the system is completely out of memory (no pages to evict, no swap available), Linux invokes the OOM (Out of Memory) Killer. The OOM killer selects a process to kill to free memory, based on a heuristic that considers the process's memory usage, runtime, and importance (root processes are protected). The goal is to kill the process that will free the most memory with the least impact. This is a last resort: ideally, the system should never reach this state. The OOM killer is controversial because it can kill important processes, but it prevents the system from hanging completely.

Memory mapping (mmap) allows a process to map a file or device into its address space. After mmap, the process can read and write the file as if it were memory—no read or write calls needed. The kernel loads pages on demand (page faults) and writes them back (for writable mappings) when evicted or msync is called. mmap is used for shared libraries (the dynamic linker maps .so files), shared memory (IPC), and large file I/O (more efficient than read/write for random access).

Transparent Huge Pages (THP) allow the kernel to use large pages (2 MB or 1 GB on x86) automatically, reducing TLB pressure for large-memory applications. Large pages mean fewer page table entries, so the TLB (which caches translations) can cover more memory, reducing TLB misses. THP is transparent: applications do not need to be modified; the kernel coalesces 4 KB pages into 2 MB pages when beneficial. Applications can also explicitly request huge pages via mmap with MAP_HUGETLB.

ℹ️ Linux Memory Zones

Linux divides physical memory into zones based on what the memory can be used for:

  • ZONE_DMA: memory below 16 MB (for legacy DMA devices)
  • ZONE_DMA32: memory below 4 GB (for 32-bit DMA devices)
  • ZONE_NORMAL: normal memory (directly mapped by the kernel)
  • ZONE_HIGHMEM: memory above the kernel's direct mapping (32-bit only)
  • ZONE_MOVABLE: movable pages (for memory hotplug, defragmentation)

The buddy allocator allocates physical pages within zones, splitting and coalescing blocks of pages (powers of 2) to satisfy allocation requests. The slab allocator (SLAB, SLUB, SLOB) allocates small objects from pre-allocated pools, reducing fragmentation and initialization overhead for frequently allocated objects like task_struct or inode.

Memory cgroups allow limiting the memory usage of a group of processes (e.g., a container). When a cgroup exceeds its memory limit, the kernel reclaims pages from that cgroup (or invokes the OOM killer for that cgroup). This is essential for containers: without memory cgroups, one container could exhaust the host's memory, affecting all other containers. The memory.max cgroup control file sets the limit; memory.current reports current usage.

💡 Linux vs. xv6 Memory Management

xv6 has a simple memory manager: a physical page allocator (free list), a kernel page table (direct-mapped), and per-process page tables (with uvmalloc, uvmdealloc). There is no swap, no page replacement (xv6 assumes enough physical memory), no mmap, no huge pages, no memory cgroups. But the fundamental mechanism—page tables, virtual-to-physical translation, TLB—is the same. xv6's kalloc/kfree is a simplified version of Linux's buddy allocator. xv6's proc_pagetable is a simplified version of Linux's mm_struct + page table. Learning xv6's memory management gives you the foundation; Linux shows you the production version with all the optimizations.

20.7 File Systems

Linux has a Virtual File System (VFS) that provides a uniform interface to multiple file systems. VFS defines a set of operations (open, read, write, close, stat, etc.) that all file systems must implement. This allows user-space programs to use the same system calls regardless of whether the file is on ext4, XFS, NFS, or a FUSE file system. VFS is the key abstraction that makes Linux's file system extensible.

The VFS has four main objects: superblock (represents a mounted file system), inode (represents a file), dentry (directory entry, links a name to an inode), and file (an open file, with a position and mode). Each file system implements these objects with its own data structures. For example, ext4 has ext4_inode on disk, which VFS wraps in a struct inode in memory. The VFS operations (like read, write) are dispatched to the file system's implementation.

/* VFS objects (simplified) */ // Superblock: one per mounted file system struct super_block { struct file_system_type *s_type; // ext4, xfs, ... struct super_operations *s_op; // alloc_inode, ... struct dentry *s_root; // root directory }; // Inode: one per file struct inode { unsigned long i_ino; // inode number umode_t i_mode; // file type + permissions loff_t i_size; // file size struct inode_operations *i_op; // create, lookup, ... struct file_operations *i_fop; // read, write, ... }; // Dentry: links a name to an inode (in-memory cache) struct dentry { struct qstr d_name; // name struct inode *d_inode; // associated inode struct dentry *d_parent; // parent directory }; // File: an open file (one per open() call) struct file { struct path f_path; // dentry + vfsmount loff_t f_pos; // current position fmode_t f_mode; // read/write mode struct file_operations *f_op; // read, write, ... };

ext4 (Fourth Extended File System) is the default file system for most Linux distributions. It is a journaling file system: it maintains a journal of pending changes before writing them to the main file system. If the system crashes, the journal can be replayed to restore consistency, avoiding the long fsck (file system check) that non-journaling file systems require. ext4 supports files up to 16 TB, file systems up to 1 EB, extents (contiguous block ranges, more efficient than indirect blocks), and delayed allocation (buffer writes and allocate blocks in bulk for efficiency).

FUSE (Filesystem in Userspace) allows file systems to be implemented in user space. A FUSE file system registers with the kernel; when a process accesses a FUSE file, the kernel forwards the operation to a user-space daemon, which implements the file system logic. This is safer (a bug in the file system does not crash the kernel) and more flexible (file systems can be written in any language). Examples include SSHFS (mount remote directories over SSH), NTFS-3G (read/write NTFS), and GlusterFS (distributed file system). The trade-off is performance: each operation crosses the user-kernel boundary twice.

The page cache is a critical performance feature. Linux caches file data in memory (the page cache) to avoid disk I/O. When a process reads a file, the kernel first checks the page cache; if the data is there (cache hit), it returns immediately. If not (cache miss), the kernel reads from disk and caches the data. Writes are also cached: write copies data to the page cache, and the kernel writes it to disk later (write-back). The sync command flushes dirty pages to disk. This dramatically improves performance but means data may be lost if the system crashes before dirty pages are written.

⚠️ Write-Back and Data Loss

Linux's default write-back policy means that write returns before data is on disk. If the system crashes, recently written data may be lost. Applications that need durability (databases, journals) use fsync to force dirty pages to disk before proceeding. fsync is expensive (it waits for disk I/O), so it should be used judiciously. The O_SYNC open flag makes all writes synchronous (each write blocks until on disk). The trade-off between performance (write-back) and durability (write-through) is a fundamental file system design decision.

Special file systems provide non-disk-backed data as files. /proc (procfs) exposes kernel and process information as files: /proc/cpuinfo (CPU info), /proc/meminfo (memory info), /proc/[pid]/ (per-process info). /sys (sysfs) exposes device and driver information. /dev (devtmpfs) provides device files. /tmp is often a tmpfs (in-memory). These pseudo-file systems demonstrate the power of the "everything is a file" philosophy: you can read kernel state by reading a file, and configure devices by writing to a file.

💡 Linux vs. xv6 File Systems

xv6 has a simple file system: a flat directory structure, inodes with direct and indirect blocks, a simple log for crash consistency, and no page cache (all I/O goes through a buffer cache). Linux's VFS, ext4, page cache, and FUSE are far more sophisticated. But the core concepts are the same: inodes, directories, file descriptors, the open-read-write-close model. xv6's struct inode is a simplified version of Linux's struct inode. xv6's log is a simplified version of ext4's journal. Learning xv6's file system gives you the foundation to understand Linux's.

20.8 Input and Output

Linux I/O is built on the device file abstraction: devices are represented as files in /dev, accessed with the same open, read, write, close system calls as regular files. There are three types of devices: character devices (accessed as a stream of bytes: terminals, serial ports, keyboards), block devices (accessed in blocks: disks, SSDs), and network devices (not represented as files; accessed via sockets).

Character devices are the simplest: the driver implements read, write, and optionally ioctl (I/O control, for device-specific operations). Examples: /dev/tty (terminal), /dev/null (discard all writes, EOF on read), /dev/random (random numbers), /dev/urandom (non-blocking random). The ioctl system call is the escape hatch for operations that don't fit the read/write model: setting terminal baud rate, ejecting a CD, querying device status.

/* Character device access */ // Open a serial port int fd = open("/dev/ttyS0", O_RDWR); // Set baud rate via ioctl struct termios options; tcgetattr(fd, &options); cfsetispeed(&options, B9600); cfsetospeed(&options, B9600); tcsetattr(fd, TCSANOW, &options); // Read and write write(fd, "AT\r", 3); read(fd, buf, 1024); // Special devices write(open("/dev/null", O_WRONLY), data, n); // discard read(open("/dev/urandom", O_RDONLY), &key, 32); // random bytes

Block devices support random access in fixed-size blocks (typically 512 bytes or 4 KB). The driver implements submit_bio (submit a block I/O request). Block devices are typically accessed through a file system (ext4, XFS) rather than directly, but can also be accessed raw via /dev/sda, /dev/nvme0n1. The I/O scheduler (block layer) reorders and merges block I/O requests for efficiency: it may sort requests by sector (elevator algorithm) to minimize disk seek, or merge adjacent requests into larger ones. Modern NVMe SSDs use a simpler scheduler (none or kyber) because they have no seek penalty.

ℹ️ The Block I/O Layer

Linux's block I/O layer sits between the file system and the device driver:

  1. VFS receives read/write
  2. File system (ext4) translates file offsets to disk blocks
  3. Page cache caches data; on miss, creates a bio (block I/O) request
  4. I/O scheduler merges and sorts bio requests
  5. Device driver (e.g., NVMe, AHCI) sends requests to hardware
  6. Hardware (disk, SSD) performs the I/O and raises an interrupt
  7. Interrupt handler completes the request, wakes the waiting process

For NVMe SSDs, the driver may use polling (busy-wait for completion) or interrupts. Polling reduces latency for high-IOPS workloads but consumes CPU.

Network I/O is handled differently from character and block devices. Network devices (NICs) are not represented as files in /dev; instead, they are accessed via the socket API. A socket is an endpoint for network communication. The socket system call creates a socket; bind assigns an address; listen marks it as a server; accept accepts a connection; connect initiates a connection; send/recv (or read/write) transfer data. The kernel's network stack (TCP/IP) handles protocol processing, and the NIC driver handles the hardware.

Interrupt handling in Linux is split into two halves: top half (the interrupt handler, runs with interrupts disabled, must be fast) and bottom half (deferred work, runs later with interrupts enabled). The top half acknowledges the interrupt, queues work, and schedules the bottom half. The bottom half (implemented via softirqs, tasklets, or workqueues) does the heavy processing. This split ensures that the system remains responsive: interrupt handlers are fast, and heavy work is deferred to a safe time.

/* Interrupt handling: top half and bottom half */ // Top half: interrupt handler (runs in interrupt context) static irqreturn_t nic_interrupt(int irq, void *dev) { // 1. Acknowledge interrupt on hardware // 2. Disable further interrupts from this device // 3. Schedule bottom half (deferred work) schedule_work(&nic_work); return IRQ_HANDLED; // Must be fast! No sleeping, no heavy work. } // Bottom half: workqueue (runs in process context) static void nic_work_handler(struct work_struct *work) { // Process received packets // Can sleep, allocate memory, etc. while (packet = rx_ring_next()) { netif_receive_skb(packet); } // Re-enable interrupts }

Asynchronous I/O allows a process to initiate an I/O operation and continue executing while the I/O is in progress. Linux supports several async I/O mechanisms: POSIX AIO (aio_read, aio_write), io_uring (a modern, high-performance ring buffer interface), and epoll (for network I/O). io_uring (Linux 5.1+, 2019) is the state of the art: it uses shared ring buffers between user space and kernel, allowing batched, zero-copy I/O with minimal system call overhead. It is significantly faster than traditional AIO for high-IOPS workloads.

💡 Linux vs. xv6 I/O

xv6's I/O is minimal: a console driver (UART), a virtio block device driver, and a virtio network driver. There is no I/O scheduler, no async I/O, no interrupt top/bottom halves. xv6's interrupt handler does all the work directly. But the concept is the same: the driver provides read and write functions, and the kernel dispatches to them when a process accesses the device file. xv6's virtio driver is a simplified version of Linux's virtio driver. Learning xv6's I/O gives you the foundation; Linux shows you the production version with all the performance optimizations.

20.9 Interprocess Communication

Linux provides several interprocess communication (IPC) mechanisms, inherited from Unix and extended. The basic mechanism is the pipe: a one-way data channel between two processes. A pipe is created with pipe(), which returns two file descriptors: one for reading and one for writing. After fork, the parent and child each have both ends; one closes the read end and writes, the other closes the write end and reads. Pipes are the foundation of the shell's | operator: ls | grep .c creates a pipe between ls and grep.

/* Pipe communication */ int fds[2]; pipe(fds); // fds[0] = read end, fds[1] = write end if (fork() == 0) { // Child: read from pipe close(fds[1]); // close write end read(fds[0], buf, 1024); printf("Got: %s\n", buf); } else { // Parent: write to pipe close(fds[0]); // close read end write(fds[1], "hello", 5); } // Shell pipeline: ls | grep .c // Creates pipe, forks two processes, connects them

Named pipes (FIFOs) are pipes that exist in the file system (created with mkfifo). Unlike anonymous pipes (which require a parent-child relationship), FIFOs can be used between unrelated processes. A process opens the FIFO for reading (blocks until a writer opens it) or writing (blocks until a reader opens it). FIFOs are useful for simple inter-process communication between unrelated programs.

Shared memory is the fastest IPC mechanism: two or more processes map the same physical memory into their address spaces. Writes by one process are immediately visible to others. Shared memory is created with shmget (System V) or shm_open (POSIX), and attached with shmat or mmap. The challenge is synchronization: without coordination, processes can race on shared data. Semaphores (see below) or mutexes are used to coordinate access. Shared memory is used for high-performance IPC where copying data (as in pipes) is too expensive.

Message queues allow processes to exchange structured messages. System V message queues (msgget, msgsnd, msgrcv) support typed messages: a receiver can select messages by type. POSIX message queues (mq_open, mq_send, mq_receive) provide a similar interface with priorities. Message queues are useful when processes need to exchange discrete messages rather than byte streams.

Semaphores are synchronization primitives for IPC. A semaphore is a counter with atomic wait (decrement, block if zero) and post (increment, wake one waiter) operations. System V semaphores (semget, semop) support arrays of semaphores with complex atomic operations. POSIX semaphores (sem_open, sem_wait, sem_post) are simpler. Semaphores are used to coordinate access to shared resources, especially shared memory.

ℹ️ Synchronization Primitives

Linux provides several synchronization primitives for both kernel and user space:

  • Mutex: mutual exclusion lock (one holder at a time)
  • Spinlock: busy-wait lock (for short critical sections, interrupt context)
  • Semaphore: counting or binary, for signaling
  • Condition variable: wait for a condition (with mutex)
  • Seqlock: lock-free reads, for frequently-read, rarely-written data
  • RCU (Read-Copy-Update): extremely fast reads (no locks), for read-mostly data
  • futex: fast user-space mutex (spins in user space, syscalls only on contention)

RCU is a Linux innovation: readers access data without locks, and writers create a copy, update it, and atomically swap the pointer. Old data is freed after all readers have finished (via a grace period). RCU is used heavily in the kernel for data structures that are read frequently but updated rarely (e.g., routing tables).

Sockets are the most general IPC mechanism, supporting both local and network communication. Unix domain sockets (AF_UNIX) are local-only sockets that use the file system for addressing. They are faster than network sockets (no TCP/IP overhead) and support passing file descriptors between processes (via SCM_RIGHTS). Unix domain sockets are used by X11, Docker, systemd, and many other services. Network sockets (AF_INET, AF_INET6) use TCP or UDP for network communication.

Signals are a simple IPC mechanism for asynchronous notification. A signal is a small integer sent to a process, causing it to execute a signal handler (or take the default action, like terminating). Common signals: SIGINT (Ctrl-C, terminate), SIGKILL (cannot be caught, force kill), SIGTERM (polite terminate), SIGSEGV (segmentation fault), SIGCHLD (child exited). Signals are coarse (no data payload in standard Unix signals) and have tricky semantics (signal handlers must be async-signal-safe). signalfd and eventfd provide file-descriptor-based alternatives that integrate with epoll.

💡 Linux vs. xv6 IPC

xv6 has pipes (the same pipe system call as Linux) and signals (a simplified version). It does not have shared memory, message queues, semaphores, or sockets. But the pipe in xv6 is the same concept as in Linux: a one-way data channel between processes. xv6's pipealloc, pipewrite, piperead are simplified versions of Linux's pipe implementation. Learning xv6's pipe gives you the foundation; Linux's additional IPC mechanisms (shared memory, sockets, semaphores) build on the same principles of synchronization and data transfer.

21.1 Design Principles

Windows 10 (and its successor Windows 11) is Microsoft's flagship operating system, designed for a wide range of devices from phones and tablets to desktops and servers. The design principles reflect decades of evolution from MS-DOS (1981) through Windows 3.x/9x (1990s) to the NT family (1993–present). The Windows NT architecture, designed by Dave Cutler (who previously designed VMS at DEC), is the foundation of all modern Windows versions. NT was designed from scratch as a 32-bit (later 64-bit), preemptive multitasking, multi-user, secure operating system.

The key design principles of Windows NT (and Windows 10) are:

  • Compatibility: run existing MS-DOS and Windows applications
  • Portability: run on multiple architectures (originally x86, MIPS, Alpha, PowerPC; now x86, x64, ARM64)
  • Reliability: robust memory protection, structured exception handling
  • Security: C2-level security (US government standard), access control
  • Extensibility: modular design, layered architecture
  • International support: Unicode throughout
  • Performance: efficient kernel, SMP support
ℹ️ Windows NT Design Goals

The Windows NT design (1989–1993) was guided by these requirements:

  • Hardware independence: a Hardware Abstraction Layer (HAL) isolates the kernel from hardware differences
  • Kernel-mode / user-mode separation: the kernel and executive run in kernel mode; applications and subsystems run in user mode
  • Object-based: resources (processes, threads, files, events) are represented as objects managed by the object manager
  • Client-server architecture: user-mode subsystems communicate with the kernel via a local procedure call (LPC) mechanism
  • Preemptive multitasking: the scheduler can preempt any thread at any time (unlike Windows 3.x cooperative multitasking)

The Windows NT architecture is layered. At the bottom is the Hardware Abstraction Layer (HAL), which isolates the kernel from hardware differences (interrupt controllers, timers, I/O ports). Above the HAL is the kernel, a small, highly optimized layer that handles thread scheduling, interrupt dispatching, and synchronization. Above the kernel is the executive, which implements the major OS functions: process/thread management, memory management, I/O management, IPC, and security. The executive exposes its services through a system call interface (the Native API).

Above the executive are user-mode subsystems. The environment subsystems provide compatibility with different APIs: the Win32 subsystem (the primary one, implements the Windows API), POSIX subsystem (deprecated, replaced by WSL), and OS/2 subsystem (deprecated). Applications call the subsystem's API, which translates calls into Native API calls to the executive. This design allows Windows to support multiple API personalities while sharing a common kernel.

⚠️ The Win32 Subsystem Dominance

Originally, Windows NT supported multiple environment subsystems (Win32, POSIX, OS/2) as peers. In practice, the Win32 subsystem became dominant: most Windows applications use the Win32 API (or higher-level frameworks like .NET, UWP, WinUI that build on Win32). The POSIX and OS/2 subsystems were deprecated. WSL (Windows Subsystem for Linux) is a modern reimagining of the environment subsystem concept: it provides a Linux-compatible environment running on the NT kernel, allowing Linux binaries to run natively on Windows.

Windows is object-based: system resources (processes, threads, files, events, semaphores, timers, registry keys) are represented as objects managed by the object manager. Each object has a type, a name, security descriptor, and methods. The object manager provides a uniform interface for creating, naming, securing, and referencing objects. This is similar to the "everything is a file" philosophy in Unix, but more structured: objects have explicit types and methods, not just read/write operations.

💡 Windows vs. Linux vs. xv6 Design

Windows, Linux, and xv6 represent three points in the design space:

  • xv6: minimal monolithic kernel, no modules, no security, teaching OS
  • Linux: monolithic kernel with loadable modules, POSIX, open source
  • Windows: layered kernel (HAL/kernel/executive), object-based, environment subsystems, commercial

All three use hardware privilege levels (user/kernel mode), page tables, and preemptive scheduling. The differences are in architecture (monolithic vs. layered), API (POSIX vs. Win32), and philosophy (Unix "everything is a file" vs. Windows "everything is an object"). Understanding all three gives you a broad perspective on OS design.

21.2 System Components

The Windows NT architecture consists of several major components, each with a specific role. Understanding these components is key to understanding how Windows works.

The Hardware Abstraction Layer (HAL) is a DLL (hal.dll) that isolates the kernel from hardware-specific details. The HAL provides abstractions for interrupt controllers, I/O ports, timers, and DMA. Different HALs exist for different hardware (ACPI, non-ACPI, MP/SMP). The HAL allows the same kernel binary to run on different hardware by abstracting the differences. This is similar to Linux's arch/ directory, but more formalized.

The kernel (ntoskrnl.exe) is the core of the OS. It handles thread scheduling, interrupt and exception dispatching, and multiprocessor synchronization. The kernel is non-pageable (always resident in physical memory) and runs at a higher IRQL (Interrupt Request Level) than most other code. The kernel provides kernel objects (dispatcher objects) for synchronization: events, semaphores, mutexes, timers, and queues.

ℹ️ IRQL (Interrupt Request Level)

Windows uses IRQL to manage interrupt priority. Each CPU has a current IRQL, and the CPU only services interrupts at a higher IRQL. The levels (on x86) are:

  • PASSIVE_LEVEL (0): normal thread execution, most system calls
  • APC_LEVEL (1): asynchronous procedure calls, some I/O completion
  • DISPATCH_LEVEL (2): thread scheduling, DPCs (deferred procedure calls)
  • Device IRQLs (3–26): device interrupts
  • HIGH_LEVEL (31): highest, only critical interrupts

Code at a given IRQL cannot be preempted by code at the same or lower IRQL. This is Windows' equivalent of Linux's spin_lock_irqsave: by raising IRQL, you prevent preemption. Code at DISPATCH_LEVEL or above cannot page fault (must be non-pageable) and cannot wait for a page.

The executive is the upper part of ntoskrnl.exe, above the kernel. It implements the major OS services:

  • Process and thread manager: creates and manages processes and threads. A Windows process is represented by an EPROCESS structure; a thread by an ETHREAD structure.
  • Memory manager: implements virtual memory, paging, and memory-mapped files. Uses a two-level page table (on x86) or multi-level (on x64).
  • I/O manager: manages devices, file systems, and I/O operations. Uses an IRP (I/O Request Packet) model: each I/O operation is an IRP that flows through the I/O stack.
  • Cache manager: provides a unified cache for file systems (unlike Linux's per-file-system page cache, Windows has a central cache manager).
  • Security reference monitor: enforces access control, checks security descriptors on every access.
  • IPC manager: implements LPC (Local Procedure Call) for inter-process communication.
  • Object manager: manages all kernel objects (processes, threads, files, events, etc.).
  • Configuration manager: manages the registry, Windows' central configuration database.

The device drivers are kernel-mode modules that interface with hardware or provide services. Windows supports several driver models: WDM (Windows Driver Model, the traditional model), WDF (Windows Driver Framework, modern, with KMDF for kernel and UMDF for user-mode drivers), minidrivers (small drivers that use a class driver for common functionality), and file system drivers (for file systems like NTFS, ReFS). Drivers can be loaded and unloaded dynamically (like Linux modules), using the Service Control Manager or the ZwLoadDriver system call.

The registry is Windows' central configuration database. It is a hierarchical database (like a file system with keys and values) that stores system configuration, hardware settings, user preferences, and application settings. The registry is organized into hives: HKEY_LOCAL_MACHINE (system-wide), HKEY_CURRENT_USER (current user), HKEY_CLASSES_ROOT (file associations), and others. The registry replaces the .ini files used in older Windows and is both a strength (central, structured) and a weakness (single point of failure, "registry rot").

21.3 Terminal Services and Fast User Switching

Terminal Services (now called Remote Desktop Services) allows multiple users to log in to a Windows system simultaneously, each with their own desktop session. This is the Windows equivalent of Unix's multi-user capability, but implemented differently. In Terminal Services, each user gets a separate session (Session 0 for services, Session 1+ for interactive users). Each session has its own window station, desktop, and window manager. Users can connect locally (console session) or remotely (via RDP—Remote Desktop Protocol).

The session is the fundamental isolation unit in Windows for interactive use. Each session has its own window station (a security boundary for UI), desktop (the visible work surface), and windows. Processes in one session cannot send messages to windows in another session (unless they have the right privileges). This isolation is stronger than in traditional Unix, where all users share a single X server (though Wayland improves this).

ℹ️ Windows Sessions
  • Session 0: services and system processes (no interactive UI since Vista, for security—prevents "shatter attacks" via window messages)
  • Session 1+: interactive user sessions (local or remote)
  • Console session: the session on the physical display
  • RDP session: a remote session via Remote Desktop Protocol

Each session has its own csrss.exe (Client/Server Runtime Subsystem), which manages the session's processes and console. The winlogon.exe process handles login for each session.

Fast User Switching allows multiple users to be logged in simultaneously on the same machine, switching between sessions without logging out. When user A locks the screen, user B can log in, creating a new session. User A's session continues running in the background (processes keep running, downloads continue). This is possible because each session is isolated: user B's processes do not interfere with user A's. Fast User Switching is essentially Terminal Services for local users: the same session infrastructure is used, just without a network connection.

Remote Desktop Protocol (RDP) is the protocol used for remote sessions. RDP transmits screen updates (as compressed bitmaps or drawing commands), keyboard and mouse input, audio, and clipboard data over a network connection. RDP is optimized for low-bandwidth connections: it uses compression, caching, and differential updates (only sending changed regions). RDP supports features like printer redirection (use local printer in remote session), drive redirection (access local drives), and clipboard sharing. RDP is the Windows equivalent of VNC or X11 forwarding in Unix.

⚠️ Session 0 Isolation

Before Windows Vista, services ran in Session 0 alongside interactive users, allowing services to display dialog boxes. This was a security vulnerability: a malicious application could send window messages to a service running with higher privileges (a "shatter attack"), exploiting the service. Starting with Vista, Session 0 Isolation separates services (Session 0) from interactive users (Session 1+). Services can no longer display UI directly; if a service needs to interact with the user, it must use a broker process in the user's session. This is a security improvement that illustrates the principle of least privilege applied to UI isolation.

Windows Terminal (2020) is a modern terminal application that supports tabs, panes, Unicode, GPU-accelerated text rendering, and multiple profiles (CMD, PowerShell, WSL, Azure Cloud Shell). It replaces the legacy cmd.exe console host with a modern, extensible terminal. Windows Terminal demonstrates the evolution of Windows from a GUI-centric OS to one that embraces command-line and developer workflows, partly in response to the popularity of Linux and macOS among developers.

💡 Windows vs. xv6 Multi-user

xv6 is single-user (no authentication, no sessions). Windows is multi-user with sophisticated session management. The contrast is stark: xv6 has no concept of "logging in"—any process can do anything. Windows requires authentication, creates isolated sessions, and enforces access control between sessions. This illustrates how much infrastructure a production multi-user OS requires: authentication, session management, window station isolation, and security descriptors. xv6 shows you the raw kernel mechanisms; Windows shows you the full multi-user stack built on top.

21.4 File System

NTFS (New Technology File System) is the primary file system for Windows, introduced with Windows NT in 1993. NTFS replaced the FAT file system (used in MS-DOS and Windows 9x) with a modern, journaling, secure file system. NTFS supports files up to 16 EB, volumes up to 256 TB (with 64 KB clusters), Unicode filenames (up to 32,767 characters), hard links, symbolic links, sparse files, file compression, and encryption (EFS—Encrypting File System).

NTFS is a journaling file system: it writes metadata changes to a log file ($LogFile) before committing them to the main file system. If the system crashes, the log can be replayed to restore consistency. NTFS journals metadata (file names, attributes, directory structure) but not data by default—data journaling can be enabled for critical files. This is similar to ext4's journaling (which also journals metadata by default).

ℹ️ NTFS Key Features
  • Journaling: metadata changes logged for crash recovery
  • Security: ACLs (access control lists) on every file and directory
  • Large file/volume support: up to 16 EB files, 256 TB volumes
  • Unicode filenames: up to 32,767 characters
  • Hard links and symbolic links: multiple names for files
  • Sparse files: efficient storage of mostly-empty files
  • File compression: transparent, per-file compression
  • EFS (Encrypting File System): per-file encryption
  • Volume Shadow Copy: point-in-time copies for backup
  • Quotas: per-user disk usage limits

NTFS organizes data using a Master File Table (MFT), a special file that contains records for every file and directory in the volume. Each MFT record is typically 1024 bytes and contains the file's attributes: standard information (timestamps, attributes), file name, data (either inline for small files or a pointer to extents for large files), and security descriptor. Small files (under ~700 bytes) can be stored entirely within the MFT record (resident files), making access very fast. Larger files use data runs (extents) that point to clusters on disk.

/* NTFS MFT record (simplified) */ // Each file/directory has an MFT record (1024 bytes) // Record contains attributes: // $STANDARD_INFORMATION: timestamps, flags // - Creation time, modification time, access time, change time // - File attributes (read-only, hidden, system, archive) // $FILE_NAME: name, parent directory reference // - File name (Unicode, up to 255 chars) // - Parent directory MFT record number // $DATA: file contents // - Resident: data stored in MFT record (small files) // - Non-resident: data runs pointing to disk clusters // $SECURITY_DESCRIPTOR: ACL (access control list) // - DACL: who can access (allow/deny entries) // - SACL: what to audit // - Owner SID // Small file (< 700 bytes): all data in MFT record → fast access // Large file: MFT record points to data runs on disk

NTFS security is based on ACLs (Access Control Lists). Every file and directory has a security descriptor containing a DACL (Discretionary ACL) and SACL (System ACL). The DACL contains access control entries (ACEs) that allow or deny specific rights to specific users or groups. When a process accesses a file, the security reference monitor checks the process's access token against the DACL. If an explicit deny matches, access is denied. If an allow matches and grants the requested right, access is granted. If no entry matches, access is denied by default. This is more expressive than Unix's owner/group/other model (which has only 3 classes × 3 bits = 9 permission bits).

Volume Shadow Copy Service (VSS) creates point-in-time copies (snapshots) of volumes, even while files are in use. VSS uses a copy-on-write mechanism: when a file is modified after the snapshot, the original blocks are copied to the snapshot before the write proceeds. This allows backups to capture a consistent point-in-time state of the file system, even if files are being modified. VSS also powers System Restore (rollback to a previous system state) and Previous Versions (restore previous versions of files).

ReFS (Resilient File System) is a newer Windows file system (introduced with Windows Server 2012) designed for high availability and data integrity. ReFS uses checksums on all metadata and (optionally) data, detecting and repairing corruption. ReFS supports storage spaces (storage pools with mirroring and parity) and can survive disk failures. ReFS is intended for server workloads (file servers, Hyper-V) and is not used for the system volume (C: drive) in client Windows.

💡 NTFS vs. xv6 File System

xv6's file system is a simplified version of a Unix file system: inodes, direct and indirect blocks, a simple log, and no security. NTFS is a production file system with journaling, ACLs, compression, encryption, and snapshots. But the core concepts are similar: both have a metadata structure (MFT vs. inodes) that describes files, both use extents or block lists to locate data, and both journal metadata for crash consistency. xv6's struct dinode is a simplified version of NTFS's MFT record. Learning xv6's file system gives you the foundation; NTFS shows you the production version with all the features.

21.5 Networking

Windows networking is built on the TCP/IP stack, implemented in the kernel as the Winsock (Windows Sockets) API and the NDIS (Network Driver Interface Specification) for network drivers. The networking stack supports TCP, UDP, IP, ICMP, and many higher-level protocols. Windows includes a firewall (Windows Defender Firewall), VPN support, and network protocols for file sharing (SMB), remote management (WinRM), and authentication (Kerberos, NTLM).

The Winsock API is Windows' implementation of the Berkeley sockets API, with Windows-specific extensions. Winsock provides socket, bind, listen, accept, connect, send, recv—the same operations as in Unix. Windows added WSAStartup (initialize Winsock), WSASocket (extended socket creation), and overlapped I/O (asynchronous I/O using OVERLAPPED structures and I/O completion ports).

/* Winsock vs. Berkeley sockets */ // Berkeley sockets (Linux, xv6-style): int sock = socket(AF_INET, SOCK_STREAM, 0); connect(sock, &addr, sizeof(addr)); write(sock, data, len); // No initialization needed // Winsock (Windows): WSADATA wsa; WSAStartup(MAKEWORD(2, 2), &wsa); // initialize Winsock SOCKET sock = socket(AF_INET, SOCK_STREAM, 0); connect(sock, &addr, sizeof(addr)); send(sock, data, len, 0); // send, not write // Must WSACleanup() when done // Overlapped I/O (async): WSAOVERLAPPED overlapped = {0}; WSASend(sock, &buf, 1, &sent, 0, &overlapped, NULL); // Returns immediately; completion via IOCP or event

I/O Completion Ports (IOCP) is Windows' high-performance async I/O mechanism, analogous to Linux's epoll and io_uring. A thread creates a completion port, associates file handles (including sockets) with it, and then waits on the port. When an async I/O completes, the completion is queued to the port, and the waiting thread retrieves it. IOCP is designed for high-throughput servers: a small pool of threads can handle thousands of connections, with the OS dispatching completions as I/O finishes. This is the proactor pattern (initiate I/O, get notified on completion), versus epoll's reactor pattern (get notified when I/O is ready, then do the I/O).

ℹ️ Windows Networking Stack
  • Winsock API: user-space socket interface
  • AFD (Ancillary Function Driver): kernel component that implements Winsock
  • TCP/IP driver (tcpip.sys): kernel network protocol stack
  • NDIS: network driver interface (miniport drivers for NICs)
  • Windows Filter Platform (WFP): kernel-level packet filtering (firewall, intrusion detection)
  • SMB: file and printer sharing protocol
  • WinRM: remote management (WS-Management protocol)
  • RRAS: routing and remote access (VPN, NAT)

SMB (Server Message Block) is Windows' file and printer sharing protocol. SMB allows a Windows client to access files and printers on a Windows server as if they were local. SMB 3.0 added SMB Direct (RDMA for high performance), SMB Multichannel (multiple connections for throughput), and SMB Encryption. The Samba software implements SMB on Linux, enabling Linux servers to share files with Windows clients. SMB is the Windows equivalent of NFS (Unix).

Windows Firewall (Windows Defender Firewall) is a stateful packet-filtering firewall integrated into the OS. It filters inbound and outbound traffic based on rules: allow/deny by application, port, protocol, IP address, and network profile (domain, private, public). The firewall is implemented in the kernel via the Windows Filtering Platform (WFP), which provides hooks at various layers of the network stack. WFP also supports intrusion detection, VPN, and parental controls.

⚠️ Network Profiles

Windows classifies networks into three profiles, each with different firewall rules:

  • Domain: connected to an Active Directory domain (most permissive, trusted)
  • Private: home or work network (moderately permissive)
  • Public: public network (most restrictive, blocks most inbound)

When you connect to a new network, Windows asks which profile to use. Choosing "Public" at a coffee shop blocks file sharing and other services, protecting you from other users on the same network. This is a practical application of the principle of least privilege applied to network access.

Active Directory is Windows' directory service for domain networks. Active Directory stores information about users, computers, and resources in a hierarchical, replicated database (based on LDAP). It provides authentication (via Kerberos), authorization (via security groups and ACLs), and policy management (via Group Policy). In an enterprise, Active Directory allows centralized management: an administrator can create a user once, and that user can log in to any computer in the domain, with consistent permissions and policies. Active Directory is the Windows equivalent of LDAP + Kerberos + configuration management on Linux.

💡 Windows vs. Linux Networking

Windows and Linux both implement the TCP/IP stack and the sockets API, but with different APIs and architectures:

  • API: Winsock (Windows) vs. BSD sockets (Linux)—similar but not identical
  • Async I/O: IOCP (Windows, proactor) vs. epoll/io_uring (Linux, reactor)
  • File sharing: SMB (Windows) vs. NFS (Linux)
  • Directory: Active Directory (Windows) vs. LDAP (Linux)
  • Firewall: WFP (Windows) vs. netfilter/iptables (Linux)

Both support the same protocols (TCP, UDP, IP) and can interoperate (Windows can mount NFS, Linux can use SMB). The differences are in the API and management tools, not the underlying protocols.

21.6 Interface

The Windows graphical user interface (GUI) is a defining feature. Unlike Linux, where the GUI (X11 or Wayland) is a user-space component separate from the kernel, the Windows GUI is deeply integrated with the OS. The Window Manager (win32k.sys) runs in kernel mode and handles window creation, drawing, and input dispatch. This integration provides performance (no user-kernel boundary for window operations) but has historically been a source of security vulnerabilities (win32k.sys is a large, complex kernel component).

The Desktop Window Manager (DWM) is the compositing window manager (introduced in Vista). DWM composites windows off-screen and then presents the final image to the display, enabling effects like transparency, animations, and glass. Before DWM, each window painted directly to the screen, which caused tearing and limited visual effects. DWM uses the GPU for compositing, providing smooth animations and effects with minimal CPU overhead.

ℹ️ Windows GUI Components
  • win32k.sys: kernel-mode window manager (window creation, input)
  • DWM (dwm.exe): compositing window manager (visual effects)
  • explorer.exe: shell (taskbar, Start menu, file manager)
  • DirectX / Direct2D: graphics APIs (GPU-accelerated rendering)
  • WPF: .NET UI framework (XAML-based)
  • UWP / WinUI: modern UI frameworks (Windows 10/11)
  • Win32 API: the core windowing API (CreateWindow, SendMessage, ...)

The Win32 API is the primary programming interface for Windows applications. Key functions include CreateWindow (create a window), ShowWindow (display a window), SendMessage (send a message to a window), GetMessage/DispatchMessage (message loop), and DefWindowProc (default message handling). Windows uses a message-driven model: the OS sends messages (like WM_PAINT, WM_KEYDOWN, WM_MOUSEMOVE) to windows, and the application's window procedure handles them. This is different from the event-loop model in X11 but conceptually similar.

/* Win32 message loop (simplified) */ // WinMain: entry point for Windows GUI applications int WINAPI WinMain(...) { // 1. The Windows shell (explorer.exe) provides the user-facing interface: the desktop, taskbar, Start menu, notification area, and file manager. The shell is a user-space process that uses the Win32 API to create windows and handle input. The shell can be customized or replaced (alternative shells exist), but most users use the default explorer.exe. The Start menu (introduced in Windows 95, removed in Windows 8, restored in Windows 10) is the primary application launcher.

Modern Windows UI has evolved through several frameworks: Win32 (classic, C/C++), WPF (.NET, XAML, 2006), UWP (Universal Windows Platform, 2015, sandboxed apps), and WinUI 3 (2021, decoupled from UWP). Windows 11 introduced WinUI as the primary UI framework, with a redesigned interface (rounded corners, centered taskbar, new Start menu). The proliferation of UI frameworks reflects Microsoft's evolving strategy: from Win32 to .NET to UWP to WinUI, each attempting to modernize the development experience while maintaining backward compatibility.

💡 Windows GUI vs. Linux GUI

The Windows GUI is integrated into the kernel (win32k.sys), while the Linux GUI (X11/Wayland) is entirely in user space. This is a fundamental architectural difference:

  • Windows: kernel-mode window manager → faster (no context switch for window operations) but less secure (bugs in win32k.sys can compromise the kernel)
  • Linux: user-space window manager → slower (context switch for window operations) but more secure (GUI bugs don't compromise the kernel) and more flexible (can replace the entire GUI)

Windows 10 has moved some GUI components to user space (UWP apps), but the core win32k.sys remains in the kernel for compatibility. This is a classic trade-off between performance and security/flexibility.

21.7 Virtualization (WSL)

The Windows Subsystem for Linux (WSL) allows Linux binaries to run natively on Windows, without a virtual machine. WSL is a modern reimagining of the environment subsystem concept from Windows NT: it provides a Linux-compatible environment that translates Linux system calls into Windows NT system calls. This allows unmodified Linux binaries (compiled for x86-64) to run on Windows, providing the best of both worlds: Windows applications and Linux tools on the same system.

WSL1 (2016) implemented Linux system calls in the Windows kernel. The LXSS subsystem translated Linux system calls (like fork, open, read) into equivalent NT system calls. WSL1 ran Linux binaries natively (no emulation), with the Windows kernel handling the system calls. This was fast (near-native performance) but had compatibility issues: not all Linux system calls had NT equivalents, and some Linux-specific behaviors (like /proc, signals) were imperfectly emulated.

/* WSL1 architecture */ // Linux binary calls: open("/home/user/file", O_RDONLY) // → Linux system call (int 0x80 or syscall instruction) // → WSL1 kernel driver (lxss.sys) intercepts // → Translates to: NtCreateFile("\\?\\...\\home\\user\\file") // → NT executive handles the file open // → Result translated back to Linux errno format // → Linux binary gets the file descriptor // No VM, no emulation — direct translation // Fast, but not 100% Linux-compatible

WSL2 (2020) takes a different approach: it runs a real Linux kernel in a lightweight virtual machine, using Microsoft's Hyper-V technology. WSL2 runs a full Linux kernel (open-source, Microsoft-maintained) in a lightweight VM with fast startup (under 2 seconds). Linux binaries run in this VM, making real Linux system calls to the real Linux kernel. This provides 100% Linux compatibility (including /proc, /sys, Docker, systemd) at near-native performance. The trade-off is that WSL2 uses more memory (a full kernel) and has slightly more overhead than WSL1.

WSL2 uses Hyper-V lightweight VMs, which are optimized for fast startup and low overhead. Unlike full Hyper-V VMs (which take 30+ seconds to start and consume significant resources), WSL2 VMs start in seconds and share the host's network and file system. The Linux kernel in WSL2 is a real kernel (from kernel.org), patched by Microsoft for WSL-specific features. This means WSL2 can run any Linux software, including Docker (which requires kernel features like cgroups and namespaces).

File system integration is a key WSL feature. WSL can access Windows files via /mnt/c (the C: drive is mounted at /mnt/c), and Windows can access WSL files via \\wsl$<distro> (WSL file system is accessible as a network share). This allows seamless file sharing between Windows and Linux applications. However, cross-filesystem access (Linux accessing Windows files, or vice versa) is slower than native access, because it goes through a translation layer. For best performance, keep Linux files in the WSL file system and Windows files in the Windows file system.

⚠️ WSL2 File System Performance

WSL2 stores its file system in a virtual disk (ext4.vhdx). Accessing files within this disk is fast (native ext4 performance). However, accessing Windows files (via /mnt/c) is slow because each operation crosses the VM boundary and is translated from ext4 semantics to NTFS semantics. For development, this means: keep your source code and build artifacts in the WSL file system (e.g., ~/projects), not in /mnt/c/Users/.... This can be 10–100× faster for file-intensive operations like git, npm install, or compilation.

WSL and Docker are closely related. Docker Desktop on Windows uses WSL2 as its backend: Docker runs inside the WSL2 VM, using the Linux kernel's container features (cgroups, namespaces). This means Docker on Windows is essentially Docker on Linux, running in a lightweight VM. Before WSL2, Docker on Windows used Hyper-V VMs (Windows containers) or a Linux VM (Docker Machine), which were heavier. WSL2 makes Docker on Windows fast and lightweight.

WSLg (WSL GUI) (2021) extends WSL to support Linux GUI applications. WSLg runs a Wayland/X server inside the WSL VM and displays Linux GUI windows on the Windows desktop, integrated with the Windows window manager. This allows running Linux GUI applications (like GIMP, Firefox, or custom tools) on Windows without a separate X server. WSLg demonstrates the deep integration possible between Windows and Linux: GUI applications from both environments coexist on the same desktop.

💡 WSL and xv6

WSL is a fascinating case study in OS design: it runs a real Linux kernel alongside the Windows kernel, with both coexisting on the same hardware. This is possible because of hardware virtualization (Hyper-V) and the environment subsystem concept from Windows NT. If you wanted to run xv6 on Windows, you would use a full VM (like VirtualBox or Hyper-V), because xv6 is not binary-compatible with either Windows or Linux. But the concept is the same: a guest OS running in a virtualized environment, with the host OS managing the hardware. WSL2 is essentially a highly optimized VM for running Linux; QEMU (which you use for xv6) is a general-purpose emulator. Both demonstrate the power of virtualization for running multiple OS environments on one machine.

22.1 Early Systems

The history of operating systems begins in the 1940s with the first electronic computers: ENIAC, EDVAC, and the Manchester Mark 1. These early machines had no operating system—programmers operated the hardware directly, entering programs via switches or punched cards. Each program run was a manual process: load the program, start execution, monitor, and record results. There was no concept of a "job" or "scheduling"—one program ran at a time, and the programmer had exclusive use of the machine.

The first operating systems appeared in the 1950s with the first commercial computers (IBM 701, 1952). These early OS were simple: they loaded programs from punched cards or tape, executed them, and printed results. The key innovation was the resident monitor: a small program that stayed in memory and loaded the next job automatically, reducing setup time. The resident monitor was the ancestor of the kernel: it managed job sequencing and I/O, freeing the operator from manual intervention.

ℹ️ Early OS Timeline
  • 1940s: No OS. Direct hardware control via switches/cards.
  • 1950s: Resident monitors. Job sequencing, simple I/O drivers.
  • 1950s: Batch processing. Jobs queued on cards/tape, processed sequentially.
  • 1960s: Multiprogramming. Multiple jobs in memory, CPU switches between them.
  • 1960s: Time-sharing. Multiple interactive users, CPU time-sliced.
  • 1970s: Personal computers. Single-user OS (CP/M, later MS-DOS).
  • 1980s: GUIs. Macintosh (1984), Windows 1.0 (1985).
  • 1990s: Open source. Linux (1991), FreeBSD.
  • 2000s: Mobile. iOS (2007), Android (2008).
  • 2010s: Cloud. AWS EC2 (2006), containers (Docker, 2013).

Batch processing was the first major OS innovation. Instead of loading each job manually, operators stacked punched cards (or magnetic tape) with multiple jobs. The OS loaded and executed each job in sequence, automatically. This reduced setup time (the time between jobs) and improved throughput. The OS provided job control language (JCL) to specify job requirements (which compiler to use, which data sets to read). Batch processing was the dominant paradigm from the 1950s through the 1970s and is still used today for background processing (payroll, billing, data processing).

The key problem with early batch systems was I/O wait: while a job was waiting for I/O (reading cards, printing results), the CPU was idle. With a single job in memory, CPU utilization could be as low as 10–20%. The solution was multiprogramming: keeping multiple jobs in memory simultaneously. When one job waits for I/O, the CPU switches to another job. This dramatically improved CPU utilization and throughput. Multiprogramming required memory protection (to prevent jobs from interfering with each other) and scheduling (to decide which job to run next)—the foundations of modern OS design.

⚠️ From Batch to Interactive

Batch processing was efficient for the computer but terrible for programmers. A programmer submitted a job and waited hours (or overnight) for results. A single typo meant resubmitting and waiting again. Time-sharing solved this by giving each user an interactive terminal and time-slicing the CPU among them. The first time-sharing system was the Compatible Time-Sharing System (CTSS) at MIT (1961), followed by Multics (1965). Time-sharing made computing interactive and is the model for all modern multi-user systems, including Unix and Linux.

The evolution from no OS to batch to multiprogramming to time-sharing illustrates the key drivers of OS evolution: efficiency (use expensive hardware better), convenience (make computing easier for users), and security (protect users from each other). These same drivers continue today: cloud computing (efficiency), mobile OS (convenience), and zero-trust security all have roots in these early developments.

💡 Early Systems and xv6

xv6 is a time-sharing, multiprogramming operating system—concepts that were groundbreaking in the 1960s. When you run xv6, you're running a system that implements ideas from CTSS and Multics: multiple processes in memory, time-sliced CPU, memory protection, and interactive use. The difference is that xv6 runs on a modern RISC-V processor in QEMU, while CTSS ran on an IBM 7094 with 32K of magnetic-core memory. But the concepts are the same. Studying xv6 connects you to 60 years of OS evolution.

22.2 Atlas

The Atlas computer (1962, University of Manchester) was one of the most influential early computers, pioneering several concepts that are now fundamental to operating systems. Atlas was designed by a team led by Tom Kilburn and was one of the fastest computers in the world at the time. Its operating system, the Atlas Supervisor, introduced concepts that are still in use today.

Atlas's most important contribution was virtual memory using demand paging. Atlas had a drum (a rotating magnetic storage device) as secondary storage and magnetic-core memory as primary storage. The Supervisor used a technique called one-level store: it presented the programmer with a large, contiguous virtual address space, backed by the drum, with pages loaded into core memory on demand. When a program accessed a page not in memory, a page fault occurred, and the Supervisor loaded the page from the drum. This was the first implementation of demand paging, now universal in all modern operating systems.

ℹ️ Atlas Innovations
  • Virtual memory / demand paging: the one-level store (1962)
  • Page replacement: the learning algorithm (precursor to LRU)
  • Spooling: Simultaneous Peripheral Operation On-Line (coined by Atlas team)
  • Interrupt-driven I/O: hardware interrupts for I/O completion
  • Extracode: software-implemented instructions (precursor to system calls)

Atlas's page replacement algorithm was also pioneering. The learning algorithm attempted to predict which page would not be needed for the longest time, based on past access patterns. This was an early form of the least-recently-used (LRU) algorithm. The Atlas team recognized that optimal page replacement (Belady's MIN algorithm, 1966) requires future knowledge, which is impossible, so they approximated it with past behavior. This insight—that page replacement must be based on heuristics because the future is unknown—remains central to memory management.

Spooling (Simultaneous Peripheral Operation On-Line) was another Atlas innovation. Slow peripherals (card readers, printers) were buffered by writing data to magnetic tape or disk, allowing the CPU to proceed with other work while the peripheral operated. For example, card images were read to tape, then the tape was read by the computer at high speed. Output was written to tape, then printed later. This overlapped I/O with computation, improving throughput. The term "spool" is still used today (print spooler, /var/spool).

Extracode was Atlas's mechanism for software-implemented instructions. Some instructions (like division, which the hardware did not support directly) were implemented as subroutines invoked by a trap. When the CPU encountered an extracode instruction, it trapped to the Supervisor, which executed the corresponding subroutine. This is the direct ancestor of system calls: the idea that some operations are implemented in software (the OS) rather than hardware, invoked via a trap mechanism. xv6's ecall instruction is the modern RISC-V equivalent of Atlas's extracode.

💡 Atlas and Modern OS

Atlas introduced virtual memory, demand paging, page replacement, spooling, and software-implemented instructions—all in 1962. Every modern operating system (Linux, Windows, macOS, xv6) uses these concepts. When you study xv6's page fault handler (usertrap in trap.c), you're seeing the descendant of Atlas's page fault handler. When you study xv6's syscalls, you're seeing the descendant of Atlas's extracode. Atlas was truly ahead of its time.

22.3 XDS-940

The XDS-940 (1964, Scientific Data Systems) was a time-sharing operating system that pioneered several important concepts. It was developed at the University of California, Berkeley, by a team led by Butler Lampson and Peter Deutsch. The XDS-940 was one of the first commercially available time-sharing systems and demonstrated that interactive computing was practical.

The XDS-940's key innovation was memory-mapped I/O and memory protection. The hardware supported a relocation register that mapped virtual addresses to physical addresses, providing each process with its own address space. This was an early form of base and limit registers: the base register specified where the process's memory started, and the limit register specified its size. Any access outside this range caused a trap. This is the simplest form of memory protection, still taught in OS courses as the foundation of virtual memory.

ℹ️ XDS-940 Contributions
  • Time-sharing: interactive multi-user computing
  • Memory protection: base and limit registers per process
  • Dynamic relocation: virtual-to-physical address translation
  • Swapping: moving processes between memory and disk
  • Paged memory: early form of paging (not full demand paging)

The XDS-940 used swapping to multiprogram: when memory was full, a process was moved (swapped) to disk to make room for another. When the swapped process was needed again, it was swapped back in. Swapping is simpler than paging (whole processes are moved, not individual pages) but less efficient (a small process may be swapped out to make room, even if only a few pages are needed). Modern systems use paging (which swaps individual pages) rather than whole-process swapping, but the concept is the same: move inactive data to disk to free physical memory.

The XDS-940 influenced later systems, particularly the SDS 940 (commercial version) and the Berkeley Time-Sharing System. The concepts of memory protection, dynamic relocation, and swapping became standard in subsequent operating systems. The XDS-940 demonstrated that time-sharing with memory protection was practical, paving the way for Unix (1971), which combined these ideas with a hierarchical file system and a powerful command interface.

💡 XDS-940 and xv6

xv6 uses page tables for memory protection, which is more sophisticated than the XDS-940's base and limit registers. But the concept is the same: each process has its own address space, and the hardware prevents a process from accessing another's memory. xv6's proc_pagetable function creates a page table that maps the process's virtual addresses to physical memory, with no access to other processes' memory or the kernel's memory (except the trampoline page). This is the modern descendant of the XDS-940's relocation and protection mechanism.

22.4 THE

THE (Technische Hogeschool Eindhoven) was an operating system designed by Edsger Dijkstra in 1965–1968. THE is famous for two contributions: the layered system structure and the semaphore as a synchronization primitive. Dijkstra designed THE to demonstrate that operating systems could be built in a structured, verifiable way, using layers and semaphores for synchronization.

The layered structure of THE organized the OS into six layers, each built on the one below:

LayerFunction
5User programs
4Input/Output management (device drivers)
3Operator-console device driver
2Memory management (segmentation)
1CPU scheduling
0Hardware

The key property of the layered structure is that each layer can only use the services of the layers below it. Layer 2 (memory management) can use the CPU scheduler (layer 1) but not the I/O manager (layer 4). This creates a strict hierarchy that makes the system easier to understand and verify: you can reason about each layer independently, knowing it only depends on lower layers. This was a revolutionary idea in 1968, when most OS were monolithic and unstructured.

ℹ️ THE's Contributions
  • Layered system structure: strict layering, each layer uses only lower layers
  • Semaphores: Dijkstra's P (wait) and V (signal) operations for synchronization
  • Structured programming: THE demonstrated that complex systems can be built systematically
  • Deadlock avoidance: Dijkstra's work on deadlock (banker's algorithm) was related

Semaphores were Dijkstra's most influential contribution. A semaphore is an integer with two atomic operations: P (proberen, "to test"—wait or decrement, block if zero) and V (verhogen, "to increment"—post or signal, wake a waiter). Semaphores can be used for mutual exclusion (binary semaphore, like a mutex) or counting (count available resources). Dijkstra showed that semaphores could solve all classic synchronization problems: mutual exclusion, producer-consumer, readers-writers, and dining philosophers. Semaphores are still a fundamental synchronization primitive in all operating systems.

/* Dijkstra's semaphore operations */ // P (wait): decrement, block if zero P(semaphore s) { if (s.value <= 0) { // Add current process to s.wait_queue // Block current process } s.value--; } // V (signal): increment, wake one waiter V(semaphore s) { s.value++; if (s.wait_queue not empty) { // Wake one process from s.wait_queue } } // Mutual exclusion: // semaphore mutex = 1; // P(mutex); // enter critical section // ... critical section ... // V(mutex); // leave critical section

The layered structure of THE influenced many subsequent operating systems. The THE multiprogramming system demonstrated that a complex OS could be built in a structured, layered way, making it easier to understand, verify, and maintain. This influenced the design of later systems, including THE's successor at Eindhoven and the Venus system. However, strict layering has limitations: it can be inefficient (layers must communicate through the hierarchy) and inflexible (a layer cannot use services from a higher layer). Modern systems use more flexible structures (microkernels, loadable modules) but retain the idea of layered abstraction.

⚠️ The Problem with Strict Layering

While THE's layered structure was elegant, strict layering has practical problems:

  • Inefficiency: a request from layer 5 to layer 0 must pass through layers 4, 3, 2, 1—each adding overhead.
  • Inflexibility: if layer 2 needs a service from layer 4, it cannot get it (layers can only use lower layers). This forces awkward workarounds.
  • Abstraction mismatch: the layering may not match the natural structure of the system, forcing functionality into the "wrong" layer.

Modern systems use relaxed layering: components are organized in layers but can communicate more flexibly. Linux, for example, is layered (hardware → kernel → system calls → user space) but allows direct communication within the kernel.

💡 THE and xv6

xv6 is not strictly layered, but it uses the concept of layered abstraction: the hardware (RISC-V) provides privilege levels; the kernel (xv6) provides system calls; user programs use the system call interface. xv6 also uses semaphores (via spinlocks and sleep/wakeup) for synchronization, directly descended from Dijkstra's work. When you study xv6's sleep and wakeup functions (in sleeplock and condvar), you're seeing the modern implementation of Dijkstra's P and V operations. THE's influence is everywhere in xv6.

22.5 Multics

Multics (Multiplexed Information and Computing Service, 1965–1970) was one of the most influential operating systems ever designed, despite being a commercial failure. Developed by MIT, Bell Labs, and General Electric (later Honeywell), Multics was an ambitious attempt to build a "computer utility"—a system that would provide computing power to a large community of users, like a power utility provides electricity. Multics introduced or refined many concepts that are now standard: hierarchical file systems, dynamic linking, memory-mapped files, a unified file abstraction, and security rings.

The hierarchical file system is perhaps Multics's most visible legacy. Before Multics, file systems were typically flat (all files in one directory) or had limited nesting. Multics introduced the tree-structured directory: files are organized in directories, which can contain subdirectories, forming a tree. Paths like /users/smith/project/main.pl navigate the hierarchy. This is now universal: Unix, Linux, Windows, macOS all use hierarchical file systems. The concept was so successful that it's hard to imagine an alternative.

ℹ️ Multics Contributions
  • Hierarchical file system: tree-structured directories
  • Dynamic linking: shared libraries loaded at runtime
  • Memory-mapped files: files mapped into virtual memory
  • Unified file abstraction: devices as special files
  • Security rings: hierarchical privilege levels (ring 0–7)
  • Virtual memory: sophisticated paging
  • Access control lists: per-file access control
  • PL/I as system language: high-level language for OS

Security rings were a Multics innovation (see Section 17.3). Multics defined 8 privilege rings (0–7), with ring 0 being the most privileged (the kernel) and ring 7 the least (user programs). Intermediate rings were intended for system services. This was more granular than the 2-ring (user/kernel) model that later became common, but in practice, most systems only use 2 rings (ring 0 and ring 3 on x86). The concept of hierarchical privilege levels, however, is universal.

Dynamic linking was another Multics innovation. Before Multics, libraries were statically linked: each program included a copy of all library code. Multics introduced shared segments: library code was loaded once and shared among all programs that used it. This saved memory (one copy of the library, not one per program) and allowed libraries to be updated without recompiling programs. Dynamic linking is now universal: .so (Linux), .dll (Windows), .dylib (macOS) are all shared libraries, descended from Multics's shared segments.

⚠️ Multics: Commercial Failure, Conceptual Success

Multics was too ambitious for its time. It was complex, slow, and over-budget. Bell Labs withdrew from the project in 1969, and Honeywell's commercial Multics systems were expensive and had limited success. The last Multics system was shut down in 2000. However, Multics's ideas were enormously influential. Two Bell Labs researchers who worked on Multics—Ken Thompson and Dennis Ritchie—went on to create Unix (1971), which simplified and popularized Multics's ideas. Unix's name is a pun on Multics: "Uni" (one) vs. "Multi" (many), reflecting Unix's simpler, single-purpose design. Unix inherited Multics's hierarchical file system, dynamic linking, and the concept of a unified file abstraction, but stripped away the complexity.

Memory-mapped files were a Multics feature that allowed a file to be mapped into a process's virtual address space. The process could then read and write the file as memory, without explicit read and write calls. The OS loaded pages on demand (page faults) and wrote them back when evicted. This is now standard: Linux's mmap system call and Windows's MapViewOfFile both implement memory-mapped files, descended from Multics.

The unified file abstraction—"everything is a file"—was refined by Multics and perfected by Unix. In Multics, devices, inter-process communication channels, and regular files were all accessed through the same file interface. Unix took this further: /dev contains device files, /proc contains process information, and network sockets use a file-descriptor-like interface. This abstraction makes Unix systems flexible and scriptable: you can redirect any input or output to any file or device, because they all use the same interface.

💡 Multics and xv6

xv6 is a direct descendant of Multics, via Unix. xv6's hierarchical file system (directories containing files and subdirectories), its file descriptor abstraction (everything is a file), and its system call interface (open, read, write, close) all trace back to Multics. When you create a directory in xv6 with mkdir, you're using a concept invented in Multics. When you redirect output with echo hello > file.txt, you're using the unified file abstraction from Multics. xv6 is, in a sense, a simplified Multics—just as Unix was. The lineage is direct: Multics → Unix → xv6.

22.6 CP/M and MS-DOS

CP/M (Control Program for Microcomputers, 1974) was the first popular operating system for personal computers, created by Gary Kildall at Digital Research. CP/M ran on 8-bit microprocessors (Intel 8080, Zilog Z80) and provided a simple file system, a command interpreter (CCP), and basic I/O (BIOS). CP/M dominated the early personal computer market (1970s–early 1980s) and established conventions that influenced later systems, including drive letters (A:, B:, C:) and file names (8.3 format: 8 characters + 3-character extension).

MS-DOS (Microsoft Disk Operating System, 1981) was Microsoft's clone-successor to CP/M, created for the IBM PC. When IBM was looking for an OS for the IBM PC (1981), they approached Digital Research (for CP/M) and Microsoft (which had bought a CP/M clone called 86-DOS from Seattle Computer Products). Microsoft's MS-DOS won the IBM contract, and the rest is history. MS-DOS was essentially a CP/M-compatible OS for the Intel 8086/8088 processor, with the same 8.3 file names and drive letters.

ℹ️ MS-DOS Characteristics
  • Single-tasking: one program at a time (no multiprogramming)
  • Single-user: no authentication, no access control
  • No memory protection: a program could access any memory
  • FAT file system: simple, no journaling, no security
  • BIOS: basic I/O system in ROM
  • Command line: COMMAND.COM interpreter
  • 640 KB limit: the famous "640K ought to be enough" (apocryphal Gates quote)

MS-DOS was a single-tasking operating system: only one program ran at a time. There was no multiprogramming (no multiple programs in memory), no memory protection (a program could overwrite the OS), and no preemptive scheduling (the OS could not take control back from a program). A misbehaving program could crash the entire system. This was acceptable for early personal computers (which were single-user and single-tasking) but inadequate as computers became more powerful and connected.

The FAT (File Allocation Table) file system was MS-DOS's file system and is still used today (on USB drives, SD cards, and for compatibility). FAT is simple: a file's data is stored in clusters (groups of sectors), and a file allocation table tracks which clusters belong to which file (as a linked list). FAT has no journaling (so it can be corrupted by crashes), no security (no permissions), and limited file sizes (FAT16: 2 GB; FAT32: 4 GB per file). exFAT and NTFS address these limitations. Despite its limitations, FAT's simplicity makes it universal: every OS can read FAT, making it the lingua franca of removable media.

/* FAT file system (simplified) */ // File Allocation Table: array of cluster pointers // Each entry: next cluster in file, or EOF marker // Directory entry (32 bytes): // [name(8)][ext(3)][attr(1)][reserved(10)] // [time(2)][date(2)][start_cluster(2)][size(4)] // Reading a file: // 1. Find directory entry → get start_cluster // 2. Read cluster at start_cluster // 3. FAT[start_cluster] → next_cluster // 4. Read next_cluster, repeat until EOF // No permissions, no journaling, no hard links // But: simple, portable, universally readable

The 640 KB limit was a famous constraint of MS-DOS. The IBM PC's address space was 1 MB (20-bit addresses), but the upper 384 KB was reserved for ROM (BIOS, video memory), leaving 640 KB for programs. This limit, combined with single-tasking, meant programs had to fit in 640 KB. Various workarounds were developed (expanded memory EMS, extended memory XMS), but the limit was a constant frustration. The transition to 32-bit (80386, 1985) and protected mode (Windows 3.x, 1990; Windows 95, 1995; Windows NT, 1993) eventually overcame this limit, but the "640K barrier" remains a symbol of early PC limitations.

⚠️ MS-DOS's Legacy

MS-DOS's influence persists in surprising ways:

  • Drive letters (C:, D:) are still used in Windows, even though they are arbitrary (Unix uses mount points).
  • 8.3 file names influenced Windows file naming (long filenames were added in Windows 95, but 8.3 is still generated for compatibility).
  • Backslash as path separator (C:\Users\...) comes from MS-DOS (Unix uses forward slash).
  • COMMAND.COM / cmd.exe syntax (dir, copy, del) is still used in Windows.
  • .exe, .com, .bat extensions are still used for executables.

These conventions, inherited from CP/M via MS-DOS, are historical accidents that persist for compatibility. They illustrate how early design decisions can persist for decades.

💡 MS-DOS vs. xv6

MS-DOS was simpler than xv6 in some ways (single-tasking, no memory protection) but more complex in others (FAT file system, device drivers, BIOS). The key difference is that MS-DOS had no protection: a program could access any memory, including the OS. xv6, despite being a teaching OS, has hardware-enforced protection (user/kernel mode, page tables). This makes xv6 more like a "real" operating system than MS-DOS was. The evolution from MS-DOS (no protection) to Windows NT (full protection) mirrors the evolution from early batch systems (no protection) to modern OS (full protection). xv6 sits on the modern side of this divide.

22.7 Macintosh and Windows

The Apple Macintosh (1984) brought the graphical user interface (GUI) to the mass market. While GUIs were invented at Xerox PARC (Alto, 1973) and commercialized by Apple (Lisa, 1983), the Macintosh made GUIs affordable and popular. The Macintosh OS (originally called "System", later "Mac OS") introduced the desktop metaphor: files and folders on a desktop, a mouse for pointing and clicking, menus, and windows. This was revolutionary: instead of typing commands, users could see and manipulate objects directly.

The original Macintosh OS (1984–2001) was a single-tasking (later cooperative multitasking) OS with no memory protection and no command line. It was designed for a single user on a single machine with 128 KB of RAM. Over time, it gained multitasking (MultiFinder, 1987), color, networking (AppleTalk), and more memory. But its foundations—cooperative multitasking, no memory protection, no preemptive scheduling—were inadequate for modern computing. Apple eventually replaced it with Mac OS X (2001, now macOS), built on a Unix foundation (Darwin, a Mach-based microkernel with BSD user space).

ℹ️ GUI History
  • 1968: Douglas Engelbart's "Mother of All Demos" (mouse, hypertext, video conferencing)
  • 1973: Xerox Alto (first GUI computer, at PARC)
  • 1983: Apple Lisa (first commercial GUI computer, expensive)
  • 1984: Apple Macintosh (affordable GUI, mass market)
  • 1985: Windows 1.0 (Microsoft, GUI for MS-DOS)
  • 1995: Windows 95 (mainstream GUI, 32-bit, preemptive multitasking)
  • 2001: Mac OS X (Unix-based, modern Mac)
  • 2007: iPhone (touch-based GUI, mobile computing)
  • 2008: Android (open-source mobile OS)

Microsoft Windows began as a GUI shell on top of MS-DOS. Windows 1.0 (1985) and Windows 2.0 (1987) were graphical environments that ran MS-DOS programs in windows. Windows 3.0 (1990) and 3.1 (1992) were more successful, adding program manager, file manager, and improved graphics. But these were still 16-bit, cooperative multitasking environments on top of MS-DOS, with no memory protection.

Windows 95 (1995) was a major milestone: it introduced 32-bit computing, preemptive multitasking, the Start menu, taskbar, and long filenames. Windows 95 was still built on MS-DOS (it booted from DOS), but it provided a modern GUI and 32-bit APIs (Win32). Windows 98 (1998) and Windows ME (2000) continued this line, but the DOS foundation was increasingly inadequate.

Windows NT (1993) was a separate, from-scratch operating system designed by Dave Cutler (see Section 21.1). NT was 32-bit, preemptive, multi-user, and secure, with full memory protection. NT was initially targeted at servers and workstations (it was expensive and required powerful hardware). Over time, as hardware improved, the NT line (NT 3.1, 3.5, 4.0, 2000, XP, Vista, 7, 8, 10, 11) replaced the DOS-based line (95, 98, ME). Windows XP (2001) was the first NT-based Windows for consumers, finally unifying the product line. All modern Windows (10, 11) are descendants of NT, not DOS.

The Mac OS X / macOS transition (2001) is a remarkable case study. Apple's classic Mac OS had reached its limits (no memory protection, cooperative multitasking). After Steve Jobs returned to Apple (via the acquisition of NeXT, 1997), Apple replaced Mac OS with Mac OS X, built on Darwin—an open-source OS based on the Mach microkernel and BSD Unix. Mac OS X combined the Unix foundation (memory protection, preemptive multitasking, security) with the Mac GUI (Aqua). This gave Mac users the stability of Unix with the usability of Mac. macOS is, to this day, a certified Unix system: you can open Terminal and run the same commands as on Linux.

⚠️ The Unix Foundation of macOS

macOS is a certified Unix system (Single UNIX Specification). Its kernel, XNU (X is Not Unix), is a hybrid kernel combining the Mach microkernel (for IPC, scheduling, memory management) with BSD (for the POSIX API, file system, networking). This is different from Linux (a monolithic kernel) and Windows NT (a layered kernel). The Mach component provides a microkernel-like message-passing infrastructure, while BSD provides the familiar Unix API. This hybrid design gives macOS the stability and security of Unix with the performance of a monolithic kernel. When you use Terminal on macOS, you're using a real Unix system—closer to Linux than to Windows.

💡 Mac/Windows and xv6

xv6 is a Unix-like system, so it's more closely related to macOS (which is Unix-based) than to Windows (which is NT-based). The system calls in xv6 (fork, exec, open, read) are the same as in macOS and Linux. Windows has different system calls (CreateProcess instead of fork+exec, CreateFile instead of open), reflecting its independent design. Studying xv6 teaches you the Unix model, which applies to macOS, Linux, and other Unix systems. Windows is a different tradition, but the concepts (processes, memory management, file systems, scheduling) are the same—only the APIs and implementations differ.

22.8 Mach

Mach (1985, Carnegie Mellon University) was an influential microkernel operating system that demonstrated the microkernel architecture. Developed by Richard Rashid and Avie Tevanian (who later went to Apple and led the Mac OS X development), Mach was designed to address the complexity and fragility of monolithic kernels by moving OS services into user-space processes, communicating via message passing.

The microkernel architecture puts only the essential services in the kernel: IPC (inter-process communication), memory management, and CPU scheduling. All other services—file systems, device drivers, network stacks, security—run as user-space processes called servers. The microkernel provides a message-passing facility: when a process needs a service (like reading a file), it sends a message to the file system server, which performs the operation and sends a reply. This is the client-server model applied to the operating system.

ℹ️ Mach Microkernel Architecture
  • Microkernel: IPC, memory management, scheduling (in kernel mode)
  • File system server: file system (user space)
  • Network server: network stack (user space)
  • Device driver servers: device drivers (user space)
  • Security server: access control (user space)

Communication is via Mach messages: a process sends a message to a port (a communication endpoint), and the receiver gets the message. The microkernel delivers messages, handling all IPC. This is the foundation of the client-server OS model.

The key advantage of the microkernel is modularity and isolation. Each server runs in its own address space, so a bug in the file system server cannot crash the network server or the kernel. Servers can be started, stopped, and restarted without rebooting the system. New services can be added without modifying the kernel. This is more flexible and more robust than a monolithic kernel, where a bug in any component can crash the entire system.

The key disadvantage is performance. In a monolithic kernel, a system call is a single trap into the kernel. In a microkernel, a "system call" may involve multiple message passes: the client sends a message to the server (trap into the kernel to send), the kernel delivers the message to the server (context switch), the server processes the request (another context switch), the server sends a reply (another trap), and the kernel delivers the reply (another context switch). This can be 10–100× slower than a monolithic system call. Mach attempted to mitigate this with optimized IPC, but the overhead remained significant.

/* Microkernel vs. monolithic system call */ // Monolithic (Linux, xv6): // read(fd, buf, n) // → trap to kernel // → kernel reads file, copies to buf // → return to user // Total: 1 trap, 1 context switch // Microkernel (Mach): // read(fd, buf, n) // → send message to file system server (trap to kernel) // → kernel delivers message to FS server (context switch) // → FS server reads file, prepares reply // → FS server sends reply (trap to kernel) // → kernel delivers reply to client (context switch) // Total: 2 traps, 2+ context switches

Mach influenced many systems. GNU Hurd (the GNU Project's kernel, still in development) is a Mach-based microkernel OS. NeXTSTEP (1989, NeXT Computer) used Mach as the basis for its OS; when Apple acquired NeXT (1997), NeXTSTEP became the foundation for Mac OS X. XNU (the macOS kernel) is a hybrid: it uses Mach for IPC and memory management but incorporates BSD code for the POSIX API and file system, running both in the kernel. This hybrid approach attempts to get the modularity of a microkernel with the performance of a monolithic kernel.

⚠️ The Microkernel Debate

The microkernel vs. monolithic kernel debate was one of the most famous in OS history, epitomized by the Tanenbaum-Torvalds debate (1992). Tanenbaum argued that microkernels were the future (citing Mach); Torvalds defended Linux's monolithic design. The debate continues:

  • Microkernels (seL4, Fuchsia's Zircon, QNX): better isolation, security, and modularity, but historically slower.
  • Monolithic kernels (Linux, Windows NT): faster, simpler to implement, but a bug in any component can crash the system.
  • Hybrid kernels (XNU/macOS, Windows NT): attempt to combine both, with mixed success.

Modern systems like seL4 (formally verified microkernel) and Fuchsia (Google's new OS, Zircon microkernel) show that microkernels are still actively developed. The debate is not settled; it reflects fundamental trade-offs in OS design.

seL4 is a modern microkernel that addresses Mach's performance and reliability concerns. seL4 is formally verified: mathematical proofs guarantee that the implementation matches its specification, and that the specification enforces security properties (confidentiality, integrity, availability). seL4's IPC is much faster than Mach's, thanks to careful design and optimization. seL4 is used in safety-critical systems (automotive, defense, medical) where formal verification is required. It demonstrates that microkernels can be both fast and reliable, challenging the performance argument against microkernels.

💡 Mach and xv6

xv6 is a monolithic kernel: all OS services (file system, device drivers, scheduler, memory manager) run in the kernel. This is the opposite of Mach's microkernel design. But the comparison is instructive: xv6's simplicity comes from having everything in one address space (no message passing), while Mach's modularity comes from separating services (at the cost of message passing). If you wanted to turn xv6 into a microkernel, you would: (1) move the file system to a user-space server, (2) move device drivers to user-space servers, (3) implement an IPC mechanism in the kernel for communication, and (4) have user programs send messages to servers instead of making system calls. This would make xv6 more modular but slower—a classic OS design trade-off.

22.9 Capabilities (Hydra/CAP)

Capability-based operating systems use capabilities as the primary protection mechanism (see Section 17.10). A capability is a token that both names a resource and confers specific access rights. Two influential capability-based systems were Hydra (1970s, Carnegie Mellon University) and CAP (1970s, Cambridge University). These systems demonstrated that capability-based protection could provide fine-grained, flexible access control.

Hydra was designed by W. A. Wulf and colleagues as a capability-based, object-oriented operating system. In Hydra, everything is an object, and access to objects is mediated by capabilities. A capability is a token that identifies an object and specifies the operations (rights) the holder can perform on it. Capabilities are stored in capability lists associated with protection domains. A process can only access objects for which it holds capabilities, and only with the rights specified in those capabilities.

ℹ️ Hydra Concepts
  • Objects: all resources (files, processes, memory, devices) are objects with types and operations
  • Capabilities: tokens that name an object and specify access rights
  • Capability lists: each protection domain has a list of capabilities
  • Rights amplification: a procedure can be granted more rights than the caller, but only through a verified code path
  • Type extension: users can define new object types with new operations

Hydra's rights amplification was a novel feature. Normally, a procedure can only exercise the rights of its caller. But some procedures need more rights than the caller—for example, a compiler needs to write to a log file that the caller cannot access directly. Hydra allowed a procedure to be designated as trusted and granted amplified rights: when called, the procedure temporarily gains additional rights, but only for the duration of the call and only through the verified entry point. This is the confused deputy solution (Section 17.2): the procedure can only use the rights it is explicitly given, not the caller's rights.

CAP (Cambridge CAP computer, 1976) implemented capabilities in hardware. The CAP (Capability Addressed Processor) had special capability registers, and memory access required a valid capability in a register. Capabilities were tagged in memory (using a tag bit) so that user programs could not forge them—only the hardware could create or modify capabilities. This hardware support made capability checking efficient and secure: every memory access was automatically checked against the capability, with no software overhead.

/* CAP capability-based addressing */ // CAP has capability registers (C-registers) // Each C-register holds a capability: // [base address][size][access rights][tag] // To access memory, load a capability into a C-register: // LOADC C1, capability_for_my_data // Then access memory relative to the capability: // LOAD R1, C1+offset ← hardware checks C1 rights // If C1 doesn't have READ right → trap (access denied) // User code cannot forge capabilities: // - Tag bit distinguishes capabilities from data // - Only privileged instructions can create/modify capabilities // - User code can copy capabilities but not create new ones

The CAP system demonstrated that hardware-supported capabilities could provide fine-grained, efficient protection. However, the hardware was complex and expensive, and the system was never commercialized. The ideas influenced later systems: the Intel iAPX 432 (1981) attempted a capability-based architecture but was too complex and slow. Modern systems use software capabilities (file descriptors, seL4 capabilities) rather than hardware capabilities, but the concept remains influential.

⚠️ Why Didn't Capability Hardware Catch On?

Despite their elegance, hardware capability systems like CAP and iAPX 432 did not succeed commercially. Reasons include:

  • Complexity: capability hardware is more complex than conventional hardware, increasing cost and development time.
  • Performance: checking capabilities on every memory access adds overhead, especially without specialized hardware.
  • Compatibility: capability systems are not compatible with existing software, requiring everything to be rewritten.
  • Market forces: the market favored cheaper, faster, compatible systems (x86) over elegant but expensive and incompatible ones.

Instead, capability-like protection is implemented in software: file descriptors (Unix), seL4 capabilities, and WebAssembly capabilities. These provide the benefits of capabilities without requiring special hardware.

Modern capability systems carry forward the ideas of Hydra and CAP. seL4 (Section 17.10) is a formally verified microkernel that uses capabilities for all resource access. WebAssembly (WASM) uses capabilities for memory, tables, and functions: a WASM module can only access what it is explicitly given. File descriptors in Unix are capabilities: a process can only access files it has opened (received a descriptor for). The confused deputy problem, which motivated Hydra's rights amplification, is still relevant today: modern systems use capability passing (passing file descriptors between processes) to solve it.

💡 Hydra/CAP and xv6

xv6 does not use capabilities for protection—it uses hardware privilege levels (user/kernel mode) and page tables. But xv6's file descriptors are a form of capability: a process can only read or write a file if it has a file descriptor for it, and the descriptor specifies the access mode (read, write). When a process calls open, it receives a capability (file descriptor); when it calls read(fd, ...), the kernel checks the capability. This is the same concept as Hydra's capabilities, just applied to files rather than all objects. If you extended xv6 to use capabilities for all resources (memory segments, devices, IPC channels), you would have a system like Hydra or seL4.

22.10 Other Influential Operating Systems

Beyond the systems already discussed, many other operating systems have influenced the field. This section covers several that made important contributions.

MS-DOS (Section 22.6) brought computing to the masses but was technologically limited. Windows 9x (95, 98, ME) bridged the gap between DOS and NT, introducing 32-bit computing and preemptive multitasking to consumers, but retained DOS compatibility that caused instability. The transition to Windows NT (XP, 2001) finally gave consumers a modern, protected OS.

CP/M (Section 22.6) established conventions for personal computer OS that persist today. Apple DOS and ProDOS were Apple II operating systems that introduced similar concepts for Apple's early computers.

OS/360 (1964, IBM) was the operating system for the IBM System/360, a family of mainframe computers. OS/360 introduced job scheduling, memory management, and I/O management for large-scale computing. OS/360's successor, MVS (Multiple Virtual Storage, 1974), introduced virtual storage (virtual memory) for mainframes. IBM's mainframe OS lineage continues today with z/OS, which runs on IBM Z mainframes and supports features like WLM (Workload Manager), RRS (Resource Recovery Services), and massive transaction processing.

ℹ️ Other Influential Systems
  • OS/360 / MVS / z/OS (IBM): mainframe OS, job scheduling, virtual storage
  • VMS (DEC VAX, 1977): influenced Windows NT (Dave Cutler)
  • TOPS-10 / TOPS-20 (DEC): time-sharing for PDP-10
  • AmigaOS (1985): preemptive multitasking for home computers
  • BeOS (1995): media-optimized, later became Haiku
  • Palm OS (1996): early PDA OS
  • Symbian (1998): smartphone OS (Nokia)
  • QNX (1980s): real-time microkernel (used in cars, medical)
  • VxWorks (1980s): real-time OS (Mars rovers, aerospace)
  • FreeBSD / NetBSD / OpenBSD: open-source BSD Unix
  • Android (2008): Linux-based mobile OS
  • iOS (2007): macOS-based mobile OS
  • Chrome OS (2011): Linux-based, web-focused
  • Fuchsia (2016): Google's new microkernel OS (Zircon)

VMS (Virtual Memory System, 1977, Digital Equipment Corporation) was the OS for the VAX minicomputer. VMS was designed by Dave Cutler, who later designed Windows NT. Many NT features trace to VMS: the layered architecture, the object manager, the IRP-based I/O system, and the security model. The name "NT" (New Technology) reflects Cutler's intent to bring VMS's design principles to a new platform. VMS was known for its stability and security and was widely used in enterprise environments. The VMS influence on Windows is a direct lineage: if you understand Windows NT, you understand much of VMS.

QNX (1980s, QNX Software Systems) is a real-time microkernel operating system used in embedded and safety-critical systems: automotive infotainment, medical devices, industrial control. QNX uses a microkernel architecture (like Mach) but is optimized for real-time performance (deterministic latency). QNX is POSIX-compliant, so Unix software can be ported. QNX demonstrates that microkernels can be practical for production systems, especially where reliability and real-time behavior are critical. QNX is used in millions of cars (BMW, Ford, GM) and medical devices.

BSD (Berkeley Software Distribution) is a family of Unix-like operating systems descended from BSD, the Berkeley version of Unix. FreeBSD is known for performance and is used by Netflix, WhatsApp, and Sony (PlayStation). NetBSD is designed for portability ("of course it runs NetBSD") and runs on dozens of architectures. OpenBSD is focused on security and correctness, with a famous "only two remote holes in the default install, in a heck of a long time" track record. BSD introduced or refined many features now standard in Linux: virtual memory, TCP/IP networking, sockets, vi, csh, and the /dev/fd filesystem. macOS's user space is largely derived from FreeBSD.

⚠️ The BSD/Linux Split

BSD and Linux are both Unix-like, but they have different lineages:

  • BSD descends from the original AT&T Unix via Berkeley. BSD was a complete OS (kernel + user space) until the AT&T lawsuit (1992–1994), which forced BSD to replace AT&T code. The resulting 4.4BSD-Lite was the basis for FreeBSD, NetBSD, and OpenBSD.
  • Linux was written from scratch by Linus Torvalds in 1991, with no AT&T code. Linux is just a kernel; the user space comes from GNU and other sources.

Both are POSIX-compliant and can run the same software, but they have different kernels, different development models, and different communities. macOS (XNU + BSD user space) is more closely related to BSD; Linux is its own lineage. The legal uncertainty around BSD in the early 1990s (the AT&T lawsuit) was one reason Linux gained traction: Linux had no such legal cloud.

Android (2008, Google) is a mobile operating system based on the Linux kernel. Android adds a runtime (ART, Android Runtime) that executes Dalvik bytecode, a application framework (Activity, Service, Content Provider, Broadcast Receiver), and a permission system (apps request permissions at install or runtime). Android's security model is application sandboxing: each app runs in its own sandbox (separate UID, separate file system namespace), and apps can only access resources they have permission for. This is a modern application of the principle of least privilege and capability-based access control.

iOS (2007, Apple) is the operating system for iPhone and iPad. iOS is based on macOS (Darwin/XNU kernel) but is heavily modified for mobile: no swap (to preserve flash storage), aggressive memory management (apps are killed when memory is low), and a strict sandboxing model (apps cannot access other apps' data). iOS introduced the app store model (curated, signed apps) and permission-based access to device features (camera, location, contacts). iOS and Android represent the modern mobile OS, where security and power efficiency are paramount.

💡 The Big Picture: OS Evolution

Operating systems have evolved from no OS (1940s) through batch (1950s), multiprogramming (1960s), time-sharing (1970s), personal computing (1980s), GUIs (1990s), mobile (2000s), and cloud (2010s). Throughout this evolution, certain concepts have persisted and been refined:

  • Processes and threads: from single job to multiprogramming to threads to containers
  • Memory management: from no protection to base/limit to paging to virtual memory to demand paging
  • File systems: from flat to hierarchical to journaling to distributed
  • Protection and security: from no protection to privilege levels to ACLs to capabilities to sandboxing
  • I/O: from polling to interrupts to DMA to async I/O

xv6 implements all of these concepts in a minimal form. When you study xv6, you're studying the distilled essence of 80 years of OS evolution. Every concept in xv6—page tables, file descriptors, system calls, scheduling—has a history that traces back to Atlas, Multics, Unix, and beyond. Understanding xv6 gives you the foundation to understand any operating system, past or future.
