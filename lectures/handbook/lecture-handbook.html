1. Operating System Overview

An operating system is, at its core, a special program that sits between user applications and the hardware. Think of it as a building manager: the building has desks, rooms, and a filing cabinet (the hardware), and the manager ensures everyone gets fair access without trampling each other. The OS does two fundamental jobs — it is a resource manager (allocating CPU time, memory, and devices) and a protector (keeping programs isolated from one another). Every design decision in an OS traces back to these two roles.

The most important boundary in the entire system is the system call interface — the thin line between user programs and the kernel. Everything above that line is unprivileged (user mode); everything below it is privileged (kernel mode). The only way to cross the boundary is through a system call, which is a controlled, hardware-enforced transition. A user program cannot simply jump into kernel memory or touch a device register — the CPU will trap and the kernel will intervene.

# USER: shell | compiler | database | your app # SVC: System Call Interface (open, read, write, fork, exec, ...) # KERNEL: File system | Processes | Memory | Network # HW: CPU | RAM | Disk | NIC

The Unix philosophy shapes how we interact with the OS. Three ideas are central: (1) everything is a file — disks, terminals, and network sockets are all accessed through file descriptors with read() and write(); (2) pipes connect programs so the output of one feeds the input of another; (3) the process model is built on fork(), exec(), and wait() — you create a copy of a process, replace its image with a new program, and then wait for it to finish. This simple model is remarkably powerful.

🔑 Key Idea

The OS provides abstraction (files, processes, sockets), isolation (each process has its own address space), and resource management (fair sharing of CPU and memory). The system call interface is the contract between user and kernel.

Throughout this course we study xv6, a teaching operating system developed at MIT. It is roughly 10,000 lines of C and assembly — small enough to read in a weekend, but real enough to boot on real hardware (or QEMU) and run real programs. Every concept we discuss has a concrete implementation in xv6 that you can read, modify, and break. When you see a reference like proc.c or trap.c in these notes, open the file and follow along.

2. RISC-V ISA Basics

RISC-V is a Reduced Instruction Set Computer architecture. The "reduced" part means the instructions are simple, fixed-length (32 bits each), and designed to execute in a single pipeline stage. This contrasts with CISC designs like x86, where instructions vary in length and complexity. The RISC philosophy is: keep the hardware simple, let the compiler do the heavy lifting, and make pipelining predictable. RISC-V is clean, modern, and open — which is why we use it as our teaching ISA.

The CPU has 32 general-purpose registers, named x0 through x31. Register x0 is special — it always reads as zero, and writes to it are discarded. This is a clever trick: many instructions need a zero operand, and having a dedicated zero register avoids needing a separate instruction encoding. The registers also have ABI names that hint at their conventional use:

RegisterABI NameRole
x0zeroHard-wired zero
x1raReturn address
x2spStack pointer
x10–x11a0–a1Function arguments / return value
x12–x17a2–a7Function arguments
x8s0/fpFrame pointer / callee-saved

RISC-V defines several instruction formats — the way bits are laid out inside the 32-bit word. The main formats are R, I, S, B, U, and J. Each format encodes an opcode, some register operands, and possibly an immediate value. The key insight is that the opcode always lives in the lowest 7 bits (bits 0–6), so the CPU can decode the instruction type quickly. The immediate field is scattered across the upper bits in a way that differs per format — this is a trade-off for keeping the register fields in consistent positions.

🔑 Key Idea

All RISC-V instructions are 32 bits. The low 7 bits are always the opcode. Immediate values are sign-extended — the highest bit of the immediate field is replicated to fill the upper bits of the 64-bit register. Always check whether an immediate is treated as signed or unsigned.

Immediate encoding deserves special attention. In the I-type format, the immediate is 12 bits and occupies bits 31–20. In S-type and B-type, the immediate is split across two non-contiguous fields — this was done so that register source fields stay in the same bit positions across formats, simplifying decode logic. When you write addi x5, x6, -1, the assembler encodes -1 as the 12-bit two's complement value 0xFFF, and the CPU sign-extends it to 0xFFFFFFFFFFFFFFFF before adding. Understanding sign extension is essential for reading assembly correctly.

3. RISC-V Assembly Programming

RISC-V assembly is the language we use to talk directly to the CPU. The arithmetic and logic instructions are straightforward: add, sub, and, or, xor, sll (shift left logical), srl (shift right logical), and sra (shift right arithmetic). Each takes three register operands: two sources and one destination. For immediate operands, append an i: addi, andi, ori, etc.

# Arithmetic examples add a0, a1, a2 # a0 = a1 + a2 sub a0, a1, a2 # a0 = a1 - a2 addi sp, sp, -16 # sp = sp - 16 (allocate stack frame) li a0, 42 # a0 = 42 (pseudo-instruction)

Load and store instructions move data between registers and memory. RISC-V is a load/store architecture — arithmetic only operates on registers, never directly on memory. The address is formed by a base register plus a signed offset. Loads come in sizes: lb (byte), lh (halfword), lw (word), ld (doubleword), and unsigned variants lbu, lhu that zero-extend instead of sign-extend. Stores are sb, sh, sw, sd.

ld a0, 8(sp) # a0 = *(sp + 8) (load 64-bit) sd a0, 8(sp) # *(sp + 8) = a0 (store 64-bit) lb a1, 0(a0) # a1 = *(a0) sign-extended byte lbu a2, 0(a0) # a2 = *(a0) zero-extended byte

Branches implement control flow. The conditional branches compare two registers and jump if the condition holds: beq (equal), bne (not equal), blt (less than, signed), bge (greater or equal, signed), and the unsigned variants bltu, bgeu. Unconditional jumps use j (pseudo for jal x0, offset) and jr (pseudo for jalr x0, 0(rs)). Note that branches use 12-bit offsets measured in bytes, and the range is limited (±4 KiB). For longer jumps, the assembler inserts a pseudo-instruction sequence.

Function calls rely on the ra (return address) register. The jal instruction jumps and links — it saves the address of the next instruction into ra, so the callee can return with ret (which is jalr x0, 0(ra)). The calling convention specifies which registers the caller can assume survive a call (callee-saved: ra, sp, s0–s11) and which the callee may freely clobber (caller-saved: a0–a7, t0–t6). Arguments are passed in a0–a7, and the return value comes back in a0 (and a1 for a 128-bit return).

Study Tip

When reading assembly, always track sp and ra. The stack grows downward. A function prologue typically does addi sp, sp, -N followed by sd ra, 0(sp). The epilogue reverses this: ld ra, 0(sp) then addi sp, sp, N then ret.

4. xv6 Kernel Programming

xv6 is structured as a traditional monolithic kernel. The source tree is small and readable: kernel/ contains the kernel C sources and assembly, user/ contains user programs and the user library, and Makefile ties it together. Key kernel files you will return to again and again include proc.c (process management), vm.c (virtual memory), trap.c (trap handling), syscall.c (system call dispatch), spinlock.c (locking), and file.c (file descriptors). The build produces kernel.bin, which is loaded by QEMU.

The kernel/user boundary in xv6 is enforced by RISC-V privilege modes. User code runs in U-mode; the kernel runs in S-mode. The boundary is crossed only via the ecall instruction, which traps into S-mode at the address in stvec. The kernel never trusts pointers passed by user programs — it validates every address against the process's page table. This is the heart of isolation: a buggy or malicious user program cannot corrupt kernel data because the hardware refuses the access.

🔑 Key Idea

Adding a system call to xv6 is a rite of passage. The steps are: (1) add a prototype to user/user.h, (2) add an entry to user/usys.pl (which generates the ecall stub), (3) add an entry to kernel/syscall.h and the dispatch table in kernel/syscall.c, (4) implement the body in kernel/sys_*.c. Five files, one feature.

xv6 has strong code conventions that you must follow. Pointers to structures are written p->field, never (*p).field. Functions that manipulate a shared structure acquire its lock first — for example, code touching struct proc fields holds p->lock. The rule is: if you read or write a field that another CPU might touch, hold the lock. Comments are terse but meaningful; a comment like // must hold p->lock is a contract, not a suggestion.

// Example: a typical xv6 system call body uint64 sys_getpid(void) { struct proc *p = myproc(); return p->pid; // myproc() holds p->lock internally }
⚠️ Locking Discipline

xv6 enforces a strict lock ordering to prevent deadlock. If function A acquires lock1 then lock2, no other code path may acquire them in the opposite order. When you add a new lock, document its position in the ordering in a comment. The classic trap: calling a function that sleeps while holding a spinlock — this is forbidden because the sleep may never wake up if the waker needs that same lock.

The Makefile is worth reading. It compiles kernel and user code separately, links the kernel at a high physical address (so it can run in place), and sets up the entry point in entry.S. The $U/_ and $K/ prefixes in the Makefile distinguish user and kernel objects. When you add a new user program, you add its name to the UPROGS list; when you add a kernel source file, you add it to the relevant variable. Build with make qemu and you get a booting system.

5. Process Management

A process is the OS's unit of execution. In xv6, each process is represented by a struct proc (defined in proc.h). This structure — sometimes called a PCB (process control block) — holds everything the kernel needs to manage the process: the page table, the trapframe (saved registers), the open file table, the kernel stack, the process state, and the PID. When you think "process," think of this struct: it is the process.

// Simplified struct proc (kernel/proc.h) struct proc { enum procstate state; // UNUSED, USED, SLEEPING, RUNNABLE, RUNNING, ZOMBIE int pid; // Process ID struct trapframe *trapframe; // Saved user registers struct context context; // Saved kernel registers for swtch pagetable_t pagetable; // User page table uint64 sz; // Size of process memory (bytes) struct file *ofile[NOFILE]; // Open files struct inode *cwd; // Current directory char name[16]; // Process name (for debugging) };

A process moves through a lifecycle of states. It begins as UNUSED, becomes USED when allocated, then RUNNABLE when ready to run. The scheduler picks a runnable process and marks it RUNNING. If it blocks on I/O or a lock, it becomes SLEEPING. When it exits, it becomes ZOMBIE until the parent calls wait() to reap it. The transition from RUNNING to RUNNABLE (a preemption) happens on a timer interrupt; the transition from RUNNING to SLEEPING happens when the process calls sleep().

fork() creates a new process that is a copy of the caller. In xv6, fork() (in proc.c) allocates a new struct proc, copies the parent's user memory (page by page), copies the file descriptor table (with reference counts incremented), and sets the child's state to RUNNABLE. The child returns from fork() with a return value of 0; the parent returns with the child's PID. This single return-value trick is how the two processes tell themselves apart.

exec() replaces the current process image with a new program loaded from a file. The process keeps its PID, open files, and current directory — but its memory is discarded and replaced with the new program's code, data, and stack. This is the second half of the Unix process-creation pattern: fork() then exec(). The shell uses this constantly — for every command you type, it forks, the child calls exec() on the command, and the parent wait()s.

🔑 Key Idea

fork() + exec() + wait() is the Unix trinity. fork duplicates, exec transforms, wait reaps. Separating creation from transformation lets the shell insert redirection and pipes between them (via dup2 and pipe before the exec).

The context switch is implemented in swtch.S. When the scheduler decides to switch from process A to process B, it calls swtch(), which saves A's callee-saved registers into A->context and loads B's from B->context. Crucially, swtch only switches the kernel context — the user registers are already saved in the trapframe when the process trapped into the kernel. The scheduler itself runs on a dedicated stack and is not a process; it is a function that loops forever, picking runnable processes.

6. Memory Management

Memory management is about giving each process the illusion of a large, private, contiguous address space — the virtual address space. The hardware, via the memory management unit (MMU), translates every virtual address to a physical address using a page table. This translation is what makes isolation possible: process A's virtual address 0x1000 maps to a different physical page than process B's 0x1000, so they cannot see each other's memory. The kernel itself also has a page table (the kernel page table), and each process has its own user page table.

RISC-V uses the Sv39 paging scheme on systems we study. Sv39 means 39-bit virtual addresses, broken into a three-level page table: level 2 (root), level 1, and level 0. Each page table is 4 KiB and holds 512 entries (PTEs, page table entries). Each PTE is 64 bits and contains a 44-bit physical page number (PPN) plus permission flags. The translation walks the tree: the root PTE points to a level-1 table, which points to a level-0 table, whose PTE points to the actual 4 KiB physical page.

LevelIndex bitsEntries per tablePoints to
Level 2 (root)bits 30–38512Level 1 table
Level 1bits 21–29512Level 0 table
Level 0bits 12–205124 KiB physical page
Offsetbits 0–11—Byte within page

Each PTE carries permission flags: V (valid), R (readable), W (writable), X (executable), U (user-accessible), and A/D (accessed/dirty bits). If a user program tries to execute a non-X page, or write a non-W page, or access a non-U page, the MMU raises a page fault — which is how the kernel enforces protection. The kernel's own pages have U=0, so user code cannot touch them even if it guesses the address.

🔑 Key Idea

A page table is a tree of PTEs. Each level narrows the address by 9 bits. The leaf PTE gives the physical page base; the low 12 bits (offset) pass through unchanged. This is why page size is 4 KiB — 12 bits of offset.

The TLB (translation lookaside buffer) caches recent virtual-to-physical translations so the CPU does not walk the page table on every memory access. When the kernel switches page tables (on a context switch), it must invalidate the TLB with sfence.vma — otherwise stale translations from the previous process would leak. In xv6, the sfence.vma is issued in kvminithart and during process switches. The TLB is the reason page table switches are not free.

In xv6, the key memory-management functions live in vm.c. proc_pagetable() allocates a fresh page table for a process. uvmalloc() grows a process's memory by mapping new pages. uvmcopy() copies a process's pages (used by fork()). copyin() / copyout() safely copy data between user and kernel space, validating addresses against the page table. mappages() installs mappings by walking the page table and creating intermediate levels as needed. Reading vm.c end to end is the single best way to understand paging.

⚠️ Common Pitfall

Never dereference a user pointer directly in the kernel. Always use copyin() / copyout() or walkaddr(). A raw dereference might work by accident (if the kernel page table happens to map that address) but is a security hole — and on RISC-V the kernel page table does not include user mappings by default, so it will usually fault.

7. Traps and System Calls

A trap is a controlled transfer of execution from user mode to kernel mode. The word "controlled" is key: the user program does not choose where in the kernel to jump. The CPU always jumps to the address in the stvec register, which the kernel set up at boot. Three things cause a trap: a system call (the user runs ecall), an exception (the CPU detects a fault like a page fault or illegal instruction), or an interrupt (hardware signals an event like a timer tick). All three use the same trap mechanism; the kernel distinguishes them by reading scause.

🔑 Key Idea

One mechanism, three triggers. Syscalls, exceptions, and interrupts all enter the kernel through the same path. The scause register tells the kernel why. This unification is elegant — the kernel has a single trap entry point that handles everything.

On a trap, the hardware does several things atomically: it saves the current program counter into sepc (so the kernel can resume), saves the current privilege mode, switches to S-mode, disables interrupts, and jumps to stvec. The kernel must then save all user registers (since it will use them), figure out the cause from scause, and dispatch accordingly. On return, the kernel restores registers, sets sepc to the instruction after ecall, and executes sret to drop back to U-mode.

In xv6, the trap path goes through the trampoline — a special page mapped at the same virtual address in both user and kernel page tables. This is necessary because at the moment of the trap, the MMU is still using the user page table, so the trap handler must be reachable via that mapping. The trampoline page contains uservec (the entry, in trampoline.S), which saves user registers into the process's trapframe, switches to the kernel page table, and jumps to usertrap() in C. On return, usertrapret() sets up the return and jumps to userret, which restores registers and executes sret.

// Simplified usertrap() dispatch (kernel/trap.c) void usertrap(void) { int which = (r_scause() & 0x8000000000000000) ? 1 : 0; if (r_scause() == 8) { // syscall p->trapframe->epc += 4; // skip ecall instruction syscall(); // dispatch via table } else if (which) { devintr(); // device interrupt } else { // exception: kill the process p->killed = 1; } }

System call dispatch uses a table. Each syscall has a number (defined in syscall.h), and syscall.c holds an array of function pointers indexed by that number. The user stub (generated from usys.pl) loads the syscall number into a7 and arguments into a0–a5, then runs ecall. In the kernel, argint(), argaddr(), and argfd() fetch the arguments from the saved trapframe. The return value goes into a0 in the trapframe, which the user sees when ecall returns.

⚠️ Two Stacks

Every process has two stacks: a user stack (in user memory) and a kernel stack (allocated separately, in proc.h). When a trap occurs, the kernel switches to the kernel stack — saved in sscratch during uservec. The kernel stack is per-process so that each process has a private stack even when in the kernel. The trampoline uses sscratch to swap sp between user and kernel stacks.

The usys.pl file is a Perl script that generates assembly stubs. Each entry like entry("write"); produces a small function that loads the syscall number and traps. This is why user programs call write(fd, buf, n) as a normal C function — the library hides the ecall. Understanding this pipeline — from C call to stub to ecall to trampoline to usertrap to syscall table — is the core of understanding how an OS actually works.

8. Interrupts and Drivers

It is important to distinguish three terms that students often conflate. A trap is the general term for any synchronous or asynchronous transfer to the kernel. An exception is a synchronous trap caused by the current instruction (page fault, divide-by-zero, illegal instruction). An interrupt is an asynchronous trap caused by an external event (timer, disk I/O completion, keyboard press) — it is not tied to any particular instruction. The hardware handles them through the same stvec path, but the scause register has its high bit set for interrupts, so the kernel can tell them apart.

TermTriggerSynchronous?Example
System callecall instructionYeswrite()
ExceptionInstruction faultYesPage fault, illegal opcode
InterruptExternal hardware signalNoTimer tick, UART RX

On RISC-V, external interrupts (from devices) are routed through the PLIC (Platform-Level Interrupt Controller). The PLIC collects interrupt signals from all devices, prioritizes them, and delivers one at a time to the CPU. The kernel acknowledges the interrupt by reading a PLIC register (which also tells it which device caused it), services the device, then completes the interrupt by writing to the PLIC's "claim" register. The timer interrupt is special — it comes from a separate RISC-V timer device and is handled via timerintr in trap.c, which schedules the next tick and may yield to the scheduler.

🔑 Key Idea

Device drivers split work into a top half (the interrupt handler, which runs with interrupts disabled and must be fast) and a bottom half (deferred work that runs later, with interrupts enabled). The top half acknowledges the hardware and queues data; the bottom half does the heavy processing. This keeps interrupt latency low.

The console driver in xv6 is the canonical example. It spans two files: uart.c (the low-level UART hardware driver) and console.c (the higher-level line discipline). When a key is pressed, the UART raises an interrupt; uartintr() reads the byte from the UART data register and pushes it into a buffer. consoleintr() then processes the byte — handling special keys like backspace and Ctrl-P, and waking any process blocked in consoleread(). On the output side, consolewrite() pushes bytes to the UART, polling the transmit-ready bit before each byte.

// Simplified console input path (kernel/console.c) void consoleintr(int c) { acquire(&cons.lock); if (c == BACKSPACE) { ... } // handle edit else { cons.buf[cons.wpos++] = c; } // buffer char wakeup(&cons.rpos); // wake reader release(&cons.lock); }

Devices are exposed to user programs as device files. In xv6, the console is file descriptor 0 (stdin), 1 (stdout), 2 (stderr) — opened automatically by the shell. The write() system call on fd 1 ends up in consolewrite() via the file table dispatch. This is the Unix "everything is a file" idea in action: the same read and write syscalls work on disk files, pipes, and devices, because the file table abstracts the underlying object behind a uniform interface.

Study Tip

Read uart.c and console.c side by side. Trace a keystroke from the UART register, through the interrupt, into the buffer, and out to a read() call in the shell. That round trip is the complete picture of how I/O works in a real OS.

9. Concurrency and Locks

When two CPUs (or two threads) access the same data, you get a race condition: the result depends on the timing of the accesses. The classic example is a shared counter: counter++ is not atomic — it is a load, an add, and a store. If two CPUs do this simultaneously, one increment can be lost. The solution is mutual exclusion: ensure only one CPU at a time can execute a critical section. The tool for this is a lock.

// Race condition: two CPUs, one counter counter = counter + 1; // CPU A loads 5, CPU B loads 5, both store 6 — one increment lost!

A spinlock is the simplest lock. It has two states: locked and unlocked. To acquire, a CPU atomically tests-and-sets the lock word; if it was already locked, the CPU spins (busy-waits) in a loop until it becomes free. On RISC-V, the atomic operation is amoswap (atomic swap), or the load-reserved / store-conditional pair (lr.w/sc.w). The xv6 implementation lives in spinlock.c and uses amoswap via inline assembly in __sync_lock_test_and_set.

// Simplified xv6 spinlock acquire (kernel/spinlock.c) void acquire(struct spinlock *lk) { push_off(); // disable interrupts on this CPU while (__sync_lock_test_and_set(&lk->locked, 1) != 0) ; // spin until we get it __sync_synchronize(); // memory barrier }
🔑 Key Idea

A spinlock disables interrupts on the acquiring CPU (via push_off). Why? Because if an interrupt fires while holding a spinlock, and the interrupt handler tries to acquire the same lock, the CPU deadlocks with itself. Disabling interrupts during a critical section prevents this self-deadlock on a single CPU.

Lock ordering is the rule that prevents deadlock. If code path A acquires L1 then L2, no other path may acquire L2 then L1 — that would be a circular wait, the classic deadlock. xv6 documents a global lock ordering in comments. When you add a lock, you must place it in this ordering. The general rule: acquire locks in a consistent global order, and release them in reverse order. If you ever see a hang where all CPUs are stuck, suspect a lock-ordering violation.

⚠️ Never Sleep With a Spinlock

A spinlock is held for a short, bounded time — never across a sleep() or any operation that might block indefinitely. If you need to wait for a condition (e.g., "data available in the buffer"), use a sleep lock instead. A sleep lock releases the CPU while waiting, so other processes can run and eventually wake you.

A sleep lock (struct sleeplock in xv6) is built on top of a spinlock and the sleep()/wakeup() primitives. To acquire, you take an internal spinlock, check a flag, and if the lock is held, call sleep() — which atomically releases the spinlock and puts the process to sleep. When the holder releases, it calls wakeup() on the sleep channel, and a waiter wakes and retries. Sleep locks are used for long-held resources like file system buffers, where spinning would waste CPU for milliseconds.

The underlying atomic instructions deserve a closer look. amoswap rd, rs2, (rs1) atomically reads the value at (rs1) into rd and writes rs2 to (rs1), all as one indivisible operation. The lr/sc pair is more flexible: lr loads and reserves the address; sc stores only if the reservation is still valid (no other write to that address occurred). This lets you build more complex atomic operations like compare-and-swap. Both rely on the memory system guaranteeing atomicity at the cache-line level.

10. File Systems

The file system provides the abstraction of files (named byte streams) and directories (named collections of files). In xv6, the file system is a simple but complete implementation that lives on a virtual disk image. It supports files, directories, hard links, and a journaling log for crash recovery. Studying it teaches you how a real file system works, from the on-disk layout up to the system call interface.

The xv6 disk is divided into regions, laid out in a fixed order. The superblock (recorded in struct superblock in mkfs/mkfs.c and fs.h) describes the layout: number of blocks, number of inodes, and the start of each region. The layout is: boot block, super block, log blocks, inode blocks, bitmap block, and data blocks.

RegionPurpose
Boot blockFirst block; reserved for bootloader
Super blockFile system parameters (sizes, offsets)
Log blocksJournal for crash recovery
Inode blocksOn-disk inodes (struct dinode)
Bitmap blockOne bit per data block (free/used)
Data blocksFile and directory contents

An inode is the on-disk record describing a file. It holds the file's type (file/directory/device), size, link count, and an array of 12 direct block pointers plus one single-indirect and one double-indirect pointer. The inode does not store the file name — names live in directory entries, which map names to inode numbers. This separation is why hard links work: multiple directory entries can point to the same inode, and the file persists until the link count reaches zero.

🔑 Key Idea

An inode is the file; the name is just a directory entry pointing to it. This is why unlink removes a name but the file's data survives until the last link is gone. The link count in the inode tracks how many names point to it.

The kernel keeps an inode cache (itable in file.c / fs.c) to avoid reading inodes from disk on every operation. When a process opens a file, the kernel looks up the inode in the cache (reading from disk if needed), increments its reference count, and returns a pointer. The cache is small — it holds only recently used inodes — and is protected by a single lock. Inodes in the cache have an in-memory ref count (how many file descriptors reference them) separate from the on-disk nlink count (how many directory entries point to them).

File descriptors are the user's handle to an open file. Each process has a table of open file descriptors (the ofile array in struct proc). A descriptor points to a struct file (in file.c), which tracks the underlying inode (or pipe, or device), the current offset, and a reference count. fork() copies the descriptor table (sharing the struct file objects, incrementing their refs); exec() preserves the table. This sharing is how shell pipes work: the child inherits the parent's descriptors, including the pipe ends.

// Simplified struct file (kernel/file.h) struct file { enum { FD_NONE, FD_PIPE, FD_INODE, FD_DEVICE } type; int ref; // reference count int readable; int writable; struct pipe *pipe; // if type == FD_PIPE struct inode *ip; // if type == FD_INODE uint off; // current offset (for inode files) };

The log layer provides crash recovery. Before modifying any file system structure, the kernel writes the intended changes to the log area on disk. Once all changes for a transaction are in the log, it writes a "commit" record. Only then does it apply the changes to their final on-disk locations and clear the log. If the system crashes mid-transaction, the recovery code (in recover_from_log()) sees an incomplete log and discards it — the file system remains consistent. If it crashes after commit but before install, recovery replays the log. This is write-ahead logging, the same principle used by enterprise databases.

⚠️ Log Discipline

xv6's log has a fixed size. A single system call must not write more blocks than the log can hold, or it will deadlock. This is why write() to a file breaks large writes into chunks that fit in the log. The begin_op() / end_op() calls in log.c delimit transactions; log_write() records the blocks to be written.

Path name resolution turns a string like /home/alice/file.txt into an inode. The function namei() (in fs.c) walks the path component by component: it starts at the root (or the current directory for relative paths), reads the directory inode, scans its entries for the next component, gets that entry's inode number, and repeats. Each step involves inode lookups (cached in the itable) and directory reads. Symlinks are not supported in base xv6, which keeps the resolver simple.

11. Page Faults and Advanced VM

A page fault is an exception raised by the MMU when it cannot translate a virtual address — either because the PTE is invalid, or because the access violates the PTE's permission bits. There are three kinds, distinguished by the access that caused them: a load page fault (a read, scause = 5), a store page fault (a write, scause = 7), and an instruction page fault (an instruction fetch, scause = 12). The kernel's page fault handler reads stval to get the faulting address and scause to get the type, then decides what to do.

scauseTypeTrigger
5Load page faultRead from unmapped/protected page
7Store page faultWrite to read-only/unmapped page
12Instruction page faultExecute from non-executable page

In base xv6, a page fault usually means the process did something wrong — accessed an invalid address, or wrote to a read-only page — and the kernel kills the process. But page faults are also a powerful mechanism: they let the kernel implement features lazily, only doing work when it is actually needed. This is the foundation of several advanced virtual memory techniques.

🔑 Key Idea

A page fault is a trap, just like a system call. The kernel gets control, sees the faulting address in stval, and can choose to fix up the mapping (map a new page, copy data, change permissions) and resume the process — all transparently. This turns the MMU into a general-purpose mechanism for demand-driven memory management.

Copy-on-write (COW) fork is the classic optimization. In standard fork(), the kernel copies every page of the parent into the child — expensive if the child immediately calls exec() and discards it all. In COW fork, the kernel instead maps the child's pages to the same physical pages as the parent, but marks them read-only in both page tables. When either process writes, a store page fault occurs. The handler then allocates a fresh page, copies the content, maps it writable, and resumes. Only pages that are actually written get copied. To implement this, you need a reference count per physical page (so you know when it is safe to reuse) and careful handling of the "already shared" case.

// COW fault handler (conceptual) void cow_fault(struct proc *p, uint64 va) { pte_t *pte = walk(p->pagetable, va, 0); uint64 pa = PTE2PA(*pte); if (kref_get(pa) == 1) { *pte |= PTE_W; // sole owner: just make writable } else { char *mem = kalloc(); memmove(mem, (char*)pa, PGSIZE); uvmunmap(p->pagetable, va, 1, 0); mappages(p->pagetable, va, PGSIZE, (uint64)mem, PTE_W|PTE_U); kref_dec(pa); // parent no longer owns this copy } }

Lazy allocation defers actually allocating memory until it is used. When a program calls sbrk() to grow its heap, the kernel just increases the process's sz field — it does not map any pages. When the program first touches the new memory, a page fault occurs, and the handler allocates a zeroed page and maps it. This makes sbrk() fast and avoids allocating memory the program never uses. The handler must check that the faulting address is within [old_sz, sz) and that it is a store fault (reading uninitialized memory should still fault, or be handled by mapping a zero page).

Demand paging extends lazy allocation to executables. When exec() loads a program, instead of reading the entire binary into memory, it maps the code and data segments as file-backed pages with the V bit clear (or with a special marker). When the program runs and touches a page, the fault handler reads the corresponding block from the executable file into a fresh page and maps it. This dramatically speeds up program startup — only the pages actually executed are loaded. If memory is tight, the kernel can evict clean file-backed pages (just drop them; they can be re-read) or write dirty pages to a swap area.

⚠️ Security Implications

Page faults have security consequences. Stack growth via faults can be abused: a program that recurses infinitely can consume all memory. Lazy allocation means malloc() succeeding does not guarantee the memory exists — the OOM killer may strike later. COW must clear the TLB entry for the parent when sharing, or the parent could write through a stale writable mapping. And page fault side channels (like Spectre/Meltdown variants) can leak data across privilege boundaries based on fault timing. Always validate the faulting address against the process's legitimate range.

mmap (memory-mapped files) lets a process map a file directly into its address space, so reads and writes to memory become file I/O. The kernel sets up a VMA (virtual memory area) describing the file, offset, and length, with pages initially unmapped. On first access, a page fault reads the file block into a page and maps it. Writes (if the mapping is writable) are flushed back to the file on munmap or msync. mmap unifies file I/O and memory: you can treat a file as an array, and the kernel handles the paging. This is how shared libraries and database engines achieve high performance — they let the page cache do the buffering, avoiding explicit read/write syscalls.

Study Tip

The xv6 labs on COW fork and lazy allocation are where these concepts become real. Start by instrumenting the page fault handler in trap.c to print stval and scause on every fault. Then implement COW by adding a reference count to kalloc.c and handling store faults in usertrap(). The hardest part is getting the reference counting right — off-by-one errors cause use-after-free bugs that manifest far from the cause.
