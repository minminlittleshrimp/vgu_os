1. What Is an Operating System?

An operating system is the most fundamental piece of software on a computer. It sits between the hardware and all other software, managing every resource the computer has: the CPU, memory, storage, and all input/output devices. Without an OS, a modern computer is just a pile of silicon that does nothing useful. The OS turns raw hardware into a usable machine.

Think of the OS as the manager of a busy restaurant. The hardware (CPU, memory, disks) is the kitchen. The applications (your web browser, text editor, games) are the customers placing orders. The OS is the head chef: it decides which order gets cooked first, which ingredients go to which station, and makes sure no customer starves while another hogs all the resources. It also acts as a protector — one misbehaving customer (a crashing program) should not bring down the entire restaurant.

The OS plays three fundamental roles simultaneously:

  • Resource Manager: The CPU can only do one thing at a time per core. The OS time-shares the CPU among dozens of running programs so they all appear to run simultaneously. It allocates memory so programs don't overwrite each other. It manages disk space and I/O devices.
  • Protector: The OS enforces isolation between programs. A bug in your web browser should not corrupt your text editor's data. The OS uses hardware features (privileged mode, virtual memory, page tables) to build walls between processes.
  • Abstractor: The OS hides hardware complexity. Instead of making every program understand disk geometry, the OS presents a simple "file" abstraction. Instead of making programs manage raw memory addresses, it gives each program its own clean virtual address space starting at 0.
Key Idea

The operating system is a resource manager, protector, and abstractor. It turns raw, hostile hardware into a clean, safe, and usable virtual machine that application programs can easily work with.

A Brief History

Operating systems have evolved through several major eras, each driven by changing hardware capabilities and user needs:

EraPeriodKey IdeaExample
Batch Systems1950s–60sRun one job at a time, no interactionIBM OS/360
Multiprogramming1960s–70sKeep multiple jobs in memory; switch when one blocks on I/OIBM CTSS
Time-Sharing1970s–80sGive each user a time slice; interactive useUnix, Multics
Personal Computing1980s–90sOne user, one machine; GUIsMS-DOS, Windows, macOS
Modern / Mobile2000s–presentMulti-core, virtualization, containers, mobileLinux, iOS, Android

In the batch era, users submitted punch cards or magnetic tape jobs. The OS ran them one at a time. This was terribly inefficient — while one job waited for a slow I/O device (like reading a tape), the expensive CPU sat idle. Multiprogramming solved this by keeping several jobs in memory at once: when job A blocked on I/O, the OS immediately switched to job B. Time-sharing extended this idea to interactive use: many users at terminals, each getting a small slice of CPU time in rapid rotation, creating the illusion that each had their own machine. Unix, developed at Bell Labs in 1969, became the most influential time-sharing system and its design principles still guide OS design today.

Why This Matters for xv6

xv6, the teaching OS used in this course, is a direct descendant of Unix Sixth Edition (1976). It demonstrates time-sharing, multiprogramming, virtual memory, and a hierarchical file system — all in about 10,000 lines of C. When you study xv6, you are studying the same design principles that power Linux and macOS today.

2. OS Structures

An operating system is a large, complex program — but it is not a monolithic blob of code. Modern operating systems are organized into layers and components, each with a clear responsibility. Understanding this structure helps you navigate the codebase and understand how the pieces fit together.

The most important boundary in an OS is the kernel/user boundary. The CPU runs in one of two (or more) privilege levels:

  • Kernel mode (supervisor mode): Full access to all hardware. Can execute any instruction, access any memory, talk to any device. The OS kernel runs here.
  • User mode: Restricted. Cannot execute privileged instructions (like halting the CPU, modifying page tables, or accessing I/O ports directly). Application programs run here.

When a user program needs to do something privileged — read a file, send a network packet, allocate memory — it cannot do so directly. It must ask the kernel to do it on its behalf using a system call. The system call is the controlled gateway across the kernel/user boundary. The kernel checks the request, validates arguments, performs the operation, and returns the result to the user program.

Key Idea

The kernel/user boundary is the most important line in an OS. User programs run unprivileged and must use system calls to request privileged operations. This is what prevents a buggy or malicious program from crashing the system or accessing other programs' data.

Monolithic vs. Microkernel

There are two major architectural approaches to OS design, and they differ in how much code runs in kernel mode:

FeatureMonolithic KernelMicrokernel
What runs in kernel modeEverything: scheduler, file system, drivers, network stackOnly the essentials: IPC, scheduling, minimal memory management
Drivers and servicesInside the kernelAs user-space processes (servers)
PerformanceFast (no context switch for services)Slower (IPC overhead between user and kernel)
StabilityA buggy driver can crash the whole systemA buggy driver crashes only itself; kernel stays up
ExamplesLinux, xv6, most Unix systemsMINIX, QNX, L4

Linux is a monolithic kernel: the entire file system, network stack, and all device drivers run in kernel mode. This makes it fast (no context switches to access services) but means a bug in a device driver can crash the entire system. The microkernel approach moves as much as possible into user-space "server" processes, communicating via message passing. This is more robust — a crashed driver can simply be restarted — but the message-passing overhead can hurt performance. In practice, most production systems (Linux, Windows, macOS) are monolithic or hybrid, while microkernels dominate embedded and safety-critical systems.

The xv6 Architecture

xv6 is a monolithic kernel, like its ancestor Unix. Its source code is organized into clear layers:

# xv6 source layout (kernel/ directory): # # entry.S, start.c - Boot code (enters supervisor mode, sets up paging) # main.c - Kernel main(): initializes subsystems, starts first process # proc.c - Process table, context switch, fork/exec/wait # vm.c - Virtual memory, page tables, kernel/user address spaces # trap.c - Trap handler: syscalls, page faults, interrupts # syscall.c - System call dispatch table # sysfile.c - File-related syscalls (open, read, write, close) # file.c, fs.c - File system implementation (inodes, directories, blocks) # spinlock.c, sleeplock.c - Locking primitives # console.c, uart.c - Console and serial I/O drivers # virtio_disk.c - Virtio block device driver

The boot sequence is: the hardware loads xv6 into memory and jumps to entry.S, which sets up the stack and calls start.c. That code transitions from machine mode to supervisor mode, enables paging, and calls main(). The main() function initializes each subsystem in order — console, virtual memory, process table, traps, file system — and then creates the first user process (init) by calling userinit(). From that point on, the system is running user processes and responding to system calls and interrupts.

System Calls Are Not Function Calls

A system call looks like a function call in C (write(fd, buf, n)), but under the hood it executes a special ecall (RISC-V) or syscall (x86-64) instruction. This traps into the kernel, switches to a kernel stack, and runs kernel code. The overhead is much higher than a normal function call — often 1-10 microseconds vs. nanoseconds.

3. Processes and Process Control

A process is a program in execution. While a program is a passive entity — a file on disk containing code and data — a process is an active entity: it has a program counter (the next instruction to execute), a set of registers, a stack, and allocated resources. When you run ./a.out, the OS creates a process that runs the program a.out.

Think of a process as a person working in an office. The program is the job description (what to do). The process is the actual person sitting at the desk, actively working through the tasks. The desk is the process's memory (code, data, stack). The person's current position in the task list is the program counter. If the person takes a break and another person sits down to work, that's a context switch.

Process States

At any moment, a process is in one of several states. The OS moves processes between these states as they execute, block on I/O, or get scheduled:

StateMeaningWhen it happens
NewBeing createdJust forked, not yet ready
ReadyWaiting to run on a CPUIn the ready queue, waiting for scheduler
RunningExecuting on a CPUScheduler picked this process
Waiting (Blocked)Waiting for an eventBlocked on I/O, sleep, or a lock
TerminatedFinished executionCalled exit(); resources being reclaimed

The key transitions are: New → Ready (creation completes), Ready → Running (scheduler dispatches the process), Running → Ready (time slice expires, preemption), Running → Waiting (process blocks on I/O or a wait call), and Waiting → Ready (I/O completes, event occurs). A process never goes directly from Waiting to Running — it must go through the Ready queue first.

The Process Control Block (PCB)

To manage processes, the OS maintains a data structure for each one, called the Process Control Block (PCB) or process descriptor. In xv6, this is the struct proc defined in proc.h. The PCB contains everything the OS needs to know about a process:

// Simplified xv6 struct proc (kernel/proc.h) struct proc { enum procstate state; // NEW, READY, RUNNING, etc. int pid; // Process ID struct proc *parent; // Parent process void *chan; // Sleep channel (for sleep/wakeup) int killed; // Flag: has been killed? uint64 sz; // Size of process memory (bytes) pagetable_t pagetable; // User page table (virtual memory) struct trapframe *trapframe; // Saved registers on trap struct context context; // Saved registers for context switch struct file *ofile[NOFILE]; // Open files table struct inode *cwd; // Current working directory };
Key Idea

The PCB is the OS's record of a process. It contains the process's state, saved registers (so execution can resume), memory layout, open files, and more. A context switch is the act of saving one process's state into its PCB and loading another process's state from its PCB.

Context Switch

When the scheduler decides to switch from process A to process B, it performs a context switch. This involves: (1) saving all of process A's registers into A's PCB (specifically the context field), (2) loading process B's saved registers from B's PCB, and (3) jumping to the instruction after B's last save point. In xv6, the actual register save/restore is done in assembly (swtch in switch.S), while the scheduling decision is made in scheduler() in proc.c.

// Simplified xv6 context switch (kernel/proc.c) void swtch(struct context **old, struct context *new); static void scheduler(void) { struct proc *p; for (;;) { for (p = proc; p < &proc[NPROC]; p++) { if (p->state == RUNNABLE) { p->state = RUNNING; c->proc = p; // Save scheduler context, load p's context swtch(&c->context, p->context); // When p yields, we come back here c->proc = 0; } } } }

Process Creation: fork / exec / wait

Unix-like systems (including xv6) create and manage processes through three fundamental system calls:

  • fork(): Creates an exact copy of the calling process. The new process (child) gets a duplicate of the parent's memory, file descriptors, and state. The only difference: fork() returns the child's PID to the parent and 0 to the child. This single-return-value-differentiates-caller design is elegant and powerful.
  • exec(filename, argv): Replaces the current process's memory image with a new program loaded from a file. The process keeps its PID, open files, and environment, but its code and data are completely replaced. If exec succeeds, it never returns — the old program is gone.
  • wait(): Blocks the parent until a child process terminates, then returns the child's exit status. This lets parents clean up after children and retrieve their results.
// Typical Unix pattern: fork + exec + wait int pid = fork(); if (pid == 0) { // Child: replace image with /bin/ls exec("/bin/ls", argv); // Only reached if exec fails exit(1); } else { // Parent: wait for child to finish int status; wait(&status); printf("child exited with %d\n", status); }
Why fork + exec Instead of a Single create_process Call?

Separating fork and exec gives enormous flexibility. Between the two calls, the parent (or the child, before exec) can redirect file descriptors, set up pipes, change the working directory, or modify environment variables. This is how shells implement I/O redirection (ls > file.txt): fork, redirect stdout in the child, then exec.

4. Threads and Concurrency

A thread is a unit of execution within a process. While a process has its own memory space (code, data, heap), threads within the same process share that memory space. Each thread has its own program counter, registers, and stack, but all threads in a process can read and write the same global variables and heap data.

Think of a process as a house. The house has rooms (code, data, heap) that everyone in the house shares. Each thread is a person living in the house. Each person has their own private workspace (their stack and registers), but they all share the kitchen, living room, and storage (the heap and global data). If two people try to use the kitchen at the same time without coordination, you get a mess. That mess is a race condition.

Threads vs. Processes

PropertyProcessThread
MemoryEach has its own address spaceShared within the same process
Creation costExpensive (copy memory, page tables)Cheap (just a stack and registers)
Context switchExpensive (change page tables, flush TLB)Cheap (just save/restore registers)
CommunicationHard (pipes, shared memory, signals)Easy (shared variables)
IsolationStrong (one crash doesn't affect others)Weak (one thread's bug can corrupt shared data)

User Threads vs. Kernel Threads

There are two levels at which threads can be managed:

  • User-level threads: Managed entirely by a user-space library (e.g., POSIX pthread library). The kernel doesn't know they exist — it sees one process. Fast to create and switch, but if one thread blocks on a system call, all threads in the process block, because the kernel can't schedule the others.
  • Kernel-level threads: Managed by the OS kernel. Each thread is visible to the scheduler. If one thread blocks, the kernel can run another thread from the same process. Most modern systems (Linux, Windows) use kernel threads (or a hybrid) for this reason.
Key Idea

Threads share memory; processes don't. Sharing memory makes communication fast and easy, but introduces race conditions — bugs that occur when multiple threads access shared data concurrently and at least one modifies it, without proper synchronization.

Race Conditions

A race condition occurs when the outcome of a program depends on the timing of thread execution. Consider two threads both incrementing a shared counter counter++. In C, this single statement is actually three operations: (1) read counter from memory, (2) add 1, (3) write the result back. If thread A reads the value 5, and before it writes back 6, thread B also reads 5 and writes 6 — the counter ends up as 6 instead of 7. One increment is lost.

// Race condition: two threads incrementing a shared counter int counter = 0; void *thread_func(void *arg) { for (int i = 0; i < 1000000; i++) { counter++; // NOT atomic! Can lose increments } return NULL; } // If two threads run this, counter may end up < 2000000

Mutual Exclusion

The solution to race conditions is mutual exclusion: ensure that only one thread at a time can execute a critical section of code that accesses shared data. A lock (or mutex) is the primary tool for this. Before entering a critical section, a thread acquires the lock; after leaving, it releases the lock. If another thread tries to acquire a held lock, it blocks until the lock is released.

// Fixed: use a lock to protect the counter int counter = 0; pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER; void *thread_func(void *arg) { for (int i = 0; i < 1000000; i++) { pthread_mutex_lock(&lock); // enter critical section counter++; pthread_mutex_unlock(&lock); // leave critical section } return NULL; }
The Critical Section Problem

A critical section is code that accesses shared data that must not be accessed by more than one thread at a time. A correct solution must satisfy three conditions: (1) Mutual exclusion — at most one thread in the critical section at a time; (2) Progress — if no thread is in the section, a thread that wants to enter cannot be indefinitely postponed; (3) Bounded waiting — there's a limit on how many times other threads can enter before a waiting thread gets its turn.

5. CPU Scheduling

When multiple processes are ready to run but there is only one CPU (or fewer CPUs than ready processes), the OS must decide which process runs next. This decision is made by the scheduler, a core component of the OS. The quality of scheduling decisions directly affects system performance, responsiveness, and fairness.

The scheduler maintains a ready queue — a list of processes that are ready to run but waiting for a CPU. Each time the CPU becomes available (because the running process blocked, yielded, or used up its time slice), the scheduler picks the next process from the ready queue. The act of switching from one process to another is called a context switch, and the time a process runs before being switched out is called a CPU burst.

Preemptive vs. Non-Preemptive

  • Non-preemptive: Once a process gets the CPU, it keeps it until it voluntarily yields (blocks on I/O or calls a yield system call). Simple, but a CPU-bound process can monopolize the CPU and starve others.
  • Preemptive: The OS can forcibly take the CPU away from a running process (e.g., when a timer interrupt fires after a time slice). This is what modern time-sharing systems use — it ensures fairness and responsiveness.

Scheduling Algorithms

AlgorithmStrategyProsCons
FCFS (First-Come, First-Served)Run processes in arrival orderSimple, fairConvoy effect: short jobs stuck behind long ones
SJF (Shortest Job First)Run the shortest job firstOptimal average wait timeMust know job length; starvation of long jobs
Round Robin (RR)Each process gets a time slice (quantum), then goes to back of queueFair, responsiveContext switch overhead; quantum must be tuned
PriorityRun highest-priority process firstImportant tasks get CPUStarvation of low-priority processes
Multilevel Feedback QueueMultiple queues with different priorities; jobs move between them based on behaviorAdapts to workloadComplex to configure
Key Idea

Round Robin is the most common scheduling algorithm in time-sharing systems. Each process gets a fixed time quantum (e.g., 10ms). When the quantum expires, the running process is preempted and moved to the back of the ready queue. This gives every process a fair share of the CPU and keeps the system responsive.

Round Robin Example

Suppose three processes arrive at time 0, with a quantum of 4ms:

# Process Burst Time # P1 10ms # P2 5ms # P3 3ms # # Round Robin (quantum = 4): # Time 0-4: P1 runs (6ms remaining) # Time 4-8: P2 runs (1ms remaining) # Time 8-11: P3 runs (done!) # Time 11-12: P2 runs (done!) # Time 12-16: P1 runs (2ms remaining) # Time 16-18: P1 runs (done!) # # Average wait time = (8 + 7 + 8) / 3 = 7.67ms

Scheduling Criteria

Different scheduling algorithms optimize for different metrics. The choice depends on the system's goals:

  • CPU utilization: Keep the CPU as busy as possible (target: near 100%).
  • Throughput: Number of processes completed per unit time.
  • Turnaround time: Total time from submission to completion (includes waiting + execution).
  • Waiting time: Time spent in the ready queue, not executing.
  • Response time: Time from request to first response (critical for interactive systems).
SJF is Optimal (But Impractical)

Shortest Job First gives the minimum average waiting time of all non-preemptive schedulers. But it requires knowing how long each job will take — which is usually impossible. In practice, systems estimate job length from past behavior (exponential averaging) and use preemptive variants like Shortest Remaining Time First (SRTF).

xv6 Scheduling

xv6 uses a simple Round Robin scheduler. The scheduler() function in proc.c loops through the process table, and whenever it finds a RUNNABLE process, it marks it RUNNING and context-switches to it. When that process yields (blocks or its timer interrupt triggers a yield), control returns to scheduler(), which continues the loop. There is no priority system — every runnable process gets equal treatment.

6. Memory Management Strategies

Memory is one of the most precious resources a computer has. The OS's job is to allocate memory to processes efficiently, keep them isolated from each other, and make the best use of whatever physical RAM is available. Before virtual memory became universal, OS designers used several strategies for managing physical memory directly.

Think of memory as a parking lot. Each process needs spaces to park its code and data. The OS is the parking attendant: it assigns spaces, tracks which are free, and reclaims them when a process exits. The challenge is that processes come in all sizes, and over time the lot becomes fragmented with gaps too small for any new arrival.

Contiguous Allocation

The simplest approach is contiguous allocation: each process gets a single contiguous block of memory. The OS maintains a list of free holes and allocates the best-fitting one when a process requests memory. There are three common strategies for choosing which hole to use:

StrategyHow it worksTrade-off
First FitUse the first hole that's big enoughFast; tends to fragment the front of memory
Best FitUse the smallest hole that's big enoughMinimizes wasted space; leaves many tiny unusable holes
Worst FitUse the largest holeLeaves large remainders; reduces tiny-fragment problem

Fragmentation

Over time, as processes are loaded and removed, memory becomes divided into small, non-contiguous free pieces. There are two types of fragmentation:

  • External fragmentation: There is enough total free memory to satisfy a request, but it is scattered in small pieces, none large enough. Example: 100KB free total, but the largest contiguous free block is only 20KB — a 50KB request fails.
  • Internal fragmentation: Allocated memory is larger than requested. If the allocator rounds up to fixed-size blocks (e.g., 4KB pages), a 1-byte allocation wastes 4095 bytes inside the allocated block.
Key Idea

External fragmentation is solved by compaction (moving processes to consolidate free space) or, more effectively, by paging (breaking memory into fixed-size pages so any free page can be used). Internal fragmentation is the cost of fixed-size allocation — some space inside each block is wasted.

Swapping

When physical memory is full, the OS can swap processes out to disk, freeing their RAM for other processes. A swapped-out process is moved entirely to a backing store (disk); when it needs to run again, it is swapped back in. This allows the system to run more processes than fit in physical memory, but at a huge performance cost — disk is thousands of times slower than RAM.

// Swapping lifecycle: // // 1. Process P is running in RAM // 2. Memory is full; OS needs space for process Q // 3. OS swaps P out: copies P's memory image to disk // 4. P's state = "swapped" (not runnable) // 5. Q is loaded into the freed RAM and runs // 6. Later, when P needs to run again: // - OS swaps some other process out // - Swaps P back in from disk // - P resumes execution
Swapping vs. Paging

Swapping moves entire processes to/from disk. Demand paging (chapter 7) is more granular: it moves individual pages (typically 4KB) to/from disk, only loading the pages a process actually needs. Modern systems use demand paging, not whole-process swapping, because it is far more efficient.

7. Virtual Memory and Paging

Virtual memory is one of the most powerful abstractions in computing. It gives each process the illusion that it has its own large, private, contiguous address space — starting at address 0 and extending to some maximum — even though physical RAM is shared among all processes and may be smaller than the virtual space. The OS and hardware work together to translate virtual addresses into physical addresses on every memory access.

Think of virtual memory like a hotel. Each guest (process) gets a room number that starts from their own perspective (room 101, 102...). But the hotel's actual room layout is different — the front desk (the MMU) translates each guest's room number to the real physical room. Two guests can both have "room 101" in their mental map, but they map to different physical rooms. No guest can access another guest's room, because the translation only works for their own mapping.

Address Spaces

Each process has its own virtual address space — the set of virtual addresses it can use. A typical layout (on 64-bit systems) looks like this:

# Process virtual address space layout: # # High addresses +-------------------+ # | Kernel space | (mapped for all processes) # +-------------------+ # | Stack (grows ↓) | ← function frames, local vars # | | # | (free space) | # | | # | Heap (grows ↑) | ← malloc'd memory # +-------------------+ # | Data (BSS + data) | ← global/static vars # +-------------------+ # Low addresses | Code (text) | ← program instructions # +-------------------+ # Address 0 | (unmapped guard) | ← NULL pointer protection

Paging

Virtual memory is implemented through paging. Both virtual and physical memory are divided into fixed-size blocks called pages (virtual) and frames (physical). A typical page size is 4KB. The OS maintains a page table for each process that maps virtual page numbers to physical frame numbers.

TermMeaning
PageA fixed-size block of virtual memory (e.g., 4KB)
Frame (Page Frame)A fixed-size block of physical memory (same size as a page)
Page TablePer-process data structure mapping virtual pages → physical frames
Page FaultException raised when a accessed page is not in physical memory
MMU (Memory Management Unit)Hardware that translates virtual addresses to physical addresses
Key Idea

Paging eliminates external fragmentation: any free frame can hold any virtual page. The page table maps each virtual page to a physical frame, so a process's virtual pages can be scattered anywhere in physical memory. The process sees a contiguous address space; the hardware translates every access.

Address Translation

When a process accesses memory at virtual address V, the MMU splits V into two parts: a page number (high bits) and a page offset (low bits). It looks up the page number in the page table to find the corresponding physical frame number, then combines that with the offset to form the physical address.

# Example: 64-bit address, 4KB pages (12-bit offset) # # Virtual address: 0x0000003a7b4f8 # Page number: 0x0000003a7b (bits 63..12) # Offset: 0x4f8 (bits 11..0) # # Page table lookup: VPN 0x3a7b → PFN 0x12c0 # Physical address: PFN || offset = 0x12c04f8

Multi-Level Page Tables

A single-level page table for a 64-bit address space would be impossibly large (petabytes). So modern systems use multi-level (hierarchical) page tables. RISC-V (and xv6) uses a three-level page table (Sv39): the virtual address is split into three indices (L2, L1, L0) and an offset. Each level points to a table of 512 entries (9 bits each). Only the tables actually needed are allocated, saving enormous amounts of memory.

// RISC-V Sv39 page table (3 levels, 4KB pages): // // Virtual address (39 bits used): // [ L2 index (9b) | L1 index (9b) | L0 index (9b) | offset (12b) ] // // Translation: // 1. Start at root table (satp register points here) // 2. L2 entry → points to L1 table // 3. L1 entry → points to L0 table // 4. L0 entry → physical frame number (PFN) // 5. Physical address = PFN || offset // // Each table = 512 entries × 8 bytes = 4KB = one page

The TLB (Translation Lookaside Buffer)

Translating every memory access through a multi-level page table would require 3-4 memory accesses per instruction — far too slow. The TLB is a small, fast hardware cache inside the MMU that stores recent virtual-to-physical translations. On a memory access, the MMU first checks the TLB; if the translation is there (a TLB hit), it's used directly in one cycle. If not (a TLB miss), the hardware (or software, depending on the architecture) walks the page table to find the translation and loads it into the TLB.

TLB and Context Switches

When the OS switches from process A to process B, the TLB still contains A's translations — which are wrong for B. The OS must either flush (invalidate) the entire TLB on every context switch (expensive — the new process starts with a cold TLB) or use ASIDs (Address Space Identifiers) to tag TLB entries by process, allowing entries from multiple processes to coexist.

Page Faults and Demand Paging

Not all virtual pages need to be in physical memory at once. The page table entry for a page can be marked invalid (the "valid bit" is 0). When a process accesses such a page, the MMU raises a page fault — a trap to the OS. The OS then: (1) finds the page's data (often on disk, in the swap area or the executable file), (2) finds a free physical frame (or evicts one using a page replacement algorithm), (3) loads the page from disk into the frame, (4) updates the page table to point to the frame and mark it valid, and (5) restarts the faulting instruction. This is demand paging: pages are loaded only when demanded by access.

Demand Paging = Lazy Loading

With demand paging, a program can start running before all its code is in memory. Only the pages needed for startup are loaded; the rest are fetched on demand. This lets programs be larger than physical memory and start faster. If a program never calls a particular function, its code page is never loaded at all.

8. Page Replacement

When a page fault occurs and there are no free physical frames, the OS must evict a page from memory to make room. The choice of which page to evict is the page replacement problem, and it has a huge impact on performance. A bad choice means evicting a page that will be needed again soon, causing another page fault — a phenomenon called thrashing, where the system spends more time paging than computing.

The ideal algorithm would evict the page that won't be used for the longest time in the future. This is called OPT or Belady's optimal algorithm. It's impossible to implement (you can't predict the future), but it serves as a benchmark: any real algorithm's performance is measured against OPT.

OPT (Optimal)Evict page not used for longest future timeTheoretical optimumImpossible to implement (needs future knowledge)
Key Idea

LRU is the best practical algorithm: it exploits locality of reference — the tendency of programs to access the same set of pages repeatedly (temporal locality) and to access nearby addresses (spatial locality). Pages used recently are likely to be used again soon, so LRU keeps them in memory.

FIFO Example

# Reference string: 7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2 # 3 frames, FIFO replacement: # # Access 7: [7] miss (page fault) # Access 0: [7, 0] miss # Access 1: [7, 0, 1] miss # Access 2: [0, 1, 2] miss (evict 7 — oldest) # Access 0: [0, 1, 2] hit! # Access 3: [1, 2, 3] miss (evict 0 — oldest) # Access 0: [2, 3, 0] miss (evict 1) # Access 4: [3, 0, 4] miss (evict 2) # Access 2: [0, 4, 2] miss (evict 3) # Access 3: [4, 2, 3] miss (evict 0) # Access 0: [2, 3, 0] miss (evict 4) # Access 3: [2, 3, 0] hit! # Access 2: [2, 3, 0] hit! # # Total: 10 page faults out of 13 accesses

The Clock Algorithm

True LRU requires updating a timestamp on every memory access, which is expensive. The clock algorithm (also called second-chance) is a practical approximation. It arranges pages in a circular list with a "hand" pointer. Each page has a reference bit set by hardware when the page is accessed. When eviction is needed, the hand advances: if the current page's reference bit is 1, clear it and move on (give it a "second chance"); if it's 0, evict that page. Pages accessed recently have their bit set and survive; pages not accessed recently have their bit cleared by the hand and get evicted.

// Clock algorithm (simplified): // // while (need to evict) { // if (page[hand].reference_bit == 1) { // page[hand].reference_bit = 0; // give second chance // hand = (hand + 1) % num_pages; // } else { // evict(page[hand]); // this one gets evicted // hand = (hand + 1) % num_pages; // break; // } // }

Thrashing

If a process doesn't have enough physical frames to hold its working set (the set of pages it's actively using), it will constantly page fault: evict a page, immediately need it again, fault, evict another, need that one, fault... The CPU spends all its time servicing page faults and almost no time executing the program. This is thrashing. The system's throughput collapses to near zero. The solution is to either give the process more frames (if available) or reduce the degree of multiprogramming (run fewer processes simultaneously).

Belady's Anomaly

With the FIFO algorithm, adding more frames can actually increase the number of page faults for certain reference strings. This counterintuitive result is called Belady's anomaly. LRU and the clock algorithm do not suffer from this anomaly — more frames always helps or stays the same.

9. Synchronization

When multiple threads or processes share data, they need synchronization — mechanisms to coordinate access to shared resources and prevent race conditions. Synchronization is one of the hardest problems in systems programming: get it wrong, and you get subtle bugs that appear only under specific timing conditions and are nearly impossible to reproduce.

The fundamental tool for synchronization is the lock. A lock protects a critical section — a piece of code that accesses shared data. Before entering the critical section, a thread acquires the lock; after leaving, it releases it. If the lock is already held, the acquiring thread waits. This ensures only one thread is in the critical section at a time.

Types of Locks

Lock TypeHow it worksWhen to use
SpinlockThread "spins" in a tight loop, repeatedly trying to acquire the lockShort critical sections; held for a few instructions; no context switch overhead
Sleeplock (Mutex)Thread that can't acquire the lock is put to sleep (descheduled) and woken when the lock is freedLonger critical sections; may block on I/O; avoids wasting CPU
Reader-Writer LockMultiple readers can hold the lock simultaneously; writers get exclusive accessRead-heavy data structures where reads outnumber writes
Condition VariableThread waits for a condition to become true; another thread signals when it mightProducer-consumer patterns, waiting for events

Spinlocks in xv6

xv6 implements spinlocks for short critical sections. A spinlock is a single integer: 0 means free, 1 means held. Acquiring the lock uses an atomic instruction (like amoswap on RISC-V) to test-and-set the value in a single indivisible operation. If the lock is held, the CPU spins in a loop retrying until it becomes free.

// Simplified xv6 spinlock (kernel/spinlock.c) void acquire(struct spinlock *lk) { push_off(); // disable interrupts on this CPU while(__sync_lock_test_and_set(&lk->locked, 1) != 0) ; // spin until we get the lock lk->cpu = mycpu(); // record which CPU holds it } void release(struct spinlock *lk) { lk->cpu = 0; __sync_lock_release(&lk->locked); // atomically set to 0 pop_off(); // re-enable interrupts }
Key Idea

A spinlock busy-waits (spins) when the lock is held. This wastes CPU cycles but avoids the cost of a context switch. Use spinlocks only for very short critical sections. For longer waits (especially if the holder might block on I/O), use a sleeplock that puts the waiting thread to sleep instead of spinning.

Why Spinlocks Disable Interrupts

Notice that xv6's acquire() calls push_off() to disable interrupts. Why? If a thread holds a spinlock and then a timer interrupt fires, the OS might switch to another thread. If that thread tries to acquire the same lock, it will spin forever — the original holder can never run to release it. This is a deadlock. By disabling interrupts while holding a spinlock, xv6 ensures the holder can't be preempted. (This only works on single-core systems or for per-CPU locks; on multicore, the spin itself handles contention from other CPUs.)

Semaphores

A semaphore is a more general synchronization primitive, invented by Edsger Dijkstra. It's an integer with two atomic operations:

  • wait(S) (also called P or down): Decrement S. If S becomes negative, the calling thread blocks until S is positive again.
  • signal(S) (also called V or up): Increment S. If S was negative (threads waiting), wake one up.

A semaphore initialized to 1 acts like a mutex (binary semaphore). A semaphore initialized to N allows up to N threads into a section simultaneously — useful for resource pools (e.g., N database connections).

// Producer-Consumer with semaphores (bounded buffer) sem_t empty = N; // N empty slots sem_t full = 0; // 0 full slots sem_t mutex = 1; // protects the buffer void producer() { while (1) { item = produce(); wait(&empty); // wait for an empty slot wait(&mutex); // enter critical section put_item(item); signal(&mutex); // leave critical section signal(&full); // announce a full slot } } void consumer() { while (1) { wait(&full); // wait for a full slot wait(&mutex); // enter critical section item = get_item(); signal(&mutex); // leave critical section signal(&empty); // announce an empty slot consume(item); } }

Monitors

A monitor is a high-level synchronization construct — a module or object that encapsulates shared data with the rule that only one thread can be executing inside the monitor at a time. Monitors use condition variables for threads to wait for specific conditions. Java's synchronized keyword implements monitors. The advantage of monitors over raw locks and semaphores is that the locking is automatic — you can't forget to release the lock, and the critical section is clearly defined by the monitor's methods.

The Bounded Buffer Problem

The producer-consumer problem (bounded buffer) is the classic synchronization challenge. Producers add items to a fixed-size buffer; consumers remove them. You must ensure: (1) producers wait when the buffer is full, (2) consumers wait when it's empty, (3) only one thread modifies the buffer at a time. The semaphore solution above elegantly handles all three conditions.

10. Deadlocks

A deadlock is a situation where two or more processes are each waiting for a resource held by another, and none can proceed. Everyone is blocked, waiting for someone else to go first, and nothing ever happens. Deadlocks are among the most insidious bugs in concurrent systems because they often don't manifest until specific timing conditions arise in production.

Imagine two people at a dinner table. There is one knife and one fork. Person A picks up the knife and waits for the fork. Person B picks up the fork and waits for the knife. Neither will give up their utensil. They are deadlocked — both will starve. This is exactly what happens in software when two threads each hold one lock and try to acquire the other's lock.

The Four Necessary Conditions

For a deadlock to occur, four conditions must all hold simultaneously. These are known as the Coffman conditions:

ConditionMeaning
Mutual ExclusionAt least one resource is held in non-shareable mode (only one process can use it at a time)
Hold and WaitA process holding at least one resource is waiting to acquire additional resources held by others
No PreemptionResources can't be forcibly taken away; they must be released voluntarily
Circular WaitThere exists a circular chain of processes, each waiting for a resource held by the next in the chain
Key Idea

All four conditions must hold for deadlock. Break any one, and deadlock is impossible. This is the basis for deadlock prevention: design the system so that at least one condition can never be true.

Resource Allocation Graph

A resource allocation graph visualizes the deadlock situation. Processes and resources are nodes. An edge from process P to resource R means P is requesting R. An edge from R to P means R is allocated to P. If the graph contains a cycle, and each resource has only one instance, then deadlock exists. If resources have multiple instances, a cycle is necessary but not sufficient for deadlock.

// Classic deadlock: two locks acquired in opposite order // // Thread 1: Thread 2: // acquire(lockA); acquire(lockB); // acquire(lockB); ← waits acquire(lockA); ← waits // ... ... // release(lockB); release(lockA); // release(lockA); release(lockB); // // Both threads block forever — deadlock!

Deadlock Handling Strategies

There are four approaches to dealing with deadlocks, ranging from "ignore it" to "actively prevent it":

StrategyApproachUsed in practice?
Ignore (Ostrich Algorithm)Pretend deadlocks don't happen; reboot if they doYes — most desktop OSes (Windows, Linux desktop)
PreventionDesign the system so at least one Coffman condition can't holdSometimes — e.g., lock ordering
AvoidanceAt each resource request, check if granting it could lead to deadlock (Banker's algorithm)Rarely — too conservative; needs max resource info
Detection & RecoveryAllow deadlocks, periodically check for them, then kill a process to break the cycleSometimes — databases, some server systems

Deadlock Prevention

Prevention works by ensuring at least one Coffman condition can never hold:

  • Break Hold and Wait: Require processes to request all resources at once, before starting. Impractical — processes don't know what they'll need.
  • Break No Preemption: If a process can't get a resource, it must release all held resources and try again. Works for some resources (e.g., locks) but not for others (e.g., a printer mid-print).
  • Break Circular Wait: Impose a total ordering on all resources and require processes to acquire them in order. If every process acquires locks in the same global order, circular wait is impossible. This is the most practical prevention technique.
Lock Ordering: The Practical Fix

The most common deadlock prevention in real code is lock ordering: assign a global order to all locks and always acquire them in that order. If Thread 1 and Thread 2 both need locks A and B, they both acquire A first, then B. No deadlock is possible. In xv6, the code comments document the required lock ordering for multi-lock operations.

Banker's Algorithm (Avoidance)

Dijkstra's Banker's Algorithm is the classic deadlock avoidance method. It models the system like a bank: each process declares its maximum resource needs upfront. When a process requests resources, the algorithm checks whether granting the request leaves the system in a safe state — one where there exists some sequence of allocations that lets all processes eventually complete. If the state is safe, the request is granted; otherwise, the process must wait. The algorithm is correct but rarely used in practice because it requires knowing maximum resource needs in advance and is conservative.

11. I/O Systems and Interrupts

A computer is useless without I/O — input from keyboards and networks, output to screens and printers, storage on disks and SSDs. The OS's I/O subsystem manages all these devices, providing a uniform interface to wildly different hardware. Understanding I/O is essential because it's where the OS meets the physical world, and it's where many performance and reliability challenges arise.

I/O devices are incredibly diverse: a keyboard sends a few bytes per second; an SSD transfers gigabytes per second; a network card handles millions of packets per second. The OS abstracts this diversity behind a few standard interfaces: block devices (random access, fixed-size blocks — disks, SSDs) and character devices (stream of bytes — keyboards, serial ports, network interfaces).

How I/O Works: Polling vs. Interrupts

When the CPU needs to interact with a device, there are two ways to know when the device is ready:

  • Polling: The CPU repeatedly reads a device status register in a loop, waiting for a "ready" bit. Simple, but wastes CPU cycles that could be doing useful work.
  • Interrupts: The device sends a hardware signal (an interrupt) to the CPU when it needs attention. The CPU can do other work and is notified when the device is ready. This is how virtually all modern I/O works.
Key Idea

An interrupt is a hardware signal that causes the CPU to stop its current execution, save its state, and jump to a predefined interrupt handler in the OS. After handling the interrupt, the CPU restores the saved state and resumes. Interrupts let the CPU do useful work while slow I/O devices operate in the background.

Interrupt Handling

When an interrupt fires, the hardware does the following automatically: (1) saves the current program counter and some registers, (2) switches to a privileged mode (kernel mode), (3) jumps to the interrupt handler address stored in an interrupt vector table. The OS's interrupt handler then processes the event and returns. In xv6, the trap handler in trap.c dispatches to the appropriate handler based on the cause of the trap (timer interrupt, device interrupt, syscall, or page fault).

// Simplified xv6 trap dispatch (kernel/trap.c) void trap(struct trapframe *tf) { if ((r_scause() & 0x8000000000000000)) { // Interrupt int which = (r_scause() & 0xff); if (which == 5) clockintr(); // Timer interrupt else if (which == 10) virtio_disk_intr(); // Disk I/O complete else if (which == 8) uartintr(); // Serial input // ... } else { // Exception or syscall if (r_scause() == 8) syscall(); // System call from user mode // ... } }

Top-Half / Bottom-Half Design

Interrupt handlers run with interrupts disabled and must be fast — a slow handler delays all other interrupts. To handle complex I/O without blocking, OS designers split interrupt handling into two parts:

  • Top half (interrupt handler): Runs immediately, in interrupt context. Does the minimum: acknowledge the interrupt, copy data from device to a buffer, schedule the bottom half. Must be fast and non-blocking.
  • Bottom half (deferred work): Runs later, in process context, with interrupts enabled. Does the heavy lifting: parsing data, waking up waiting processes, starting the next I/O. In Linux, this is done via softirqs, tasklets, or workqueues.

Device Drivers

A device driver is the OS code that knows how to talk to a specific piece of hardware. It translates generic OS requests ("read block 42") into device-specific commands ("write these values to these I/O ports"). Drivers are notoriously the buggiest part of an OS — they run in kernel mode, so a bug can crash the system, and they deal with complex, poorly documented hardware. In xv6, the virtio disk driver (virtio_disk.c) and console driver (console.c) are examples.

DMA (Direct Memory Access)

Without DMA, the CPU must copy every byte of I/O data between the device and memory — a huge waste for large transfers. DMA is a hardware feature where a dedicated DMA controller transfers data directly between the device and memory, bypassing the CPU. The CPU sets up the transfer (source, destination, length) and is interrupted when it's done. This lets the CPU do other work during large I/O operations.

DMA and Cache Coherence

DMA transfers data directly to/from physical memory, bypassing the CPU cache. This can cause cache incoherence: the CPU has a stale cached copy while DMA wrote new data to memory. The OS must flush or invalidate caches around DMA operations to ensure the CPU sees the correct data. Modern hardware often handles this automatically, but some architectures require explicit cache management.

12. File Systems

A file system is the OS subsystem that organizes data on storage devices into files and directories. Without a file system, a disk is just a flat array of blocks. The file system imposes structure: it tracks which blocks belong to which file, organizes files into a directory hierarchy, and provides names, permissions, and metadata (sizes, timestamps, types).

Think of a file system as a library. The raw disk is a warehouse full of unorganized books. The file system is the librarian's catalog: it records where each book (file) is shelved, what section (directory) it's in, who can read it (permissions), and its metadata (author, date, size). When you ask for a file by name, the file system looks it up in the catalog and finds the physical location on disk.

Files and Directories

A file is a named collection of related data. In Unix, a file is just a sequence of bytes — the OS doesn't impose any structure (no "records" or "fields"). The interpretation is up to the application. A directory (or folder) is a special file that contains a list of (name, file) pairs. Directories can contain other directories, forming a tree (or, with links, a graph) structure.

Allocation Methods

The file system must track which disk blocks belong to each file. There are three classic allocation strategies:

Key Idea

Unix file systems (including xv6) use inodes (index nodes). Each file has an inode that stores metadata and an array of block pointers. The first 12 pointers point to direct data blocks; the 13th points to an indirect block (containing more pointers); the 14th to a double-indirect block; the 15th to a triple-indirect block. This allows small files to be fast (direct access) while supporting very large files (through indirection).

The xv6 File System

xv6 implements a simple Unix-like file system. The disk is divided into regions:

// xv6 file system layout on disk: // // Block 0: [ boot block ] (unused by FS) // Block 1: [ superblock ] (FS metadata: size, nblocks, ninodes) // Block 2..: [ log ] (write-ahead log for crash recovery) // Block ..: [ inode blocks ] (array of on-disk inodes) // Block ..: [ bitmap ] (free block bitmap) // Block ..: [ data blocks ] (actual file/directory data) // // On-disk inode (kernel/fs.h): // type (file/dir/device), nlink, size, addrs[13] // addrs[0..11] = direct block numbers // addrs[12] = indirect block (256 more pointers)

The xv6 file system supports three types of files: regular files (data), directories (lists of directory entries), and device files (special files that map to I/O devices). It also supports hard links — multiple directory entries pointing to the same inode — and symbolic links are not implemented in basic xv6 but are a common extension.

Directory Structure

A directory is a file containing an array of directory entries, each with an inode number and a name. The root directory (/) has inode 1 in xv6. To resolve a path like /home/user/file.txt, the file system: (1) starts at the root inode, (2) reads the root directory data, (3) searches for "home" and gets its inode number, (4) reads the "home" directory, (5) searches for "user", and so on until it reaches the final file.

// xv6 directory entry (kernel/fs.h) struct dirent { ushort inum; // inode number (0 = free entry) char name[DIRSIZ]; // file name (14 bytes in xv6) };
The Log for Crash Recovery

xv6 uses a write-ahead log for crash recovery. Before modifying file system data, xv6 writes all intended changes to the log area on disk. Once the complete transaction is in the log, it "commits" by writing a commit record. Only then does it apply the changes to the actual file system blocks. If the system crashes mid-transaction, the log can be replayed (or discarded) on reboot, ensuring the file system is never left in an inconsistent state.

13. Mass-Storage and I/O Scheduling

While SSDs have replaced mechanical hard drives in many systems, the principles of disk I/O scheduling remain important. Even with SSDs, I/O is orders of magnitude slower than memory, and intelligent scheduling can dramatically improve throughput and latency. This chapter covers how the OS organizes and optimizes access to mass storage.

Disk Structure (Mechanical HDDs)

A traditional hard disk drive consists of one or more platters (circular disks) coated with magnetic material. Data is stored in concentric tracks on each platter surface. Tracks are divided into sectors (typically 512 bytes or 4KB). A read/write head on a movable arm accesses data. The time to access a sector has three components:

  • Seek time: Time to move the head to the correct track (slowest — milliseconds).
  • Rotational latency: Time for the correct sector to rotate under the head.
  • Transfer time: Time to read/write the data once the head is positioned.

Because seek time dominates, disk scheduling algorithms try to minimize head movement. SSDs have no moving parts, so seek time is near zero — but they still benefit from I/O scheduling for fairness and wear-leveling.

Disk Scheduling Algorithms

AlgorithmStrategyProsCons
FCFSService requests in arrival orderSimple, fairExcessive head movement
SSTF (Shortest Seek Time First)Service the request closest to current head positionMinimizes seek timeStarvation of distant requests
SCAN (Elevator)Head sweeps in one direction servicing requests, then reversesFair; no starvationRequests at extremes wait longer
C-SCAN (Circular SCAN)Like SCAN, but jumps back to start after reaching the endMore uniform wait timesWasted movement on the return trip
LOOK / C-LOOKLike SCAN/C-SCAN, but only goes as far as the last request (not the disk edge)More efficient than full SCANSlightly more complex
Key Idea

The elevator algorithm (SCAN) is the most widely used disk scheduling strategy. Like an elevator, the disk head moves in one direction, servicing all requests in its path, then reverses. This prevents the head from thrashing back and forth and ensures no request waits indefinitely.

SCAN Example

# Disk has 200 tracks (0-199). Head at 53, moving toward 199. # Request queue: 98, 183, 37, 122, 14, 124, 65, 67 # # SCAN (moving up first): # 53 → 65 → 67 → 98 → 122 → 124 → 183 → [199] → 37 → 14 # Total head movement: (199-53) + (199-14) = 146 + 185 = 331 tracks # # Compare FCFS: # 53 → 98 → 183 → 37 → 122 → 14 → 124 → 65 → 67 # Total: 45+85+146+85+108+110+59+2 = 640 tracks # # SCAN nearly halves the head movement!

RAID (Redundant Array of Independent Disks)

RAID combines multiple physical disks into a single logical unit to improve performance, reliability, or both. Different RAID levels offer different trade-offs:

LevelNameHow it worksProsCons
RAID 0StripingData spread across N disks (no redundancy)Fastest; full capacityNo fault tolerance — one disk fails, all data lost
RAID 1MirroringIdentical data on 2 disksGood read speed; tolerates 1 failure50% capacity wasted

RAID 5 is the most popular RAID level for general-purpose storage. It stripes data across N+1 disks with distributed parity, giving good read performance, tolerating a single disk failure, and wasting only 1/N of the capacity. The parity is computed with XOR: if any one disk fails, its data can be reconstructed from the remaining data and the parity.

SSD Considerations

SSDs store data in flash memory cells and have no moving parts, so seek time and rotational latency are effectively zero. However, SSDs have their own challenges: wear leveling (each cell can only be erased a limited number of times), write amplification (writing one page may require erasing and rewriting an entire erase block), and garbage collection (reclaiming pages that are no longer in use). Modern SSDs include a flash translation layer (FTL) that handles these issues transparently, making the SSD look like a simple block device to the OS.

14. System Calls and Traps

The system call is the fundamental interface between user programs and the operating system kernel. User programs run in unprivileged mode and cannot directly access hardware, modify page tables, or perform I/O. When they need any of these services, they make a system call — a controlled, secure transition from user mode to kernel mode.

Think of a system call like the counter at a bank. You (the user program) can't go into the vault yourself (kernel mode). You fill out a request form (put arguments in registers) and hand it to the teller (execute the ecall instruction). The teller checks your request, performs the operation in the vault, and hands you the result. You never enter the vault yourself — the teller controls everything.

The Trap Mechanism

The hardware mechanism that switches from user mode to kernel mode is called a trap. A trap can be triggered by three things:

  • System call: The user program explicitly requests kernel service (e.g., ecall on RISC-V, syscall on x86-64).
  • Exception (fault): The program does something illegal — divides by zero, accesses an invalid address, executes an illegal instruction. The CPU traps to the OS, which typically terminates the process.
  • Interrupt: A hardware device signals the CPU (timer expired, I/O complete, keyboard input). The OS handles the interrupt and resumes the interrupted program.
Key Idea

All three — syscalls, exceptions, and interrupts — use the same trap mechanism. The hardware saves the current state (PC, registers), switches to kernel mode, and jumps to a trap handler. The OS examines the cause and dispatches accordingly. After handling, it restores the saved state and returns to user mode (or terminates the process, for fatal exceptions).

Syscall Dispatch in xv6

When a user program calls exec(), the C library wrapper puts the syscall number in a register (a7 on RISC-V) and executes ecall. The hardware traps to the kernel. xv6's trap handler saves the user registers into a trapframe, reads the syscall number from a7, and dispatches to the corresponding kernel function via a function pointer table.

// Simplified xv6 syscall dispatch (kernel/syscall.c) static uint64 (*syscalls[])(void) = { [SYS_fork] sys_fork, [SYS_exit] sys_exit, [SYS_wait] sys_wait, [SYS_exec] sys_exec, [SYS_read] sys_read, [SYS_write] sys_write, [SYS_open] sys_open, [SYS_close] sys_close, [SYS_kill] sys_kill, [SYS_getpid] sys_getpid, // ... }; void syscall(void) { int num = p->trapframe->a7; // syscall number if (num > 0 && num < NELEM(syscalls) && syscalls[num]) { p->trapframe->a0 = syscalls[num](); // call handler, store result in a0 } else { p->trapframe->a0 = -1; // unknown syscall } }

The User/Kernel Transition

The transition from user to kernel mode involves several steps, each with a cost:

  1. Execute the trap instruction (ecall / syscall). The hardware: saves the user PC, switches to kernel mode, jumps to the trap vector.
  2. Save user registers. The kernel saves all user registers (into the trapframe) because the kernel will use those registers for its own work.
  3. Switch to kernel stack. The user stack is in user memory and may be inaccessible or corrupted. The kernel uses its own stack.
  4. Handle the syscall. The kernel runs the actual system call handler.
  5. Restore user registers and return. The sret (RISC-V) or iret (x86) instruction restores the user PC and switches back to user mode.
Syscall Overhead

A system call is much more expensive than a function call — typically 1-10 microseconds vs. nanoseconds. This is why programs that make many small syscalls (like reading a file one byte at a time) are slow. The fix is buffering: read a large chunk in one syscall and process it in user space, or use batching APIs like io_uring (Linux) that submit multiple I/O operations in one syscall.

You rarely write ecall directly. The C standard library (glibc on Linux) provides wrapper functions: fork(), read(), write(), etc. These wrappers put the syscall number in the right register, execute the trap instruction, and return the result. In xv6, user/usys.S contains these auto-generated wrappers.

15. Protection and Security

Protection and security are about ensuring that programs and users can only access the resources they're authorized to use. Protection is the mechanism — the hardware and OS features that enforce access rules. Security is the broader goal — protecting the system from malicious attacks, unauthorized access, and data theft. A well-designed OS provides multiple layers of defense.

Think of protection like the security system of a building. There are outer doors (user/kernel boundary), interior doors with different keys (file permissions), ID badges (authentication), and security guards (the OS checking every access). No single layer is sufficient — defense in depth means if one layer fails, others still protect the system.

Access Control

The OS controls access to resources through access control. There are two main models:

  • Discretionary Access Control (DAC): The owner of a resource decides who can access it. Unix file permissions (rwx for owner/group/others) are DAC. Flexible, but the owner can accidentally grant too much access.
  • Mandatory Access Control (MAC): The system enforces access rules that users cannot override. Security classifications (Top Secret, Secret, Confidential) are MAC. More secure, but less flexible. SELinux and AppArmor bring MAC to Linux.

Unix File Permissions

Unix uses a simple but effective DAC model. Each file has an owner (user), a group, and a set of permission bits for three classes: owner, group, and others. Each class has three bits: read (r), write (w), execute (x).

# Unix permission bits: rwxrwxrwx # owner | group | others # # Examples: # rwxr-xr-x (755) - owner: full; group & others: read + execute # rw-r--r-- (644) - owner: read+write; group & others: read only # rwx------ (700) - owner: full; nobody else can access # # For directories: # r = can list contents # w = can create/delete files in it # x = can cd into it and access files by name # # Change permissions: chmod 644 file.txt # Change owner: chown alice file.txt

Key Idea

Protection rings are hardware-enforced privilege levels. x86 has 4 rings (0-3); most OSes use only ring 0 (kernel) and ring 3 (user). RISC-V has three modes: Machine (M), Supervisor (S), and User (U). The OS kernel runs in S mode; user programs run in U mode. The hardware prevents user-mode code from executing privileged instructions or accessing kernel memory — this is the foundation of process isolation.

Authentication

Before access control can work, the system must know who is making a request. This is authentication — verifying identity. Common methods:

  • Passwords: The most common. The system stores a hash (not the plaintext) and compares the hash of the entered password. Vulnerable to guessing, phishing, and brute force.
  • Multi-factor authentication (MFA): Combine something you know (password) with something you have (phone/token) or something you are (biometric). Much stronger than passwords alone.
  • Public key cryptography: SSH keys, certificates. The user proves possession of a private key without revealing it. Used for automated systems and secure shell access.

Isolation Mechanisms

Beyond access control, the OS provides several mechanisms to isolate programs from each other:

  • Virtual memory: Each process has its own address space. A process cannot read or write another process's memory (unless they explicitly share it via shared memory or mmap).
  • Sandboxing: Running untrusted code in a restricted environment with limited access to files, network, and system calls. Examples: browser tabs, Docker containers, seccomp filters.
  • Containers: Lightweight virtualization using OS-level isolation (namespaces, cgroups). Processes in a container see their own filesystem, process list, and network, but share the host kernel. Faster than full VMs but weaker isolation.
  • Virtual machines: Full hardware virtualization. Each VM runs its own kernel. Strongest isolation (a VM escape is very rare) but heaviest overhead.
The Principle of Least Privilege

Every program, process, and user should have only the privileges needed to do its job — no more. A web server doesn't need to read /etc/shadow. A text editor doesn't need raw disk access. Following this principle limits the damage from bugs and attacks: if a program is compromised, the attacker only gets that program's limited privileges, not full system access.

Defense in Depth

No single security measure is sufficient. Defense in depth means layering multiple independent protections: hardware privilege levels, virtual memory isolation, file permissions, authentication, firewalls, encryption, and auditing. If an attacker breaches one layer, others still stand. This is why modern systems combine kernel/user separation, ASLR, stack canaries, DEP, and sandboxing — each makes the next attack harder.
