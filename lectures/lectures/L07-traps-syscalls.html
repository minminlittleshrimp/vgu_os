SECTION 1

What Is a Trap?

System calls . exceptions . interrupts - all use the same mechanism

What is a Trap?

"You're working in your office (user mode) and need something from the vault (kernel). You can't just walk in - you ring the bell (ecall), the manager opens the door, does the work, and sends you back."

Definition

A trap is a controlled transfer of execution from user mode to kernel mode. It is triggered by three kinds of events:

  • System call - user program requests a kernel service (ecall)
  • Exception - CPU detects an error (page fault, divide by zero, illegal instruction)
  • Interrupt - hardware signals an event (timer, I/O completion)

All three use the same mechanism

Whether it's a syscall, a page fault, or a timer tick - the CPU follows the same trap path. The kernel distinguishes them by reading the scause register.

Why "controlled"?

The user program cannot choose where to jump in the kernel. The CPU always jumps to stvec - a fixed address the kernel set up. The user has no say in the entry point.

trap = ecall / fault / IRQ
-> CPU jumps to stvec (kernel-controlled)
-> kernel reads scause to dispatch

Why Traps Are Necessary

Two privilege worlds

User mode (U-mode): user programs run here. No direct access to hardware, physical memory, or privileged CPU registers. If a program tries, the CPU traps.

Supervisor mode (S-mode): the kernel runs here. Full access to memory, devices, and CSRs. Can set up page tables, handle interrupts, manage processes.

The boundary is hardware-enforced

The CPU itself checks privilege on every memory access and CSR instruction. A user program cannot bypass this - it's wired into the silicon.

Traps are the only door

There is no "side entrance." The only way for user code to execute kernel code is through a trap. This is what makes protection possible:

  • The kernel decides what services to expose (syscalls)
  • The kernel decides who gets service (permission checks)
  • The kernel decides when to return (it controls sret)

Without traps, no protection

If user programs could call kernel functions directly, any process could read any file, access any device, or crash the system. Traps are the foundation of process isolation.

SECTION 2

What Happens During a Trap

The challenge of user->kernel transition . ecall . key CSRs

The Challenge of User->Kernel Transition

"When you ring the bell, a lot has to happen before the kernel can run C code: switch mode, save registers, switch page tables, switch stack."

CPU is set up for USER

Before the trap, the CPU is running user code. Its state is:

  • 32 general registers (x0-x31) hold user values
  • PC points at the user instruction
  • Mode = U-mode
  • satp = user page table
  • sp = user stack

Kernel needs a completely different setup

To run kernel C code, the CPU must be in:

  • Mode = S-mode (supervisor)
  • All 32 user registers saved (so they can be restored later)
  • satp = kernel page table
  • sp = kernel stack
  • PC = kernel C function (usertrap)

The gap

ecall only does part of this. The rest must be done in assembly - because C code needs a valid stack and page table, which don't exist yet.

What ecall Does (and Doesn't Do)

ecall DOES

  • Switch to S-mode - privilege level changes from U to S
  • Save user PC in sepc - so the kernel knows where to return
  • Jump to stvec - the trap vector address (set by kernel)
  • Disable interrupts - SIE -> SPIE, then SIE = 0
ecall: U->S mode
sepc = user PC
PC = stvec
SIE=0 (interrupts off)

ecall does NOT

  • Save the 32 user registers - they're still in the CPU, will be overwritten
  • Switch page tables - satp is still the user page table
  • Set up a kernel stack - sp is still the user stack
  • Save sp, ra, gp, tp - nothing is saved except PC

Why this matters

After ecall, the CPU is in S-mode but still using the user's page table and stack. The kernel must do the rest in assembly - the trampoline - before it can safely run C code.

SECTION 3

Trap Flow

Trampoline page . uservec . sscratch trick

Trap Flow: User to Kernel and Back

The Trampoline Page

Key idea

The trampoline is a single page mapped at the same virtual address in both the user page table and the kernel page table.

Why same address?

When a trap occurs, satp still points to the user page table. The CPU jumps to stvec, which is the trampoline's virtual address. The trampoline must be accessible before the page table switch - so it must exist in the user page table.

Location

The trampoline lives at the very top of virtual address space:

TRAMPOLINE = MAXVA - PGSIZE (VA 0x3fffff000)

The trapframe sits just below it: TRAPFRAME = TRAMPOLINE - PGSIZE (VA 0x3ffffe000)

Both are the same address in kernel and user page tables, so after switching satp, the code keeps running without a fault.

"The trampoline is like an airlock between two rooms. It exists in both rooms at the same position. You enter from one side, the atmosphere changes, and you exit into the other room."

No PTE_U flag

The trampoline page is mapped in the user page table without the PTE_U (user-accessible) bit. This means user code cannot execute it directly - only the kernel can enter it via a trap.

What's in the trampoline?

  • uservec - trap entry: saves user registers, switches to kernel stack, jumps to usertrap()
  • userret - trap exit: restores user registers, switches to user page table, executes sret

uservec: Saving User Registers

From trampoline.S (simplified)

uservec:
    csrw sscratch, a0      # save user a0
    li   a0, TRAPFRAME      # a0 = TRAPFRAME addr
    sd   ra, 40(a0)         # save all 32 user regs
    sd   sp, 48(a0)
    # ... save gp, tp, t0-t6,
    #     s0-s11, a1-a7 ...
    csrr t0, sscratch       # get user's a0 back
    sd   t0, 112(a0)        # save it in trapframe
    ld   sp, 8(a0)          # kernel stack
    ld   tp, 32(a0)         # CPU ID
    ld   t0, 24(a0)         # usertrap() address
    jr   t0                 # jump to C code

Step by step

  1. csrw sscratch, a0 - stash user's a0 into sscratch (which held TRAPFRAME addr)
  2. li a0, TRAPFRAME - load TRAPFRAME address into a0 (now usable as base)
  3. sd ra, 40(a0) ... - save all 32 user registers into the trapframe, using a0 as base pointer
  4. csrr t0, sscratch - retrieve the user's original a0 from sscratch
  5. sd t0, 112(a0) - store user's a0 at trapframe offset 112
  6. ld sp, 8(a0) - load kernel stack from trapframe
  7. ld tp, 32(a0) - load CPU ID (hartid)
  8. ld t0, 24(a0) - load usertrap() address
  9. jr t0 - jump to C code - now we have a valid stack!

Why assembly?

At this point there is no valid stack and no C runtime. Every instruction must be hand-written assembly that doesn't rely on sp or callee-saved registers.

The sscratch Trick

"You have one free hand (a0) but need to carry two things: the user's a0 and the TRAPFRAME address. So you stash user's a0 in your pocket (sscratch), grab TRAPFRAME, then pull user's a0 out and store it properly."

The problem

When uservec starts, a0 holds a user value that must be saved. But to save anything, we need the TRAPFRAME address as a base pointer - and the only register we can freely clobber is a0.

The solution: sscratch

Before returning to user mode, the kernel sets sscratch = TRAPFRAME address. On the next trap, csrw sscratch, a0 swaps a0 and sscratch in one atomic step.

Definition

};

Two kinds of fields

Kernel fields (offsets 0-32): filled by usertrapret() before returning to user. Used by uservec on the next trap to set up the kernel environment.

User fields (offsets 40-280): saved by uservec on trap entry, restored by userret on trap exit. These are the 32 user registers.

One trapframe per process

Each process has a struct trapframe allocated in its proc struct. The address is stored in sscratch when the process is running, so uservec can find it instantly.

Offset 112 = a0

This is why uservec does sd t0, 112(a0) - offset 112 is where a0 lives in the trapframe. The user's a0 was temporarily in sscratch and is now stored properly.

usertrapret() fills kernel fields

Before returning to user mode, usertrapret() writes kernel_satp, kernel_sp, kernel_trap, and kernel_hartid into the trapframe. This ensures the next trap can immediately find the kernel environment without any C code.

SECTION 5

usertrap() - The C Handler

Dispatch by scause . usertrapret

usertrap() Code

From trap.c (simplified)

uint64 usertrap(void) {
  if ((r_sstatus() & SSTATUS_SPP) != 0)
    panic("not from user mode");
  w_stvec((uint64)kernelvec);
  struct proc *p = myproc();
  p->trapframe->epc = r_sepc();
  if (r_scause() == 8) {        // syscall
    if (killed(p)) kexit(-1);
    p->trapframe->epc += 4;     // skip ecall
    intr_on();
    syscall();
  } else if ((which_dev = devintr()) != 0) {
    // device interrupt
  } else if ((r_scause()==15 ||
             r_scause()==13) &&
             vmfault(...) != 0) {
    // page fault (lazy alloc)
  } else {
    setkilled(p);  // unexpected: kill
  }
  if (killed(p)) kexit(-1);
  if (which_dev == 2) yield();  // timer
  usertrapret();
  return MAKE_SATP(p->pagetable);
}

What usertrap does

  1. Verify we came from user mode (check SPP)
  2. Redirect kernel traps to kernelvec
  3. Save user PC from sepc into trapframe
  4. Dispatch by scause:
    • 8 -> system call
    • device -> devintr()
    • 13/15 -> page fault
    • else -> kill process
  5. Yield on timer interrupt
  6. usertrapret() - set up for return

Engineering note: epc += 4

sepc points at the ecall instruction itself. We want to return to the next instruction, so we add 4 (size of one instruction). Without this, the process would re-execute ecall forever.

usertrap Key Steps

1. Verify from user mode

Check sstatus.SPP. If the trap came from S-mode (kernel), something is very wrong - panic(). usertrap only handles user traps.

2. Redirect traps to kernelvec

Set stvec = kernelvec. Now if a trap happens while in the kernel, it goes to kerneltrap instead of uservec. This prevents infinite recursion.

3. Save user PC

p->trapframe->epc = r_sepc() - the hardware saved the user PC in sepc; we copy it into the trapframe so it survives across C function calls.

4. Dispatch by scause

scauseAction
8System call -> syscall()
devicedevintr() handles it
13 / 15Page fault -> vmfault()
othersetkilled(p) - kill process

5. Yield on timer

If which_dev == 2 (timer interrupt), call yield() to give another process a turn. This is the heart of preemptive scheduling.

6. usertrapret()

Fill kernel fields in trapframe, set sstatus and sepc for the return to user. Then return the user page table address so userret can switch satp.

usertrapret()

What it does

Sets up the trapframe for the next trap and configures CPU state for return to user mode.

// Fill kernel fields in trapframe
tf->kernel_satp = r_satp();
tf->kernel_sp = p->kstack + PGSIZE;
tf->kernel_trap = (uint64)usertrap;
tf->kernel_hartid = r_tp();

// Set sstatus for user return
// clear SPP -> return to U-mode
w_sstatus(r_sstatus() & ~SSTATUS_SPP);
// set SPIE -> enable interrupts
w_sstatus(r_sstatus() | SSTATUS_SPIE);

// Set return PC
w_sepc(tf->epc);

Kernel fields

  • kernel_satp - current kernel page table
  • kernel_sp - top of this process's kernel stack
  • kernel_trap - address of usertrap()
  • kernel_hartid - current CPU ID

These are read by uservec on the next trap to set up the kernel environment instantly.

sstatus manipulation

Clear SPP -> sret will return to U-mode. Set SPIE -> interrupts will be enabled after sret.

sepc = trapframe->epc

The user PC (possibly advanced by +4 for syscalls) is written back to sepc. When userret executes sret, the CPU loads PC = sepc and the user resumes.

SECTION 6

System Call Dispatch

User stubs . kernel dispatch table . argument passing

User-Side Stubs (usys.pl)

Generated by usys.pl

The file usys.pl is a Perl script that generates assembly stubs for every system call. Each stub follows the same pattern:

.global fork
fork:
    li a7, SYS_fork    # syscall number
    ecall               # trap to kernel
    ret                 # return to caller
.global write
write:
    li a7, SYS_write   # syscall number
    ecall               # trap to kernel
    ret                 # return to caller

What the stub does

  1. li a7, SYS_xxx - load the syscall number into a7. The kernel reads this to know which syscall is requested.
  2. ecall - trap into the kernel. The CPU switches to S-mode and jumps to uservec.
  3. ret - after the kernel returns (via userret + sret), a0 holds the return value. ret jumps back to the C caller.

Arguments already in place

The C calling convention already put arguments in a0-a5. The stub doesn't need to move them - the kernel reads them directly from the trapframe.

Return value in a0

The kernel writes the return value into trapframe->a0. When userret restores registers, a0 holds the result - exactly where the C caller expects it.

Kernel-Side Dispatch (syscall.c)

From syscall.c

static uint64 (*syscalls[])(void) = {
  [SYS_fork]   sys_fork,
  [SYS_exit]   sys_exit,
  [SYS_read]   sys_read,
  [SYS_write]  sys_write,
  // ... 22 total
};

void syscall(void) {
  int num = myproc()->trapframe->a7;
  if (num > 0 && num < NELEM(syscalls)
      && syscalls[num])
    myproc()->trapframe->a0 =
      syscalls[num]();
  else
    myproc()->trapframe->a0 = -1;
}

How dispatch works

  1. Read syscall number from trapframe->a7 - this is the value the user stub put there before ecall.
  2. Bounds check - verify num is within the table and the slot is non-NULL.
  3. Call the handler - syscalls[num]() invokes the corresponding kernel function (e.g., sys_fork()).
  4. Store return value - write the result into trapframe->a0, which userret will restore into the user's a0.

Invalid syscall number

If num is out of range or the slot is NULL, trapframe->a0 = -1. The user gets -1 as the return value - the standard error indicator.

Function pointer table

The syscalls[] array is indexed by syscall number. Each entry is a function pointer to the implementation. This is a classic O(1) dispatch - no switch statement needed.

Argument Passing

Convention

  • Syscall number -> a7
  • Arguments -> a0-a5 (up to 6 arguments)
  • Return value -> a0

The user stub doesn't move arguments - the C calling convention already placed them in a0-a5. The kernel reads them from the trapframe.

Kernel-side accessors

Inside sys_* functions, the kernel uses helper functions to read arguments from the trapframe:

argint(n) - how it works

int
argint(int n)
{
  return *(
    int*)(myproc()->
      trapframe->a0 + n);
}

Wait - that's not quite right. Actually, argint(n) reads the n-th argument from the trapframe's argument registers:

int
argint(int n)
{
  struct trapframe *tf =
    myproc()->trapframe;
  switch (n) {
    case 0: return tf->a0;
    case 1: return tf->a1;
    case 2: return tf->a2;
    // ... a3-a5
  }
}

Validation is critical

argaddr(n) returns a user pointer, but the kernel must validate it before dereferencing. Functions like copyin() / copyout() safely copy data across the user/kernel boundary, checking that the address is within the process's legal memory.

SECTION 7

Return to User

userret . kerneltrap

userret (trampoline.S)

From trampoline.S (simplified)

userret:
    # a0 = TRAPFRAME addr
    # a1 = user page table (satp)

    # flush instruction cache
    sfence.vma zero, zero

    # switch to user page table
    csrw satp, a1
    sfence.vma zero, zero

    # restore user a0 LAST
    ld a0, 112(a0)   # a0 = user's a0

    # restore all 32 user regs
    ld ra, 40(a0)    # ... wait, a0 changed!
    # (actual code uses t0 as temp)

    sret             # PC=sepc, mode=U

Actual order matters

The real userret restores a0 last, because once a0 is overwritten with the user value, it can no longer be used as the trapframe base pointer. All other registers are restored first using a0 as base.

kerneltrap()

Traps FROM kernel mode

While the kernel is running (in S-mode), traps can still occur - timer interrupts, device interrupts, or (buggy) exceptions. These are handled by kerneltrap(), not usertrap().

What kerneltrap does

  1. Save sepc, sstatus, scause - the kernel may call C functions that modify these CSRs.
  2. Call devintr() to check if it's a device interrupt.
  3. If device: handle it (timer -> yield() if myproc() != 0).
  4. If not a device interrupt: panic() - the kernel should never fault.
  5. Restore sepc, sstatus, scause.

Why kernel traps are simpler

No need to save all 32 registers - the compiler already saved callee-saved registers at the call site. No page table switch - the kernel is already using the kernel page table. No stack switch - already on the kernel stack.

Timer interrupt -> yield()

When a timer interrupt fires while in kernel mode, kerneltrap calls yield() only if myproc() != 0 - i.e., if there is a current process. The scheduler itself (no current process) should not yield.

panic on unexpected traps

If the kernel hits a page fault or illegal instruction, that's a kernel bug. There's no safe recovery - panic() halts the system and prints a message. This is by design: kernel bugs must be found, not hidden.

Key Takeaways

Traps are the only door

User -> kernel transition is hardware-enforced. ecall is the only way in. The kernel controls the entry point (stvec), the dispatch (scause), and the return (sret).

Trampoline = airlock

One page, same address in both page tables. uservec saves user state and enters the kernel; userret restores user state and exits. No PTE_U - user can't enter directly.

Trapframe = saved state

32 user registers + kernel environment fields. uservec saves, userret restores. usertrapret() pre-fills kernel fields for the next trap.

Syscall dispatch = O(1) table

User stub puts number in a7, args in a0-a5. Kernel reads a7, indexes into syscalls[], calls handler, returns result in a0.
