SECTION 1

Page Faults

What they are . causes . xv6 handling

What is a Page Fault?

"A page fault is like opening a drawer and finding it empty. You thought the thing was there, but it's not. Now you have to go find it and put it in the drawer before you can use it."

Definition

A page fault occurs when the CPU accesses a virtual address whose PTE is invalid (PTE_V = 0) or doesn't have the right permissions (e.g. writing to a read-only page).

What happens

  1. CPU translates VA -> PA via page table
  2. PTE is invalid or permission denied
  3. CPU traps into the kernel (exception)
  4. scause = 12, 13, or 15
  5. stval = faulting virtual address
  6. Kernel decides: fix it or kill the process

Not always an error

Page faults are not necessarily errors. They are the mechanism that enables lazy allocation, copy-on-write, and memory-mapped files. The kernel uses them as opportunities to set up pages on demand.

Page Fault Causes

When a page fault occurs, the CPU sets scause to indicate the type and stval to the faulting virtual address.

scauseTypeTrigger
13Load page faultRead from invalid/unmapped VA
15Store page faultWrite to invalid/read-only VA
12Instruction page faultExecute from invalid VA

stval register

stval (Supervisor Trap Value) contains the faulting virtual address - the exact VA that caused the fault. The kernel reads it via r_stval() to know which page to fix.

Common causes

  • Page not allocated - lazy allocation: sbrk grew p->sz but didn't map pages yet
  • Permission denied - writing to a read-only page (COW shared page)
  • Page not present - swapped out (xv6 doesn't swap, but real OSes do)
  • Null pointer - accessing VA 0, which is unmapped
  • Stack overflow - stack grows past guard page into unmapped region

Kernel response

For each fault, the kernel checks stval against p->sz and the VMA table. If the address is valid but unmapped -> allocate. If permission issue -> COW fix or kill. If truly invalid -> kill() the process.

Page Fault Handling in xv6

In xv6, page faults are caught in usertrap() (trap.c). The handler checks scause and calls vmfault() to resolve the fault.

From trap.c - usertrap()

} else if ((r_scause() == 15 ||
           r_scause() == 13) &&
          vmfault(p->pagetable, p->sz,
                  r_stval(),
                  (r_scause() == 13) ? 1 : 0
          ) != 0) {
  // page fault on lazily-allocated page
  // vmfault returned error -> kill process
  p->killed = 1;
}

Breakdown

  • scause 13 = load (read) page fault
  • scause 15 = store (write) page fault
  • vmfault() tries to resolve the fault
  • If it fails (returns non-zero) -> kill the process

The flow

  1. User program accesses a VA
  2. MMU finds PTE invalid -> trap
  3. usertrap() reads scause
  4. If 13 or 15 -> call vmfault()
  5. vmfault allocates / fixes the page
  6. Return to user - retry the instruction
  7. Now the PTE is valid -> instruction succeeds

Key insight

The faulting instruction is re-executed after vmfault fixes the page. The CPU's sepc register still points to the faulting instruction, so sret returns to it. This retry is what makes lazy allocation transparent to user code.

SECTION 2

Lazy Allocation

Allocate pages on demand . vmfault . flow

What is Lazy Allocation?

Traditional approach (eager)

When a program calls sbrk(n) to grow the heap by n bytes, the kernel immediately allocates and maps every page:

  • kalloc() for each 4KB page
  • mappages() to insert into page table
  • Even if the program never uses those pages

This is wasteful - many programs request more memory than they use.

Lazy approach

sbrk(n) just grows p->sz - no pages allocated. Pages are allocated on first access via page fault.

  • sbrk(n) -> p->sz += n (instant)
  • Program reads/writes new address -> page fault
  • vmfault() -> kalloc + mappages
  • Return to user, retry -> success

Benefits

Faster sbrk - no kalloc/mappages overhead. Less memory wasted - unused pages are never allocated. Sparse heaps work efficiently - programs that request large ranges but touch little get exactly what they need.

vmfault() - The On-Demand Allocator

vmfault() in vm.c is the heart of lazy allocation. It checks the faulting address, allocates a page if needed, and maps it.

From vm.c

uint64
vmfault(pagetable_t pagetable, uint64 sz,
        uint64 va, int write)
{
  if (va >= sz)
    return -1;  // out of bounds -> kill

  pte_t *pte = walk(pagetable, va, 0);
  if (pte == 0 || (*pte & PTE_V) == 0) {
    // page not allocated -> allocate now
    uint64 mem = (uint64)kalloc();
    memset((void*)mem, 0, PGSIZE);
    mappages(pagetable, va, PGSIZE, mem,
             PTE_W | PTE_U | PTE_R);
    return 0;  // success
  }
  // ... handle COW, permissions ...
}

Step by step

  1. Bounds check - if va >= sz, the address is outside the process's memory -> return -1 (kill)
  2. Walk page table - walk() finds the PTE for va
  3. Check PTE_V - if not valid, the page doesn't exist yet
  4. kalloc - allocate a fresh 4KB physical page
  5. memset to 0 - zero-fill (security: no stale data)
  6. mappages - insert into page table with PTE_W | PTE_U | PTE_R
  7. Return 0 - success, retry the instruction

Parameters

  • pagetable - the process's page table
  • sz - process memory size (upper bound)
  • va - faulting virtual address (from stval)
  • write - 1 if store fault, 0 if load fault

SECTION 3

Copy-on-Write (COW)

Share pages . copy only when written . reference counting

What is Copy-on-Write?

The problem with fork()

When fork() creates a child, it copies all parent pages to the child via uvmcopy():

  • kalloc() a new page for each parent page
  • memmove() to copy the data
  • mappages() in child's page table

This is expensive - O(n) in memory size. And often the child immediately calls exec() and discards all copied pages!

COW solution

fork() shares pages between parent and child - both point to the same physical pages, but marked read-only. Pages are copied only when written.

  • fork -> map child to same physical pages (no copy)
  • Both parent and child PTEs have PTE_W cleared
  • Write to shared page -> page fault (scause=15)
  • vmfault detects COW -> copies page -> sets PTE_W

Benefits

Fast fork - no page copying. Shared pages until modified - if child only reads, no copy ever happens. exec-friendly - child calls exec -> old pages freed, no copy was wasted.

COW Implementation

Implementing COW requires changes to fork, vmfault, and a reference counting mechanism.

1. fork() - share instead of copy

Instead of uvmcopy() (which copies), map child pages to the same physical pages as parent. Clear PTE_W in both parent and child PTEs.

// In fork, for each parent page:
*pte_parent &= ~PTE_W;  // clear W
*pte_parent |= PTE_COW; // mark COW (bit 8)
// child PTE points to same PA
*pte_child = *pte_parent; // same PA, no W

2. Write to shared page -> fault

When either process writes, the MMU sees PTE_W is clear -> store page fault (scause=15) -> vmfault() is called.

3. vmfault() - detect and copy

// In vmfault, after PTE_V check:
if (*pte & PTE_COW) {
  // This is a COW page
  uint64 pa = PTE2PA(*pte);

  // If only 1 reference, just set W
  if (ref_count(pa) == 1) {
    *pte |= PTE_W;
    *pte &= ~PTE_COW;
    return 0;
  }

  // Multiple refs -> copy
  uint64 new = (uint64)kalloc();
  memmove((void*)new, (void*)pa, PGSIZE);
  *pte = PA2PTE(new) | PTE_W
       | PTE_U | PTE_R | PTE_V;
  dec_ref(pa);  // old page loses a ref
  return 0;
}

4. Reference counting

Track how many processes share each physical page. When ref count drops to 1, the last owner can just set PTE_W - no copy needed. xv6 lab uses a reference count array indexed by physical page number.

COW Flow

Visual timeline of copy-on-write: fork shares pages, then a write triggers the copy.

Reference Counting for COW

COW needs to track how many processes share each physical page. When the count drops to 1, no copy is needed - just set PTE_W.

Why reference counting?

Without ref counting, vmfault would always copy on a COW fault - even if only one process still references the page. That's wasteful. With ref counting:

  • ref == 1 -> last owner -> just set PTE_W, no copy
  • ref > 1 -> shared -> copy, then decrement old page's ref
  • ref == 0 -> no one uses it -> kfree() the page

Implementation in xv6 lab

A reference count array indexed by physical page number. Each physical page pa maps to ref_array[(pa - KERNBASE) / PGSIZE]. Increment on fork share, decrement on kfree or COW copy.

Operations

EventAction
kalloc new pageref = 1
fork shares pageref++ (increment)
COW copy in vmfaultold ref--, new ref = 1
kfree (page freed)ref--; if 0 -> free
COW fault, ref == 1just set PTE_W (no copy)

Thread safety

The ref count array must be protected by a lock (spinlock). Multiple CPUs can fork and free simultaneously. Without locking, the increment/decrement race condition would corrupt the count, leading to use-after-free or double-free bugs.

SECTION 4

Guard Pages

Stack protection . layout . overflow detection

Stack Guard Pages

The stack overflow problem

If a program's stack grows beyond its allocated space (deep recursion, large local arrays), it can overwrite adjacent memory - another process's stack, heap data, or kernel memory. This is a security vulnerability and a debugging nightmare.

Guard page solution

A guard page is an unmapped page placed below the stack. If the stack overflows, the access hits the guard page -> page fault -> kernel kills the process (instead of corrupting other memory).

  • Guard page has PTE_V = 0 (not valid)
  • Any access -> immediate page fault
  • Kernel sees fault below stack -> kill() the process
  • Other memory is safe

From memlayout.h

// Each kernel stack gets a guard page
#define KSTACK(p) (TRAMPOLINE - (p+1)*2*PGSIZE)

// Layout per process:
//   [guard page] [kernel stack]
//   [guard page] [kernel stack]
//   ...

Each process gets 2 pages: one guard (unmapped) + one stack. The guard page sits directly below the stack, so any stack overflow immediately hits it.

User stack guard

The user stack also has a guard page. In xv6, the first page below the user stack is left unmapped. A null pointer dereference or stack overflow into this region triggers a page fault that kills the process - a clean failure instead of silent corruption.

SECTION 5

Memory-Mapped Files (mmap)

File-backed pages . VMA . lazy loading

What is mmap?

Definition

mmap(addr, length, prot, flags, fd, offset) maps a file into the process's address space. After mmap, reads and writes to the mapped region go directly to the file, not anonymous memory.

Parameters

  • addr - suggested VA (often 0 = kernel chooses)
  • length - number of bytes to map
  • prot - PROT_READ, PROT_WRITE, PROT_EXEC
  • flags - MAP_SHARED, MAP_PRIVATE
  • fd - file descriptor of the file to map
  • offset - offset within the file

Lazy by nature

mmap does not read the file into memory immediately. It only records the mapping. Pages are loaded on demand via page fault - when the program first reads or writes the mapped region.

  • mmap -> record VMA (no I/O)
  • First read -> page fault -> readi from file
  • Write -> mark page dirty
  • munmap or exit -> write back if dirty

Why mmap?

No need for explicit read/write calls - the file is memory. The kernel handles paging automatically. Large files can be accessed without loading the entire file. Multiple processes can share read-only mappings efficiently.

mmap Flow

Step-by-step: mmap records the mapping, then page faults load file data on demand.

1. mmap() - record mapping

mmap finds a free VA range and records a VMA (Virtual Memory Area) entry mapping that range to (fd, offset). No pages allocated, no I/O.

2. Access -> page fault

When the program reads or writes the mapped region, the PTE is invalid -> page fault (scause=13 or 15) -> vmfault() is called.

3. vmfault() - load from file

vmfault checks the VMA table. If the faulting VA is in a file-backed VMA:

  1. kalloc() a new page
  2. readi(ip, ...) - read file data into the page
  3. mappages() with appropriate permissions
  4. If MAP_SHARED + write -> mark PTE_D (dirty)

4. Write-back

When the page is dirty and either munmap is called or the process exits, the kernel writes the modified page back to the file via writei(). For MAP_PRIVATE, writes create a private copy (like COW) - the file is not modified.

5. munmap()

munmap(addr, length) removes the mapping. For each mapped page:

  • If dirty and MAP_SHARED -> writei back to file
  • uvmunmap - remove PTE, kfree the page
  • Remove the VMA entry

Summary

mmap = lazy file-backed memory. The file becomes part of the process's address space. Pages appear on demand, changes are written back automatically. This is how shared libraries, memory-mapped I/O, and file-backed shared memory work.

VMA - Virtual Memory Area

A VMA tracks a contiguous range of virtual addresses and what backs them. vmfault checks the VMA table to decide how to handle each page fault.

What a VMA tracks

FieldPurpose
startStart VA of the mapping
endEnd VA (exclusive)
filePointer to inode (NULL = anonymous)
offsetOffset within the file
protPermissions (R / W / X)
flagsMAP_SHARED or MAP_PRIVATE

Stored per-process

Each process has its own VMA table (an array of VMA structs). In xv6 lab, struct proc contains struct vma vma[NVMA] where NVMA = 16. Each mmap call fills one VMA slot.

vmfault decision logic

When vmfault(va) is called, it checks the VMA table:

  1. VA in anonymous VMA? -> lazy alloc: kalloc + zero-fill + map
  2. VA in file-backed VMA? -> kalloc + readi from file + map
  3. PTE has PTE_COW? -> COW: copy page (or set W if ref==1)
  4. VA not in any VMA and < sz? -> lazy heap alloc
  5. VA >= sz and not in VMA? -> invalid -> kill process

The unifying idea

Page faults + VMA table = one mechanism, many policies. The same vmfault handler serves lazy allocation, COW, and mmap - it just checks the VMA table and PTE flags to decide what to do. This is the power of virtual memory abstraction.

Advanced Page Table Features

PTE bits . manipulation . super pages

PTE Permission Bits (riscv.h)

Each PTE contains permission bits that control access. These bits are what make guard pages, COW, and kernel/user separation possible.

BitValueNameMeaning
01PTE_VValid - PTE is active
12PTE_RReadable
24PTE_WWritable
38PTE_XExecutable
416PTE_UUser-accessible

Reserved bits

Bits 8-9 are reserved in the RISC-V spec - the hardware ignores them. xv6 labs use bit 8 (PTE_COW = 256) as a software-managed COW flag. The kernel sets it; the hardware doesn't interpret it.

How bits are used

  • Guard pages - PTE_V = 0: any access -> fault
  • COW - PTE_W cleared + PTE_COW set: write -> fault
  • Trampoline - PTE_U cleared: only kernel can access
  • Read-only data - PTE_R set, PTE_W clear: write -> fault
  • Code pages - PTE_X + PTE_R, no PTE_W: write -> fault

Without PTE_U

If PTE_U is not set, only the kernel can access that page. User-mode access -> fault. This is how the kernel protects its own code, data, and the trampoline page from user programs. The kernel can still access them because it runs in supervisor mode.

Page Table Manipulation

xv6 provides several functions to read and modify page table entries. These are the building blocks for lazy allocation, COW, and mmap.

FunctionPurpose
walk(pt, va, alloc)Returns pointer to PTE for va. If alloc=1, creates intermediate levels as needed.
mappages(pt, va, sz, pa, perm)Creates mappings: for each page in [va, va+sz), sets PTE to point to pa with perm.
uvmunmap(pt, va, npages, do_free)Removes npages mappings starting at va. If do_free=1, also kfrees the physical pages.
uvmdealloc(pt, oldsz, newsz)Shrinks from oldsz to newsz. Calls uvmunmap for freed pages.
uvmcopy(old, new, sz)Copies all pages from old to new page table (used by fork).
copyin / copyoutCopies data between user and kernel space, using walk to translate addresses.

Direct PTE manipulation

walk() returns a pte_t * - a direct pointer to the PTE. You can modify flags directly:

pte_t *pte = walk(pagetable, va, 0);

// Set write permission
*pte |= PTE_W;

// Clear write permission
*pte &= ~PTE_W;

// Mark as COW (reserved bit 8)
*pte |= (1 << 8);

// Check if valid
if (*pte & PTE_V) { ... }

// Get physical address
uint64 pa = PTE2PA(*pte);

Caution

After modifying a PTE, the hardware TLB may still hold the old entry. Use sfence_vma() to flush the TLB for that address, ensuring the CPU sees the updated PTE on the next access. This is critical when changing permissions (e.g. clearing PTE_W for COW).

Super Pages (2 MB)

RISC-V Sv39 supports 2 MB super pages - a level-1 PTE that directly maps a 2 MB region instead of 512 individual 4 KB pages.

How it works

Normal Sv39 has 3 levels: L2 -> L1 -> L0 -> 4 KB page. A super page stops at L1: the L1 entry has PTE_V + leaf flags (PTE_R/W/X) set, directly mapping a 2 MB region.

  • 1 super page = 2 MB = 512 x 4 KB
  • One PTE instead of 512 PTEs + 1 L0 table
  • Saves one page table page per 2 MB region
  • Fewer TLB misses - one TLB entry covers 2 MB

Trade-offs

Super pages reduce page table size and improve TLB hit rates for large allocations. But they require physical alignment (2 MB-aligned PA) and waste memory if only a small portion of the 2 MB is used (internal fragmentation).

xv6 does not use super pages

By default, xv6 only uses 4 KB pages for simplicity. The hardware supports super pages, but xv6's walk() and mappages() always go to level 0. Using super pages would require modifying walk to detect L1 leaf entries and mappages to create them.

When super pages matter

Real OSes (Linux, FreeBSD) use super pages (called huge pages) for large allocations, kernel mappings, and database workloads. A 1 GB process with 4 KB pages needs ~2 MB of page tables; with 2 MB super pages, only ~4 KB. The TLB coverage improvement is even more significant.

Sv39 page sizes

LevelPage size
L0 (leaf)4 KB
L1 (leaf)2 MB (super page)
L2 (leaf)1 GB (giant page)

Key Takeaways

Page faults enable everything

Lazy allocation, COW, and mmap all rely on the same mechanism: vmfault() catches the fault, checks the VMA table and PTE flags, and resolves it. The instruction is then retried transparently.

Lazy allocation saves time & memory

sbrk just grows p->sz. Pages are allocated on first access via page fault. Faster sbrk, no wasted memory on unused pages.

COW makes fork fast

fork shares pages read-only. Copy happens only on write, via page fault + vmfault. Reference counting avoids unnecessary copies when only one reference remains.

Guard pages protect stacks

An unmapped page below each stack catches overflows. Access -> page fault -> kill process. Prevents silent memory corruption. KSTACK(p) places a guard + stack per process.

mmap maps files into memory

mmap records a VMA mapping VA range -> file. Pages loaded on demand via readi. Dirty pages written back on munmap or exit. One mechanism, many uses.

PTE flags control access

PTE_V, PTE_W, PTE_U, PTE_R, PTE_X - and reserved bit 8 for COW. walk() gives direct PTE access. sfence_vma() flushes the TLB after changes.
