SECTION 1

What Is an ISA?

The contract between software and hardware

The Hardware-Software Contract

"An ISA is like a restaurant menu. The menu (ISA) tells you what dishes (instructions) you can order. The kitchen (CPU) figures out how to cook them."

Definition

An ISA (Instruction Set Architecture) is the contract between software and hardware. It defines:

  • Instructions - what operations the CPU understands
  • Registers - named storage locations inside the CPU
  • Memory addressing modes - how instructions reference memory
  • Data types - word size, integer/float representation
  • Privilege levels - who can execute which instructions
ISA = the interface
Microarchitecture = how the CPU actually implements it

Why this matters for OS

The OS kernel runs at a higher privilege level than user programs. The ISA defines exactly how that privilege transition works - system calls, traps, interrupts. Without understanding the ISA, you cannot understand how the OS controls hardware.

Same ISA, different CPUs

An Intel Core i7 and an AMD Ryzen implement the same ISA (x86-64) but with completely different microarchitectures. Software compiled for x86-64 runs on both - that is the power of the ISA abstraction.

Why the ISA Matters

Key insight

Same C code, three different ISAs, three different assembly listings, three different machine-code byte streams. The ISA is the boundary where portability ends and hardware specificity begins.

SECTION 2

CISC vs RISC

Two philosophies of CPU design

Two Philosophies

CISC - Complex Instruction Set Computer

  • Many instructions (1000+)
  • Variable-length encoding (1-15 bytes)
  • Memory-to-memory operations (e.g. add [a], [b])
  • Fewer registers (16 GP)
  • Complex decoding - must parse variable-length fields
  • Example: rep movsb - one instruction copies a string

RISC - Reduced Instruction Set Computer

  • Few instructions (~50 base)
  • Fixed-length encoding (4 bytes)
  • Load/store only - arithmetic uses registers, not memory
  • Many registers (31-32 GP)
  • Simple decoding - every instruction is exactly 4 bytes
  • Example: ld -> add -> sd - three instructions
CISC: fewer instructions, more work per instruction
RISC: more instructions, less work per instruction, but faster each

Why RISC Won (Mostly)

"CISC is like a Swiss Army knife - lots of tools, but heavy and complex. RISC is like a set of simple, specialized tools - each one does one thing fast."

Why RISC is simpler to build fast

  • Pipelining is easier - all instructions same size, predictable decode
  • Simpler decoding - no variable-length parsing
  • Less silicon - smaller decode unit, more room for cache
  • Compilers prefer simple instructions - easier to optimize and schedule
  • Power efficiency - simpler decode = less energy per instruction

Engineering reality: modern x86 is RISC inside

Modern Intel/AMD CPUs internally translate CISC instructions into RISC-like micro-ops (uops). The front-end decodes x86 into uops, then the execution engine is essentially a RISC processor. So even CISC CPUs are RISC at the execution level.

The irony

x86 survived because of its software ecosystem, not because CISC is better. The ISA is CISC, but the silicon is RISC. ARM and RISC-V skipped the CISC layer entirely.

SECTION 3

ISA Overviews

x86 . ARM . RISC-V - history, registers, privilege

x86 - The CISC Giant

History

  • 1978 - Intel 8086, 16-bit, start of x86
  • 1985 - 80386, 32-bit (IA-32)
  • 2003 - AMD64 / x86-64, 64-bit extension
  • Backward compatible to the 8086 - 45+ years of legacy

Characteristics

  • Variable-length instructions: 1-15 bytes
  • 16 GP registers (rax, rbx, rcx, rdx, rsi, rdi, rbp, rsp, r8-r15)
  • Memory operands in most arithmetic instructions
  • Complex addressing modes (base + index x scale + displacement)

x86 Privilege: Ring 0 and Ring 3

Ring 0 - Kernel mode

The OS kernel runs here. Full access to all hardware, memory, and privileged instructions. Highest privilege.

Ring 3 - User mode

User applications run here. Restricted memory access, cannot execute privileged instructions. Must use syscalls to request kernel services.

Syscall mechanism

Enter kernel: syscall instruction (Ring 3 -> Ring 0).
Return to user: sysret instruction (Ring 0 -> Ring 3).

Rings 1 and 2

Defined by x86 but almost never used by modern OSes. Designed for device drivers and OS services, but Linux/Windows only use Ring 0 and Ring 3.

ARM - The RISC Mobile King

History

  • 1985 - ARM2, first commercial RISC CPU (Acorn)
  • 2011 - ARMv8 / AArch64 (ARM64), 64-bit
  • Dominates mobile phones, tablets, Apple Silicon (M1-M4)

Characteristics

  • Fixed 4-byte instructions
  • 31 GP registers (x0-x30, plus SP)
  • Load/store architecture
  • Conditional execution (ARMv8: conditional select)

"ARM is like a fuel-efficient car - it doesn't have every feature, but it gets you there using less power. That's why it conquered mobile."

ARM64 Privilege: Exception Levels

EL0 - User

Applications run here. Restricted memory, no privileged instructions.

EL1 - OS Kernel

The OS kernel (Linux, macOS XNU) runs here. Manages processes, memory, drivers.

EL2 - Hypervisor

Hardware virtualization layer. KVM, type-1 hypervisors. Can trap EL1 operations.

EL3 - Secure Monitor

TrustZone secure world transition. Highest privilege - can switch between secure and non-secure states.

Syscall mechanism

Enter kernel: svc (Supervisor Call) instruction (EL0 -> EL1).

RISC-V - The Open RISC

History

  • 2010 - Designed at UC Berkeley
  • Open ISA - free to implement, no licensing fees
  • Modular: base ISA + optional extensions
  • Clean design - no 40 years of legacy

RV64GC - what xv6 uses

RV64GC = RV64I + M + A + F + D + C

  • RV64I - base 64-bit integer ISA (47 instructions)
  • M - multiply/divide
  • A - atomic operations
  • F - single-precision float
  • D - double-precision float
  • C - compressed 16-bit instructions

"RISC-V is like open-source software, but for hardware. Anyone can read the spec, build a chip, and contribute. No vendor lock-in."

Why RISC-V matters

  • Education - clean, small, readable spec (~150 pages)
  • Research - easy to extend with custom instructions
  • Industry - SiFive, Western Digital, Google (Android RISC-V)
  • xv6-riscv - MIT 6.1810's teaching OS targets RV64GC

Not just one ISA

RISC-V is a family of ISAs. You pick a base (32/64/128-bit) and add only the extensions you need. An IoT chip might use RV32IMC; a server chip might use RV64GC + vector extensions.

How to read an ISA name

RV64IMAFDC means: 64-bit base integer ISA, with multiply, atomic, float, double, and compressed extensions. The G shorthand means IMAFD together.

Modularity = the key innovation

Unlike x86 (one monolithic ISA) or ARM (profile-based), RISC-V lets chip designers pick exactly the extensions they need. A smartwatch chip doesn't pay for floating-point hardware it won't use.

xv6-riscv requires

RV64I + M (for mul/div in kernel) + A (for spinlocks). The C extension is optional but commonly enabled. F/D are not used by the kernel itself.

RISC-V Privilege Levels

U-mode - User

Applications run here. Cannot execute privileged instructions, cannot access kernel memory. Privilege level 0.

S-mode - Supervisor (OS Kernel)

The OS kernel (xv6, Linux) runs here. Can manage page tables, handle traps, configure interrupts. Privilege level 1.

M-mode - Machine

Firmware and bootloader (OpenSBI on RISC-V). Full hardware access, including security features (PMP). Privilege level 3 - highest.

Syscall mechanism

Enter kernel: ecall (Environment Call) - U -> S transition.
Return to user: sret (Supervisor Return) - S -> U transition.

No hypervisor level in base spec

RISC-V has an optional H extension for hypervisor support (HS-mode), but the base privilege model is just U/S/M - simpler than ARM's four levels.

Same concept, different names

Every ISA needs: user/kernel separation, a way to enter the kernel (syscall), a way to return, a page table pointer, and a trap vector base. The concepts are identical - only the names and mechanisms differ.

For xv6 on RISC-V

xv6 uses ecall for syscalls, stvec to set the trap handler, satp to point to the page table, and sret to return to user mode. These are the RISC-V names you'll see in the xv6 source.

RISC-V's zero register (x0)

RISC-V hardwires x0 to always read as zero and discard writes. This means add x0, x0, 0 is a NOP, and mv to x0 discards a value - no special instruction needed.

x86's register scarcity

With only 16 GP registers, x86 spills to the stack more often. RISC-V's 32 registers give compilers more room to keep values in registers, reducing memory traffic.

Instruction Encoding Comparison

Why fixed-length matters

Fixed-length encoding means the CPU can decode any instruction in a single step - it always knows where the next instruction starts. Variable-length (x86) requires sequential parsing, which complicates pipelining and superscalar execution.

x0 is special

Register x0 always reads as 0 and writes are discarded. This eliminates the need for a dedicated zero-immediate instruction - just use x0 as a source operand.

Register groups

a0-a7 = function arguments (8 args in registers). t0-t6 = temporary scratch. s0-s11 = preserved across calls. ra = return address for jal/jalr.

Register Conventions

Caller-saved (t0-t6, a0-a7)

The caller must save these registers if it needs their values across a function call. The callee is free to overwrite them.

  • t0-t6 - temporary scratch registers
  • a0-a7 - argument registers (also hold return value in a0)

Callee-saved (s0-s11, sp, ra)

The callee must preserve these registers. If the callee uses them, it must save the original values on the stack and restore them before returning.

  • s0-s11 - saved registers (s0 = frame pointer)
  • sp - stack pointer (must be restored)
  • ra - return address (must be preserved if callee calls another function)

"Caller-saved registers are like scratch paper - you can write on it, but don't expect it to survive if you hand it to someone else. Callee-saved registers are like a shared notebook - if you borrow it, you must put it back exactly as you found it."

x0 is always zero

x0 is neither caller-saved nor callee-saved - it is hardwired to zero. Reading it always gives 0; writing to it does nothing. This is a RISC-V design choice that simplifies the ISA.

Stack alignment

The stack pointer sp must always be 16-byte aligned at function entry. This is a hard requirement of the RISC-V calling convention - violating it causes misalignment faults on some operations.

SECTION 6

RISC-V Instruction Formats

How 32 bits are carved into fields

Instruction Formats Overview

All instructions are 32 bits

(Except C extension: 16-bit compressed instructions.) The 32 bits are carved into fields - opcode, register selectors, and immediates - in different layouts depending on the instruction type.

Four main formats

  • R-type - Register: add rd, rs1, rs2
  • I-type - Immediate: addi rd, rs1, imm
  • S-type - Store: sw rs2, offset(rs1)
  • U-type - Upper immediate: lui rd, imm

Plus B-type (branches) and J-type (jumps) - variants of S and U.

Consistent field positions

Opcode is always bits [6:0]. rs1 is always bits [19:15]. This consistency simplifies decoding - the decoder can extract opcode and rs1 without knowing the format yet.

U-type, J-type, and B-type

U-type - Upper Immediate

20-bit immediate + rd + opcode. Used for:

  • lui rd, imm - Load Upper Immediate (places imm in top 20 bits)
  • auipc rd, imm - Add Upper Immediate to PC (for PC-relative addressing)

J-type - Jump

20-bit immediate + rd + opcode. Used for:

  • jal rd, offset - Jump and Link (rd = return address, PC += offset)

The 20-bit immediate is sign-extended and represents a +/-1 MB range.

B-type - Branch

12-bit immediate + rs1 + rs2 + funct3 + opcode. Used for:

  • beq, bne, blt, bge, bltu, bgeu - conditional branches

12-bit immediate gives +/-4 KB branch range (always even - LSB is always 0).

Engineering note: immediate bits are shuffled

The immediate bits in B-type and J-type look scrambled (imm[12|10:5], imm[4:1|11], etc.). This is by design: the shuffling keeps the opcode in bits [6:0] and rs1 in bits [19:15] across all formats. The decoder extracts opcode and rs1 first, then rearranges the immediate based on format.

Pseudo-instructions

RISC-V defines pseudo-instructions - convenient aliases that the assembler expands to real instructions:

  • mv rd, rs -> addi rd, rs, 0 (move register)
  • li rd, imm -> addi rd, x0, imm (load immediate, small)
  • li rd, imm -> lui + addi (load immediate, large)
  • nop -> addi x0, x0, 0 (no operation)

Why no mov instruction?

RISC-V avoids dedicated move/nop instructions. Instead, x0 (hardwired zero) makes addi rd, rs, 0 a move and addi x0, x0, 0 a nop. Fewer instructions, same functionality.

No flags register

Unlike x86, RISC-V has no condition flags register (no ZF, CF, etc.). Branch instructions compare registers directly (beq rs1, rs2, label). This simplifies the pipeline - no flag dependencies between instructions.

Load/store architecture

RISC-V is a load/store architecture: arithmetic instructions (add, sub, etc.) operate only on registers. To use a memory value, you must first lw/ld it into a register, compute, then sw/sd the result back.

address = base register (rs1) + signed offset (imm)

Addressing mode

RISC-V has exactly one addressing mode for memory: base + signed offset. The offset is a 12-bit signed immediate (range -2048 to +2047). No indexed, scaled, or post-increment addressing - just base + offset.

Signed vs unsigned loads

lb sign-extends the byte to 64 bits (preserves negative values). lbu zero-extends (treats as unsigned). lw sign-extends 32 bits to 64 bits in RV64 - important when loading 32-bit values on a 64-bit CPU.

Pseudo-instructions for control flow

  • j offset -> jal x0, offset (jump, discard return address)
  • jr rs -> jalr x0, rs, 0 (jump to register, discard return)
  • ret -> jalr x0, ra, 0 (return to caller)
  • call offset -> auipc ra, ...; jalr ra, ra, ... (call, far range)

jal vs jalr

jal uses a 20-bit immediate offset (PC-relative, +/-1 MB). jalr uses a register + 12-bit offset (can jump anywhere in 64-bit address space). Function calls use jal for nearby functions and auipc+jalr for far calls.

ret = jalr x0, ra, 0

The ret pseudo-instruction is just jalr with x0 as the link register (discard return address) and ra as the target. Since x0 discards writes, this is a pure jump to ra - the return address saved by the original jal.

Summary - Key Takeaways

The ISA is the contract

An ISA defines the instructions, registers, memory addressing, and privilege levels that software relies on. Same C code compiles to different assembly on x86, ARM, and RISC-V.

RISC won (mostly)

Fixed-length instructions, load/store architecture, many registers. Even modern x86 translates CISC into RISC-like micro-ops internally.

RISC-V privilege: U / S / M

User mode (U), Supervisor/OS kernel (S), Machine/firmware (M). Syscall = ecall, return = sret. xv6 runs in S-mode.

32 registers, clear conventions

x0 = zero, ra = return address, sp = stack, a0-a7 = args, s0-s11 = saved, t0-t6 = temporaries. Caller-saved vs callee-saved.

Six instruction formats

R, I, S, U, B, J - all 32 bits. Opcode always [6:0], rs1 always [19:15]. Immediates are shuffled to keep field positions consistent.

Load/store + base+offset

Arithmetic uses registers only. Memory access via lw/sw with base + signed offset. One addressing mode, simple and fast.

ISA = instructions + registers + memory model + privilege levels
xv6 on RISC-V = RV64GC, S-mode, ecall/sret, 32 GP registers
