SECTION 1

File System Overview

The Unix file model . disk layout . superblock

The Unix File Model

"In Unix, everything is a file. Your keyboard is a file. Your screen is a file. The disk is a file. Even the list of files is a file (directory)."

One unified interface

The same four operations work on all of them:

  • open - get a handle (file descriptor)
  • read - pull bytes from the file
  • write - push bytes into the file
  • close - release the handle

Why this matters

You don't need separate APIs for the keyboard, the screen, the disk, and directories. One set of system calls handles everything. This is the core design principle of Unix - and xv6 inherits it.

xv6 File System Layout

The disk is divided into contiguous regions. Each has a fixed purpose defined in fs.h and param.h.

Layout order on disk

Block 0 is unused (reserved for boot). Block 1 is the superblock. Then log, inode blocks, bitmap, and data blocks - in that order. The superblock records where each region starts.

struct superblock (fs.h)

The superblock is the master header of the file system. It records the magic number, total size, and the starting block of every region.

Definition

struct superblock {
  uint magic;      // FSMAGIC = 0x10203040
  uint size;       // total blocks (FSSIZE)
  uint nblocks;    // number of data blocks
  uint ninodes;    // number of inodes
  uint nlog;       // number of log blocks
  uint logstart;   // first log block number
  uint inodestart; // first inode block number
  uint bmapstart;  // first bitmap block number
};

What each field does

  • magic - sanity check: is this really an xv6 FS?
  • size - total blocks on the disk (2000)
  • nblocks - data blocks available for files
  • ninodes - max number of files/dirs (50)
  • nlog - blocks reserved for the log
  • logstart / inodestart / bmapstart - offsets to each region

Read once, used everywhere

readsb() reads the superblock from disk into memory at boot. Every other FS routine uses these values to locate inodes, the bitmap, and the log.

SECTION 2

Inodes

On-disk structure . block addressing . in-memory cache . operations

On-Disk Inode - struct dinode (fs.h)

An inode is the metadata of a file: its type, size, link count, and where its data blocks live. The file name is not stored here - it lives in directory entries.

Definition

struct dinode {
  short type;   // file type
  short major;  // major device no.
  short minor;  // minor device no.
  short nlink;  // hard link count
  uint size;    // file size in bytes
  uint addrs[NDIRECT + 1];
    // 12 direct + 1 indirect
};

type values

ValueConstantMeaning
00free (unused)
1T_DIRdirectory
2T_FILEregular file
3T_DEVICEdevice file

Key constants

  • NDIRECT = 12 - direct block pointers
  • NINDIRECT = BSIZE / sizeof(uint) = 256 - indirect pointers
  • MAXFILE = NDIRECT + NINDIRECT = 268 - max blocks per file
  • Max file size = 268 x 1024 = 274,432 bytes

Inode Block Addressing

An inode stores NDIRECT + 1 = 13 block addresses. The first 12 point directly to data blocks. The 13th points to an indirect block containing 256 more pointers.

In-Memory Inode - struct inode (file.h)

The kernel keeps a cache of inodes in memory. The in-memory struct inode wraps the on-disk dinode with extra fields for locking and reference counting.

Definition

struct inode {
  uint dev;           // device number
  uint inum;          // inode number
  int ref;            // reference count
  struct sleeplock lock;
  int valid;           // has it been read from disk?

  short type;          // copy of dinode fields
  short major;
  short minor;
  short nlink;
  uint size;
  uint addrs[NDIRECT + 1];
};

Extra fields vs dinode

  • dev / inum - identifies which inode on which device
  • ref - how many file descriptors point to this inode
  • lock - sleeplock for safe concurrent access
  • valid - lazy read: load from disk only when first accessed

The itable

The kernel maintains a fixed-size array: struct inode itable[NINODE] with NINODE = 50. This is the inode cache - recently used inodes stay in memory.

Key functions

  • iget(dev, inum) - find or create in-memory inode, increment ref
  • iput(ip) - decrement ref; if 0, may evict from cache

Inode Operations

The kernel provides a set of functions to manage inodes. Each operates on struct inode * and handles disk I/O transparently.

FunctionPurposeKey detail
ialloc(dev, type)Allocate a new inodeScans bitmap for free inode, sets type, writes to disk
iget(dev, inum)Get in-memory inodeReturns cached or newly loaded inode; increments ref
ilock(ip) / iunlock(ip)Lock / unlock for accessSleeplock; ilock also reads from disk if !valid
iput(ip)Release inodeDecrements ref; if 0 and nlink == 0, frees blocks + inode
readi(ip, dst, off, n)Read data from inodeTranslates offset -> block number -> bread -> copy
writei(ip, src, off, n)Write data to inodeAllocates blocks as needed via bmap, updates size

Pattern: lock before use

Most operations require ilock(ip) first, then readi/writei/dirlookup, then iunlock(ip). The lock ensures no other thread modifies the inode mid-operation.

SECTION 3

Directories

Directory entries . path resolution

Directory Structure

A directory is just a file whose content is an array of dirent entries. Each entry maps a name to an inode number.

Definition (fs.h)

#define DIRSIZ 14

struct dirent {
  ushort inum;           // inode number
  char   name[DIRSIZ];  // name (null-padded)
};

Key facts

  • DIRSIZ = 14 - max file name length
  • inum = 0 means the entry is free (deleted)
  • ROOTINO = 1 - the root directory's inode number
  • Each entry is 16 bytes: 2 (inum) + 14 (name)

Directories are files

Because a directory is just a file, you read it with readi and write it with writei. The only difference is that the data is interpreted as dirent entries.

Path Resolution

Resolving a path like /home/user/file.txt means walking directory entries one component at a time, starting from the root.

Two key functions

  • namei(path) - resolves a full path to an inode *
  • nameiparent(path) - returns the parent inode + the last component name (for creating/deleting entries)

How it works

  1. Start at root inode (ROOTINO = 1) if path begins with /
  2. For each component (e.g. home, user, file.txt):
  3. Call dirlookup(parent, component) -> next inode
  4. Repeat until the last component

Each step is a disk read

Each dirlookup reads directory data blocks from disk (or cache). Deep paths = more I/O. This is why path resolution is expensive.

SECTION 4

File Table

struct file . file descriptors . read/write dispatch

struct file (file.h)

A struct file is the kernel's representation of an open file. It wraps an inode (or pipe or device) with a current offset and access mode.

Definition

struct file {
  enum { FD_NONE, FD_PIPE,
         FD_INODE, FD_DEVICE } type;
  int ref;            // reference count
  char readable;      // opened for read?
  char writable;      // opened for write?
  struct pipe *pipe;  // FD_PIPE
  struct inode *ip;   // FD_INODE / FD_DEVICE
  uint off;            // FD_INODE (offset)
  short major;         // FD_DEVICE
};

Why a separate struct?

Two processes opening the same file get different struct file entries - each with its own offset. But they share the same inode. This is why fork() children share the offset but open() does not.

The ftable

The kernel has a fixed array: struct file ftable[NFILE] with NFILE = 100. This is the file table - a system-wide pool of open file objects.

File table functions

  • filealloc() - find a free entry, set ref = 1
  • filedup(f) - increment ref (used by fork, dup)
  • fileclose(f) - decrement ref; if 0, release inode and free entry

File Descriptor Table

Each process has its own array of file descriptors. A file descriptor (FD) is simply an index into this array.

Per-process structure

From proc.h, each struct proc has:

struct file *ofile[NOFILE];
  // NOFILE = 16

FD 0, 1, 2 are conventionally stdin, stdout, stderr.

How FDs work

  • open() -> finds lowest free slot in ofile[] -> stores struct file * -> returns the index
  • read(fd, ...) -> looks up ofile[fd] -> calls fileread
  • close(fd) -> calls fileclose(ofile[fd]) -> sets ofile[fd] = 0

fork() and exec()

  • fork() - child gets a copy of the parent's ofile[]. Each entry gets filedup() - so parent and child share the same struct file (and thus the same offset).
  • exec() - preserves ofile[] across the exec. Open files survive program replacement.

file Operations - fileread / filewrite

fileread and filewrite are the dispatch layer. They check the file type and route to the correct handler.

fileread(f, addr, n)

int
fileread(struct file *f, uint64 addr, int n)
{
  if (!f->readable) return -1;

  switch (f->type) {
  case FD_PIPE:
    return piperead(f->pipe, addr, n);
  case FD_DEVICE:
    return devsw[f->major].read(1, addr, n);
  case FD_INODE:
    ilock(f->ip);
    int r = readi(f->ip, 0, addr,
                  f->off, n);
    if (r > 0) f->off += r;
    iunlock(f->ip);
    return r;
  }
  return -1;
}

filewrite(f, addr, n)

Same dispatch pattern, but:

  • Checks f->writable first
  • FD_PIPE -> pipewrite
  • FD_DEVICE -> devsw[major].write
  • FD_INODE -> writei, then update off

Key observations

  • The offset (f->off) is maintained here, not in the inode - so two FDs to the same file have independent positions
  • readable / writable are checked before any work - set at open() time based on flags
  • For FD_INODE, the inode is locked during the I/O

open() Flow

sys_open is the most complex file syscall. It resolves the path, optionally creates the file, allocates a struct file, and returns a file descriptor.

Step-by-step

  1. argstr - get the path string from user space
  2. argint - get the flags (O_CREATE, O_RDONLY, O_WRONLY, O_RDWR)
  3. If O_CREATE is set: ialloc a new inode (type T_FILE)
  4. Otherwise: namei(path) -> get existing inode
  5. filealloc() - get a free struct file from ftable
  6. Set f->type = FD_INODE, f->ip = ip, f->off = 0
  7. Set readable / writable based on flags
  8. Find lowest free slot in myproc()->ofile[]
  9. Store f there, return the index as the fd

Simplified code

sys_open(void)
{
  char path[MAXPATH];
  int fd, omode;
  struct file *f;
  struct inode *ip;

  argstr(1, path, MAXPATH);
  argint(2, &omode);

  if (omode & O_CREATE) {
    ip = create(path, T_FILE, 0, 0);
  } else {
    ip = namei(path);
    ilock(ip);
  }

  f = filealloc();
  f->type = FD_INODE;
  f->ip = ip;
  f->off = 0;
  f->readable = !(omode & O_WRONLY);
  f->writable = (omode & O_WRONLY) ||
                (omode & O_RDWR);

  fd = fdalloc(f);
  return fd;
}

read() / write() Flow

sys_read and sys_write are thin wrappers: they extract arguments from user space, look up the file, and delegate to fileread / filewrite.

sys_read

sys_read(void)
{
  struct file *f;
  int n;
  uint64 p;

  argfd(0, 0, &f);   // get fd -> file
  argaddr(1, &p);     // get buf addr
  argint(2, &n);      // get byte count

  return fileread(f, p, n);
}

argfd helper

argfd extracts the fd from user registers, validates it, and looks up myproc()->ofile[fd]. If the fd is out of range or the slot is empty, it returns -1.

sys_write

sys_write(void)
{
  struct file *f;
  int n;
  uint64 p;

  argfd(0, 0, &f);
  argaddr(1, &p);
  argint(2, &n);

  return filewrite(f, p, n);
}

The full chain

  1. User calls read(fd, buf, n)
  2. Trap -> sys_read
  3. argfd -> ofile[fd] -> struct file *
  4. fileread(f, buf, n) dispatches by type
  5. For FD_INODE: readi(ip, ..., off, n)
  6. readi -> bmap -> bread -> copy to user
  7. Update f->off += bytes_read
  8. Return bytes read to user

SECTION 6

Logging

Crash consistency . log protocol . log flow

Why Logging?

The crash consistency problem

A single file operation (like write) may require multiple disk writes: update the data block, update the inode size, update the bitmap. If power fails mid-operation, the file system is left inconsistent - half the writes done, half not.

The logging solution

Write all changes to a log area first. Only when all writes are safely on disk (the commit point), apply them to their final locations. This is write-ahead logging (WAL).

Crash recovery

  • Crash before commit -> log is incomplete -> discard it -> no changes applied -> file system stays consistent
  • Crash after commit, before install -> log is complete -> replay on next boot -> all changes applied
  • Crash during install -> some changes applied, some not -> replay log -> idempotent, so re-applying is safe

Analogy

Think of it like writing a check: you write the check (log), then you transfer the money (install). If the bank crashes after writing the check but before the transfer, you just tear up the check. If it crashes during the transfer, you redo it from the check.

Log Protocol

The log is managed by three functions: begin_op, the write phase, and end_op. From log.c: MAXOPBLOCKS = 10 - max blocks per single operation.

1. begin_op()

Called at the start of a file system operation. Waits until the log is not in use, then reserves space.

  • If a commit is in progress, sleep until done
  • Increment log.lh.n reservation counter
  • Multiple operations can share one log transaction

2. Write phase

During the operation, disk writes (via bwrite) go to the log area, not the final location. The buffer cache tracks which blocks are "dirty" and logs them.

  • log_write() records the block in the log header
  • If the same block is written twice, only one log entry is kept (absorption)

3. end_op()

Called at the end of the operation. If this is the last concurrent operation:

  1. Write the log header to disk -> commit point
  2. Install: copy logged blocks to their final locations
  3. Clear the log header (set count = 0) -> log is empty

Key constants (log.c)

ConstantValueMeaning
MAXOPBLOCKS10Max blocks per operation
LOGSIZEMAXOPBLOCKSMax log entries
nlog30Log blocks on disk (param.h)

The commit point

Writing the log header (with the count of logged blocks) is the atomic commit point. Before this write: crash = discard. After this write: crash = replay. The disk guarantees a single sector write is atomic.

Group commit

Multiple syscalls can batch into one transaction. begin_op increments a counter; end_op decrements it. Only when the counter reaches 0 does the actual commit happen. This amortizes the cost of committing.

SECTION 7

Device Files

Device switch . how device files work

devsw - Device Switch

The device switch table (devsw) is how xv6 implements the "everything is a file" principle for hardware devices. Each device registers read/write function pointers.

Definition (file.h)

struct devsw {
  int (*read)(int, uint64, int);
  int (*write)(int, uint64, int);
};

extern struct devsw devsw[];

Console device

From console.c:

#define CONSOLE 1

void
consoleinit(void)
{
  devsw[CONSOLE].read  = consoleread;
  devsw[CONSOLE].write = consolewrite;
}

How device files are created

  1. mknod("console", CONSOLE, 0) creates a directory entry with type = T_DEVICE, major = 1, minor = 0
  2. open("console", ...) resolves the path -> gets the inode -> sees type == T_DEVICE -> sets f->type = FD_DEVICE, f->major = 1
  3. fileread(f, ...) sees FD_DEVICE -> calls devsw[f->major].read(...) -> consoleread
  4. filewrite(f, ...) similarly calls devsw[f->major].write(...) -> consolewrite

The beauty of devsw

User code calls read(fd, buf, n) - it doesn't know or care whether fd is a regular file, a pipe, or the console. The kernel dispatches transparently via devsw. This is the Unix file abstraction in action.

Key Takeaways

Everything is a file

One interface - open/read/write/close - works on regular files, directories, devices, and pipes. The devsw table makes this possible for hardware.

Inodes are the core

On-disk dinode stores metadata + 12 direct + 1 indirect pointer (268 blocks max). In-memory inode adds locking and reference counting via the itable cache.

Directories are files of entries

A directory is a file containing dirent entries (name -> inode number). Path resolution walks these entries from root via dirlookup.

Logging ensures crash safety

Write-ahead logging: buffer in log -> commit -> install -> clear. Crash before commit = discard. Crash after commit = replay. begin_op / end_op bracket every operation.
