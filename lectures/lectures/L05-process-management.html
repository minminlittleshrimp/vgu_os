SECTION 1

The Process Abstraction

A process is the OS's fundamental unit of isolation and execution

What is a Process?

"A process is like a person at a desk. They have their own notebook (memory), their own desk drawer (open files), and their current task (PC). The OS is the office manager who decides who gets to work and when."

What the OS tracks per process

  • Memory - a private address space (page table)
  • Open files - file descriptors, current directory
  • Execution state - registers, program counter, stack
  • Kernel stack - for executing system calls

The illusion of exclusivity

Each process believes it has the entire machine to itself. The OS creates this illusion by time-sharing the CPU and space-sharing memory through virtual address spaces.

Why this matters

Without the process abstraction, every program would need to cooperate with every other program. The process boundary is what makes isolation and protection possible - one buggy program cannot crash another.

Process State Machine

struct proc - from proc.h

xv6 kernel/proc.h
struct proc {
  struct spinlock lock;
  enum procstate state;
  void *chan;           // sleep channel
  int killed;
  int xstate;           // exit status
  int pid;
  struct proc *parent;  // (under wait_lock)
  uint64 kstack;        // kernel stack VA
  uint64 sz;            // process memory size
  pagetable_t pagetable;
  struct trapframe *trapframe;
  struct context context;  // for swtch()
  struct file *ofile[NOFILE]; // NOFILE=16
  struct inode *cwd;
  char name[16];
};

Key fields

  • lock - protects this proc's state fields
  • state - the current lifecycle state
  • chan - sleep channel for sleep/wakeup
  • trapframe - saved user registers on syscall/trap
  • context - saved callee-saved regs for swtch()
  • pagetable - this process's virtual address space

Locking discipline

p->lock protects individual process state. wait_lock protects the parent-child relationship. ofile[] and cwd are accessed under p->lock.

Why kstack is a VA, not a pointer

kstack stores the virtual address of the kernel stack, not a C pointer - the kernel stack is mapped in the process's kernel page table, not the user page table.

SECTION 2

Process Table and CPU State

How xv6 tracks all processes and per-CPU execution context

Process Table and CPU Array

Global process table

From proc.c: struct proc proc[NPROC] where NPROC = 64. This is a fixed-size array - xv6 does not dynamically allocate process slots.

Per-CPU array

struct cpu cpus[NCPU] where NCPU = 8. Each CPU has its own scheduler context and a pointer to the currently-running process.

struct cpu fields

  • struct proc *proc - the process currently running on this CPU
  • struct context context - the scheduler's own saved context
  • int noff - push_off nesting depth
  • int intena - interrupts enabled before first push_off
// proc.c - global arrays struct proc proc[NPROC]; // NPROC = 64 struct cpu cpus[NCPU]; // NCPU = 8 // proc.h - struct cpu struct cpu { struct proc *proc; // current process struct context context; // scheduler context int noff; // push_off nesting int intena; // interrupts before push_off };

Why a fixed-size array?

Simplicity. No dynamic allocation needed for the process table itself. The scheduler simply scans proc[] linearly looking for RUNNABLE processes - O(NPROC) per scheduling decision, fine for 64 entries.

Per-CPU State - mycpu() and myproc()

mycpu()

Returns &cpus[cpuid()]. cpuid() reads the hardware thread ID from tp register (RISC-V). Must be called with interrupts disabled to avoid migration mid-call.

myproc()

Returns mycpu()->proc - the process currently running on this CPU. This is how kernel code finds "the current process" without passing it as a parameter.

The scheduler runs in CPU context, not process context

Each CPU's context field is the scheduler's own saved context. When the scheduler calls swtch(), it switches from the scheduler context to a process context. When the process yields, it switches back.

// mycpu - returns pointer to this CPU's struct struct cpu* mycpu(void) { int id = cpuid(); return &cpus[id]; } // myproc - returns the running process struct proc* myproc(void) { push_off(); // disable interrupts struct cpu *c = mycpu(); struct proc *p = c->proc; pop_off(); // restore interrupt state return p; }

push_off / pop_off

myproc() must disable interrupts (push_off) before reading cpuid(), because a timer interrupt could migrate us to another CPU mid-call. pop_off restores the previous interrupt state.

Context Structure - what swtch() saves

xv6 kernel/proc.h
struct context {
  uint64 ra;
  uint64 sp;
  uint64 s0;
  uint64 s1;
  uint64 s2;
  uint64 s3;
  uint64 s4;
  uint64 s5;
  uint64 s6;
  uint64 s7;
  uint64 s8;
  uint64 s9;
  uint64 s10;
  uint64 s11;
};

Only callee-saved registers

ra (return address), sp (stack pointer), and s0-s11 (callee-saved registers). Caller-saved registers (a0-a7, t0-t6) are already on the stack - the compiler guarantees they're saved at call sites.

swtch.S - the actual switch

swtch(old, new) saves the current context into old, loads new into the registers, then executes ret - which jumps to new->ra. The function never "returns" normally; it resumes wherever the target context left off.

Why not save all registers?

The RISC-V calling convention already guarantees caller-saved registers are spilled to the stack at every call. swtch() is just a function call - the compiler has already saved a and t registers. Only s registers (plus ra and sp) need explicit saving.

SECTION 3

Process Lifecycle

allocproc . fork . exit . wait - the four pillars of process management

allocproc() - creating a process slot

Step 1: Find a free slot

Scans proc[] for a process with state == UNUSED. Acquires p->lock on the found slot.

Step 2: Allocate PID

Calls allocpid() which atomically increments a global counter under a lock.

Step 3: Allocate trapframe

Allocates a physical page via kalloc() for p->trapframe. This page holds saved user registers during syscalls and traps.

Step 4: Create page table

Calls proc_pagetable(p) to create an empty user page table with the trampoline and trapframe pages mapped.

Step 5: Set up context

Sets p->context.ra = forkret (first function to run) and p->context.sp = p->kstack + PGSIZE (top of kernel stack). Sets state = USED.

allocproc() - simplified flow for (p = proc; p < &proc[NPROC]; p++) { acquire(&p->lock); if (p->state == UNUSED) goto found; release(&p->lock); } return 0; found: p->pid = allocpid(); p->trapframe = kalloc(); // alloc page p->pagetable = proc_pagetable(p); // set up scheduler return context p->context.ra = (uint64)forkret; p->context.sp = p->kstack + PGSIZE; p->state = USED; return p; // still locked!

Returns locked

allocproc() returns the process with p->lock still held. The caller (typically fork()) finishes setup and then sets the state to RUNNABLE before releasing the lock.

kfork() - the fork implementation

1. Allocate a new proc

Calls allocproc() to get a new USED slot (locked).

2. Copy user memory

Calls uvmcopy(p->pagetable, np->pagetable, p->sz) - a deep copy of all user pages. Each page is duplicated so parent and child are fully independent.

3. Copy trapframe

*np->trapframe = *p->trapframe - the child starts with the same register state as the parent.

4. Set fork return value

np->trapframe->a0 = 0 - the RISC-V calling convention returns values in a0. The child sees fork() return 0; the parent sees the child's PID.

5. Duplicate files & set parent

Increments reference counts on all open files via filedup(). Sets np->parent = p under wait_lock. Sets np->state = RUNNABLE and releases lock.

kfork() - key steps np = allocproc(); // new slot, locked // deep copy user memory uvmcopy(p->pagetable, np->pagetable, p->sz); np->sz = p->sz; // copy register state *np->trapframe = *p->trapframe; // child returns 0 from fork() np->trapframe->a0 = 0; // duplicate open files for (i = 0; i < NOFILE; i++) if (p->ofile[i]) np->ofile[i] = filedup(p->ofile[i]); np->cwd = idup(p->cwd); // set parent, make runnable acquire(&wait_lock); np->parent = p; release(&wait_lock); np->state = RUNNABLE; release(&np->lock); return np->pid; // parent gets child PID

kexit() - the exit implementation

1. Close all open files

Iterates ofile[] and calls fileclose() on each. Releases the current directory via iput(cwd).

2. Reparent children to init

Scans proc[] under wait_lock. Any child whose parent is this process gets parent = initproc. This ensures no process is orphaned - init reaps them.

3. Set exit status

p->xstate = status - stores the exit code so the parent can read it via wait().

4. Become zombie

Sets p->state = ZOMBIE. The process is now dead but its proc slot cannot be freed until the parent calls wait().

5. Wake parent & yield

Calls wakeup(p->parent) to unblock a parent sleeping in wait(). Then calls sched() to switch back to the scheduler - this call never returns.

kexit(int status) - key steps // 1. release resources for (i = 0; i < NOFILE; i++) { if (p->ofile[i]) { struct file *f = p->ofile[i]; p->ofile[i] = 0; fileclose(f); } } iput(p->cwd); // 2. reparent children to init acquire(&wait_lock); for (pp = proc; pp < &proc[NPROC]; pp++) { if (pp != p && pp->parent == p) { pp->parent = initproc; if (pp->state == ZOMBIE) wakeup(initproc); } } // 3-4. set exit status, become zombie p->xstate = status; p->state = ZOMBIE; // 5. wake parent, switch to scheduler wakeup(p->parent); release(&wait_lock); sched(); // never returns

kwait() - the wait implementation

1. Scan for zombie children

Under wait_lock, scans proc[] for any process whose parent == p and state == ZOMBIE.

2. If found - reap the child

  • Copy xstate to user space via copyout()
  • Call freeproc() to free the child's trapframe, page table, and reset state to UNUSED
  • Return the child's PID

3. If no zombie children

If the scan finds children but none are ZOMBIE, the parent sleeps on itself (sleep(p, &wait_lock)) until a child exits and calls wakeup(p->parent).

4. If no children at all

If the scan finds no children, wait() returns -1 immediately - there is nothing to wait for.

kwait() - simplified flow acquire(&wait_lock); for (;;) { // scan for zombie children for (pp = proc; pp < &proc[NPROC]; pp++) { if (pp->parent == p) { havekids = 1; if (pp->state == ZOMBIE) { // found a zombie - reap it pid = pp->pid; copyout(p->pagetable, addr, (char*)&pp->xstate, sizeof(int)); freeproc(pp); release(&wait_lock); return pid; } } } if (!havekids) { release(&wait_lock); return -1; // no children } // no zombie yet - sleep until child exits sleep(p, &wait_lock); }

freeproc() - the cleanup

Frees the trapframe page (kfree), frees the page table (proc_freepagetable), resets all fields to zero, and sets state = UNUSED. The slot is now available for allocproc().

SECTION 4

The Scheduler

How xv6 multiplexes CPUs across runnable processes

scheduler() - the per-CPU infinite loop

The main loop

Each CPU's scheduler() is an infinite loop that scans proc[] for RUNNABLE processes and runs them one at a time.

Step by step

  • intr_on() - enable interrupts (allow timer preemption)
  • For each p in proc[]: if p->state == RUNNABLE, acquire p->lock
  • Set p->state = RUNNING, set c->proc = p
  • Call swtch(&c->context, &p->context) - switch to process
  • When control returns: c->proc = 0, release p->lock

If nothing is runnable

If no RUNNABLE process is found, the CPU executes wfi (wait for interrupt) - it halts until a timer or device interrupt wakes it, then loops again.

scheduler() - per-CPU loop void scheduler(void) { struct cpu *c = mycpu(); for (;;) { intr_on(); // enable interrupts for (p = proc; p < &proc[NPROC]; p++) { acquire(&p->lock); if (p->state != RUNNABLE) { release(&p->lock); continue; } // run this process p->state = RUNNING; c->proc = p; swtch(&c->context, &p->context); // process yielded - back here c->proc = 0; release(&p->lock); } } }

swtch returns to scheduler, not to the process

When a process calls sched(), swtch saves the process context and loads the scheduler's context. The scheduler resumes right after the swtch() call - it has no idea how long it slept.

sched() - yielding back to the scheduler

What sched() does

Called by a process that wants to yield (due to sleep(), exit(), or timer interrupt). It switches from the process context back to the scheduler context.

Preconditions - must hold p->lock

The caller must hold myproc()->lock and only that lock. If other locks are held, the scheduler may deadlock - another CPU spinning on the same lock will never get it.

Must not be interruptible

Interrupts must be off when sched() is called (enforced via push_off). A context switch with interrupts on could corrupt the CPU state tracking.

The actual switch

swtch(&p->context, &mycpu()->context) - saves the process's callee-saved registers into p->context, loads the scheduler's saved context from c->context, and rets into the scheduler.

sched() - the yield function void sched(void) { struct proc *p = myproc(); // sanity checks if (!holding(&p->lock)) panic("sched p->lock"); if (mycpu()->noff != 1) panic("sched locks"); if (p->state == RUNNING) panic("sched running"); if (intr_get()) panic("sched interruptible"); // switch to scheduler context swtch(&p->context, &mycpu()->context); }

Why the strict invariants?

These panic() checks catch bugs early. If a developer calls sched() while holding extra locks, or with interrupts on, the kernel halts immediately rather than silently corrupting state or deadlocking later.

Context Switch Flow

forkret() - first function in a new process

What is forkret()?

The first function executed by a newly created process after swtch() switches to it from the scheduler. It is the ra value set by allocproc().

First call - bootstrapping init

On the very first process (the init process), forkret() performs one-time initialization: it initializes the filesystem and then exec()s /init. This is the kernel's transition from boot to user space.

Subsequent calls - just return

For all other processes, forkret() simply returns. Since it was called via swtch()'s ret, returning here means falling through to the trap return path - the process "returns" from the trap that brought it into the kernel, resuming user code.

forkret() - simplified void forkret(void) { static int first = 1; release(&myproc()->lock); if (first) { // one-time init first = 0; fsinit(ROOTDEV); userinit_done = 1; } // return to trap return path // -> usertrapret() -> sret to user }

Why release the lock here?

allocproc() returns with p->lock held. The scheduler acquires it, calls swtch(), and the new process wakes up in forkret(). The lock must be released here - not in the scheduler - because the scheduler has already moved on to scanning other processes.

SECTION 5

Sleep and Wakeup

How processes wait for events without burning CPU cycles

sleep() and wakeup() - the coordination primitives

sleep_prepare(chan)

Acquires p->lock and sets p->chan = chan. This links the process to the channel it's waiting on.

sleep(chan, lk)

  • Releases lk (the caller's lock, e.g. wait_lock)
  • Sets p->state = SLEEPING
  • Calls sched() -> switches to scheduler
  • On wake: re-acquires lk, clears p->chan

wakeup(chan)

Scans all processes in proc[]. For each with p->chan == chan and state == SLEEPING, acquires p->lock and sets state = RUNNABLE.

sleep() - simplified void sleep(void *chan, struct spinlock *lk) { struct proc *p = myproc(); acquire(&p->lock); release(lk); // release caller's lock p->chan = chan; p->state = SLEEPING; sched(); // yield to scheduler // woken up here p->chan = 0; release(&p->lock); acquire(lk); // re-acquire caller's lock } wakeup() - simplified void wakeup(void *chan) { for (p = proc; p < &proc[NPROC]; p++) { acquire(&p->lock); if (p->state == SLEEPING && p->chan == chan) { p->state = RUNNABLE; } release(&p->lock); } }

The Lost Wakeup Problem

"If you check the alarm clock, then go to sleep, but someone rings the alarm between your check and your sleep - you sleep forever. The alarm rang, but you weren't sleeping yet, so you missed it."

The race condition

Without coordination, a process might: (1) check a condition, (2) decide to sleep, (3) but before it calls sleep(), another CPU calls wakeup(). The wakeup finds no sleeping process, does nothing. The process then sleeps - and never wakes up.

The solution: atomic sleep

sleep() atomically releases the caller's lock and goes to sleep. wakeup() acquires p->lock before checking the state. Because sleep() holds p->lock until after state = SLEEPING, a concurrent wakeup() either:

  • Sees RUNNABLE (before sleep sets SLEEPING) -> no-op, process runs normally
  • Sees SLEEPING -> sets RUNNABLE, process wakes up

There is no window where the wakeup is "lost."

sleep/wakeup as Condition Variables

The pattern

sleep_prepare(chan) + sleep(chan, lk) + wakeup(chan) is xv6's equivalent of a condition variable. The channel is the "condition" being waited on; the lock protects the shared state.

Where it's used in xv6

  • Pipe - pipewrite() wakes piperead() when data is written; piperead() sleeps on &pi->nread when the pipe is empty
  • Console - consoleread() sleeps on consoleread channel until input arrives via keyboard interrupt
  • UART - uartwrite() sleeps on uart_tx_r when the transmit buffer is full
  • Sleeplock - sleeplock uses sleep/wakeup to implement a lock that can be held across long I/O operations without blocking the CPU

Why not just spin?

A spinlock burns CPU cycles while waiting. For short waits (a few instructions) this is fine. But for I/O - waiting for a disk read, a key press, or a pipe to fill - spinning would waste the entire CPU. sleep() lets the scheduler run other processes while waiting.

The channel is just an address

The sleep channel is an arbitrary void* - it's never dereferenced. It's used purely as an identity token. Two processes sleeping on the same pointer are waiting for the same event. Common patterns: &p->chan, &pi->nread, or a global variable address.

Mesa-style semantics

xv6's sleep/wakeup follows Mesa semantics: when wakeup() sets a process to RUNNABLE, the process does not run immediately. By the time it actually runs, the condition may no longer be true - so the caller must re-check the condition in a loop after sleep() returns.

Summary - Key Takeaways

Process = isolation unit

A process bundles a private address space, open files, and execution state. The struct proc in xv6 captures all of this, protected by p->lock.

Lifecycle: alloc -> runnable -> running -> zombie -> free

allocproc() creates the slot, fork() copies the parent, exit() marks zombie, wait() reaps and frees. Every transition is under p->lock.

Context switch = save callee-saved regs

swtch() saves only ra, sp, and s0-s11. Caller-saved registers are already on the stack. The switch is between process context and scheduler context.

Sleep/wakeup = condition variables

sleep() atomically releases a lock and sleeps; wakeup() acquires p->lock before setting RUNNABLE. This prevents lost wakeups - the core coordination problem.

Scheduler = simple round-robin

Each CPU runs an infinite loop scanning proc[] for RUNNABLE processes. No priority, no preemption policy beyond timer interrupts. Simple and correct.

Locking discipline is critical

p->lock protects process state. wait_lock protects parent-child relationships. sched() requires exactly one lock held and interrupts off. Violations cause panic().
