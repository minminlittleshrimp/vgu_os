SECTION 1

Physical Memory Allocation

kalloc, kfree, and the free list

Physical memory layout

From memlayout.h

  • KERNBASE = 0x80000000 - start of kernel in RAM
  • PHYSTOP = KERNBASE + 128*1024*1024 (128 MB) - end of managed RAM
  • Physical memory from end (end of kernel image) to PHYSTOP is managed by kalloc.c
  • Below KERNBASE is I/O space (UART, VIRTIO, PLIC)

Why 0x80000000?

On RISC-V (QEMU), RAM starts at 0x80000000. The first part holds the kernel image (loaded by the bootloader). Everything after end is free for kalloc() to hand out as 4 KB pages.

kalloc / kfree - the free list

kalloc.c - core allocator

struct run {
  struct run *next;
};

struct {
  struct spinlock lock;
  struct run *freelist;
} kmem;

void *
kalloc(void) {
  struct run *r;
  acquire(&kmem.lock);
  r = kmem.freelist;
  if (r)
    kmem.freelist = r->next;
  release(&kmem.lock);
  if (r)
    memset(r, 5, PGSIZE); // junk fill
  return (void*)r;
}

void
kfree(void *pa) {
  struct run *r;
  r = (struct run*)pa;
  memset(r, 1, PGSIZE);  // junk fill
  acquire(&kmem.lock);
  r->next = kmem.freelist;
  kmem.freelist = r;
  release(&kmem.lock);
}

How it works

  • kalloc() - acquire lock, pop first page from freelist, memset to 0x05, return pointer.
  • kfree() - memset to 0x01, push page back onto freelist head.
  • kinit() calls freerange(end, PHYSTOP) - adds every 4 KB page between end and PHYSTOP to the free list.
  • One global spinlock protects the list.

Simple by design

The allocator is a single linked list of 4 KB pages. No coalescing, no size classes - every allocation is exactly one page. This is fine for a teaching OS.

PGSIZE = 4096

From riscv.h: PGSIZE = 4096, PGSHIFT = 12. Every page is 4 KB, aligned to 4 KB.

Why junk fill?

kalloc fills with 0x05

When kalloc() returns a page, it fills it with 0x05 bytes. If you see 0x05050505 in a debugger, you are reading freshly allocated but uninitialized memory.

kfree fills with 0x01

When kfree() reclaims a page, it fills it with 0x01 bytes. If you see 0x01010101 in a pointer, you are reading freed memory - a use-after-free bug.

Debugging aid

These junk patterns are not required for correctness. They exist to make bugs visible. In a debugger or crash dump, the pattern immediately tells you the state of the memory.

Real-world analogy

Linux uses 0x6b for allocated and 0x6a for freed (KASAN/KMEMLEAK). Same idea: recognizable poison patterns catch dangling references and uninitialized reads.

0x05050505 -> freshly allocated (uninitialized)
0x01010101 -> freed (use-after-free!)

SECTION 2

Sv39 Page Tables

Three-level paging on RISC-V

Sv39 three-level page table

39-bit virtual address

Sv39 splits a 39-bit VA into three 9-bit VPN fields and a 12-bit offset. Each 9-bit index selects one of 512 entries in a page table page.

From riscv.h

PX(level, va) extracts the 9-bit index for a given level:
(((va) >> 12 + (level)*9) & 0x1FF)

Page table size

Each page table = 512 PTEs x 8 bytes = 4096 bytes = one 4 KB page. So every page table itself occupies exactly one physical page.

Address space size

  • VA range: 0 to 2^39 - 1 = 512 GB
  • Pages per table: 512 x 512 x 512 = 134M leaf PTEs
  • Full table tree: 3 pages deep, allocated lazily

Page table entry (PTE)

PTE format (64 bits)

  • Flags (bits 0-9): V, R, W, X, U, plus RISC-V reserved bits
  • PPN (bits 10-53): physical page number - the upper 44 bits of the physical address, shifted right by 12
  • Reserved (bits 54-63): unused by Sv39

Key macros (from riscv.h)

PA2PTE(pa) = ((pa) >> 12) << 10
PTE2PA(pte) = (pte >> 10) << 12
MAKE_SATP(pagetable) = SATP_SV39 | ((pagetable) >> 12)

SATP register

The satp CSR holds the mode (Sv39 = 8) and the physical address of the root (L2) page table, right-shifted by 12. Writing satp switches address spaces.

walk() - the core translation function

vm.c - walk()

pte_t *
walk(pagetable_t pagetable,
     uint64 va, int alloc)
{
  if (va >= MAXVA)
    panic("walk");

  for (int level = 2; level > 0; level--) {
    pte_t *pte = &pagetable[PX(level, va)];
    if (*pte & PTE_V) {
      // follow to next level
      pagetable = (pagetable_t)PTE2PA(*pte);
    } else {
      if (!alloc ||
          (pagetable = (pte_t*)kalloc()) == 0)
        return 0;
      memset(pagetable, 0, PGSIZE);
      *pte = PA2PTE(pagetable) | PTE_V;
    }
  }
  // return pointer to L0 PTE
  return &pagetable[PX(0, va)];
}

What walk() does

  • Iterates from level 2 down to level 1.
  • At each level, looks up pagetable[PX(level, va)].
  • If the PTE is valid (PTE_V), follows it to the next-level table.
  • If not valid and alloc is set, kalloc()s a new page, zeros it, and installs it as a valid PTE.
  • Returns a pointer to the level-0 PTE - the leaf entry that maps the page.

Kernel-only function

walk() is called only in supervisor mode. User code cannot invoke it directly - the hardware MMU does the same walk internally on every memory access.

Why it matters

This is the software equivalent of what the MMU does in hardware. copyin, copyout, and mappages all rely on walk() to find or create PTEs.

mappages() - mapping VA to PA

vm.c - mappages()

int
mappages(pagetable_t pagetable,
         uint64 va, uint64 size,
         uint64 pa, int perm)
{
  uint64 a, last;
  pte_t *pte;

  a = PGROUNDDOWN(va);
  last = PGROUNDDOWN(va + size - 1);
  for (;;) {
    if ((pte = walk(pagetable, a, 1)) == 0)
      return -1;
    if (*pte & PTE_V)
      panic("mappages: remap");
    *pte = PA2PTE(pa) | perm | PTE_V;
    if (a == last)
      break;
    a += PGSIZE;
    pa += PGSIZE;
  }
  return 0;
}

What mappages() does

  • Maps a VA range [va, va+size) to a PA range starting at pa.
  • For each 4 KB page in the range: calls walk() to get (or create) the L0 PTE.
  • Sets *pte = PA2PTE(pa) | perm | PTE_V.
  • Panics on remap - if the PTE is already valid, that's a bug (double mapping).

Permission parameter

perm is a combination of PTE_R | PTE_W | PTE_X | PTE_U. PTE_V is always OR'd in by mappages itself.

PGROUNDDOWN

PGROUNDDOWN(a) = a & ~(PGSIZE-1) - aligns down to a page boundary. PGROUNDUP aligns up. Both ensure page-aligned addresses.

SECTION 3

Kernel Address Space

Direct-mapped, with device and trampoline regions

Kernel page table - kvmmake()

kvmmake() creates the kernel page table

Called once during boot (kvminit()). Creates a single page table shared by all kernel-mode code.

RegionVA rangePerm
UART00x10000000R | W
VIRTIO00x10001000R | W
PLIC0x0C000000R | W
Kernel textKERNBASE -> etextR | X
Kernel dataetext -> PHYSTOPR | W
TrampolineTRAMPOLINER | X

Direct mapping (identity map)

Most of kernel memory is direct-mapped: VA == PA. So 0x80000000 in kernel VA points to the same physical address. This simplifies kernel code - no translation needed for most pointers.

Kernel text: R | X (no W)

Kernel code is read + execute but not writable. This prevents accidental corruption of kernel instructions. The data section is read + write but not executable.

Trampoline

TRAMPOLINE = MAXVA - PGSIZE. It maps to the trampoline.S code page, used for user/kernel transitions. Mapped with R | X in both kernel and user page tables.

Device registers

UART0, VIRTIO0, PLIC are memory-mapped I/O. They are mapped with R | W so the kernel can read/write device registers at their physical addresses.

SECTION 4

User Address Space

Per-process page tables, sbrk, fork copy

User page table - proc_pagetable()

proc_pagetable() creates a per-process page table

Each process gets its own page table. This is how isolation works - process A's VA 0x1000 maps to a different physical page than process B's VA 0x1000.

What it maps

  • TRAMPOLINE - R | X, no PTE_U (kernel-only). Same trampoline code as kernel table.
  • TRAPFRAME - R | W, no PTE_U. Per-process trapframe page (saved registers on syscall/trap).
  • User text - R | X | U. The program's instructions.
  • User data/heap - R | W | U. Globals, then heap (grows via sbrk).
  • User stack - R | W | U. At the top of the user VA, just below TRAPFRAME.

Why no PTE_U on trampoline/trapframe?

The trampoline and trapframe pages are kernel-managed. If they had PTE_U, user code could read or corrupt saved register state. The PTE_U bit is the key isolation mechanism - without it, only supervisor mode can access that page.

proc_pagetable() source

Allocates a root page table via uvmcreate(), then mappages() the trampoline and trapframe pages. If any step fails, it uvmfree()s and returns 0.

Switching address spaces

proc_pagetable() returns the root PA. The scheduler writes it into satp via w_satp() + sfence.vma to flush TLB. This is the actual "context switch" for memory.

RISC-V super pages (not used by xv6)

RISC-V Sv39 supports super pages: 2 MB (leaf at L1) and 1 GB (leaf at L2). These map large regions with a single PTE, reducing TLB pressure. xv6 does not use super pages - all pages are 4 KB - but Linux and other production OSes do.

uvmalloc / uvmdealloc - sbrk internals

vm.c - uvmalloc()

uint64
uvmalloc(pagetable_t pagetable,
         uint64 oldsz, uint64 newsz,
         int xperm)
{
  char *mem;
  uint64 a, last;

  a = PGROUNDUP(oldsz);
  last = PGROUNDUP(newsz - 1);
  for (;;) {
    if (a >= last) break;
    mem = kalloc();
    if (mem == 0) {
      uvmdealloc(pagetable, a, oldsz, 0);
      return 0;
    }
    memset(mem, 0, PGSIZE);
    if (mappages(pagetable, a, PGSIZE,
                 (uint64)mem,
                 PTE_R|PTE_U|xperm) != 0) {
      kfree(mem);
      uvmdealloc(pagetable, a, oldsz, 0);
      return 0;
    }
    a += PGSIZE;
  }
  return newsz;
}

uvmalloc()

  • Grows the process from oldsz to newsz.
  • For each new page: kalloc() a 4 KB page, memset to 0, mappages() with PTE_R | PTE_U | xperm.
  • xperm is typically PTE_X for text, 0 for data.
  • If any allocation fails, rolls back via uvmdealloc().

uvmdealloc()

  • Shrinks from oldsz to newsz.
  • For each page removed: uvmunmap() (clears PTE), then kfree() (returns to free list).
  • sbrk(n) calls growproc(n) which calls these two.

Zero-fill guarantee

uvmalloc always memsets new pages to 0. This ensures new heap memory doesn't leak data from a previous process - important for security.

uvmcopy() - why fork is expensive

vm.c - uvmcopy()

int
uvmcopy(pagetable_t old, pagetable_t new,
        uint64 sz)
{
  pte_t *pte;
  uint64 pa, i;
  char *mem;

  for (i = 0; i < sz; i += PGSIZE) {
    if ((pte = walk(old, i, 0)) == 0)
      panic("uvmcopy: pte");
    if ((*pte & PTE_V) == 0)
      panic("uvmcopy: page not present");
    pa = PTE2PA(*pte);
    if ((mem = kalloc()) == 0)
      goto err;
    memmove(mem, (char*)pa, PGSIZE);
    if (mappages(new, i, PGSIZE,
                 (uint64)mem,
                 PTE_R|PTE_W|PTE_X|PTE_U) != 0) {
      kfree(mem);
      goto err;
    }
  }
  return 0;

err:
  uvmunmap(new, 0, i / PGSIZE, 1);
  return -1;
}

Deep copy - every page is copied

uvmcopy() is called by fork(). For every valid page in the parent's page table, it:

  • walk() to find the parent PTE.
  • kalloc() a new physical page for the child.
  • memmove() copies all 4 KB from parent to child.
  • mappages() installs the new PTE in the child's table with the same flags.

Why this is expensive

If a process has 1000 pages (4 MB), fork() copies all 1000 pages. This is O(n) in the number of pages. For large processes, fork() is dominated by this copy.

Copy-on-write (CoW)

Real OSes use copy-on-write: both parent and child share the same physical pages (read-only), and only copy when one of them writes. xv6 does not implement CoW - it always copies eagerly. This is a known simplification for teaching.

SECTION 5

User/Kernel Data Transfer

copyin, copyout, copyinstr

copyin / copyout - safe data transfer

vm.c - copyin()

int
copyin(pagetable_t pagetable,
       char *dst, uint64 srcva, uint64 len)
{
  uint64 n, va0, pa0;

  while (len > 0) {
    va0 = PGROUNDDOWN(srcva);
    pa0 = PTE2PA(*walk(pagetable, va0, 0));
    n = PGSIZE - (srcva - va0);
    if (n > len) n = len;
    memmove(dst, (void *)(pa0 + (srcva - va0)), n);

    len -= n;
    dst += n;
    srcva += n;
  }
  return 0;
}

vm.c - copyout()

int
copyout(pagetable_t pagetable,
        uint64 dstva, char *src, uint64 len)
{
  uint64 n, va0, pa0;

  while (len > 0) {
    va0 = PGROUNDDOWN(dstva);
    pa0 = PTE2PA(*walk(pagetable, va0, 0));
    n = PGSIZE - (dstva - va0);
    if (n > len) n = len;
    memmove((void *)(pa0 + (dstva - va0)), src, n);

    len -= n;
    src += n;
    dstva += n;
  }
  return 0;
}

Never dereference user pointers directly!

The kernel runs with the kernel page table active. A user VA (e.g. 0x1000) in the kernel's address space points to completely different physical memory - or may be unmapped. Dereferencing it is a security hole or a crash.

copyin()

  • Copies len bytes from user VA srcva to kernel buffer dst.
  • Uses walk() to translate each user VA to a PA.
  • Handles page boundaries - copies page by page.
  • Used by sys_read, sys_exec, etc.

copyout()

  • Copies len bytes from kernel buffer src to user VA dstva.
  • Same page-by-page walk + memmove.
  • Used by sys_write, sys_pipe, etc.

Security check

In real xv6, copyin/copyout also verify the PTE has PTE_U set and the right R/W permissions. The simplified version above omits the error checks for clarity.

copyinstr - copying strings from user space

vm.c - copyinstr()

int
copyinstr(pagetable_t pagetable,
          char *dst, uint64 srcva,
          uint64 max)
{
  uint64 n, va0, pa0;
  int got_null = 0;

  while (got_null == 0 && max > 0) {
    va0 = PGROUNDDOWN(srcva);
    pa0 = PTE2PA(*walk(pagetable, va0, 0));
    n = PGSIZE - (srcva - va0);
    if (n > max) n = max;

    char *p = (char *)(pa0 + (srcva - va0));
    while (n > 0) {
      if ((*p = *p) == '\0') {
        got_null = 1;
        break;
      }
      p++;
      n--;
    }
    max -= n;
    srcva += n;
  }
  return got_null ? 0 : -1;
}

What copyinstr() does

  • Copies a null-terminated string from user VA srcva to kernel buffer dst.
  • Like copyin, but stops at '\0' or max bytes.
  • Uses walk() to translate each page, handles page boundaries.
  • Returns 0 on success (found '\0'), -1 if max reached without null.

Where it's used

exec() uses copyinstr to copy argv strings from user space into the kernel, then places them on the new user stack. Also used by sys_open, sys_chdir, etc. to copy path strings.

Why not just strcpy?

strcpy dereferences the pointer directly. In kernel mode, a user pointer is invalid. copyinstr translates through the user's page table, not the kernel's. This is the safe path.

max parameter

max prevents a malicious user from passing an extremely long non-null-terminated string, which could overflow kernel buffers. Always pass MAXPATH (or similar) as the limit.

Key takeaways

1. Sv39 three-level paging

39-bit VA -> 3 x 9-bit VPN + 12-bit offset. 512 PTEs per table, 4 KB per table. walk() traverses the tree.

2. PTE flags = protection

V, R, W, X, U. PTE_U is the user/kernel gate. Kernel pages have no PTE_U; user pages must have it.

3. Kernel = direct-mapped

VA == PA for most kernel memory. Device registers and trampoline are separately mapped. One shared kernel page table.

4. User = per-process

Each process has its own page table. satp switch = address space switch. sbrk grows/shrinks via uvmalloc/uvmdealloc.

5. fork copies all pages

uvmcopy() deep-copies every page - O(n) in pages. No copy-on-write in xv6. This is why fork is expensive.

6. Always use copyin/copyout

Never dereference user pointers in kernel mode. copyin, copyout, copyinstr translate through the user's page table safely.
