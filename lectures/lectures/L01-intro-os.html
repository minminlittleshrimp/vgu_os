What is an Operating System?

What is the purpose of an OS?

An OS is like a building manager. It makes sure everyone gets a desk (CPU), a room (memory), and access to the filing cabinet (disk) - without anyone trampling anyone else.

Multiplex

Share hardware among many applications. Time-slice the CPU, partition memory, queue disk requests.

Isolate

Protect apps from each other. A bug in one program must not crash the system or steal another's data.

Share

Allow controlled data sharing between cooperating applications - pipes, files, shared memory.

Abstract

Hide hardware details for portability and convenience. Programs see files, not disk blocks.

Design tensions

Every design decision is a compromise

Different OSes make different choices. There is no "correct" answer - only trade-offs appropriate to the target workload.

Goal Avs.Goal B
Efficient<->Abstract / portable
Powerful<->Simple interfaces
Flexible<->Secure
Portable<->Exploit new hardware

Example: system call interface

A thin syscall layer (like xv6's 22 syscalls) is simple and portable, but every operation crosses the user/kernel boundary. A thick library OS can batch operations for efficiency, but is harder to reason about.

Example: page table granularity

4 KB pages (xv6 default) give fine-grained protection but large page tables. 2 MB huge pages reduce table size but waste memory on small allocations.

SECTION 1

Isolation: The Core Problem

Without it, a bug in one program can crash the entire system

Why isolation?

The problem

Without isolation, a bug in one program can crash the entire system or steal another program's data.

Three facets

  • Resource isolation - one app can't hog all CPU, memory, or disk.
  • Memory isolation - one app can't read or write another app's memory.
  • Security - malicious code can't break out of its sandbox.

Analogy

Imagine a shared apartment where anyone can enter any room, eat anyone's food, and use the bathroom for hours. Chaos. Isolation is giving each person their own locked room.

Hardware support required

  • User/supervisor mode - user code can't execute privileged instructions.
  • Virtual memory - each process gets its own address space.

Strawman: no OS (apps touch hardware directly)

Pros

Efficient and flexible - no overhead, full hardware access.

Cons - no isolation!

App 1 can read App 2's memory. App 1 can hog the CPU. App 1 can overwrite the disk. This is why we need a protected kernel.

Hardware support for isolation

Key principle

Kernel runs in supervisor mode; apps run in user mode. The only way to cross the boundary is through system calls (the ecall instruction on RISC-V).

SECTION 2

System Calls

The controlled bridge between user and kernel

What is a system call?

Definition

A system call is a controlled transfer from user mode to kernel mode, allowing user programs to request kernel services.

Analogy

A system call is like going to the bank teller. You can't walk into the vault yourself. You fill out a form (arguments), hand it to the teller (ecall), the teller does the work in the vault (kernel), and hands you the result (return value).

What happens

  • Looks like a function call, but it's a special CPU instruction (ecall on RISC-V).
  • The CPU switches to supervisor mode and jumps to a known kernel entry point.
  • The kernel validates arguments and performs the operation.
  • Return value comes back in register a0.

xv6 syscall numbers (from syscall.h)

SYS_fork=1 . SYS_exit=2 . SYS_wait=3 . SYS_read=5 . SYS_write=16 . SYS_exec=7 . SYS_open=15 . SYS_close=21 . SYS_sbrk=12 . SYS_pipe=4

Example: read and write

ex1.c - copy input to output

#include "kernel/types.h"
#include "user/user.h"

int main() {
    char buf[64];
    int n;
    while ((n = read(0, buf, sizeof(buf))) > 0) {
        write(1, buf, n);
    }
    exit(0);
}

What each call does

  • read(fd, buf, n) - read up to n bytes from FD fd into buf.
  • write(fd, buf, n) - write n bytes from buf to FD fd.
  • FD 0 = stdin, FD 1 = stdout.
  • Return value: bytes read/written, or -1 on error.

Behind the scenes

Each read() and write() is a stub generated by usys.pl: it loads the syscall number into a7, executes ecall, and returns. The kernel dispatches via syscalls[] array in syscall.c.

SECTION 3

Processes: fork, exec, wait

The Unix process model

fork: creating a new process

ex3.c - fork a child process

int main() {
    int pid = fork();
    if (pid == 0) {
        // child process
        printf("I am the child\n");
    } else {
        // parent process
        printf("I am the parent, child pid=%d\n", pid);
    }
    exit(0);
}

What fork() does

  • Creates a copy of the calling process.
  • Both parent and child continue running from the same point.
  • fork() returns the child's PID to the parent, and 0 to the child.
  • The child gets its own memory space, file descriptors, and PID.

In xv6 source (proc.c)

kfork() calls allocproc() to get a new struct proc, copies the parent's page table via uvmcopy(), duplicates file descriptors with filedup(), and sets np->state = RUNNABLE.

exec: running a program

ex4.c - replace current process with a program

int main() {
    char *argv[] = {"echo", "hello", "world", 0};
    exec("echo", argv);
    // exec does NOT return if successful!
    printf("this line never runs\n");
    exit(0);
}

What exec() does

  • exec(filename, argv) replaces current memory with the program.
  • Preserves file descriptors and PID.
  • Does not return if successful - the old code is gone.
  • argv is the array of command-line arguments passed to main().

Why fork + exec (not one call)?

Between fork() and exec(), the child can do things - like redirect I/O. This separation gives flexibility.

The shell pattern: fork + exec + wait

ex5.c - the shell pattern

int main() {
    int pid = fork();
    if (pid == 0) {
        // child: run the command
        char *argv[] = {"ls", 0};
        exec("ls", argv);
    } else {
        // parent: wait for child
        int status;
        wait(&status);
        printf("child exited: %d\n", status);
    }
    exit(0);
}

What the shell does

  • The shell does this for every command you type.
  • fork() creates child; child calls exec(); parent wait()s.
  • exit(status) -> wait(&status): exit status passed to parent.
  • Convention: status 0 = success, 1 = error.

I/O redirection

For echo hello > out: child does close(1); open("out", ...); exec("echo", ...). open() picks the lowest unused FD - after close(1), that's FD 1. exec() preserves FDs, so echo writes to the file without knowing it.

Pipes: connecting processes

ex7.c - pipe between processes

int main() {
    int p[2];
    pipe(p);          // p[0]=read, p[1]=write
    int pid = fork();
    if (pid == 0) {
        close(p[0]);  // child doesn't read
        char *argv[] = {"ls", 0};
        close(1); dup(p[1]);
        exec("ls", argv);
    } else {
        close(p[1]);  // parent doesn't write
        char *argv[] = {"wc", 0};
        close(0); dup(p[0]);
        exec("wc", argv);
    }
    exit(0);
}

How pipes work

  • pipe(p) creates a unidirectional data channel.
  • p[0] = read end, p[1] = write end.
  • dup() copies an FD to the lowest unused number.
  • This is how the shell implements ls | wc.

In xv6 source (pipe.c)

A pipe is a 512-byte circular buffer (struct pipe) with nread/nwrite counters. Writers sleep when full (sleep()), readers sleep when empty. wakeup() on each operation.

SECTION 4

xv6: A Teaching Operating System

Small enough to read in a weekend, real enough to boot

What is xv6?

Analogy

xv6 is like a teaching version of Unix. It's small enough to read in a weekend, but real enough to boot, run programs, and handle files. It is the "Hello World" of operating systems.

Facts

  • A teaching OS developed at MIT (R. Cox, F. Kaashoek, R. Morris).
  • Re-implements Unix 6th edition (1975) for RISC-V.
  • ~10,000 lines of C + assembly.
  • Runs on QEMU emulator.
  • Source: kernel/, user/, mkfs/.

Repository

https://github.com/mit-pdos/xv6-riscv

What happens

  • make compiles kernel + user programs, builds fs.img.
  • make qemu launches QEMU with the kernel and disk image.
  • The shell (sh) starts automatically.

Boot sequence

entry.S (M-mode) -> start.c -> switch to S-mode -> main() -> consoleinit() -> kvminit() -> kvmmake() -> procinit() -> userinit() -> scheduler().

Key takeaways

1. OS = multiplex + isolate + share + abstract

The OS manages hardware resources, protects programs from each other, enables controlled sharing, and hides hardware details.

2. Isolation is the core problem

Hardware support: user/supervisor mode + virtual memory. System calls are the only bridge.

3. fork + exec + wait = Unix process model

fork copies, exec replaces, wait collects. Separation enables I/O redirection.

4. xv6 is our lab

~10K lines, RISC-V, real enough to boot. We will read and modify it throughout the course.
