SECTION 1

The Concurrency Problem

Why concurrency is hard . race conditions . critical sections

Why Concurrency is Hard

"Imagine two cooks sharing one kitchen. If both reach for the same knife at the same time, someone gets cut. Locks are the rule: only one cook holds the knife at a time."

Three sources of concurrency

  • Multiple CPUs - cores run in parallel, accessing the same memory
  • Interrupts - a device interrupt can preempt a thread mid-operation
  • Preemption - the scheduler can switch threads at (almost) any point

The core problem

When two execution threads access the same shared data and at least one writes, the result depends on timing. This is a race condition.

What goes wrong

A single C statement like counter++ is not atomic. It compiles to: load -> add -> store. Another CPU can sneak in between these steps and corrupt the result.

The fix

Use locks to ensure only one thread executes the critical section at a time. The lock is the "kitchen rule" - one cook, one knife.

Race Condition Example: kalloc()

The scenario

Two CPUs call kalloc() simultaneously. Both read the freelist and get the same page. Both update the freelist - one page is lost forever.

Step by step

  1. CPU1 reads freelist -> page A
  2. CPU2 reads freelist -> page A (same!)
  3. CPU1 writes freelist -> page B (A's next)
  4. CPU2 writes freelist -> page C (A's next, but B is now lost)

Result: page B is lost

The freelist now points to C, skipping B entirely. A memory leak - the page is allocated to no one.

Critical Section

Definition

A critical section is a piece of code that accesses shared data that must not be accessed by more than one thread at a time.

The pattern

Every critical section follows the same three-step pattern:

acquire(lock);
  // critical section
  // access shared data
release(lock);

What the lock guarantees

Only one thread can be inside the critical section at a time. Other threads that call acquire() will wait until the holder calls release().

Rules for correct locking

  1. Mutual exclusion - at most one thread in the critical section
  2. Progress - if no thread is in the section, a waiting thread can enter
  3. Bounded waiting - a thread cannot wait forever

In xv6

Almost every shared data structure has its own lock: kmem.lock (page allocator), ftable.lock (file table), itable.lock (inode table), p->lock (per-process).

Granularity tradeoff

Coarse locks (one lock for everything) are simple but limit parallelism. Fine locks (one per object) allow more parallelism but are harder to get right.

SECTION 2

Spinlocks

struct spinlock . acquire . release . push_off/pop_off . holding

struct spinlock

From spinlock.h - the simplest lock in xv6. The thread spins (loops) until the lock is free.

Definition

struct spinlock {
  uint locked;      // Is the lock held?
  char *name;       // For debugging
  struct cpu *cpu;  // CPU holding the lock
};

Field breakdown

  • locked - the actual lock state. 0 = free, 1 = held. Updated atomically via amoswap.
  • name - human-readable name for debugging. Helps identify which lock panicked.
  • cpu - pointer to the CPU currently holding the lock. Used by holding() to detect double-acquire.

Why "spin"?

The lock is called a spinlock because the waiting thread while-loops ("spins") checking the lock variable until it becomes free. No sleeping - the CPU is busy-waiting.

When to use

Spinlocks are for short critical sections - a few instructions. For long waits (I/O, disk), use a sleeplock instead.

acquire()

From spinlock.c - the function that takes the lock.

Code

void
acquire(struct spinlock *lk)
{
  push_off();  // disable interrupts

  if (holding(lk))
    panic("acquire");

  // Atomically exchange locked with 1.
  // If old value was 0, we got the lock.
  // If old value was 1, spin and retry.
  while (__atomic_exchange_n(&lk->locked, 1,
         __ATOMIC_ACQUIRE) != 0)
    ;  // spin

  lk->cpu = mycpu();
}

Step by step

  1. push_off() - disable interrupts on this CPU. Prevents a timer interrupt from preempting us while we hold the lock.
  2. holding(lk) - check if we already hold this lock. If so, panic (double-acquire = deadlock).
  3. __atomic_exchange_n - atomically set locked = 1 and return the old value. Compiles to amoswap.w.aq.
  4. Spin loop - if old value was 1 (someone else holds it), keep trying.
  5. lk->cpu = mycpu() - record which CPU holds the lock (for holding()).

Key: amoswap.w.aq

The __atomic_exchange_n compiles to the RISC-V amoswap.w.aq instruction - an atomic swap of a register with memory. No other CPU can sneak in between the read and write.

Why disable interrupts?

If an interrupt fires while we hold the lock, and the interrupt handler tries to acquire the same lock, we deadlock - the handler spins waiting for a lock we already hold, but we can't release it because the handler never returns.

release()

From spinlock.c - the function that frees the lock.

Code

void
release(struct spinlock *lk)
{
  if (!holding(lk))
    panic("release");

  lk->cpu = 0;
  __atomic_store_n(&lk->locked, 0,
                   __ATOMIC_RELEASE);
  pop_off();  // re-enable interrupts
}

Step by step

  1. holding(lk) - verify we actually hold this lock. If not, panic (releasing a lock you don't own is a bug).
  2. lk->cpu = 0 - clear the CPU pointer before releasing the lock. This prevents a race where another CPU sees locked = 0 but cpu still points to us.
  3. __atomic_store_n - atomically set locked = 0. Compiles to amoswap.w.rl (release fence). This is the moment other spinning CPUs can grab the lock.
  4. pop_off() - restore interrupt state. If this was the outermost push_off, interrupts are re-enabled.

Order matters

Clear cpu before clearing locked. If you did it the other way, another CPU could acquire the lock and see stale cpu data - a data race on the cpu field.

Mirror of acquire

release() is the exact mirror of acquire(): clear state -> release lock -> restore interrupts. Every acquire must have a matching release.

push_off() / pop_off()

These manage interrupt nesting. A CPU may acquire multiple locks - we can't re-enable interrupts until the last lock is released.

push_off()

void
push_off(void)
{
  int old = intr_get();
  intr_off();          // disable
  if (mycpu()->noff == 0)
    mycpu()->intena = old;
  mycpu()->noff++;
}

pop_off()

void
pop_off(void)
{
  struct cpu *c = mycpu();
  if (intr_get())
    panic("pop_off");
  c->noff--;
  if (c->noff == 0 && c->intena)
    intr_on();         // re-enable
}

How it works

  • push_off(): save the old interrupt state, disable interrupts, increment noff (nesting counter).
  • pop_off(): decrement noff. If it reaches 0, restore the old interrupt state.

Why nesting?

Suppose acquire(A) disables interrupts, then acquire(B) also calls push_off. When release(B) calls pop_off, interrupts must stay disabled because we still hold A. Only release(A) should re-enable them.

The deadlock scenario

Without push_off: CPU holds lock A -> timer interrupt -> handler tries to acquire A -> spins forever -> the original thread never runs -> deadlock. Disabling interrupts prevents this.

holding()

A debugging helper that checks whether the current CPU holds a given lock.

Code

int
holding(struct spinlock *lk)
{
  int r;
  push_off();
  r = (lk->locked &&
       lk->cpu == mycpu());
  pop_off();
  return r;
}

What it checks

Returns 1 if the lock is held and the holder is the current CPU. This is used in two places:

  • acquire() - panics if already holding (prevents self-deadlock)
  • release() - panics if not holding (prevents releasing someone else's lock)

Why push_off here?

holding() reads lk->locked and lk->cpu. These can be modified by other CPUs. push_off ensures we read a consistent snapshot without being interrupted mid-check.

Debugging value

The name and cpu fields exist primarily for holding() and panic messages. When something goes wrong, the panic tells you which lock and which CPU - invaluable for debugging concurrency bugs.

SECTION 3

Sleeplocks

Why sleeplocks . acquiresleep/releasesleep . spinlock vs sleeplock

Why Sleeplocks?

The problem with spinlocks

Spinlocks waste CPU while waiting. If the critical section is long (e.g., disk I/O), a spinning CPU burns cycles doing nothing - for potentially milliseconds.

The sleeplock solution

For long-held locks, use a sleeplock: the holder sleeps instead of spinning. The CPU is free to run other threads. When the lock is released, the sleeper is woken up.

Key difference

Spinlock = busy-wait (CPU spins). Sleeplock = block (CPU runs other work, thread is woken when ready).

struct sleeplock - from sleeplock.h

struct sleeplock {
  uint locked;
  struct spinlock lk;  // protects this struct
  char *name;
  int pid;  // process holding lock
};

Field breakdown

  • locked - lock state (0 = free, 1 = held)
  • lk - an inner spinlock that protects the sleeplock's own fields. Short critical sections only.
  • name - for debugging
  • pid - process ID of the holder (not CPU, because the holder may sleep and wake on a different CPU)

acquiresleep() / releasesleep()

acquiresleep() - from sleeplock.c

void
acquiresleep(struct sleeplock *lk)
{
  acquire(&lk->lk);       // spinlock
  while (lk->locked) {
    sleep_prepare(lk);    // set sleep channel
    release(&lk->lk);     // release spinlock
    sleep();              // sleep until woken
    acquire(&lk->lk);     // re-acquire spinlock
  }
  lk->locked = 1;
  lk->pid = myproc()->pid;
  release(&lk->lk);
}

releasesleep()

void
releasesleep(struct sleeplock *lk)
{
  acquire(&lk->lk);
  lk->locked = 0;
  lk->pid = 0;
  wakeup(lk);             // wake sleepers
  release(&lk->lk);
}

How acquiresleep works

  1. Acquire inner spinlock - protect the sleeplock's fields.
  2. Check locked - if held, prepare to sleep.
  3. Release spinlock - so others can access the sleeplock (e.g., to release it).
  4. Sleep - the thread blocks. CPU runs other threads.
  5. On wakeup - re-acquire spinlock, re-check locked.
  6. Got the lock - set locked = 1, record pid, release spinlock.

The sleep/wakeup pattern

sleep() atomically releases the spinlock and puts the thread to sleep. wakeup() moves sleeping threads back to the ready queue. The while loop handles spurious wakeups.

releasesleep

Simply sets locked = 0, clears pid, and calls wakeup(lk) to wake any thread sleeping on this lock.

Spinlock vs Sleeplock

PropertySpinlockSleeplock
Critical sectionShort (few instructions)Long (I/O, disk, network)
While waitingSpins (busy-wait, wastes CPU)Sleeps (frees CPU for other work)
Can the holder sleep?No - would deadlockYes - that's the point
InterruptsDisabled (push_off/pop_off)Enabled
Held byCPU (lk->cpu)Process (lk->pid)
Implementationamoswap.w.aqspinlock + sleep/wakeup
xv6 useskmem.lock, ftable.lock, p->lockinode locks, buffer cache

Rule of thumb

If the critical section does no I/O and is short, use a spinlock. If it might sleep (disk read, network wait), you must use a sleeplock - a spinlock would waste CPU or deadlock.

Nesting

A sleeplock contains a spinlock internally. The spinlock protects the sleeplock's metadata for the brief moments it's being checked or updated. The long wait happens outside the spinlock.

SECTION 4

Lock Ordering

Lock ordering rules . xv6 lock order . deadlock

Lock Ordering Rules

"Two people need both a pen and paper. If one grabs the pen first, the other grabs the paper first, both wait forever. The fix: agree that everyone grabs the pen before the paper."

The rule

If you need to hold multiple locks at the same time, always acquire them in the same order on every code path. This prevents deadlock.

What happens if you don't

Thread 1: acquire A -> acquire B. Thread 2: acquire B -> acquire A. Both block forever - deadlock. Each holds what the other needs.

Strategies

  • Global order - assign a fixed order to all locks. Always acquire in that order.
  • Lock hierarchy - organize locks into levels. Never acquire a lower level while holding a higher one.
  • Release and retry - if you can't get the second lock, release the first and start over (lock-free retry).

In practice

xv6 documents a lock order in the source code comments. Every developer must follow it. Violating it leads to subtle, hard-to-reproduce deadlocks.

Debugging tip

If your system hangs, suspect a lock-order violation. Use holding() and the name field to trace which locks are held.

xv6 Lock Order

From xv6 source - the canonical lock acquisition order. Never acquire a lower-numbered lock while holding a higher-numbered one.

#LockProtects
1wait_lockParent/child relationship (wait/exit)
2p->lockPer-process state (proc struct)
3kmem.lockPage allocator (freelist)
4ftable.lockFile table (file[] array)
5itable.lockInode table
6pi->lockPer-pipe state
7cons.lockConsole I/O

The rule

If you hold lock #N, you may acquire lock #M only if M > N. For example, holding p->lock (#2), you can acquire kmem.lock (#3), but not wait_lock (#1).

Why this order?

The order reflects the call graph: wait() calls into the process table, which may call kalloc(), which may touch the file table, etc. Top-down ordering prevents cycles.

Deadlock Example

The scenario

  • CPU1 holds Lock A, wants Lock B
  • CPU2 holds Lock B, wants Lock A
  • Both spin forever - neither will give up its lock

The fix: lock ordering

Agree that Lock A is always acquired before Lock B. Now:

  • CPU1: acquire A -> acquire B OK
  • CPU2: acquire A -> acquire B OK (waits for A first)

No cycle, no deadlock.

Four conditions for deadlock

  1. Mutual exclusion - locks are exclusive
  2. Hold and wait - hold one, wait for another
  3. No preemption - can't force-release a lock
  4. Circular wait - a cycle in the wait-for graph

Lock ordering breaks condition 4.

SECTION 5

Common Patterns in xv6

Process table . file table . pipes

Locking the Process Table

The proc[] array is shared across all CPUs. Every access must be protected.

Who acquires p->lock?

  • scheduler() - acquires p->lock before accessing each proc's state
  • kfork() - acquires p->lock to initialize a new proc
  • kexit() - acquires p->lock to set state to ZOMBIE
  • kill() - acquires p->lock to set the kill flag

wait_lock

wait_lock protects the parent pointer - the parent/child relationship. It must be held before p->lock when traversing children (lock order: wait_lock -> p->lock).

The pattern

acquire(&p->lock);
  // access proc fields
  // (state, parent, xstate, ...)
release(&p->lock);

Per-process lock, not global

Each proc has its own lock. This allows fine-grained parallelism - CPU1 can work on proc[0] while CPU2 works on proc[1]. A single global lock would serialize everything.

Why not one lock for all procs?

Granularity. A single ptable.lock (as in older xv6) forces all CPUs to serialize on process operations. Per-process locks allow true parallelism - the scheduler on each CPU can independently manage its own proc.

Locking the File Table

The ftable.lock spinlock protects the global file[] array.

Who uses ftable.lock?

  • filealloc() - acquires ftable.lock to find a free file slot. Scans file[] for ref == 0, increments ref, releases.
  • filedup() - acquires ftable.lock to increment ref (duplicate a file descriptor).
  • fileclose() - acquires ftable.lock to decrement ref. If ref hits 0, frees the file.

Why a single lock?

The file table is a fixed-size array scanned linearly. A single lock is simple and sufficient - the critical sections are short (find slot, bump ref count). Fine-grained per-file locks would add complexity for little gain.

The pattern

// filealloc - find a free file slot
struct file*
filealloc(void)
{
  struct file *f;
  acquire(&ftable.lock);
  for (f = ftable.file;
       f < ftable.file + NFILE; f++) {
    if (f->ref == 0) {
      f->ref = 1;
      release(&ftable.lock);
      return f;
    }
  }
  release(&ftable.lock);
  return 0;
}

Short critical section

The lock is held only for the scan + ref update - a few microseconds. This is why a spinlock (not sleeplock) is appropriate.

Locking Pipes

Each pipe has its own lock (pi->lock). This allows multiple pipes to operate in parallel.

pipewrite()

  • Acquires pi->lock
  • Writes data into the pipe buffer
  • Calls wakeup(&pi->nread) to wake readers
  • If buffer is full, sleeps on &pi->nwrite
  • Releases pi->lock

piperead()

  • Acquires pi->lock
  • If buffer is empty, sleeps on &pi->nread
  • Reads data from the pipe buffer
  • Calls wakeup(&pi->nwrite) to wake writers
  • Releases pi->lock

Sleep when full/empty

When the pipe buffer is full, the writer sleeps. When it's empty, the reader sleeps. This is the producer-consumer pattern.

Sleep channel

The "sleep channel" is just an address - here &pi->nread or &pi->nwrite. wakeup(chan) wakes all threads sleeping on that channel. It's a convention, not a data structure.

Why per-pipe lock?

Each pipe has its own lock so that different pipes don't interfere. Two processes using pipe A can run in parallel with two processes using pipe B. A global pipe lock would serialize all pipe operations.

Atomic Operations

RISC-V atomics . why not just a variable?

RISC-V Atomics

Atomic instructions are the foundation of locks. They make read-modify-write indivisible.

InstructionOperation
amoswap.w.aq rd, rs, (rs1)Atomic swap: rd = M[rs1], M[rs1] = rs
lr.w rd, (rs1)Load-reserved: rd = M[rs1] (marks address)
sc.w rd, rs, (rs1)Store-conditional: M[rs1] = rs if still reserved
amoadd.w rd, rs, (rs1)Atomic add: rd = M[rs1], M[rs1] += rs
amoand.w rd, rs, (rs1)Atomic AND
amoor.w rd, rs, (rs1)Atomic OR
amoxor.w rd, rs, (rs1)Atomic XOR

Suffixes

  • .aq - acquire fence (no later mem ops move before)
  • .rl - release fence (no earlier mem ops move after)
  • .aqrl - both

amoswap.w.aq - the spinlock instruction

xv6's __atomic_exchange_n(&lk->locked, 1, __ATOMIC_ACQUIRE) compiles to amoswap.w.aq. It atomically:

  1. Reads the old value of locked into a register
  2. Writes 1 to locked
  3. Returns the old value

All in one indivisible step. No other CPU can observe or modify locked between the read and write.

LR/SC - alternative approach

lr.w (load-reserved) + sc.w (store-conditional) is a LL/SC pair. lr loads and marks the address. sc stores only if the mark is still valid (no other write happened). If it fails, retry.

Other amo ops

amoadd.w, amoand.w, amoor.w are atomic read-modify-write variants. Useful for counters, flags, and bitmasks without full locks.

Why Not Just Use a Variable?

Naive (broken) approach

// BROKEN - race condition!
void acquire_broken(struct spinlock *lk)
{
  while (lk->locked)   // read
    ;                   // spin
  lk->locked = 1;       // write
  // GAP between read and write!
}

What goes wrong

  1. CPU1 reads locked = 0 -> exits loop
  2. CPU2 reads locked = 0 -> exits loop
  3. CPU1 writes locked = 1
  4. CPU2 writes locked = 1
  5. Both think they hold the lock!

With amoswap (correct)

// CORRECT - atomic
void acquire(struct spinlock *lk)
{
  while (__atomic_exchange_n(
           &lk->locked, 1,
           __ATOMIC_ACQUIRE) != 0)
    ;  // spin
}

Why this works

__atomic_exchange_n compiles to amoswap.w.aq. The read and write happen in a single atomic step. There is no window for another CPU to sneak in:

  1. CPU1 calls amoswap: reads 0, writes 1, gets 0 -> has lock
  2. CPU2 calls amoswap: reads 1, writes 1, gets 1 -> spins
  3. Only one CPU can see the old value of 0.

The key insight

Atomicity is not about speed - it's about correctness. Without atomic instructions, there is always a gap between "check" and "act" where another thread can interfere. amoswap closes that gap.

Key Takeaways

Concurrency creates races

Multiple CPUs, interrupts, and preemption mean shared data can be accessed simultaneously. Without protection, data corrupts - pages get lost, counters go wrong.

Spinlocks for short sections

acquire() spins on amoswap.w.aq until the lock is free. push_off disables interrupts to prevent self-deadlock. Use for brief, non-sleeping critical sections.

Sleeplocks for long waits

When the critical section may sleep (I/O, disk), use a sleeplock. The holder sleeps instead of spinning, freeing the CPU. Built on top of a spinlock + sleep/wakeup.

Lock ordering prevents deadlock

Always acquire locks in the same order. xv6 defines a lock hierarchy (wait_lock -> p->lock -> kmem.lock -> ...). Violating it causes circular wait - deadlock.
